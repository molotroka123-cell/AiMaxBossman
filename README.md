# 🦊 BOSSMAN

### Не просто поговорить с ИИ. Поручить работу — и получить результат.

**Личный AI-командный центр на собственном компьютере: модели, агенты, управление Windows, файлы, сайты, изображения, видео и память — в одном проекте.**

Bossman вырос из простой идеи: почему ИИ должен заканчивать работу на фразе «вот инструкция», если ему можно дать инструменты, рабочее пространство и возможность проверить, что получилось?

Мы строим систему, которой можно объяснить задачу человеческим языком, увидеть ход работы, вмешаться в нужный момент и получить не только ответ, но и сохранённый результат. Не набор несвязанных чатов, а своё рабочее пространство с моделями, действиями, историей и правилами.

**Это авторский проект Тимура, который разрабатывается с помощью AI-инструментов и открытых технологий. И он уже работает на настоящем компьютере — с локальной генерацией изображений и первым проверенным видеоклипом.**

**Одна секунда — небольшой ролик, но большой шаг для продукта.** Важно не количество секунд само по себе. Важно, что прошла вся цепочка: запрос → задача Studio → настоящий AI-движок → файл → проверка → сохранённое доказательство.

Первая попытка нашла настоящий баг: движок уже использовал новый размер, а сохранённая задача ещё содержала старый. Studio отвергла результат. Мы исправили применение пресета, добавили регрессионный тест и повторили генерацию. Именно после этого получили успешный прогон.

Это замер конкретного короткого профиля, а не обещание скорости для любого разрешения и любой длительности. Режимы 5/10/15/30 секунд добавлены в код, но их живые прогоны ещё впереди. Склейка длинных сегментов пока проверена с тестовым движком.

<a id="why"></a>
## Зачем мы это делаем

Обычный чат помогает придумать решение. Bossman мы строим для следующего шага — **довести решение до действия**.

Не просто «вот текст для файла», а работа с файлом. Не просто «открой приложение», а наблюдение за рабочим столом и управляемое действие. Не просто «когда-нибудь можно генерировать видео», а вызов движка и проверенный MP4.

Целевая цепочка проекта:

**Задача → подходящий контекст → модель и инструменты → разрешённое действие → проверка → результат → полезный опыт.**

Основные блоки этой цепочки уже есть в коде. Полное автоматическое использование памяти и универсальная автономность — отдельные задачи, а не обещание, спрятанное в красивой схеме.

Самое интересное здесь — соединение возможностей. Модель сама по себе не управляет жизненным циклом приложения, не гарантирует сохранность файлов и не превращает ответ «готово» в доказательство. Эту работу берёт на себя продуктовая часть Bossman.

## Что находится внутри

### 🧠 Модели, задачи и агенты

Command Center объединяет подключение моделей, проекты, задачи, инструменты и наблюдение за исполнением. Есть Gateway, контроль доступности провайдеров, ограничения бюджета и правила выбора разрешённого пути выполнения.

Мы используем локальные модели для задач, которые можно решать на своём компьютере, а внешние модели — там, где это разрешено и оправдано. Облачный вызов не должен появляться незаметно только потому, что локальный путь оказался сложнее.

Задача для нас — не одно сообщение в чате. У неё есть состояние, результат, возможное ожидание подтверждения и история. Непонятный исход нужно разобрать, а не спрятать за уверенным ответом модели.

### 🖥️ Работа с настоящим компьютером

Computer Use связывает агента с инструментами рабочего стола: запуском приложения, наблюдением за окном, вводом, действиями и проверкой результата. Для владельца есть **«Стоп» и «Продолжить»**.

В сохранённом живом Windows-прогоне проверены **12 из 12 сценариев**, включая запуск и фокус окна, ввод кириллицы, остановку во время ввода, продолжение с новым наблюдением и сохранение текста с проверкой содержимого на диске. Это доказательство конкретных сценариев на конкретной сборке, не обещание управления любой программой без ошибок.

Здесь много невидимой, но важной инженерии: не печатать в чужое окно, не нажимать по устаревшему снимку, не считать неизвестное условие успешно проверенным, не принимать слово модели за разрешение владельца.

[Как проходили живые проверки и исправления](owner-repair/repair-ledger.md) · [Текущий кандидат Computer Use](https://github.com/molotroka123-cell/AiMaxBossman/pull/71)

### 🎨 Локальные изображения

В Studio подключён **Z-Image-Turbo через sd.cpp**. Реальная генерация изображения на Radeon 8060S зафиксирована в отчёте владельческого прогона: с наблюдаемым Vulkan backend и проверенными файлами модели.

Это уже не только форма с полем для промпта. В проекте есть путь от настройки модели до обработки задачи и сохранения результата. Отдельно существуют инструменты импорта, редактирования, библиотеки и экспорта изображений.

Более сильные модели и удобные профили качества — следующий этап сравнения. Мы не называем новый кандидат «лучшим на этом компьютере», пока не проверили его здесь.

### 🎬 Видео: генерация и работа с результатом

Есть два разных слоя, и оба важны:

**AI-генерация** создаёт новые кадры через модель. **Video Studio** работает с проектом, таймлайном, правками и экспортом. Обычный FFmpeg-рендер мы не выдаём за генерацию нейросетью.

В текущей рабочей ветке добавлены TestRun и пресеты 5/10/15/30 секунд. Длинные режимы реализованы как цепочки сегментов с продолжением от последнего кадра предыдущего, а не как незаметное зацикливание одного короткого видео. Подробности происхождения и склейки сохраняются отдельно.

Доработан расчёт времени задачи для тяжёлых настроек. Это защита от неверного фиксированного дедлайна, **не ускорение самой модели**. Для больших роликов по-прежнему важны ресурсы, настройки и отдельные испытания.

Самый свежий живой результат показан в начале README. Длинные ролики, живой I2V и сценарии отмены/восстановления требуют собственных аппаратных проверок.

### 🌐 Сайты, файлы и рабочий контекст

Web Designer — отдельная рабочая область для проекта сайта, предпросмотра, правок, сохранения и отката. Файловые инструменты и контекст нужны, чтобы агент работал с реальными материалами проекта, а не только с последними репликами диалога.

Одна из уже исправленных проблем хорошо показывает подход: при повторном выборе элемента или обновлении страницы мог исчезать набираемый текст. Мы исправили поведение и добавили проверки, которые воспроизводят потерю ввода. Красивый интерфейс не считается готовым, если он теряет работу человека.

### 🔌 Инструменты разработки

Bossman использует внешние инструменты как исполнителей, а не как замену всей системе. Например, в рабочую RC-линию добавлена поддержка разных поколений OpenCode API: сервис больше не должен выглядеть исправным только потому, что вместо API вернул HTML со статусом 200.

Наша часть — связать исполнитель с задачей, её разрешённой областью, состоянием и проверкой. Зелёная надпись «подключено» должна означать работающий путь, а не просто живой порт.

<a id="telegram"></a>
### 📱 Telegram и личный пульт

В проекте есть Telegram-интеграция для связи с владельцем. Следующий согласованный шаг — довести её до удобного **личного пульта одного администратора**: задачи, статус, разрешённые снимки экрана, подтверждения, STOP и продолжение.

Расширенный пульт из последнего задания пока не объявлен полностью завершённым. Его цель — управлять тем же Bossman с телефона, а не запускать параллельного бота с отдельными правами и бесконтрольным доступом к компьютеру.

<a id="learning"></a>
## Самая интересная часть: Bossman, который пользуется своим опытом

Мы хотим, чтобы исправленная однажды проблема не приходилось разбирать с нуля при каждом новом диалоге.

В проекте уже есть долгосрочные заметки, структурированные факты, поисковые индексы и **LearningStore** для проверенных эпизодов, уроков и навыков. Есть учебный контур с разделением тренировочных заданий и отложенных проверок.

Идея дальнейшей работы простая:

**Локальный Qwen пробует → тест показывает результат → Claude помогает в сложном случае → решение проверяется → полезный урок сохраняется → Qwen находит его при новой похожей задаче.**

Мы сохраняем не магическое «теперь модель всё знает», а практическую шпаргалку:

> Как выглядела ошибка? В чём оказалась причина? Что не помогло? Что сработало? В каких условиях это применимо? Как проверить исправление? Где лежат код и доказательства?

Например, урок из сегодняшнего видеотеста — не «всегда ставь разрешение 640×352». Урок: **нормализованные параметры должны попасть в сохранённую задачу до запуска; итоговый файл нужно сравнивать именно с этой задачей**. Такой принцип полезен далеко за пределами одного клипа.

Память должна быть доступной будущим локальным моделям: понятные записи, поиск по точной ошибке и смыслу, ссылки на источники, учёт версии проекта, без свалки одинаковых документов. Найденный контекст должен быть коротким и полезным, а не занимать весь запрос.

**Что уже есть:** хранилища и проверяемый учебный pipeline. **Что ещё нужно доказать:** автоматический поиск нужного урока после перезапуска и выигрыш на новых заданиях без помощи учителя. Наличие памяти само по себе не означает рост интеллекта; веса моделей в этом контуре не меняются.

[Как устроена долговременная память](docs/evo/DURABLE_MEMORY_OPERATING_CONTRACT.md) · [Как измерять обучение Qwen](docs/evo/LOCAL_QWEN_APPRENTICE_BENCHMARK.md) · [Как Claude должен помогать ученику](docs/owner/TOMORROW_MASTER_PROMPT_QWEN_FIRST.md)

<a id="principles"></a>
## Сильный агент — это ещё и контроль

Возможность действовать без возможности остановить действие — плохой личный помощник. Поэтому управление владельца является частью продукта, а не отдельной памяткой.

| Принцип | Что он означает человеческим языком |
|---|---|
| `never / ask / allowed` | Одни действия запрещены, другие требуют подтверждения, третьи разрешены заранее |
| Проверка результата | «Модель сказала, что сделала» и «результат действительно получен» — разные вещи |
| STOP и восстановление | Владелец должен иметь возможность вмешаться; продолжение не должно слепо повторять неизвестный результат |
| Область проекта | Доступ к одной рабочей папке не означает доступ ко всему компьютеру |
| Приватность и бюджет | Режим LOCAL_ONLY, секреты и лимиты нельзя обходить незаметным облачным вызовом |
| Проверенные уроки | Запись в памяти не может сама себе выдать права или подтвердить опасное действие |

Это реализуемые и тестируемые границы, а не заявление об абсолютной неуязвимости. Остаточные ограничения и непроверенные случаи остаются видимыми в [KNOWN_LIMITATIONS](KNOWN_LIMITATIONS.md).

<a id="performance"></a>
## Всё это — на одном компьютере

Целевая машина проекта:

**AMD Ryzen AI Max+ 395 · Radeon 8060S · 128 GB unified memory · Windows 11.**

Не серверная стойка и не отдельная NVIDIA-видеокарта. Мы используем локальные языковые и генеративные модели на системе с общей памятью и проверяем реальную совместимость, а не делаем вывод из красивого названия модели.

При этом большая память не отменяет ограничений вычислений. Одновременное присутствие языковых моделей и тяжёлой видеомодели — отдельный режим нагрузки. Успешный короткий TestRun выше выполнялся с выгруженными LLM; переносить его время на другую конфигурацию нельзя.

Наша цель — удобные профили под задачу: быстрый тест, повседневная работа и качество. Выбор должен опираться на реальные замеры времени, памяти и результата.

## Как запускать без приключений

Для запуска нужен не случайный ZIP из списка, а **конкретный проверенный commit, его Windows-архив и SHA-256**. Веса локальных моделей настраиваются отдельно; README не заменяет проверку файлов и окружения.

1. Откройте [INSTALL.md](INSTALL.md) и актуальный handoff кандидата. Выберите архив именно нужного SHA.
2. Распакуйте его в отдельную папку. Сохраните копию рабочих данных по [инструкции отката](docs/owner/ROLLBACK_RU.md).
3. Запустите `Start-Bossman.cmd`. Начните с тестового проекта и одной проверенной локальной модели, без доступа к важным рабочим файлам.
4. Используйте `Owner-Run.cmd` и `Evening-Test.cmd`, затем пройдите сценарии из [OWNER_ACCEPTANCE.md](OWNER_ACCEPTANCE.md). Машинные проверки не заменяют действия владельца.
5. Для локального медиадвижка есть `Media-Setup.cmd`, для учебного контура — `Coaching.cmd`, для сбора диагностики — `Collect-Diagnostics.cmd`.

Если программа дала сбой, сохраняем задачу, версию, диагностику и результат. Исправление проходит проверку и попадает в новый кандидат, а не устанавливается незаметной подменой файлов внутри старого архива.

## Куда идём дальше

Приоритет ближайшей 1.0 — не бесконечно увеличивать список кнопок, а закончить полезные цепочки.

**Видео и фото:** сравнить новые модели на этом железе, получить понятные профили качества, проверить длительные ролики и управление ресурсами.

**Управление с телефона:** довести Telegram до одного удобного пульта владельца, с подтверждениями и STOP поверх существующего пути исполнения.

**Память:** автоматически находить подходящие проверенные решения при старте и продолжении задачи, сохранять порядок в знаниях и проверять восстановление после перезапуска.

**Самостоятельный ремонт под наблюдением:** Qwen готовит исправление в изолированном рабочем окружении, тесты проверяют, Claude разбирает сложные случаи, владелец контролирует установку. Это не разрешение агенту самостоятельно переписывать работающую систему или собственные ограничения.

В репозитории есть и экспериментальные направления, включая Fleet и Trading Lab. Они не превращаются в production-возможности от одного упоминания здесь: удалённое исполнение имеет отдельную приёмку, торговые сценарии остаются READ-ONLY/PAPER без разрешения на реальные ордера.

<a id="development"></a>
## Как Bossman теперь развивается: Claude + Codex + Aster 6

Чтобы проект не превратился в десятки расходящихся «финальных» веток, у нас снова одна конечная точка — **`release/bossman-owner`**. Рабочие и аудиторские ветки существуют только как изолированные полосы работы и должны сходиться обратно в неё через проверяемый merge.

Три роли работают параллельно:

- **Claude** — главный интегратор и учитель: решает архитектурные конфликты, сложные случаи, безопасность и принимает финальный delta в release-кандидат.
- **Codex** — параллельный инженер-аудитор: ищет забытые, наполовину подключённые и реально сломанные функции, пишет ограниченные фиксы с регрессиями в своей ветке и не трогает worktree Claude.
- **Aster 6** — экономный независимый аудитор: не повторяет весь аудит по кругу, а проверяет новые delta и самые рискованные поверхности — fake success, restart/replay, approvals, файлы, ресурсы, provenance моделей и packaging.

Главная идея: **мы больше не ограничиваемся только минимальным набором для V1.0**. Стабильная 1.0 — база, но аудит идёт по всей первоначально задуманной системе: Gateway и модели, агенты и миссии, память, Browser/Computer Use, файлы, Web Designer, Image/Video/Music Studio, Telegram, Fleet, OpenCode, observability, budgets, упаковка, обновление и UX.

При этом никто не «улучшает» систему ценой правды о ней: старый зелёный CI не переносится на новый SHA, мок не считается живым runtime, а конфликтующие результаты сохраняются и воспроизводятся вместо того, чтобы один агент перезаписывал отчёт другого.

<a id="journey"></a>
## Что здесь наше — и почему мы этим гордимся

Мы не обучали с нуля Qwen или Wan и не выдаём работу открытого сообщества за собственную. Bossman опирается на существующие модели и инструменты: llama.cpp, stable-diffusion.cpp, Playwright, FFmpeg и другие компоненты. У кода, весов и дополнительных сервисов свои лицензии и условия использования.

**Наша работа — превратить эти компоненты в личную систему:** связать модели с задачами, инструменты с разрешениями, интерфейс с настоящим состоянием, файлы с проверкой, ошибки с воспроизведением, а будущие решения — с полезной памятью.

И здесь есть чем гордиться. Проект уже пережил реальные поломки: неправильный фокус окна, кириллицу, самоперезапуск Edge, гонку подтверждений, потерю ввода, несовместимость API и расхождение видеопресета с сохранённой задачей. Эти истории превратились в исправления и тесты, а не исчезли из отчёта.

**Bossman — проект про собственный инструмент, собственное железо и понятный контроль. Не «ИИ когда-нибудь сможет», а «вот код, вот проверка, вот результат».**

Не сокращать набор обязательных workflows. Дополнительно сверить реальные jobs,
checkout/build SHA и байты архива: один ответ certifier не заменяет эти улики.

```bash
python tools/exact_sha_certify.py --sha "$TESTED_SHA" --runs-json runs.json --output exact-sha-certification.json
```

Очередь, пропуск, отмена, `action_required`, пустой прогон и результаты другого SHA
не считаются PASS. Даже документационный commit не получает новый exact-SHA
сертификат автоматически. Этот README не меняет код, правила, release candidate
или результаты уже проведённых проверок.
