# Bossman как установленный продукт

Что именно доказано про продукт, который **ставится**, а не про рабочую копию,
из которой он собран. Документ описывает измерения, а не намерения: у каждого
утверждения назван прогон, который его получает, и то, чего он НЕ говорит.

## 1. Цепочка

```
чистая установка → доктор → запуск → HTTP готов → UI готов
                 → сценарий → перезапуск → возобновление
```

Целиком её проходит одно задание — `.github/workflows/installed-product.yml`,
`windows-latest`. Оно ставит продукт тем же способом, каким его ставит
владелец из исходников: колёса из одноразового git-worktree на HEAD и
`pip install <wheel>` в пустой venv. Ни одного `pip install -e`.

| Звено | Чем доказано | Где |
|---|---|---|
| чистая установка | 4 независимых признака editable-установки проверены и ни один не сработал; `bcc/_build.json` называет коммит | `tools/installed_product_chain.py`, звено «чистая установка» |
| доктор | поставляемый `bossman_doctor.py` исполнен интерпретатором установки; схема отчёта и разделение «виновата машина / виновата поставка» взяты импортом из `tools/bundle_evening_test.py` | звено «доктор» |
| запуск | `python -m bcc` поднят из установки, отвечает на `/api/identity` | звено «запуск» |
| HTTP готов | `/api/identity` называет **installed_build** и ожидаемый SHA; `/api/system` без входа 401; неверный токен 401; вход; все обещанные подсистемы в `ok` | звено «HTTP готов» |
| UI готов | настоящая страница в настоящем Chromium, запущенном **самой установкой** | звено «UI готов» |
| сценарий | документ владельца доведён до версии N тремя правками, каждая перечитана отдельным GET | звено «сценарий» |
| перезапуск | процесс убит `kill` (SIGKILL / TerminateProcess), смерть проверена, поднят заново, `started_at` сменился | звено «перезапуск» |
| возобновление | версия документа пережила убийство без отката, следующая правка дала N+1, запись по устаревшей версии отвергнута | звено «возобновление» |

Вердикт один: `PASS` (0), `FAIL` (1), `OWNER_HARDWARE_REQUIRED` (2).
Звено со статусом `NOT_RUN` даёт **FAIL**, а не молчание: незапущенная
проверка строже не становится, но в отчёте выглядит как «замечаний нет».

## 2. Где проходила граница «editable / настоящая установка» — и где проходит теперь

### Было

Продуктовый процесс во всех прогонах, которые называли себя установленными,
действительно поднимался из установки. Но **никто этого не измерял**: и
`scripts/verify_clean_install.py`, и `scripts/windows_owner_tasks.py`
полагаются на то, что из окружения убран `PYTHONPATH`, и сообщают
`CLEAN_INSTALL=PASS`, ни разу не назвав, откуда пришёл `bcc`. Ни одного
упоминания `sys.prefix`, `__editable__` или `direct_url.json` в обоих файлах
нет. Утверждение «поставили настоящий пакет» держалось на аккуратности
окружения, а не на проверке.

Единственная браузерная улика о продукте добывается в
`.github/workflows/windows-bundle.yml`, задание `owner-experience`, шаг
**Install browser test controller**:

```
python -m pip install -e . -e './bossman-core[dev]' -e './command-center[dev,browser]'
```

Сервер под тестом там действительно из архива (`-I`, `PYTHONPATH` снят,
`test_editors_user_acceptance.py` сверяет `bcc.__file__` с `sys.prefix`), но
браузер и весь контроллер живут во ВТОРОМ интерпретаторе, в который
репозиторий поставлен в режиме правки на месте.

А улика «интерфейс готов» вне браузера — это буквально двести на корень.
`tools/verify_installed_product.py`:

```python
assert b"<html" in request("/").lower()
```

и `scripts/verify_clean_install.py`:

```python
assert "<html" in body, "интерфейс не отдаётся"
return "index.html отдан"
```

### Стало

1. Звено «чистая установка» **измеряет** границу и умеет из-за неё покраснеть.
   Проверяются четыре независимых признака, потому что каждый по отдельности
   обходится:
   * каждый пакет продукта импортирован из-под `sys.prefix`;
   * `direct_url.json` дистрибутива не говорит `dir_info.editable: true`
     (именно этот случай выглядит как обычная установка: файлы находятся, их
     подставляет путевой хук);
   * в `site-packages` нет хвостов `__editable__*`;
   * на пути импорта нет каталога рабочей копии.
2. Страницу открывает **сама установка** своим `playwright` и своим Chromium —
   второй интерпретатор с `pip install -e` не участвует.
3. Граница проверяется и **глазами владельца**: подсказка у `#build-sha`
   заполняется из `/api/identity` и прямо различает «установленная сборка» и
   «рабочий чекаут». Страница, отданная из чекаута, звено не проходит.

## 3. Почему «UI готов» — это не двести на корень

В поставляемом `command-center/ui/index.html` и `#login`, и `#shell` объявлены
`hidden`, а `<main class="view" id="view">` **пуст**. Снять `hidden` и
наполнить `#view` может только отработавший `app.js`. Поэтому звено требует:

* `#login` стал видимым — скрипт выполнился;
* вход выполнен **настоящей формой**: поле `#login-token`, кнопка
  `#login-submit`;
* `#shell` стал видимым;
* `#build-sha` заполнен и в подсказке стоит ожидаемый SHA и слова
  «установленная сборка»;
* в `#view` есть текст — приложение отрисовало страницу, а не только оболочку;
* доступных органов управления не меньше, чем их лежит в поставляемой разметке
  (8: шесть кнопок, ссылка, поле ввода). Это **пол**, а не цель: число
  пересчитывается из того же `index.html` тестом, поэтому разойтись с
  поставкой молча не может;
* ноль ошибок в консоли страницы и ноль неотданных ресурсов своего источника.

Улики: `ui-ready.png` и `ui-ready.html` в артефакте прогона.

## 4. Что считается возобновлением

Не «процесс снова отвечает» и не «строка в базе на месте», а **работа
продолжилась**:

* до убийства документ владельца доведён до версии N;
* процесс убит `kill`, смерть проверена (на POSIX — сигналом нулевой длины по
  PID и молчанием прежнего порта; на Windows — только молчанием порта, и
  отчёт говорит об этом прямо);
* после перезапуска версия та же N, тело документа то же — ничего не
  откатилось;
* следующая правка даёт N+1, **а не 1**;
* запись по УСТАРЕВШЕЙ версии по-прежнему отвергается. Без этой пары «версия
  выросла» доказывалось бы счётчиком, принимающим что угодно.

## 5. OWNER_HARDWARE_REQUIRED

Помечено ровно одно звено — **«окно рабочего стола»**, и только потому, что
интерактивного сеанса рабочего стола GitHub не даёт физически. Заявлять
«окно открылось» нечем.

При этом всё, **что проверить можно**, за этой пометкой не прячется: пять
точек входа (`bcc`, `bcc-desktop`, `bcc-open`, `bossman`, `bossman-gateway`)
обязаны быть установлены и ответить на `--help`, иначе звено красное. Само
звено не может уронить прогон и не может быть покрашено в зелёный: вердикт
цепочки при нём — `OWNER_HARDWARE_REQUIRED`, и настоящий отказ соседнего
звена он не прячет.

Отдельно и заранее: модели на раннере нет. Ничего, что требует LLM, эта
цепочка не проверяет и не заявляет.

## 6. Очередь и стоимость

Группа `concurrency` — своя: `installed-product-${{ github.ref }}`. У сборки
архива группа `windows-bundle-<ref>`, у владельческого прогона
`windows-owner-tasks-<ref>`. GitHub держит ровно **один ожидающий** прогон на
группу, поэтому общая группа означала бы, что новая цепочка выбивает из
очереди сборку продукта, который скачивает владелец. `cancel-in-progress:
false`: начавшийся прогон доводится до конца.

Фильтр веток — тот же, что у пары Windows-заданий, и объявлен в
`tools/owner_facing_branches.json`; `tests/test_windows_workflows_cover_owner_
branches.py` сверяет его настоящей семантикой шаблонов GitHub. Ветка, выпавшая
из фильтра, не даёт красного — она не даёт ничего (BL-089).

Задание поднимается правкой **самого продукта** (`command-center/**`,
`bossman-core/**`, `bossman_shared/**`, `apps/**`), а не только правкой своего
драйвера. Это отличие от `windows-owner-tasks.yml`, чей фильтр путей
ограничен `scripts/windows_owner_tasks.py`, `scripts/verify_clean_install.py`
и собственным файлом: единственный прогон с чистой установкой и жёстким
убийством до сих пор НЕ запускался, когда менялся продукт.

## 7. Как запустить руками

```bash
python scripts/installed_product_install.py --out dist/installed --json install.json
dist/installed/venv/bin/python -I tools/installed_product_chain.py \
    --expected-sha "$(git rev-parse HEAD)" \
    --doctor scripts/bossman_doctor.py \
    --evidence proof --json proof/installed-product-chain.json \
    --require-browser
```

На Windows — `dist\installed\venv\Scripts\python.exe`. Установщик требует
чистого дерева: установка из грязного дерева уликой для коммита не является
и разрешена только явным `--allow-dirty` как диагностика.

`--browser-executable` открывает страницу уже стоящим в системе браузером —
для машины владельца и для сред, где загрузка сборок playwright закрыта
политикой сети. Проверку это не ослабляет: страница по-прежнему обязана
отрисоваться в настоящем браузере.

## 8. Чего этот прогон НЕ говорит

* ничего про живые модели и про выполнение задач агентом — модели на раннере
  нет;
* ничего про GPU, ускорение, камеру и скорость на машине владельца — это
  `tools/owner_machine_report.py` и `scripts/target_hardware_acceptance.py`;
* ничего про скачиваемый архив одним файлом — это `windows-bundle.yml`,
  отдельное задание и отдельная улика;
* ничего про то, что окно приложения открывается.
