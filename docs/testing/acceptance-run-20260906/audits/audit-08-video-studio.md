## Углубление root-cause кластера A

Кластер A распадается на **три независимых механизма**, а не один:

1. **`WinError 32` — POSIX-семантика «открытый дескриптор пинит inode» не существует на Windows.**
   Модуль сам декларирует контракт (read_verification.py:10-12: *«An open descriptor pins the inode, so unlink+recreate, rename or a symlink swap of the pathname after the check cannot substitute the bytes that are served»*). Реализация держит `VerifiedRead.descriptor` открытым через `os.open` (read_verification.py:93). На Windows `os.open` → CRT `_wopen` → share-режим `FILE_SHARE_READ|FILE_SHARE_WRITE` **без `FILE_SHARE_DELETE`**. Пока дескриптор жив (скачивание в полёте, `handle` не detached/closed):
   - `path.unlink()` → `DeleteFileW` требует DELETE-доступ + отсутствие чужих handle без `FILE_SHARE_DELETE` → **ERROR_SHARING_VIOLATION (WinError 32)**;
   - `os.replace(x, path)` → `MoveFileExW(MOVEFILE_REPLACE_EXISTING)` на цель с живым handle → **WinError 5/32**.
   Тесты A1/A2 (`test_video_descriptor_boundary.py:98,108,182,212`: `path.unlink()` / `artifact.unlink()` под живым handle) на Windows падают прямо в тестовом теле. Дополнительно `PermissionError` в `guarded` маппится в **403** (features/video_studio.py:94-95), тогда как контракт/тесты ждут **409** (features/video_studio.py:105-106; test_video_descriptor_boundary.py:198) — рассинхрон кодов ответа.

2. **Identity-кортёж `(st_dev, st_ino, st_size, st_mtime_ns, st_ctime_ns)` на NTFS двойственный** (read_verification.py:104-105):
   - *ложные отрицания*: Windows `st_ctime` = **creation time**, не change-clock; `mtime_ns` имеет гранулярность 100 ns и восстанавливается `os.utime`; same-size in-place rewrite в одном 100ns-кванте с восстановленным mtime/ctime оставляет кортеж **неизменным** — сам модуль это признаёт (read_verification.py:22-26, 41-44, `REQUIRES_CONTENT_RECHECK`). Единственная реально работающая компонента против подмены — `st_ino` (NTFS file ID).
   - *ложные срабатывания*: `path.stat()` в строках 163, 168, 171-172, 182-183, **213** — это повторное/третье открытие **по имени**. `os.replace` байт-идентичного контента (штатный re-upload: media.py:227; hard-link publish: render.py:537) подменяет inode → кортеж меняется при **неизменном контенте** → «media changed» → **422 вместо 200**. Причём на строке 213 identity-чек **решает раньше** контентного re-hash (215-219), хотя на nt решать может только хеш.
   - окно гонки: между `open_descriptor` (os.open+fstat, :160) и `identity(path)` (:163) либо между worker-открытием по имени (:176) и пост-чеками чужой `os.replace` прерывает запрос, чей **собственный дескриптор** заведомо держит верифицированные байты — guard pathname-windowed там, где весь дизайн descriptor-bound.

3. **`422 при download re-check` — следствие пп. 1-2 + рассинхрон сообщений.** После append-перезаписи (test_video_studio_read_verification.py:274-277) тест ждёт `'hash mismatch'` в тексте 422; если перезапись попадает в identity-окно (или тестовая последовательность содержит unlink/replace под handle), первым срабатывает «media changed before/during read verification» (:164/:172) либо `PermissionError`→403 — контракт сообщения/кода нарушен, хотя защита по существу корректна.

## Позитивные подтверждения (не находки)

- `REQUIRES_CONTENT_RECHECK` re-hash в `resolve` (read_verification.py:215-219) и `validate_for_gate` (export_receipt.py:90-101) — корректная Windows-компенсация инертности stat-identity; не ослабляет проверок.
- CAS в `store.apply` (store.py:190-195) с `rowcount != 1` + `_write_lock` (BEGIN IMMEDIATE / FOR UPDATE) — корректная точка сериализации.
- `process()` kill+reap на отмене/таймауте (media.py:82-92) на основном пути корректен; `blocking()` (media.py:26-33) не бросает файлового воркера под rmtree TemporaryDirectory.
- `ReadVerificationBusy` → 503 + Retry-After (features/video_studio.py:92-93) без утечки деталей хранилища — корректно.
- Descriptor-bound отдача (descriptor_stream.py: не пере-открывает pathname, RANGE/416/закрытие на всех путях) — семантика верна и на Windows.
