## 2. Что сделано в этой сессии

**Исследование восьми репозиториев → восемь ТЗ (~3900 строк).** Ни одного
вердикта «ВНЕДРЯТЬ»: семь агентов из восьми независимо пришли к «берём идею,
не берём зависимость». Цифры, а не мнения: mem0 — ~8400 токенов на сохранение;
graphiti — 15–40k на эпизод; memsearch ищет 2.15 с против наших 0.025 мс;

**Пять дефектов в нашем коде, найденных исследованием** (все исправлены,
8 тестов, каждый падал до правки):

1. `expand` моста бросал `RuntimeError`, а вызывающий по контракту ловит
   `KeyError` → handler падал целиком;
2. мост не передавал `--exclude` → исключения хранилища молча не работали;
3. `stats` отдавал строку там, где контракт требует dict;
4. абсолютные пути с `$HOME` уходили в контекст модели;
5. **ответ MCP-сервера не обрезался вовсе** — один вызов с `limit=50` заливал
   десятки килобайт в контекст (у `terminal.run` лимит был, у MCP забыли).

**Ядро скиллов:** 16 скиллов (не 15 — пак не знал про Obsidian-аддон),
починен парсер, терявший `metadata.version` из-за двоеточия в описании.

**Функция «Изображения»:** 16/16 пунктов приёмки, mock-провайдер;
реальные провайдеры — PARTIAL, ни один не подключён.

**Таблица `facts`:** две оси времени по идее graphiti, без графовой СУБД и без
вызовов LLM. Правило: `invalid_at` старого = `valid_at` **нового**, а не «сейчас».

## 4. Self-learning pipeline — PARTIAL, что именно мешает

Аудит: `docs/CORE_SKILLS_AUDIT.md`. Восемь из десяти проверок пака проходят.

**Что работает:** расширение прав создаёт approval и не применяется без решения
человека; версии хранятся; Skill Forge предлагает только после ≥3 повторов.

**Что не работает — ровно две вещи, и обе про одно:**

1. Таблица `evaluations` привязана к `task_id`/`run_id`, **а не к версии
   скилла**. Skill Evaluator'у некуда писать сравнение baseline и кандидата →
   PROMOTE/REJECT опирается только на человека.
2. Нет автоматических переходов между стадиями: `Memory Curator` не вызывается
   после миссии, `Failure Retrospective` не запускается при провале.

**Точный следующий шаг (в этом порядке):**

1. Таблица сравнения версий скиллов в `bcc/db.py` (владелец схемы — лид):
   `skill_id`, `baseline_version_id`, `candidate_version_id`, метрики, вердикт.
2. Замкнуть **один** переход, самый дешёвый и полезный: хук `after_run` при
   статусе `failed` → предложить `Failure Retrospective`. Это превратит петлю из
   инструкции в механизм, ничего при этом не отдавая системе на самоуправление.

**Два скилла, которых не хватает** (обоснование — §7 аудита, оба не влезают в
существующие): `requirement-clarify` (неоднозначное требование не угадывать) и
`external-evidence-check` (внешние данные проверять до записи в долговременную
память — иначе ложь со страницы отравляет решения месяцами).

## 7. Дальше: OpenClaw

Архитектура, предложенная владельцем (BOSSMAN — control plane, OpenClaw —
execution engine для каналов связи), ложится на уже построенное:

- **Permission Bridge** — канонический слой `decide_effect` + approvals готов,
  формат правил `{tool, resource, effect, reason}` совпадает с его таблицей;
- **Shared Skills** — источник истины уже один, `default_skill_roots` смотрит в
  `.agents/skills`, `.opencode/skills`, `.claude/skills`; добавить
  `.openclaw/skills` — одна строка;
- **Shared Memory** — `memory.search` есть; если OpenClaw окажется MCP-клиентом,
  мост памяти и скиллов уже готов без нового кода;
- **Один inference server на три системы** — это работа Resource Brain (PARTIAL).

**Риск, который нельзя упустить:** OpenClaw впервые даёт BOSSMAN возможность
писать реальным людям (Telegram, WhatsApp). Дефолт обязан быть **ASK на
отправку в канал**, AUTO — только после явной настройки на конкретный канал и
контакт. Ночная миссия, написавшая клиенту, не чинится откатом.
