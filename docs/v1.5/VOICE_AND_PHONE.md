# Собственный голос и телефонный агент

**SPECIFICATION.** Ни provider account, ни voice enrollment, ни PSTN-звонок данным пакетом не создаются.

## 1. Что должен уметь Bossman

Владелец записывает собственный голос, проверяет короткое синтезированное демо и разрешает конкретные способы использования. Через Bossman CMD можно попросить озвучить текст, отправить разрешённое голосовое сообщение, позвонить на разрешённый номер и уточнить наличие товара/условия доставки.

Голос используется с согласия его владельца. Для разговора с третьим лицом стандартное представление: «Здравствуйте, я AI-ассистент, звоню по поручению владельца». Нельзя выдавать voice clone за биометрическое подтверждение личности, проходить им bank voice authentication, притворяться человеком при прямом вопросе или подменять caller ID. Это продуктовые границы, не обещание юридической достаточности одной фразы.

## 2. Enrollment и приватность

`record/import → audio validation → one-speaker check → owner consent receipt → voice profile candidate → owner listening test → activate for granted uses`.

Исходные записи, embeddings/адаптеры и consent — локально с ограниченными ACL и шифрованием, вне Git/evidence. Непубличный voice_profile_id; digest только во внутреннем журнале. Экспорт/передача samples облачному TTS — отдельное назначение с явно выбранным получателем. Отзыв блокирует новые TTS-запросы и очищает управляемые кэши; удаление у провайдера подтверждается его API, не только удалением локального файла.

Начать с чистой разговорной записи без музыки и посторонних голосов; требования к длительности/формату берутся из выбранного runtime. Не обещать обучение весов от speaker conditioning. Для каждого профиля записывать `conditioning_only / fine_tuned / cloud_profile` и факт изменения весов. RU, EN и CZ проверять по отдельности: сходство голоса не доказывает разборчивость языка.

## 2a. UX загрузки исходного MP3 (DRAFT, не реализовано)

Загрузка ~15-минутной записи — не разовая техническая операция «положить файл в папку», а первое впечатление владельца от фичи, поэтому интерфейс (CMD/Dashboard/Telegram — какой канал ни использовался бы) должен явно показывать прогресс, а не тишину на несколько минут:

- **Приём файла**: drag-and-drop или явный выбор файла в Dashboard, либо отправка как документ/аудио в Telegram владельцем; сразу подтверждение — имя файла, длительность, размер, формат — до начала обработки, чтобы не пришлось гадать, взялся ли файл вообще.
- **Пошаговый прогресс**, а не один спиннер: декодирование → VAD/оценка шума → локальная ASR-транскрипция → выбор чистых сегментов → сборка профиля. Каждый шаг — отдельная строка статуса с процентом или счётчиком (например «сегменты: проверено 40/85, годных 12»), потому что ASR 15 минут — не мгновенная операция и владелец должен видеть, что процесс не завис.
- **Результат — не просто «готово»**: показать, сколько чистых референс-сегментов отобрано, их суммарную длительность, обнаруженные стили (нейтральный/энергичный/…), и дать явно прослушать 1–2 коротких сгенерированных тестовых фразы этим голосом перед тем, как профиль станет активным (это тот же owner listening test из §2, просто с нормальным UI, а не логом в консоли).
- **Понятные ошибки, а не стектрейс**: слишком короткая/шумная запись, музыка на фоне, несколько голосов в записи — каждая причина отказа формулируется по-человечески и подсказывает, что исправить (например «в записи слышно два голоса — нужна запись только владельца»), а не «ValueError: speaker_count != 1».
- **Отмена и повтор**: возможность остановить обработку долгого файла и загрузить другой без перезапуска бэкенда.

Это требование к UX, не к движку транскрипции/клонирования — реализация экрана/диалога подключается к тому же локальному пайплайну из §2, ничего нового в части полномочий или сети не добавляет.

## 3. Архитектура в существующем backend

```text
Call task + bounded owner grant
 → telephony adapter / SIP / verified number
 → signed incoming webhook + authenticated media stream
 → VAD / streaming STT
 → transcript as untrusted conversation data
 → Bossman task model + tool/policy checks
 → TTS from allowed own-voice profile
 → stream playback / interruption / hangup
 → reconciled provider status + task outcome receipt
```

Номер линии/оператор связи не заменяются одним OpenRouter key. Выбор провайдера, географии, номера, тарифа и доступности делается отдельно. Voice conversation может быть local-first по STT/LLM/TTS, но обычный телефонный вызов использует сеть оператора и не является полностью offline.

## 4. Кандидаты реализации и источники

Twilio Programmable Voice Media Streams — проверенный документальный пример transport: bidirectional WebSocket audio, `<Connect><Stream>`, проверка подписи. Это не решение о покупке Twilio. Его ограничения stream/DTMF проверять перед сценарием IVR; телефонное меню не обходить имитацией неподдерживаемого API.

ElevenLabs — optional cloud own-voice provider, не локальный runtime. Professional Voice Cloning требует подтверждения собственного голоса; cloud voice нельзя обещать экспортировать как локальные веса. Для local TTS выбрать совместимый лицензированный checkpoint по фактическому AMD/Windows benchmark, не по демо чужого GPU. Ссылки и границы: [SOURCES_AND_BASELINE.md](SOURCES_AND_BASELINE.md).

## 5. Runtime requirements

Измерять p50/p95 от конца реплики до начала ответа, STT ошибки по числам/размерам/адресам, TTS real-time factor, barge-in, echo, packet loss и reconnect. Latency target назначается до теста; если local slow, не переключаться скрыто на платный TTS. На стоимость резервировать минуты, распознавание, синтез и LLM.

STOP немедленно прекращает планирование нового speech/tool actions и посылает hangup; подтверждение закрытия звонка/stream логируется отдельно. Timeout не порождает автоматический повторный звонок. Busy/voicemail/wrong person фиксируются и не считаются выполнением цели. Обратный звонок и повторная попытка входят в заранее заданные call count и время.

Голос собеседника — не команда владельца. Просьба «пришлите паспорт/оплатите другой счёт» не расширяет делегацию. Разговор может собрать сведения, но покупку завершает отдельный commerce workflow. Recording по умолчанию выключен; streaming processing и сохранение аудиозаписи имеют разные согласия. До реального PSTN проверить применимые правила и правила провайдера для получателя/страны, не считать локальное owner consent универсальным разрешением записи чужого разговора.

## 5a. Фоновые звуковые эффекты в голосовых сообщениях (DRAFT, не реализовано)

**SPECIFICATION.** Ни один эффект, синтезатор эффектов или библиотека звуков этим разделом не подключаются и не покупаются.

Отдельный от enrollment запрос владельца: голосовое сообщение в Telegram через Jeff озвучивается собственным клонированным голосом (см. §1–2) и по явному указанию в том же запросе получает наложенный фоновый звук — например «на фоне полиция» или «шум ремонта у соседей». Это не искажение содержания речи, а добавление окружающего звука к дорожке; текст, который слышит получатель, должен точно совпадать с тем, что попросили озвучить.

### Почему это не тривиальная фича
Синтетический звук «сирена/ремонт» на фоне голосового сообщения — это создание обманчивого впечатления об окружении говорящего для получателя сообщения. У этого есть законные применения (шутка между своими, атмосфера для игры/подкаста, тест TTS-пайплайна) и есть однозначно запрещённые (создать у получателя ложное представление, что владельцу требуется помощь/что-то происходит прямо сейчас, чтобы получить деньги/действие; имитация звонка в экстренную службу; использование против третьего лица без его ведома). Граница проводится по получателю и по цели, не по факту «эффект есть», поэтому фиче нужен явный список разрешённых получателей/каналов и явное подтверждение цели при каждом использовании с малознакомым получателем — не разовое согласие на голос вообще.

### Обязательные требования перед реализацией
- **Источник эффектов**: только явно лицензированная библиотека звуков или локально сгенерированный шум (не запись реальных чужих экстренных вызовов/чужих квартир). Каждый использованный сэмпл — с источником и лицензией в манифесте, не «найдено в интернете».
- **Явная маркировка для владельца при создании**: перед отправкой Bossman показывает owner’у, что именно будет отправлено (текст + название эффекта + получатель), это отдельное подтверждение, не совпадающее с общим consent на голос из §2.
- **Ограничение на получателя**: эффекты, способные создать впечатление реальной опасности/экстренной ситуации (сирены, крики, взрыв и т.п.), разрешены только для получателей из отдельного allow-list «в курсе, что это эффект»; для остальных получателей такие категории эффектов не предлагаются вообще, а не просто «требуют подтверждения».
- **Никогда не как замена самого сообщения**: эффект не может исполнять роль контента (например, заменять словесную просьбу о помощи самим звуком сирены без слов) — это уже не эффект, а имитация происшествия.
- **Прослеживаемость**: task_id, voice_profile_id, effect_id/источник и получатель — в той же evidence-модели, что и обычное TTS-сообщение по §6; отзыв голосового профиля должен также блокировать использование эффектов с этим профилем.
- **STOP** останавливает генерацию/отправку так же, как обычное TTS-сообщение.

### Приёмка (добавление к §6)
E. Голосовое сообщение с разрешённым эффектом на разрешённого тестового получателя: владелец видит превью текста+эффекта до отправки, подтверждает, получатель получает именно это.
F. Попытка запросить эффект из ограниченной категории (имитация экстренной ситуации) на получателя не из allow-list — отказ с объяснением, не тихая подмена на безопасный эффект.
G. Отзыв голосового профиля во время ожидающей отправки с эффектом — сообщение не уходит.

Это черновой раздел для планирования после закрытия freeze 1.5–1.7; он не меняет статус §1–4 и не активирует голосовой enrollment.

## 6. Приёмка

A. Offline audio loopback с синтетическим собеседником.
B. Звонок на собственный/явно разрешённый тестовый номер: двусторонний диалог, interruption, STOP, cost receipt.
C. Отдельно разрешённый звонок магазину: конкретный вопрос, верный номер, представление ассистентом, outcome facts с указанием степени подтверждения.
D. No permission/expired grant/revoked voice/поддельный webhook/слова собеседника как owner instruction — отрицательные контроли.

API call completed не значит «товар есть». Вывод о наличии отмечать как устный ответ магазина, а не оплаченный заказ. Результаты и redacted transcript привязаны к task_id/voice/model/runtime/grant; samples не публикуются.
