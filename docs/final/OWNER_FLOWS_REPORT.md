# Сквозные владельческие потоки (раздел 21)

Задание запрещает заканчивать одними юнит-тестами: «Do not finish with unit
tests only. Run actual integrated workflows.» Семь потоков A–G прогнаны
инструментом `scripts/owner_flows.py`; машинный результат —
`docs/final/owner_flows.json`.

Правило, которое каждый поток соблюдает буквально (раздел 0):

```
внешний результат -> наблюдение -> НЕЗАВИСИМАЯ проверка Bossman
-> улика -> гейт завершения -> ЗАВЕРШЕНО
```

Поэтому каждый поток заканчивается **перечитыванием реальности** — файлом с
диска, проектом из базы после перезапуска процесса, повторным декодированием
видео, — а не ответом того, кто работу выполнял.

## Итог

| Поток | Что проверялось | Итог |
|---|---|---|
| **A** программирование | заявка → Mission IR → кодовый бэкенд → правка репозитория → независимый diff → тесты | **NOT_RUN** |
| **B** сайт | Веб-дизайнер → правка → превью → перезапуск → переоткрытие → настоящий браузер | **PASS** |
| **C** компьютер | Windows-MCP → окно → ввод → сохранение → перечитывание пост-состояния | **NOT_RUN** |
| **D** файлы | File Intelligence → анализ → предложение → исполнение → перечитывание → откат | **PARTIAL** |
| **E** видео | рецепты кадров → таймлайн → рендер → ffprobe → полное декодирование → переоткрытие | **PASS** |
| **F** память | сессия 1 решает → процесс убит → сессия 2 вспоминает | **PASS** |
| **G** составной | сайт + браузер + файл на диске + память одной задачей | **PASS** |

Четыре PASS, два NOT_RUN с названными причинами, один PARTIAL.

## B — сайт

```
проект из шаблона (id=1)
превью отдано сервером: 15268 символов
элемент выбран перебором: bd-13
правка применена: версия 1 -> 2
повторная правка: прежняя правка НА МЕСТЕ
после перезапуска процесса правка на месте
настоящий Chromium показывает правку владельцу: да
```

Отдельно проверена **историческая регрессия «Apply → revert»**, которую
задание называет поимённо: повторное применение НЕ откатывает предыдущую
правку. Второе применение получило 422 («внутри элемента есть вложенные теги»)
— и это правильный отказ продукта, а не сбой: важно, что первая правка после
него на месте.

Последний шаг — не «сервер отдал правильный HTML», а **отрисованная страница в
настоящем Chromium**, открытая через настоящий вход. Это разные утверждения, и
первое слабее.

## E — видео, целиком на настоящем FFmpeg

```
материал изготовлен и импортирован: 3 файла
раскадровка: 4 кадра, 8.5 с, ритм 0.50 с/удар (120 уд/мин)
нехватки названы вслух: кадр «benefit» пропущен — материала не осталось;
                        план короче цели на 0.5 с — рецепты не растягиваются
таймлайн собран НАСТОЯЩИМИ командами: 4 клипа
рендер и проверка: decoded=True passed=True 1280x720
файл переоткрыт с диска и декодирован ЗАНОВО: passed=True
отрицательный контроль (заведомо неверный ожидаемый размер): passed=False
```

Три вещи здесь важнее самого PASS:

1. **Нехватка материала сокращает план и называется вслух.** Три файла на пять
   рецептов — кадр «benefit» пропущен, и это написано, а не замазано. Задание
   запрещает изготавливать успех; здесь это видно в выводе.
2. **Отрицательный контроль.** Проверка вывода обязана уметь сказать «нет».
   Без этой строки «passed=True» ничего не стоило бы: функция, всегда
   возвращающая True, прошла бы поток.
3. **Переоткрытие.** Файл декодируется второй раз, уже с диска, а не по памяти
   о том, что рендер завершился успешно.

## F — память через настоящую смерть процесса

Сессия 1 и сессия 2 — **разные процессы** (`subprocess`), а не два объекта в
одном. Иначе «пережило перезапуск» доказывалось бы кэшем в памяти.

```
сессия 1 (отдельный процесс) записала решение и завершилась
сессия 2 (новый процесс) вспомнила: да
чужой репозиторий этого не видит: да
после обновления выигрывает новая версия: да
происхождение названо: да
```

Это ровно сценарий раздела 7, проверенный как ПОТОК, а не как модульный тест.

## G — составной

Одна задача, четыре независимых подтверждения: браузер показывает правку, файл
лежит на диске и перечитан, решение запомнено и пережило смену процесса.
Составной поток считается пройденным только когда подтвердились ВСЕ четыре.

## A — программирование: почему NOT_RUN, а не PASS

```
BOSSMAN_OPENHANDS_COMMAND не задан
127.0.0.1:11434 не отвечает
```

Поток A целиком состоит из работы модели над репозиторием: заявка → Mission IR
→ кодовый бэкенд правит файлы → независимый diff → тесты. Без модели и без
кодового сайдкара выполнять нечего. Можно было бы прогнать «каркас» — создать
задачу, посмотреть на переходы состояний — и записать PASS. Это было бы
подлогом: раздел 28 прямо запрещает считать недоступный бэкенд успехом.

## C — компьютер: почему NOT_RUN

Платформа прогона — Linux. Windows-MCP управляет окнами Windows. Раздел 29
допускает `TARGET_HARDWARE_READY` только если тесты действительно шли на
целевом классе машин; здесь тот же принцип на уровне ОС.

## D — файлы: почему PARTIAL, и одна моя ошибка по дороге

File Intelligence отвечает (HTTP 200), подсистема жива. Но предложить
содержательные имена файлов без локальной модели нечему, а исполнять
переименования, придуманные развёрткой, значило бы проверять развёртку, а не
продукт. Полный поток D — с анализом, предложением, исполнением,
перечитыванием файловой системы и откатом — остаётся владельческим.

**Ошибка, которую стоит записать.** В первом прогоне клиент ходил с заголовком
`Authorization: Bearer`, а продукт принимает `X-BCC-Token`. Все потоки получили
401 — и по этому 401 поток D едва не был записан как «подсистема отказывает
fail-closed, и это правильное поведение». Формулировка звучала убедительно и
была ложной: отказ по отсутствию аутентификации и отказ по существу — разные
вещи. Правильный ответ получен только после починки заголовка.

Инвариант: прежде чем объяснять отказ свойствами продукта, убедитесь, что
запрос вообще дошёл до продукта.

## Чего эти потоки не доказывают

* A и C не выполнялись вовсе — по ним нет ни положительного, ни
  отрицательного знания.
* D проверен до границы, за которой нужна модель.
* Ни один внешний OSS-бэкенд в потоках не участвовал: реестр адаптеров пуст по
  решению раздела 4. Потоки шли по РОДНЫМ путям Bossman, и это честное
  описание того, что сейчас есть.
* PASS означает «поток прошёл на этой машине в этом окружении», а не «работает
  у владельца». Целевое железо — `TARGET_HARDWARE_REPORT.md`.

## Как повторить

```
python scripts/owner_flows.py --json docs/final/owner_flows.json
python scripts/owner_flows.py --only E,F
```

Нужны `ffmpeg`/`ffprobe` (поток E) и Chromium (потоки B и G). Без них
соответствующий поток получает NOT_RUN с причиной, а не тихо «проходит».
