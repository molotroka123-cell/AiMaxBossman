## Общие правила

Использовать существующие backend, проекты и файлы, базу данных, память, реестр моделей, очередь задач, разрешения и журнал доказательств. CLI, UI и Telegram управляют одним экземпляром Bossman. Не создавать второе ядро, отдельную память терминала или параллельный движок задач.

Путь изменений: изолированный кандидат → заранее зафиксированные проверки → независимая верификация → ревью → разрешённое продвижение. Учительская правка, попадание в память, сценарная модель и учебный эксперимент на маленьком наборе не считаются доказательством самостоятельного обучения.

Каждая проверка фиксирует точный SHA, идентичность установки, отпечаток конфигурации, хеши набора данных и оценщика, время, реальные модели и инструменты, затраты и вмешательства учителя. Секреты в журнал не входят. Пороги и объём выборки определяются до запуска по существующему контракту; после результата их не меняют. Если контракт не задаёт порог, его утверждают до измерения.

P0 — остаток готовности 2.1 или обязательная общая защита. P1 — расширение 2.2. Отсутствие аппаратуры, доступа или независимых данных означает BLOCKED / OWNER_REQUIRED / INSUFFICIENT_EVIDENCE, а не PASS. Готовый коммерческий пилот можно принимать отдельно при прохождении его собственных обязательных проверок.

## A22-01. Идентичность и карта доказательств

**Исходное состояние.** Метаданные seed ещё содержат дату 05.10 и исторический source SHA. Реестр содержит 900 записей, включая 471 с уровнем `ci`, но ни одной с уровнем `owner_pc`. Это сохранённые квитанции разных коммитов. Несвязанный точный путь к файлу не означает потерянную функцию. Runtime сейчас недоступен.

**Реализация.** Переиспользовать `command-center/bcc/capability_tree_seed.json`, `docs/architecture/tree-registry.json`, `tools/tree_registry_sync.py` и `tools/tree_apply_evidence.py`, а также существующий верификатор сборки. Добавлять связи на уровне возможностей; не создавать по листу на каждый файл. Статусы применять через штатные инструменты с доказательствами.

**Предусловия.** Интегратор выбрал точный кандидат, сохранил чужие изменения и установил текущую идентичность backend. Доступны архив и его манифест.

**Вход.** Дерево репозитория, регистрации API/инструментов/UI, существующие квитанции, архив и установленный runtime.

**Выход.** Таблица «возможность → код → вход → проверка → квитанция», список отсутствующих и устаревших связей, сверенные SHA и хеш архива.

**Приёмка.** На настоящем Windows установленный runtime сообщает тот же source SHA, который записан в проверенном архиве. Все обязательные возможности имеют актуальные доказательства. Квитанция другого SHA, изменённый архив и неизвестный маршрут отклоняются отрицательными контролями. Остановка проверки сохраняет NOT_RUN; после перезапуска нельзя незаметно превратить незавершённую проверку в PASS. Отдельно сверяются данные опубликованного дерева.

**Зависимости.** Существующие сборка, API/OpenAPI, публикация дерева и правила release. Следующий шаг — восстановить доступ к runtime и определить его действительную идентичность.

## A22-02. Один Bossman в CLI, UI и Telegram

**Исходное состояние.** Клиент терминала и backend-инструменты существуют. Свежая сквозная проверка общего состояния не выполнена; часть файлов терминала и пульта изменена другими исполнителями.

**Реализация.** Использовать `command-center/bcc/terminal_cli/`, `command-center/bcc/features/terminal.py`, `command-center/bcc/telegram_companion/` и существующий движок задач. Клиент подключается к выбранному backend; не обходит его прямым вызовом модели или записью в базу.

**Предусловия.** A22-01, доступный owner-only пульт, диагностируемая идентичность экземпляра без раскрытия токенов.

**Вход.** Одна синтетическая задача и один тестовый файл проекта, доступные через три интерфейса.

**Выход.** Один ID задачи, одинаковые файлы, модель, разрешения, события и итоговый хеш результата.

**Приёмка.** На Windows задача, созданная в CLI, видна и продолжается через UI/Telegram. Разрыв соединения клиента не дублирует действие; повторное подключение получает продолжение журнала. STOP из Telegram останавливает ту же задачу и отображается в UI. После перезапуска backend сохраняются задача и привязка одобрения, завершённое действие не повторяется. Подключение к ошибочному экземпляру даёт явный отказ.

**Зависимости.** A22-01, A22-04, A22-05; контракт Terminal Run.

## A22-03. Реальный Computer Use на Windows

**Исходное состояние.** Наблюдение, UIA, привязка к HWND/PID, мышь/клавиатура и STOP имеют тесты с подменёнными адаптерами. В историческом аудите 11.10 работа на реальном рабочем столе не проверялась.

**Реализация.** Использовать `command-center/bcc/features/tools_computer.py`, существующие Windows-адаптеры, `command-center/ui/pages/control.js` и `tools/cu_acceptance/`. Действия браузера выполняются настоящими browser tools. Текстовое заявление модели не заменяет действие на компьютере.

**Предусловия.** A22-04, свободный рабочий стол, разрешённое безопасное приложение, например Блокнот, и заранее определённая область задачи.

**Вход.** Настоящая owner Telegram задача создать синтетический текст и сохранить тестовый файл; наблюдение исходного состояния.

**Выход.** Видимое состояние нужного окна, файл, наблюдения до/после, независимый вердикт и подтверждённая доставка в тот же пульт. Общий task ID прослеживается через все этапы.

**Приёмка.** На настоящем Windows неизвестный заранее безопасный вариант задачи выполняется мышью и клавиатурой. Окно подтверждено по HWND/PID. Неверное окно, устаревшее наблюдение, поле пароля и запрещённая комбинация клавиш не приводят к действию. STOP во время ожидания или ввода прерывает поддействия; RESUME требует нового наблюдения. Перезапуск сохраняет STOP и не воспроизводит старую команду. Отрицательный контроль «успех без изменения файла/окна» получает FAIL.

**Зависимости.** A22-01, A22-04, A22-05; доступ к реальному рабочему столу.

## A22-04. Разрешения, конституция и выход к провайдерам

**Исходное состояние.** Разрешения, компилятор естественных команд и approvals существуют. `BOSSMAN_LOCAL_ONLY` защищает границу вызовов моделей; это не общий сетевой экран. Браузер, почта, Telegram, скачивание и обновление каталогов требуют отдельной сетевой политики.

**Реализация.** Переиспользовать `command-center/bcc/permissions.py`, `command-center/bcc/v2/permissions.py`, `command-center/bcc/autonomy/constitution.py`, `command-center/bcc/features/nl_permissions.py` и `bossman_shared/privacy.py`. Свести решения AUTO/ASK/DENY на одних классах действий; не создавать второй механизм разрешений. Название uncensored не расширяет полномочия.

**Предусловия.** Одобренная владельцем конституция с версией, хешем, сроком и областью; модель не может изменять её сама.

**Вход.** Намерение вызвать инструмент, субъект доступа, область задачи, конфиденциальность и бюджет.

**Выход.** Проверяемое решение с причиной и ссылкой на одобрение, без секретов.

**Приёмка.** CLI/UI/Telegram дают одинаковое решение. Расширение прав требует владельца; самоодобрение модели невозможно. После таймаута локальной модели приватный запрос не уходит в облако, а завершается явным отказом. Разрешённое веб-исследование учитывается отдельно и не называется полной офлайн-работой. STOP имеет приоритет над ожидающим одобрением; перезапуск сохраняет запреты и привязки. Независимый скрытый набор включает prompt injection, перенаправления, варианты адресов, устаревшие одобрения, повторы и попытки доступа другого участника.

**Зависимости.** A22-02, A22-03, A22-05; независимое ревью безопасности.

## A22-05. Сохранность миссий, восстановление и лимиты

**Исходное состояние.** Очередь, повторы, fencing, журнал, аренды и бюджеты имеют исторический прогон из 98 тестов. Непрерывная работа установленного экземпляра без наблюдения владельца не доказана.

**Реализация.** Использовать `command-center/bcc/features/missions.py`, `command-center/bcc/engine.py`, `command-center/bcc/scheduler.py`, `command-center/bcc/mission_budget.py` и `command-center/bcc/autonomy/`. Один владелец задания, ограниченные повторы с задержкой, максимальное число сбоев, резерв диска и RAM. COMPLETE допустим только после наблюдаемого постусловия.

**Предусловия.** A22-04; зафиксированные лимиты, безопасные тестовые действия и политика восстановления.

**Вход.** Цель, постусловие, бюджет и разрешённые стратегии восстановления.

**Выход.** Миссия с контрольными точками, результатом и квитанциями либо доказуемым блокером.

**Приёмка.** На Windows перезапуск после действия, но до подтверждения его получения, не повторяет действие. Инъекции: остановка процесса, provider 503, потеря сети, заполненный рабочий диск, истёкшая аренда, устаревшее событие и частично записанный файл. Результат — ограниченное восстановление или BLOCKED, без бесконечных повторов. STOP прерывает инструмент и не возобновляет задание без разрешённого RESUME. После перезапуска согласованы аренды, бюджет, повторы и курсор. Скрытые проверки используют неизвестные моменты сбоя и конкурирующие миссии.

**Зависимости.** A22-01, A22-04; существующие целевые тесты очереди и восстановления.

## A22-06. Строгое самоисправление

**Исходное состояние.** Эксперимент 10.10 исправил ограничение CLI в 500 задач. Принятый patch получен прямым вызовом Mistral в обход инструментального цикла sidecar. Урок пережил перезапуск, но аналогичная задача goal-budget не решена; три цикла выполнены как 1 из 3.

**Реализация.** Использовать `tools/north_star/`, существующие coding tasks и local sidecar, изолированные рабочие копии, RESULT_VERIFIER и coding recipes. Сохранять неудачные и учительские попытки. Повтор известного исправления не считать новым циклом.

**Предусловия.** A22-04/05; три независимо обнаруженных реальных дефекта; хеши оценщика и скрытых проверок запечатаны до patch; учитель не сообщает решение.

**Вход.** Квитанция воспроизводимого дефекта.

**Выход.** Минимальный patch кандидата, регрессия красный→зелёный, отрицательный контроль, независимое ревью, проверенный урок и доказательство перезапуска.

**Приёмка.** Настоящий coding path на Windows записывает реальные worker/model ID. Исходная версия воспроизводит дефект; кандидат исправляет его, не подменяя существующие проверки. Плохой patch отклонён без изменения stable. STOP прекращает worker/проверку; перезапуск сохраняет курсор. Строгий первый цикл включает успешную аналогичную задачу после перезапуска; затем проходят три разных цикла без скрытой учительской правки. Скрытые проверки недоступны worker. Недоступность модели фиксируется отдельно от качества решения.

**Зависимости.** A22-01, A22-04, A22-05; действительно доступная модель и независимый оценщик.

## A22-07. Перенос навыка и сохранение способностей

**Исходное состояние.** TRANSFER_MEASURED_GAIN не запускался в сохранённом North Star эксперименте. Учебный Soup-пилот с 69% не прошёл собственный порог и не является доказательством переноса. Недостаточный корпус не заменяет требуемую выборку retention gate.

**Реализация.** Использовать `bossman-core/bossman/learning_guard/` и существующие механизмы скрытых наборов, A/B, продвижения и журнала доказательств. Разделять источники и семейства шаблонов обучения и проверки. Сравнивать исходную модель и кандидата на одном запечатанном наборе; статистический критерий и объём выборки определить до вызовов модели.

**Предусловия.** A22-06; независимо проверенные метки; воспроизводимая конфигурация; owner attestation на точный SHA, если его требует существующий процесс.

**Вход.** Версии baseline/кандидата/уроков и скрытый набор.

**Выход.** Ответы и трассы по каждому случаю, оценки, стоимость и вмешательства; вердикт улучшение/ухудшение/недостаточно данных.

**Приёмка.** После полного перезапуска Windows неизвестные аналогичные задачи выполняются без ответа учителя. Прежние способности не ухудшены по обязательным порогам. Источники и содержимое train/holdout не пересекаются. Загрязнённый или недостаточный корпус отклоняется до модельных запросов. STOP оставляет незавершённый прогон без итогового PASS; продолжение не пропускает неудобные случаи выборочно.

**Зависимости.** A22-06, A22-08, A22-09; независимая разметка и достаточная выборка.

## A22-08. Жизненный цикл памяти и уроков

**Исходное состояние.** BM25, SQLite, контекстные бюджеты, ранжирование и Obsidian присутствуют. Поиск записи не означает приобретения способности; тест чистой библиотеки не доказывает подключение всех путей runtime.

**Реализация.** Использовать tools_memory, context_engine, knowledge_fabric, memory_retrieval_v16, coding recipes и skill evaluations. Различать DRAFT/VERIFIED/REVOKED, происхождение, устаревание, противоречия и изоляцию участников. Контекст ограничен бюджетом.

**Предусловия.** A22-04/05; резервные копии и миграции; синтетические заметки вместо личных данных.

**Вход.** Проверенная квитанция или урок с хешем источника.

**Выход.** Версионированная запись, происхождение найденных фрагментов и собранный контекст.

**Приёмка.** Windows CLI/UI/Telegram используют одну версию урока. Непроверенное заявление не становится VERIFIED; отравленная, чужая, устаревшая или отозванная запись не расширяет права. STOP атомарно прерывает загрузку. После перезапуска база и индексы согласованы; повреждённый производный индекс перестраивается без потери базы. Независимый набор проверяет релевантность и бюджет поиска; рост способности оценивается отдельно в A22-07.

**Зависимости.** A22-04, A22-07; резервное копирование и миграции.

## A22-09. Обучение моделей и продвижение кандидатов

**Исходное состояние.** Soup отсутствует в feature-модулях проверенного unified HEAD. Отдельный PR #109 и текстовый пилот не являются внедрением в текущую установку, обучением видео или разрешённым продвижением модели. GGUF нельзя автоматически считать входом Transformers SFT.

**Реализация.** После ревью использовать существующий optional Soup adapter, model_foundry_v16, learning_guard и обычный запуск задания через терминал. Обучать изолированного кандидата в отдельном окружении. Разделять текстовый планировщик, OCR/vision, identity LoRA и diffusion/video: это разные задания и приёмки. Две фотографии не дают доказательства полного обучения тела и лица.

**Предусловия.** Проверенные лицензии весов и данных, происхождение и согласие; хеши, совместимость аппаратуры, бюджет RAM/диска; независимые группы источников train/holdout. Платное облако требует отдельного разрешения.

**Вход.** Манифест данных, хеш базовой модели и конфигурация тренера.

**Выход.** Checkpoint с манифестом, сравнение до/после и вердикт качества кандидата.

**Приёмка.** Реальное обучение на Windows создаёт новые веса и записывает шаги, время и ресурсы. Baseline и кандидат оцениваются одинаково на независимом наборе. Отсутствующие зависимости, несовместимый GPU и нехватка памяти дают явную ошибку без подмены mock. STOP сохраняет валидный checkpoint; продолжение после перезапуска ограничено и не переписывает базовые веса. Утечка между наборами и повреждённые веса отклоняются. Кандидат ниже порога не активируется. Production требует ревью, разрешённой promotion и retention на точном SHA.

**Зависимости.** A22-04/05/07/08; ревью optional Soup integration.

## A22-10. Загрузка сервера и прогоны 24/48 часов

**Исходное состояние.** Есть сервисные скрипты удалённого доступа, ожидание сети и ограниченные перезапуски. Холодная загрузка до готового пульта и 24 часа работы с настоящей моделью не подтверждены. Снятие пароля не является обязательным условием backend-сервера и не выполняется по этой спецификации.

**Реализация.** Использовать существующие Windows startup/service/launcher, remote_access.py, readiness/health, tools/ux_soak и autonomy supervisor. Различать headless backend и доступ к интерактивному рабочему столу. Claude Remote не должен быть единственным каналом управления.

**Предусловия.** A22-01/04/05; одобренное окно обслуживания, контрольные точки активных заданий, backup/rollback. Включение после пропадания питания требует подтверждения настройки firmware на реальном компьютере.

**Вход.** Запрос безопасной перезагрузки или план длительного прогона.

**Выход.** Квитанция boot→backend health→готовность пульта; отчёты 24h и затем 48h.

**Приёмка P0.** На Windows перезагрузка не обрывает активное обучение/рендер: сначала ожидание безопасной точки или отказ. После запуска сохранены исходники, данные и разделение stable/candidate. Неготовая модель отображается явно. STOP переживает reboot.

**Приёмка P1.** 24 часа, затем 48 часов настоящих ограниченных миссий с учётом модели, стоимости, RAM и диска. Внедряются сетевые и процессные сбои. Сценарный soak учитывается отдельно. Ошибка запуска даёт ограниченный повтор и видимый статус без шторма перезапусков. Независимая сверка событий и постусловий обнаруживает молчаливые сбои.

**Зависимости.** A22-01/05/12; owner hardware и согласованное обслуживание.

## A22-11. Подключение второго устройства

**Исходное состояние.** remote_client содержит регистрацию устройств и scoped token для chat/events/approve через Postgres. Работа второго ноутбука, общий вычислительный кластер и распределённый inference не доказаны.

**Реализация.** Использовать существующие DeviceService/store, `bossman-core/scripts/bootstrap_remote_device.py` либо проверенный owner UI, scopes, отзыв устройств и общий API. ID устройства не заменяет секретный credential. Не обещать объединение VRAM без отдельной реализации и проверки RPC.

**Предусловия.** A22-01/04/05; ноутбук владельца, защищённое соединение, достижимость сервера; сырые токены не попадают в отчёты и скриншоты.

**Вход.** Запрос владельца на подключение устройства и назначение scopes.

**Выход.** ID зарегистрированного устройства, защищённый credential и статус общего backend.

**Приёмка.** Два настоящих Windows-устройства работают с одним ID созданной задачи. Устройство без нужного scope не выполняет admin/reboot; отозванный токен и повтор запрещённого запроса отклоняются. Восстановление сети не дублирует действие. Разрешённый STOP с любого интерфейса останавливает одну общую задачу. После перезапуска сохраняются отзыв и идемпотентность. Независимые проверки включают чужое устройство, другого пользователя и правильный ID с неверным токеном.

**Зависимости.** A22-02/04/05/10; настройка сети владельцем, если требуется.

## A22-12. Оркестрация без Claude/Codex

**Исходное состояние.** Граф агентов, provider fleet, NL orchestra, economy swarm и Rave существуют. Квитанция графа не доказывает выполнение workers. Название модели и известный баланс не доказывают текущую доступность.

**Реализация.** Использовать существующие Rave/control_plane/organization/provider_fleet_v16, model_health, управление ресурсами и допуск задач. Независимые read-only аудиторы работают параллельно; общие файлы изменяет один интегратор. Приватные данные остаются в разрешённом локальном пути. В проверяемом production path явно отключить fallback на Claude/Codex.

**Предусловия.** A22-04/05; проверенная доступность моделей, лицензии и лимиты стоимости. Баланс при наличии read-only endpoint проверяется отдельно без вывода ключа; неизвестный баланс — UNKNOWN, а не ноль. Платные генерации не следуют из проверки ключей.

**Вход.** Ограниченная цель с независимыми параллельными стадиями.

**Выход.** Граф заданий, трассы реальных моделей/инструментов, проверенный результат, стоимость, повторы и задержка.

**Приёмка.** Настоящий Windows backend запускает две независимые стадии и их верификацию без Claude/Codex. Трасса подтверждает настоящие вызовы и инструменты. Сбой worker даёт ограниченное восстановление; недоступность провайдера отображается явно. Сообщение модели без результата не считается успехом. STOP прерывает весь граф и активные операции; перезапуск восстанавливает аренды без лишних процессов и повторного commit. Скрытые задачи отличаются от известных; неверный результат отклоняется отрицательным контролем. Скорость и стоимость последовательного/параллельного исполнения сравниваются на одинаковом наборе, экономия не предполагается заранее.

**Зависимости.** A22-04/05/07/10; отдельная проверка ключей и балансов интегратором.

## Итоговая приёмка и порядок работ

Матрица по ID использует NOT_RUN → RUNNING → PASS / FAIL / BLOCKED / OWNER_REQUIRED / INSUFFICIENT_EVIDENCE. Каждый итог связан с квитанцией; незавершённый прогон не получает PASS. Настоящее исполнение Windows описывается отдельно от mock и старых CI receipts.

Рекомендуемый порядок: A22-01 → A22-04/05 → A22-02/03 → A22-06 → A22-07/08/09 → A22-10/11/12. Зависимости описывают приёмку; они не запрещают независимую безопасную подготовку. Работать по одному законченному вертикальному шагу, переиспользуя существующие компоненты.

Обязательные P0 принимаются на одном точном SHA. Незавершённые P1 можно сохранить как план, но нельзя объявить всю 2.2 готовой. Учительские и самостоятельные результаты, локальные и облачные вызовы, техническая готовность и доход учитываются отдельно. Merge, публикация, замена установленной сборки и freeze выполняются только через существующий процесс с обязательными gates.
