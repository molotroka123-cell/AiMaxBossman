# Аудит: нагрузка на ПК и «само закрылось» (BOSSMAN desktop, UX2)

Дата: 2026-09-04. Ветка: `claude/bossman-control-v03-43igbk`. Проверено на машине владельца.

## Симптомы владельца

1. Двойной клик по `BOSSMAN.lnk` — окно не открывается.
2. Компьютер начал грузиться и шуметь.
3. В один из моментов окно (или процесс) «само закрылось».

## Факты из логов использования

- `%TEMP%\bossman-desktop.log` (запуск `pythonw -m bcc.desktop --host 127.0.0.1 --port 8801`):
  сервер `http://127.0.0.1:8801/` поднялся, Chrome с профилем
  `command-center/data/desktop-profile` запущен, ошибок нет.
- Профиль `desktop-profile/` содержит файлы Chrome (`Default`, `Crashpad`, …) —
  браузер реально стартовал и работал с этим профилем.
- После завершения: процессов `python/pythonw/chrome --app` нет, `SingletonLock`
  отсутствует — завершение было штатным (окно закрылось → `proc.wait()`
  вернулся → сервер остановлен → процессы вышли). Зомби нет.
- Топ процессов в момент жалобы: `OpenCode` (792 МБ — runtime агента),
  `audiodg`, `msedge`, `explorer`. Процессов BOSSMAN в списке нет.

## Почему грузился и шумел ПК

1. Первый старт Chrome с пустым профилем (`--user-data-dir` новый) — дорогая
   операция: создание профиля, `BrowserMetrics`, шейдерный кэш. Плюс uvicorn,
   плюс сам агент OpenCode (два процесса, до ~1 ГБ).
2. Каждый двойной клик при «не открывается» поднимал ещё один сервер + ещё один
   Chrome на том же порту/профиле — нагрузка складывалась.
3. Вывод: шум = сумма «первый прогрев Chrome-профиля» + повторные запуски
   + фоновый агент. Не утечка: после закрытия окна всё выгружается (проверено —
   процессов не осталось).

## Почему «само закрылось» (разбор)

Механика `bcc.desktop`: `launch_window()` ждёт `proc.wait()` — смерть процесса
Chrome автоматически останавливает сервер. То есть «само закрылось» = завершился
именно процесс Chrome, сервер лишь последовал за ним. Причины по вероятности:

1. **Второй Chrome на том же профиле (основная).** Второй процесс с занятым
   `user-data-dir` не открывает окно, а молча завершается (profile lock).
   Сценарий воспроизводится: мой диагностический запуск на `:8801` держал
   профиль, а параллельный даблклик по ярлыку (`:8800`) поднимал второй сервер
   и второй Chrome на том же профиле → мгновенный выход → «само закрылось».
   Исправлено: `desktop.lock` + отказ от второго окна с понятным сообщением.
2. **Тихий краш Chrome.** Каталог `Crashpad` в профиле есть; без `chrome_debug.log`
   доказать/опровергнуть было нечем. Исправлено: добавлен `--enable-logging`,
   теперь `desktop-profile/chrome_debug.log` пишется всегда.
3. **Окно за другими окнами / закрыто пользователем.** Нельзя исключить;
   теперь каждый запуск фиксируется в `data/desktop-run.log` (старт, код выхода
   браузера, время жизни), проверка занимает секунды.

## Что исправлено этим коммитом

- `command-center/bcc/desktop.py`:
  - `desktop-run.log` — постоянный журнал запусков (переживает `pythonw` без консоли);
  - `desktop.lock` — single-instance guard: второе окно при живом первом не
    запускается, возвращается код 0 с объяснением; мёртвый замок затирается;
  - замок снимается в `finally`, время жизни окна и код выхода логируются;
  - окно, прожившее < 10 с, печатает подсказку с путями обоих логов;
  - `--enable-logging` в `browser_argv` (флаги без секретов, как раньше).
- `command-center/tests/test_ux2_desktop.py`: +2 теста
  (`test_second_window_refused_while_first_instance_alive`,
  `test_fast_browser_exit_is_logged_with_hint`). Файл: 14/14 PASS.

## Как проверить владельцу

1. Даблклик по `BOSSMAN` → окно Command Center, вход по токену из
   `command-center\data\token` (один раз, дальше cookie).
2. Если окно снова закроется само: открыть `command-center\data\desktop-run.log`
   (последняя строка `browser-exit code=… lifetime=…`) и
   `command-center\data\desktop-profile\chrome_debug.log` — прислать обе строки.

## Остаточные риски (не подтверждены, наблюдать)

- Конкуренция за порт 8800 с ручным `bcc` (покрыта веткой «подключаюсь к нему»).
