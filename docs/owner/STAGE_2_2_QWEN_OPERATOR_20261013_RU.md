# Этап 2.2: локальная Qwen uncensored как оператор Bossman (L1 Lab)

Дата: 2026-10-13. Ветка: `feat/stage22-qwen-operator-20261013`. Конституция v1 не менялась и не обходилась.

## 1. Что сделано одной фразой

Владелец пишет в пульт `/work <задание>`; локальная Qwen uncensored планирует, зовёт бесплатные облачные модели
(исполнитель черновика и независимый проверяющий), правит исходники Bossman **внутри изолированной лаборатории**
(отдельный git worktree + ветка `lab/*`), сама гоняет тесты, коммитит в лабораторную ветку и присылает отчёт с
чеками. В основной проект ничего не попадает: push / merge / apply оператору недоступны.

## 3. Агент-оператор

Создан обычным `POST /api/agents` (значения даёт `qwen_operator.agent_values`):
`Qwen-Operator L1 (uncensored)`, role `operator:l1-lab`, модель `owner-local-community-uncensored`
(Ollama `bossman-community-qwen-uncensored:latest`), tools = `read_file, search, list_dir, edit_file, write_file,
run_tests`, `budget_usd = 0`, `require_tests_before_finish = true`.

Права записаны **областью** (`permissions.operator_l1`): запись/терминал только в лаборатории, git только commit на
`lab/*`, `git.push = false`, `git.merge = false`. Голых `filesystem.write` / `terminal.run` / `git.write` в строке
агента нарочно нет, поэтому общий tool-loop движка считает их невыданными (запрос подтверждения).

Роли (по умолчанию; меняются `POST /api/qwen-operator/config`):

| Роль | Модель по умолчанию |
|---|---|
| planner, coder, diagnostician | Qwen uncensored (`bossman-community-qwen-uncensored`, запасная `bossman-uncensored-chat`; отвечала первая) |
| verifier | бесплатная облачная модель другого семейства (OpenRouter `nvidia/nemotron-3-ultra-550b-a55b:free`, запас NIM) |
| worker (черновик) | та же бесплатная облачная |

Если ни одна бесплатная облачная не ответила: проверяющий = второй вызов той же локальной Qwen со свежим
контекстом, в отчёте строка `NOT_INDEPENDENT_same_model_fresh_context`; шаг worker = `NOT_RUN` с причиной.

## 4. Правила решений владельца (как велел владелец)

«У Qwen полный доступ, а на запретах он спрашивает меня и пишет рекомендации и опасения; стопов у модели нет.»

Что происходит на пункте из списка «всегда решение пользователя» (деньги, публикации/сообщения третьим лицам, ключи,
удаление данных, отключение защиты, конституция/гейт одобрений, force-push, деплой, push/merge):

1. шаг **не падает и не пропускается молча**: создаётся одна строка `approvals` (kind `operator_decision`);
2. владельцу в пульт уходит одно сообщение: точное действие, зачем, рекомендация оператора, опасения, кнопки
   «Разрешить / Отклонить» (`/work_yes N`, `/work_no N`);
3. остальные шаги продолжаются;
4. итог решения записывается честно:
   `APPROVED_EXECUTED` (разрешено и выполнено в лаборатории), `DENIED_BY_OWNER`,
   `APPROVED_BLOCKED_BY_RULE_4` (push/merge: владелец разрешил, но правило 4 конституции v1 требует одобрения
   Claude и Codex для того же SHA, оператор это не выполняет), `APPROVED_NOT_EXECUTED` (файлы
   конституции/гейта, деньги, публикации, ключи: это делает сам владелец).

Самокоррекция: максимум 3 попытки на ошибку; обязательная проверка (тесты именованы и проходят в лаборатории);
если хуже/не прошло, откат `git apply -R`, диагност объясняет причину, следующая попытка получает диагностику;
после 3-й попытки остановка с чистой лабораторией. Бесконечных циклов нет.

Дедлайна задачи нет (убран по решению владельца): задача ограничена только 3 попытками, проверкой и откатом и
**СТОП/паузой владельца**. У отдельных вызовов остаются технические тайм-ауты (одна команда, один вызов сайдкара).
Ожидание ответа владельца на решение тоже без срока (до ответа, СТОП или `/work_stop`).

СТОП владельца остаётся его выключателем: `<data>/computer/STOP`, `<data>/autonomy/STOP`, `delegation_locked`
пульта (`/stop`, `/pause`, `/lock`) блокируют старт `/work` и останавливают задачу между шагами; STOP отменяет
запущенный оператор (`cancel_agents`).

## 5. Контекст 256k (замер, не обещание)

`docs/owner/evidence/stage22/ctx_measurement.json`, реальная модель, ступени 32k / 131k / 262144:

| num_ctx | загрузка | итог |
|---|---|---|
| 32768 | 32 с | отвечает |
| 131072 | 59 с | отвечает |
| 262144 | 60 с | отвечает; `context_length` = 262144, размер в памяти 39,6 ГБ, свободной RAM 89,9 → 49,6 ГБ |

Машина держит 256k (RAM 119,6 ГБ, унифицированная). Условие: рядом не должна грузиться вторая крупная модель;
перед этим оператор выгружает базовый тег (`keep_alive=0`), все локальные роли работают через один производный тег
`...-ctx256k` (метаданные, веса не копируются), чтобы в памяти был один экземпляр. На ступенях 32k/131k `ps` не
вернул `context_length` (поле null): подтверждение контекста есть только для ступени 256k. Во время замера на машине
был виден рендер видео (sd-cli) в начале сессии; он не пострадал, но параллельная нагрузка на GPU не измерялась.

### Честные оговорки к прогону

* **Качество результата.** Докстринг модели утверждает «127.0.0.0/8», а функция сравнивает только с
  `127.0.0.1`, `localhost`, `::1`. Это неточность оператора, и независимый облачный проверяющий её **пропустил**
  (одобрил). Вывод: проверка одной моделью не заменяет глаза владельца/Claude+Codex на SHA; поэтому продвижение
  заблокировано, и коммит на ветке `lab/*` нужно просмотреть до любого релиза.
* Планировщик сам добавил команду «запустить тест» ещё до правки: она отработала в лаборатории (разрешена),
  вернула exit 4 «файл не найден» и записана в чек; обязательная проверка после правки прошла.
* Токены кодера сайдкар не вернул (в чеке `null`); время и результат тестов есть.
* Доставка в настоящий Telegram, живой backend и перезапуск **не** проверялись (запрещено в задании).
* Облачные шаги идут через управляемый free-only адаптер реестра, а не как отдельные задачи движка: в таблице задач
  Bossman эти вызовы не появляются (в чеке оператора есть модель/токены/стоимость).
* Ветка исполнения решения после одобрения (`APPROVED_EXECUTED`, `APPROVED_BLOCKED_BY_RULE_4`) проверена тестами с
  подменами (30 + 6 тестов), не живым прогоном с Telegram-кнопкой.
* Три ранних прогона в тот же день прервались до результата (ошибка кодировки вывода в моём скрипте, потом
  убитый фоновый процесс); остались лабораторные worktree `lab-*` в тестовом каталоге данных, они безвредны.

## 7. Что Qwen может сейчас / что требует поправки конституции

| Возможность | Сейчас | Нужно |
|---|---|---|
| Читать код/логи, планировать, звать бесплатные облачные модели | да | — |
| Править код Bossman в лаборатории, запускать тесты, коммитить на `lab/*` | да, без вопросов | — |
| Просить решение владельца с рекомендацией и опасениями (пульт, кнопки) | да, шаг ждёт, остальные идут | — |
| Править файлы гейта одобрений / конституции / бюджетов / ключей / собственный охранник | нет; решение владельца, оператор не исполняет даже после «Разрешить» | поправка конституции + ручное изменение владельцем |
| Выполнить `rm`, сеть, пакеты в лаборатории | после «Разрешить» владельца (однократно, в лаборатории) | — |
| push / merge / apply в основной проект | нет; «Разрешить» фиксируется как `APPROVED_BLOCKED_BY_RULE_4` | правило 4 v1: одобрение Claude **и** Codex на тот же SHA + Release владельца. В черновике v2 правило 4 заменено независимыми проверяющими моделями |
| Автоуровни L2-L4 (кандидат, безопасное применение, длинная автономия) | нет: пин конституции отсутствует, цикл автономии `BLOCKED` | владелец сам пинит файл (`bossman autonomy constitution pin`); v2-черновик: `C:\Users\asd\Bossman\creative-runs\STAGE-2-2-20261013\BOSSMAN_CONSTITUTION_v2_DRAFT.md` |
| Деньги, публикации, сообщения людям, ключи, деплой | только запросом решения владельцу; не исполняется оператором | — |

Важное различие: оператор запускается **командой владельца** (одно `/work` = одна задача, очереди целей нет), а не
циклом автономии, поэтому блокировка цикла из-за отсутствия пина его не отключает; но он и не расширяет права:
уровень остаётся L1 Lab.

merge). Оператор этого не делает.
