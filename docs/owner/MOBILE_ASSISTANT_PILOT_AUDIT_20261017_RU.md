## Что уже есть в коде

### Мобильный интерфейс

- PWA входит через owner pairing token; серверная сессия использует HttpOnly cookie и CSRF token. На входе предусмотрены ограничения частоты запросов.
- API ограничен allowlist; неизвестные пути отклоняются. Список агентов в мобильном клиенте ограничен локальными моделями, а неявный или удалённый выбор агента не принимается.
- Приложение создаёт и открывает беседы, отправляет сообщения, получает события/результаты через task endpoints и SSE, показывает запросы подтверждения владельцу.
- Команда остановки в мобильном потоке относится к выбранной задаче/диалогу. Её нельзя считать доказанным глобальным STOP для всех операций и очередей ПК.
- Текущий коммит добавил вкладку видео с каталогом, очередью и оценками времени. Это интерфейс статуса генерации, а не доказательство полного управления рабочим столом.

### Telegram и существующий компьютерный агент

- `/task` показывает задачу и требует краткоживущее одноразовое `/confirm` для исполнения; привязка результата проверяется по чату.
- `/search` ограничен владельцем и блокируется в состояниях STOP/pause. `/work` — ограниченный оператор изменений, не произвольный удалённый рабочий стол.
- PC-agent bridge имеет маршруты состояния, запуска/остановки/возобновления, аудита и подтверждений. Исходники и контрактные тесты есть, но живое управление экраном в этом аудите не запускалось.
- Есть уведомления о подтверждениях и завершённых задачах; `/watch` отслеживает потерю связи. Наличие отдельного watcher для входящей почты не подтверждено.

### Почта

- Gmail-интеграция предоставляет поиск и чтение. OAuth по умолчанию read-only (`gmail.readonly`); IMAP также ограничен чтением. Вложения не скачиваются.
- Агент допускается только при owner-привязке; гостевая привязка должна отклоняться. Отправка и черновики выключены по умолчанию, write-инструменты требуют отдельного запроса.
- Обработчики трактуют письма и веб-страницы как недоверенные данные. Тесты проверяют разрешённые цели, разрешения и подтверждение.
- В мобильном API отдельного почтового маршрута не найдено. Не подтверждён полный процесс «телефон → задача → разрешённый поиск/чтение Gmail → уведомление владельцу»; push-уведомлений о новых письмах не обнаружено.

## Что проверено

На точном SHA `e1f574b` мобильный набор тестов завершился: `125 passed in 5.36s`. Набор использует MockTransport и фиктивные состояния. Он проверяет протоколы мобильного клиента, но не телефон, домашний компьютер, браузер, почту или живую модель.

Контрактные тесты Command Center ранее прошли на `85f952b`: Gmail/браузер/задачи — 74; уведомления и fail-closed delegation — 2; PC-agent/STOP/approval — 83; Telegram PC-control — 9; ограниченный браузер и global STOP — 23; три повторно запущенных code-mode timeout-теста — 3. Проверено, что дерево `command-center` на `e1f574b` не изменилось относительно `85f952b`. Кроме того, объединённый набор этих контрактов запущен после fast-forward на точном SHA `e1f574b`: **194 passed in 169.71s**. Отдельный более широкий набор на старой точке дал `92 passed, 3 failed` из-за шестисекундного таймаута помощника; три целевых кейса позднее прошли отдельно. Исходный результат широкого набора остаётся FAIL.

## Рекомендуемый следующий шаг

На выделенной owner-only тестовой конфигурации подключить тестовый Gmail аккаунт только с правами чтения и synthetic-письмом. Затем одним коротким вертикальным тестом пройти мобильный запрос, показ подтверждения, разрешённые `search/read`, получение результата и audit receipt; параллельно на безвредном окне Notepad проверить видимый postcondition и фактическую остановку через мобильный и Telegram интерфейсы. Сохранить runtime/build/model идентичности и ресурсные замеры. До этих наблюдений считать пилот кодово подготовленным, но не production-проверенным.
