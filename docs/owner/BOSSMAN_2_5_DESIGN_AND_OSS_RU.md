# Bossman 2.5 — проект этапа и проверенные OSS-кандидаты

Дата снимка: 2026-10-18

Исходники Bossman: `ceee487e826b9c920655cc79fcb91096503766a4` (`main`)
Статус документа: дизайн и аудит исходного состояния; не сертификат готовности продукта.

## 1. Цель этапа

**Bossman 2.5 — единый проверяемый цикл выполнения поручений.** Владелец начинает
задание из Telegram, Command Center, мобильного приложения или CLI; тот же backend
выполняет разрешённые шаги, хранит один task ID и актуальный статус, проверяет
постусловие и возвращает результат с уликами. Интерфейсы являются разными окнами
одного Bossman, а не отдельными агентами.

Этап не означает полный доступ без ограничений, гарантированный доход или обучение
весов. Владелец остаётся владельцем решений о release, расходах и внешних эффектах.
Сетевые публикации, отправка людям, переводы, покупки и необратимые изменения не
попадают в автономный контур этого этапа.

### Вывод по готовности

Компоненты **частично существуют**, но Bossman 2.5 не найден как завершённый,
принятый этап. Ключевой разрыв — доказательства сквозного сценария на актуальном
исходнике и установленной Windows-сборке, а также владельческая проверка телефонного
пульта, STOP, авторизации и восстановления.

## 3. Definition of Done для 2.5

Все условия относятся к одному точному source SHA; Windows-результаты дополнительно
привязаны к hash установленного архива, run ID и версии harness.

1. **Один task record.** Telegram, мобильный UI, Command Center и CLI читают и
   обновляют один task ID, очередь, статус, результаты и approvals. Никакой второй
   memory store, worker core или permission engine для интерфейса.
2. **Права по умолчанию закрыты.** Аутентифицированный владелец; посторонний
   отвергается. Одобрение одноразовое, привязано к actor, task, точному действию и
   сроку. Любые `bypassPermissions` в рабочем пути блокируют live-приёмку до
   безопасного устранения и повторной проверки. Не обходить этот gate ради теста.
3. **Один STOP на контур.** Во время безопасного действия STOP запрещает новые
   операции, останавливает активный worker, переживает restart и не повторяет уже
   выполненный side effect. Проверить локальным тестовым приложением/fixture.
4. **Наблюдение и независимая проверка.** Для каждого эффекта есть свежая
   observation; успех устанавливается отдельным verifier/postcondition, а не
   сообщением модели. Сохраняются input/output hashes, tool/version, source,
   timestamp, status и причина отказа. Нет улики — `NOT_RUN`/`BLOCKED`.
5. **Восстановление.** Crash/restart продолжает по сохранённому checkpoint,
   перечитывает реальное состояние перед возобновлением и не дублирует внешний
   эффект. Сценарий неизвестного результата остаётся в `RECONCILE_REQUIRED`.
6. **Память без ложного обучения.** Уроки имеют происхождение, SHA, область
   применимости и состояние `DRAFT/VERIFIED/REVOKED`. До/после сравниваются на заранее
   замороженной unseen выборке; teacher patch, memory hit и повтор задания не
   засчитываются как transfer gain.
7. **Приёмка ограниченного набора.** До запуска зафиксировать минимум 30 безопасных
   holdout-сценариев по task lifecycle, browser read-only, локальным файлам,
   STOP/restart, неправильному пользователю и неизвестному исходу. Пороги и набор
   после результата не менять. Сохранить PASS/FAIL/BLOCKED/NOT_RUN и негативные
   контроли.
8. **Один полезный вертикальный сценарий.** Закончить одну локальную работу,
   например «взять синтетический контракт → разобрать страницы/таблицы → найти
   источник и поля → сформировать отчёт с цитируемыми фрагментами → проверить файл
   и вернуть его в тот же пульт». Личные данные и реальные внешние действия не нужны.
9. **Фактическая нагрузка и стоимость.** Записать p50/p95 задержки, peak RAM/VRAM,
   CPU/GPU время и стоимость платных вызовов (для этого прогона должна быть 0).
   Сравнить с baseline того же host; ухудшение не скрывать.
10. **Идентичность релиза.** Матрица возможностей синхронизирована штатными
    инструментами. Source SHA, tree source SHA, installed build/archive hash,
    test run ID и commit отчёта согласованы. Без owner-PC acceptance не заявлять
    production/freeze.

Критерии качества для автоматизации следует объявить до прогона. Системные
безопасностные критерии: 100% отказов неавторизованных действий, 100% STOP-проверок
останавливают тестовый worker, 100% заявлений `VERIFIED` имеют verifier receipt.
Порог успеха holdout нельзя выбирать после просмотра результата; его фиксирует
исполнитель из действующего acceptance harness и публикует до запуска.

### Отдельный риск MCP

MCP расширяет поверхность инструментов, а не добавляет права. Каждый сервер должен
получать минимальный allowlist методов; tool arguments валидируются по схеме; текст
страниц/документов помечается как недоверенные данные; вызов обязан наследовать task
identity, approvals, timeout, STOP и audit receipts существующего Bossman. Не заводить
вторую очередь или отдельные credentials. Репозитории без обнаруженной явной
лицензии не копировать: в частности, не включать неподтверждённый `ted-mcp`.

## 6. Порядок одного приёмочного прогона

1. Перечитать применимый `AGENTS.md`, `origin/main`, dirty state, точный source SHA,
   актуальную acceptance matrix и runtime identity. Старый реестр/отчёт считать
   историческим до проверки хэшей.
2. Сначала аудитировать безопасность и активную конфигурацию по разрешённому
   локальному owner runbook. Не читать секреты и не включать неизвестный режим.
   При активном `bypassPermissions`, смешанных версиях или неопределённом владельце
   остановить только live-сценарий и записать `BLOCKED`.
3. На основании кода и существующих тестов выбрать один самый короткий сквозной
   безопасный сценарий. Запустить только его целевые регрессии и acceptance harness;
   не запускать платные запросы, real messaging, покупки, деплой или destructive
   компьютерные операции.
4. Пять OSS-кандидатов минимум сверить по точному upstream SHA/license и выполнить
   compatibility review. Интегрировать только кандидата, у которого PoC доказал
   измеримую пользу; если внедрение не нужно для DoD, оставить его рекомендацией.
5. Сделать предрегистрацию holdout и порогов до измерения. Запустить baseline/after
   с одинаковыми задачами, моделями, seed, средой, budgets и evaluator. Скрытый набор
   не раскрывать модели/патчу до фиксации кандидата.
6. Сохранить исходные логи/receipts, SHA файлов, расход, resource metrics и
   скриншоты реального UI, если owner-run UI доступен. Если недоступен — `NOT_RUN`,
   не макет и не скриншот старой сборки.
7. Проверить `git diff`, секреты, лицензии, тестовые результаты и соответствие SHA.
   Не делать автоматический merge/release. Итог `BOSSMAN_2_5_READY=PASS` возможен
   только при закрытии всех обязательных DoD; иначе список точных блокеров и один
   следующий безопасный шаг.

## 7. Скриншоты

На снимке исходников не было получено нового изображения реального UI. Для 2.5 нужны
скриншоты из свежей локальной/owner-run сборки: очередь с единым task ID, approval,
STOP в действии, финальный verifier receipt и экран capability status. Каждый снимок
связывается с source SHA, build hash, временем и run ID; личные сообщения, фото,
секреты и несвязанные окна не снимать. Макеты, README-картинки и старые снимки не
считать доказательством работы.
