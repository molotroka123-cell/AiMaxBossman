## 1. Что было сломано и что делает фикс (проверено чтением кода)

1. `Watchdog._healthy(pid)` в `bcc/pit/heartbeat.py` раньше возвращал `beat.pid == pid and availability == "up"`, где `pid` = `Popen.pid` процесса, который сторож сам породил (`cmd_watch.spawn`: `[sys.executable, "-m", "bcc.pit.cli", "start", ...]`).
2. На Windows `python.exe` из venv — лаунчер (redirector): он запускает настоящий интерпретатор базового Python как ДОЧЕРНИЙ процесс. `Popen.pid` — PID лаунчера, а `Heartbeat.snapshot()` пишет `os.getpid()` — PID настоящего интерпретатора. Эти числа не равны никогда.
3. Это не «обычный выход ребёнка принят за смерть»: ветка выхода (`child.poll() is not None`) ни при чём. Ломалась проверка здоровья: после `startup_grace` (90 с) свежий heartbeat считался «чужим», `_healthy` = False, сторож делал `_end_child(child, 0.0)` (terminate/kill) с причиной `unhealthy` и перезапускал здорового Jeff по backoff — вживую 30.09: ~16 рестартов в час, каждые 2-4 минуты.
4. Фикс (коммит `2bbd28aa`): `_healthy` принимает heartbeat, если `availability == "up"` И (`beat.pid == pid` ИЛИ `beat.pid` входит в `psutil.Process(pid).children(recursive=True)`; хелпер `_descendant_pids` без psutil / при исчезнувшем процессе возвращает пустое множество и не падает).
5. Негативные контроли остались: чужой PID и протухший (`stale`) heartbeat по-прежнему «нездоровы»; тесты — `command-center/tests/test_jeff_watchdog_launcher_pid.py`, плюс два реальных процессных теста сделаны launcher-aware.
