**Моё решение по упаковке:** завтра можно готовить **честную продажную демонстрацию одного сценария**, если D1 подтверждён. Называть всю систему production-ready или Tier 5 до D3/полной приёмки нельзя. В коммерческих материалах показывать конкретный работающий результат и список ограничений, а не число функций как сертификат.

## 3. Одна архитектура для ускорения

`телефон / Telegram / Command Center / CLI → существующий Task Kernel → policy, approval, budget, STOP → разрешённый инструмент / локальная модель → независимая проверка результата → один receipt и UI`.

Мои предложения:

1. **Свести показ к одному вертикальному заданию.** Нужен не новый «Bossman 3», а один общий task ID от команды до результата. На всех экранах показывать одну и ту же заявку, статус, цену и ошибку. Любой внешний эффект отдельно требует своего существующего разрешения.
2. **Убрать ложное завершение.** HTTP 200, ответ модели, созданный файл и `pytest PASS` — разные свидетельства. Завершение ставит независимый verifier после проверки постусловия; неизвестный исход остаётся `UNKNOWN/RECONCILE_REQUIRED`.
3. **Продвигать кандидата по одному SHA.** Код и навык появляются в изолированном worktree; затем проверка, owner review/Apply, сборка, установка, архив/hash, live owner-run. Красный required CI блокирует выпуск; документация не перекрашивает его.
4. **Самоулучшение измерять, а не объявлять.** Заморозить неизвестные разработчику задания и оценщик; измерить baseline локальной модели, позволить ей предложить ограниченную правку, отдельно проверить результат, повторить после restart и оценить перенос. Улучшенный промпт — не обучение весов; запись в память — не прирост интеллекта. Никакой кандидат не редактирует stable напрямую.
5. **Локальность как контракт.** Личные чаты, фото, клиентские записи и ключи остаются на ПК. Публичные источники отмечаются URL, временем и лицензией; в облако только минимальный очищенный проектный пакет с разрешением и cap.

## 5. Обязательные владельческие и технические ворота

- **G0 — источник и выпуск:** свежий `origin/main`; `git status`; required CI без необъяснённых failure/cancelled; source SHA, архив/hash, installed SHA и runtime `/health/live` совпадают. Проверка tree/meta отдельно. Исторические screenshots не переносятся на новую сборку.
- **G1 — реальные действия:** одна миссия через существующие интерфейсы; независимое постусловие; STOP отменяет очередь и запрещает поздний side effect; после restart не появляется дубль. Следы содержат минимум данных и не раскрывают ключи.
- **G2 — локальный агент:** известны модель, контекст, latency, RAM/VRAM и цена для этой миссии. При недоступной модели нет тихого переключения на платную/облачную. Советы модели не расширяют permissions.
- **G3 — самоулучшение:** сохранены baseline, untouched holdout, evaluator, diff, отрицательный контроль и повтор после рестарта. Owner Apply остаётся отдельным действием.
- **G4 — продажа:** легальный публичный/лицензированный источник, калькуляция, качество результата, клиентское согласие и отдельный факт оплаты. Реальная торговля, кошелёк, публикация, массовая рассылка и платный вызов не запускаются документом.

При провале gate сохранять `FAIL/BLOCKED/NOT_RUN` и короткий receipt с точной причиной. Откат должен возвращать **предыдущую принятую сборку и её данные**, а не только Git HEAD. Для первой клиентской поставки нужны резервная копия, пробное восстановление, ручной запасной процесс и контакт ответственного человека.

## 7. Моя первая рекомендация интегратору

**Один следующий шаг:** дождаться завершения required CI на `ef3cae25`, собрать сырые логи каждого текущего failure/cancelled и сопоставить с предыдущим `026df035`; выбрать первый воспроизводимый дефект, исправить в существующем модуле и показать зелёный чек на точном новом кандидате. Параллельно без изменения кода подготовить сценарий owner-run и один коммерческий образец из [пилотов](COMMERCIAL_PILOTS_RU.md). Если `main` уже ушёл, переснять базу до работы.

**Мои гипотезы о выгоде:** чистый выпуск уменьшит срывы показов; одна миссия улучшит доверие; War Terminal или SwapMe быстрее дадут проверяемую полезность, чем ещё десять функций без поставки. Эти гипотезы надо измерять временем до результата, числом исправлений владельца, затратами и фактом приёмки, а не числом строк кода.
