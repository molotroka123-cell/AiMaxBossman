# ТЗ: обучение LoRA на собственных фото владельца (локально) — 08.10.2026

Статус: ПЛАН. Ничего не обучено. Всё ниже — NOT_RUN до запуска на ПК владельца.
Цель: модель, которая держит внешность владельца на локальной базе лучше последнего прогона, и это проверено на отложенной выборке и слепым сравнением с эталоном.

## 1. Что берём и чего не берём
- Данные: только фото владельца, полученные им самим. В обучающий набор не попадают фото других людей, экраны, чужое видео и скриншоты из видео других людей. Если на фото есть посторонние — кадр исключается или обрезается.
- Согласие: владелец сам. Запись в `consent.md` в папке датасета: кто, когда, для чего. Без этого файла обучение не начинать.
- Эталон качества (правая сторона примера) — только как образец того, чего хотим по стабильности, а не данные для обучения.
- Базовая модель: владелец указывает одну локальную базу (чекпоинт и версия). Базу не менять, веса не перезаписывать.

## 2. Датасет
- 25–40 фото, разные ракурсы, освещение и выражения лица; разрешение не меньше 1024 по короткой стороне; без сильного сжатия.
- Удалить дубликаты и размытые кадры (порог резкости — фиксировать в отчёте).
- Подписи: короткие, с уникальным триггер-токеном (например `OWNERX`), без выдуманных деталей.
- Сплит: train — основной набор; validation — 5 фото, не участвуют в обучении, для ранней остановки; holdout — 5–10 фото или фиксированный набор, который никогда не попадает в обучение и используется только для финального замера.

## 3. Обучение
- Только LoRA, базовые веса заморожены. Ранг и шаги фиксировать до запуска и записать в конфиг.
- Сохранять контрольные точки каждые N шагов; выбирать по validation, не по красоте на глаз.
- Все параметры, версия базы, хэши датасета и конфиг пишутся в манифест запуска.

## 4. Проверка (что считаем доказательством)
Заранее, до обучения, фиксируются пороги:
1. **Идентичность:** косинусное сходство эмбеддингов лица на holdout-фото против обучающих фото владельца — порог X (определить на базовой модели без LoRA как нижнюю границу).
2. **Переобучение:** генерации под промптами вне датасета (фон, одежда, освещение) не должны копировать кадры из train — проверка ближайшего соседа по эмбеддингу; порог Y.
3. **Артефакты:** доля генераций с явными дефектами (руки, лицо, двоение) по фиксированному набору из 30 промптов; порог Z.
4. **Слепое сравнение:** владелец сам смотрит пары «до/после» и эталон на одинаковых промптах, не зная, какая сторона какая. Преимущество нового варианта считается по числу выборов.
Отчёт: все четыре числа, сравнение с базой без LoRA и с предыдущим прогоном, вердикт PASS / FAIL / INSUFFICIENT_EVIDENCE. FAIL и INSUFFICIENT — честные ответы, их не скрывать.

## 5. Что НЕ считается доказательством
Один удачный кадр, визуальное «вроде похоже», лучший из N прогонов, тест на фото из train, оценка без слепого сравнения.

## 6. Приёмка и откат
- Новый адаптер регистрируется как версия с хэшем; предыдущая остаётся доступной.
- Промоция только если все четыре порога пройдены. Иначе — откат к предыдущей версии или к базе без LoRA.
- Адаптер не включается автоматически в стабильную сборку; только через кандидатный поток с подтверждением владельца.

## 7. Приватность
- Фото хранятся только на ПК владельца, в папке данных вне репозитория. В GitHub не публикуются ни фото, ни эмбеддинги, ни пути — только агрегированные числа и хэши.
- Удаление по запросу владельца: датасет, манифесты с путями и адаптеры удаляются; в отчёте остаётся только дата удаления.

## 8. Железо и окружение
- Обучение на ПК владельца (AMD/Windows). Есть ли рабочий путь обучения на его GPU, не доказано: `pv-lora-train` и `cap-36` в дереве — blocked/idea. Сначала проверка окружения (`env_check`), затем обучение. Если путь не работает — честный вывод: NOT_RUN, без облачных GPU без отдельного разрешения владельца.

## 9. Порядок работ
1. Владелец кладёт фото в папку датасета и пишет `consent.md`.
2. Проверка окружения и базовый замер без LoRA (пороги из п.4).
3. Обучение пробного адаптера (короткий прогон) — проверка, что процесс вообще идёт.
4. Полное обучение с фиксированным конфигом.
5. Замеры по п.4, слепое сравнение владельцем, отчёт, вердикт.

## 10. Дополнение владельца: выбор архитектуры и 30 фото через Higgsfield (08.10)

Владелец поручил локальному Claude: самому выбрать лучшую архитектуру для сборки Genjutsu (несколько моделей) и после 10 своих фото сгенерировать через Higgsfield API 30 фото для обучения. Главное требование — **модель стабильно держит одного владельца**. Ниже — условия, при которых это можно считать доказанным.

### 10.1 Выбор архитектуры (решает локальный Claude, по замеру)
- Кандидаты: минимум два реально установленных на ПК (в том числе путь Wan2.1 VACE через `stable-diffusion.cpp`, описанный в `bugtest-20261001/genjutsu/GENJUTSU_LOCAL_RU.md`) плюс Genjutsu от Higgsfield как внешний эталон. Список определяется по тому, что реально стоит на ПК, не по памяти.
- Все кандидаты гоняются на одном и том же фиксированном наборе запросов и считаются по одним и тем же четырём метрикам из раздела 4. Выбирается кандидат, прошедший пороги; победа «на глаз» не засчитывается.
- Если кандидатов с рабочим обучением на AMD/Windows нет — вердикт NOT_RUN и список того, что нужно (не выбирать архитектуру по обещаниям из README).

### 10.2 Фото владельца и отложенная выборка
- 10 фото — слишком мало, чтобы одновременно обучать и проверять. Либо владелец даёт 14–16, либо **минимум 3 из 10 откладываются в holdout**: они не загружаются в Higgsfield и не попадают в обучение.
- Эти фото — только владельца, без посторонних, с `consent.md` (раздел 1).

### 10.3 Генерация 30 фото через Higgsfield (синтетика)
- Это платное внешнее действие и передача фото владельца стороннему сервису. Выполняется только на ПК, только после явного подтверждения владельца на каждый запуск. Бюджет задаётся заранее: сначала запрос цены (`prepare`/quote), максимум кредитов, без автоматического продолжения при превышении. В журнал пишутся хэши отправленных файлов, не сами фото.
- Синтетика **не получает статус «топовых» автоматически**. Каждое сгенерированное фото проходит фильтр: сходство лица с реальными фото владельца не ниже порога, нет явных артефактов (руки, лицо, двоение), нет дублей. Прошедшие помечаются `synthetic`.
- Риск: 30 синтетических против 7–10 реальных — это до ~80% синтетики, и модель может «выучить стиль Higgsfield», а не лицо. Поэтому: вес реальных фото выше (повтор), доля синтетики в батче ограничена и фиксируется в конфиге.
- Доказательство пользы синтетики — только сравнением: (A) обучение на реальных фото, (B) реальные + прошедшая фильтр синтетика. B берётся в сборку, только если превосходит A на holdout по метрикам раздела 4 и в слепом сравнении. Иначе синтетика не используется.

### 10.4 Что считается провалом
Сходство на holdout ниже порога; рост артефактов относительно A; слепое сравнение не в пользу B; любое использование holdout-фото при генерации или обучении.

### 10.5 Что нужно от владельца
Название базы/кандидатов (по списку установленного), 10–16 фото + `consent.md`, лимит кредитов Higgsfield на эксперимент, подтверждение на каждую платную генерацию.
