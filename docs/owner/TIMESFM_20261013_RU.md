## 3. Честный бэктест (rolling origin)

Протокол: на каждом срезе `t` все методы видят только `y[:t]` и прогнозируют `y[t:t+h]`. Срезы равномерно по второй половине ряда. **Основной прогон — 40 срезов**, контрольный — 20 срезов (тот же вывод, кроме оговорённых строк). Метрика — MASE (MAE, делённая на MAE одношагового наивного прогноза на истории; ниже — лучше; <1 значит лучше наивного шага). В скобках — MAE в единицах ряда (для приватного ряда MAE не публикуется). Покрытие — доля фактических точек внутри полосы TimesFM q0.1–q0.9 (номинал 80%). Базовые линии: последнее значение, сезонный наивный (период указан), скользящее среднее (окно = период; для BTC — 10), ETS (statsmodels Holt-Winters, без тренда, аддитивная сезонность при достаточной длине).

Ряды (все локальные, только чтение, копия БД снята через sqlite backup в scratch):

|---|---|---|---|
| `bossman_cpu_pct_1min` | `bcc.db` → `system_metrics.cpu_pct`, среднее за минуту, 12.10 10:46 – 13.10 10:46 | 1441 | 1 мин / 60 |
| `bossman_events_per_hour` | `bcc.db` → `events`, число событий в час, 29.09 – 13.10 | 331 | 1 ч / 24 |

Вывод без приукрашивания:
- **Выигрыш есть там, где у ряда есть структура** (поток событий Bossman с суточным ритмом): TimesFM лучше всех базовых линий на всех трёх горизонтах, на 16–33% по MASE, в обоих прогонах.
- **Цена BTC (тики OCR) — TimesFM ПРОИГРЫВАЕТ** «последнему значению» на всех горизонтах (на 4–33%). Это случайное блуждание: ни одна модель тут не даёт преимущества, и TimesFM не исключение.
- **Загрузка CPU по минутам — TimesFM проигрывает «последнему значению»** (на 40 срезах на всех горизонтах; на h=60 заметно, на 29%). Выиграл только h=1 в прогоне на 20 срезах — то есть результат неустойчив.
- **Приватный дневной объём** — TimesFM лучший на 7 и 30 днях, но отрыв от ETS маленький (3–5%) и MASE ≈ 0.96–0.97, то есть почти уровень наивного шага; на 1 день — ничья с ETS / проигрыш сезонному наивному на 20 срезах.
- Полоса q0.1–q0.9 откалибрована прилично: 77–94% при номинале 80% (чаще шире, чем нужно).
- Срезов 20/40 — это мало для статистической значимости, особенно на коротких рядах (234–331 точки). Разницы в 3–5% надо считать ничьей.

Повторить замер: `command-center/scripts/timesfm_backtest.py` (запуск из venv TimesFM; пути к копиям БД и к приватному CSV передаются аргументами; приватный ряд печатается только безразмерными метриками).

## 4. Как включить в Bossman

Компонент — `command-center/bcc/forecast/timesfm_local.py`, маршруты — `command-center/bcc/features/forecast.py`. По умолчанию **выключено**. Включается переменными окружения бэкенда:

```
BOSSMAN_TIMESFM=1
BOSSMAN_TIMESFM_PYTHON=C:\Users\asd\Bossman\venv-timesfm-20261013\Scripts\python.exe
BOSSMAN_TIMESFM_MODEL_DIR=C:\Users\asd\Bossman\models\timesfm\timesfm-2.5-200m-pytorch
# необязательно: BOSSMAN_TIMESFM_TIMEOUT_S=120
```

После перезапуска бэкенда:
- `GET /api/forecast/status` — доступно ли, причина если нет, модель/ревизия/лицензия, лимиты, загружена ли.
- `POST /api/forecast` с телом `{"series": [числа], "horizon": 30}` → `point` (прогноз), `quantiles` {`0.1`…`0.9`}, `model`, `revision`, `license`, `package` (версии timesfm/torch), `model_ms`, `total_ms`, `disclaimer`.

Без переменной/весов/runtime ответ — 503 `unavailable: <причина>` (например «disabled: set BOSSMAN_TIMESFM=1», «model not found: …»). Оба маршрута — под токеном владельца.

Устройство: модель грузится лениво при первом прогнозе в отдельном процессе изолированного venv (torch не попадает в интерпретатор Bossman), запросы идут из рабочего потока по одному, event loop не блокируется, жёсткий таймаут убивает зависший воркер. Альтернатива — extra `bossman-command-center[forecast]` (ставит `timesfm[torch]==3.0.2` прямо в Bossman; в `runtime` НЕ входит).

Лимиты: ряд 16…4096 точек (модель смотрит на последние 1024), горизонт 1…256, только конечные числа, |x| ≤ 1e12, один прогноз одновременно.

## 5. Чем это НЕ является

- **Не торговый совет и не гарантия.** На цене BTC модель хуже «завтра будет как сегодня». Использовать прогноз для сделок нельзя.
- Не прогноз «по смыслу»: модель видит только числа одного ряда, без новостей, ковариат и календаря (XReg-ковариаты 2.5 не подключены).
- Не замена простым правилам: на шумных рядах без структуры (минутная загрузка CPU, тики цены) «последнее значение» точнее.
- Не TimesFM 3.0 (его веса некоммерческие) и не GPU: на CPU один прогноз ≈0.2–0.7 с, пакеты медленные.
- Тесты в CI идут на фейковом прогнозаторе; настоящий прогноз проверяется локальным тестом, который в CI пропускается.
