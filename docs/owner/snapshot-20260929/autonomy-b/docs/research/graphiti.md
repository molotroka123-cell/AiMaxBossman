## 2. Что делает на самом деле (по исходникам)

### 2.1 Модель данных

Три вида узлов и рёбра между ними (`graphiti_core/nodes.py`, `edges.py`):

- **`EpisodicNode`** — сырой кусок входа (`content`), его тип (`message`/`text`/`json`),
  `valid_at` (когда эпизод произошёл), `created_at`, `group_id` (раздел графа).
- **`EntityNode`** — сущность: `name`, `summary`, `name_embedding`, `attributes` (типизированные
  поля из пользовательской Pydantic-модели), `labels`.
- **`CommunityNode`** — кластер сущностей (строится отдельной операцией, не на каждом эпизоде).
- **`SagaNode`** — цепочка связанных эпизодов (нововведение свежих версий).
- **`EntityEdge`** — **и есть «факт»**: поля `name` (тип связи), `fact` (текст факта),
  `fact_embedding`, `episodes` (какие эпизоды его породили) и четыре временных поля.

### 2.2 Bi-temporal: как именно это реализовано

Четыре поля на ребре — это и есть весь механизм (`graphiti_core/edges.py`, класс `EntityEdge`):

| Поле | Смысл | Ось |
|---|---|---|
| `valid_at` | когда факт **стал** правдой в мире | event time |
| `invalid_at` | когда факт **перестал** быть правдой в мире | event time |
| `created_at` | когда граф **узнал** о факте | transaction time |
| `expired_at` | когда граф **пометил** факт устаревшим | transaction time |

Ключевое: **старое ребро не удаляется**. Оно остаётся в графе с проставленными
`invalid_at` и `expired_at`. Это и есть заявленный bi-temporal: можно спросить «что мы
считали правдой на дату X» и «что было правдой на дату X» — это разные запросы.

**Проверено экспериментально** (`/tmp/research/graphiti-exp/run2.py`, part A). Два эпизода:
«BOSSMAN хранит состояние в SQLite» (valid_at 2026-01-10), затем «BOSSMAN переезжает на
Postgres» (valid_at 2026-06-01). Итоговое состояние графа:

```
'BOSSMAN использует Postgres как хранилище'
   valid_at=2026-06-01  invalid_at=None        expired_at=None
'BOSSMAN использует SQLite как хранилище'
   valid_at=2026-01-10  invalid_at=2026-06-01  expired_at=2026-08-28 10:30:33  ← перекрыт
```

Механизм работает и работает красиво. `invalid_at` старого ребра проставлен **не «сейчас»,
а `valid_at` нового ребра** — то есть в терминах реального мира, а не в терминах момента
записи. Это правильная реализация.

### 2.3 КАК разрешается противоречие — самое важное наблюдение

Разрешение противоречий **не автоматическое и не детерминированное. Это решение LLM.**

Цепочка (`graphiti_core/utils/maintenance/edge_operations.py`):

1. Для нового ребра ищутся кандидаты-«противоречия» гибридным поиском
   (`EDGE_HYBRID_SEARCH_RRF`) — строки 407–420.
2. `resolve_extracted_edge()` шлёт LLM промпт `dedupe_edges.resolve_edge` со списком
   существующих фактов и просит вернуть `contradicted_facts: [индексы]` (строка 726).
3. **Только те рёбра, которые LLM пометила как противоречащие**, попадают в
   `resolve_edge_contradictions()` (строка 766) — а она уже чисто арифметическая:
   сравнивает `valid_at`/`invalid_at` и проставляет `invalid_at`/`expired_at`.

Проверено: в первом прогоне мой фейковый LLM возвращал `contradicted_facts: []` — и граф
спокойно оставил **все три** взаимоисключающих факта про хранилище BOSSMAN валидными,
`invalid_at=None` у всех. Никакой «автоматической инвалидации» без LLM не происходит.

README (строка 147, таблица против GraphRAG) утверждает «Contradiction Handling: **Automatic**
fact invalidation». Формулировка вводит в заблуждение: автоматизирована только *арифметика
дат*, а *суждение о противоречии* — это вызов модели со всеми свойственными ей ошибками.
Для нас это значит: качество темпоральности = качеству промпта на нашей локальной модели.

### 2.4 Поиск

`Graphiti.search()` по умолчанию использует `EDGE_HYBRID_SEARCH_RRF`
(`graphiti_core/graphiti.py:1570`): BM25 (полнотекстовый индекс БД) + косинус по
`fact_embedding`, слитые через Reciprocal Rank Fusion. **LLM в поиске не участвует** —
только 1 вызов эмбеддера на запрос. Поиск дёшев; дорога только запись.

Есть рецепты с `cross_encoder`, `mmr`, `node_distance`, `episode_mentions`
(`search_config_recipes.py`), но они не по умолчанию.

**Важно:** поиск по умолчанию **не отфильтровывает устаревшие факты**. В моём прогоне
`search()` вернул и SQLite-факт, и Postgres-факт — просто с проставленными датами.
Фильтрация возможна через `SearchFilters(valid_at=…, invalid_at=…, expired_at=…)`
(`search_filters.py`), но это ответственность вызывающего. То есть граф **размечает**
устаревшее, а решает — потребитель (наш агент или наш код).

### 2.5 Где хранит состояние

Собственного хранилища нет. Нужен графовый бэкенд (`graphiti_core/driver/`):

| Драйвер | Тип | Статус |

| **Kuzu** | встроенный | **DEPRECATED**, «upstream project is no longer maintained», кидает `DeprecationWarning` |
| **Neptune** | AWS | облако |

### 4.1 Что у нас уже фактически является «историей фактов»

Это ключевой вопрос задания. Смотрим `command-center/bcc/db.py` (единственный владелец схемы):

- `tool_calls` — **каждый** вызов инструмента: `step`, `tool`, `args`, `args_hash`,
  `effect` (auto/ask/deny), `status`, `approved_by`, `result_preview`. Это полный аудит действий.
- `interventions` — `target_kind`, `target_id`, `reason`, `action`
  (paused/stopped/switched/throttled/escalated), `detail`, `created_at`. Это **журнал решений**.
- `checkpoints` — `run_id`, `step`, `messages` — полный контекст рассуждения на каждом шаге.
- `kpi_history` — `key`, `value`, `delta`, `ts` — **уже темпоральный ряд**, append-only.
- `task_runs` — `attempt`, `status`, `result`, `error`, `tokens_in/out`, `cost_usd`.

Чего у нас **нет**: понятия «утверждение, которое было истинно с X по Y». Все наши таблицы
описывают **события** («в 14:03 вызван инструмент», «в 15:20 миссия остановлена»), а не
**состояния с интервалом валидности** («с января по июнь мы хранили состояние в SQLite»).

Это реальный, а не выдуманный пробел. Но он **уже, чем весь Graphiti**: нам не хватает
одного столбца-пары на одной новой таблице, а не графовой СУБД с LLM-пайплайном.

## 6. Что берём

**Берём идею, не код.**

1. **Пара осей времени на факте.** Не одна метка `created_at`, а четыре поля:
   когда стало правдой / перестало быть правдой / когда мы узнали / когда пометили устаревшим.
2. **Не удалять, а перекрывать.** Старая запись остаётся с проставленным `invalid_at`.
   История решений не переписывается задним числом.
3. **`invalid_at` старого = `valid_at` нового**, а не «сейчас». Это отличает настоящую
   темпоральность от журнала изменений.
4. **Явные временные фильтры в API поиска** — как у них в `search_memory_facts`.
   Наш `memory.search` может получить `as_of` / `include_superseded`.
5. **Отдавать модели факт вместе с его временными метками**, а не молча прятать
   устаревшее. Пусть модель видит «раньше было А, с июня — Б».

Всё это реализуемо у нас **одной таблицей** и правкой одного инструмента — см. раздел 11.

## 8. Цена — количественно

### 8.1 Вызовы LLM на один эпизод (измерено, не оценено)

Скрипты: `/tmp/research/graphiti-exp/run.py`, `run2.py`. Фейковый LLM-клиент считает вызовы,
фейковый эмбеддер, встроенная FalkorDB Lite, сеть не используется.

**Реальные факты, растущий граф (`run.py`):**

| Эпизод | Вызовов LLM | Вызовов эмбеддера | Какие промпты |
|---|---|---|---|
| 1-й (пустой граф) | **2** | 8 | `extract_nodes`, `extract_edges` |
| 2-й | **3** | 8 | + `dedupe_edges.resolve_edge` |
| 3-й | **4** | 8 | + `dedupe_nodes.nodes` |

**Масштабирование по числу связей (`run2.py`, part B, граф непустой):**

| Сущностей / рёбер в эпизоде | Вызовов LLM | Вызовов эмбеддера |
|---|---|---|
| 2 / 2 | **4** | 12 |
| 4 / 4 | **6** | 24 |
| 8 / 8 | **10** | 48 |
| 16 / 16 | **18** | 96 |

**Формула, подтверждённая замером:**

```
LLM-вызовов ≈ 2 + N_рёбер            (на непустом графе)
Эмбеддингов ≈ 6 × N_сущностей
```

`dedupe_edges.resolve_edge` вызывается **отдельно на каждое** извлечённое ребро
(`edge_operations.py:489-508`, `semaphore_gather` по списку). Это и есть линейный рост.

Сверх формулы добавляются, если включены соответствующие возможности:
`extract_nodes.extract_attributes` — **по вызову на каждую типизированную сущность**;
`extract_edges.extract_timestamps` — на каждое ребро без дат; `summarize` — пачками по 30.
С кастомными типами сущностей (а именно они нужны, чтобы моделировать «решение», «клиента»,
«соглашение по коду») счёт легко доходит до **3 + 2×N_сущностей + N_рёбер**.

### 8.2 Размер промптов (измерено)

Для эпизода в **одно предложение**, 2 сущности, 1 ребро:

| Промпт | символов | ≈ токенов |
|---|---|---|
| `extract_nodes.extract_text` | 3 630 | ~1 210 |
| `extract_edges.edge` | 5 346 | ~1 780 |
| `dedupe_edges.resolve_edge` | 2 255 | ~750 |
| **Итого на эпизод** | **~11 200** | **~3 700** |

То есть **нижняя граница — почти 4 000 входных токенов на одно предложение.** Промпты
сами по себе огромные (системная часть + JSON-схема Pydantic, которая дописывается в
конец сообщения в `llm_client/client.py:215`).

И это ещё не всё: в контекст извлечения кладутся **последние 10 эпизодов целиком**
(`RELEVANT_SCHEMA_LIMIT = 10`, `search_utils.py:64`, используется в `graphiti.py:1090`).
На реальных эпизодах BOSSMAN (лог прогона, diff, переписка) это легко **15–40k входных
токенов на эпизод**.

### 8.3 Что это значит для нас в день

Осторожная прикидка: BOSSMAN за активный день порождает порядка 200 событий, достойных
записи в память (завершённые прогоны, решения, вмешательства).

- 200 эпизодов × 4 вызова = **~800 вызовов LLM/день только на ведение графа**
- 200 × ~20k входных токенов = **~4 млн входных токенов/день**

На локальной модели это не деньги, а **время и занятая VRAM**. При 800 вызовах и даже
1,5 с на вызов — это ~20 минут чистой генерации в день, конкурирующей за ту же память,
что и рабочие задачи. На облачной модели это прямые деньги против `missions.cloud_budget_usd`.

Наша текущая память (`local_index.py`, BM25 на stdlib) стоит **ноль вызовов LLM**.
Это не «хуже» — это другой порядок цены.

### 8.4 RAM / диск / сервисы

| Вариант | RAM | Отдельный сервис | Проверено |
|---|---|---|---|
| **FalkorDB Lite** (встроенная) | **~24–31 МБ RSS** на пустом графе | нет | **да**, замер `ps -eo rss` |
| FalkorDB (Docker) | ~50–150 МБ + Docker | да | нет |
| Neo4j 5.26 (Docker) | **порядка 1–2 ГБ** (JVM heap + page cache) | да | **нет, оценка** |

Диск: venv **187 МБ**; `falkordb.so` один весит **53 МБ**, `redis-server` — 14 МБ.

FalkorDB — это Redis-модуль, то есть **граф целиком живёт в RAM**, с persistence в RDB.
Рост потребления линеен по числу рёбер и, главное, по эмбеддингам: при 1536-мерных
векторах OpenAI одно ребро — ~6 КБ только на `fact_embedding`. 100 000 фактов ≈ **600 МБ RAM**
только под векторы. На нашей машине со 128 ГБ unified memory это не катастрофа, но это
память, отобранная у моделей — ровно то, от чего README нашего каталога предостерегает.

Вердикт по железу: **встроенная FalkorDB Lite приемлема** (десятки МБ), Neo4j — нет.
Но требование Python 3.12+ для `falkordblite` надо сверить с нашим рантаймом.

### 8.5 Офлайн

Работает, с оговорками. LLM — через `OpenAIGenericClient` на любой OpenAI-совместимый
`/v1` (Ollama, llama.cpp), настраивается `OPENAI_API_URL` (`factories.py:326`, комментарий
прямо упоминает Ollama). Эмбеддер — `sentence-transformers` (extra). Реранкер по умолчанию
всё равно OpenAI и требует явной подмены (5.3).

Отдельный риск: все промпты требуют **structured output строго по JSON-схеме Pydantic**.
В конфиге есть `LLM_STRUCTURED_OUTPUT_MODE: json_schema|json_object` с комментарием, что
для OpenAI-совместимых провайдеров схема «не всегда надёжно соблюдается». На локальной
модели среднего размера это будет источник постоянных отказов ингеста.

## 9. Риски

1. **Цена ингеста** (8.1–8.3) — главный риск. Скрытый расход, который наш учёт не видит.
2. **Качество темпоральности = качеству локальной модели** (2.3). Если модель не распознала
   противоречие, устаревший факт останется валидным навсегда и будет выдаваться в поиске
   наравне с актуальным. Это **хуже**, чем отсутствие темпоральности: создаёт ложную уверенность.
3. **Structured output на локальной модели** (8.5) — молчаливые сбои извлечения.
4. **Четвёртое хранилище** в системе. Бэкап, миграции, консистентность с SQLite.
5. **483 открытых issue** при 30k звёзд. Проект живой (push сегодня), но нагруженный.
6. **Вендорская гравитация.** README прямо противопоставляет Graphiti (self-hosted, «build
   your own tools», «performance depends on your setup») и Zep Cloud («sub-200ms at scale»,
   SLA, дашборд). Open-source часть намеренно оставлена менее удобной. Развитие идёт
   в сторону, выгодную платному продукту.
7. **Kuzu уже объявлен deprecated** — прецедент: встроенные бэкенды у них не в приоритете.
   `falkordblite` может повторить судьбу.
8. **CLA.** В репозитории есть `Zep-CLA.md` — контрибуции требуют подписания CLA в пользу
   Zep Software. На использование не влияет, на возможность форкнуть с патчами — влияет
   организационно.
9. **Сопровождение.** 36 688 строк чужого кода в критическом пути памяти.

## 10. Приватность

### Что уходит наружу по умолчанию

**Телеметрия включена по умолчанию.** `graphiti_core/telemetry/telemetry.py`:

```python
POSTHOG_API_KEY = 'phc_UG6EcfDbuXz92neb3rMlQFDY0csxgMqRcIPWESqnSmo'
POSTHOG_HOST = 'https://us.i.posthog.com'
env_value = os.environ.get('GRAPHITI_TELEMETRY_ENABLED', 'true').lower()   # ← default 'true'
```

`posthog` — **обязательная** зависимость в `pyproject.toml`, не опциональная.

**Что именно отправляется.** Проверено: `capture_event` вызывается **ровно из одного места** —
`graphiti.py:266`, событие `graphiti_initialized`, при создании объекта `Graphiti`. Поля:
анонимный UUID (кэшируется в `~/.cache/graphiti/telemetry_anon_id`), версия graphiti,
`platform.machine()`, и **какие провайдеры выбраны**: `llm_provider`, `embedder_provider`,
`reranker_provider`, `database_provider`.

**Содержимое эпизодов, тексты фактов, имена сущностей наружу не уходят.** Это честно.
Отправляется факт запуска и конфигурация стека. Но событие отправляется при **каждом**
создании объекта, а не раз в установку.

**Как выключить:** `GRAPHITI_TELEMETRY_ENABLED=false`. Работает
(`is_telemetry_enabled()` проверяет переменную). Также автоматически отключается под pytest.

### Второй, более серьёзный канал

Дефолты всей библиотеки — OpenAI: LLM, эмбеддер и реранкер. При наивной настройке
**полное содержимое каждого эпизода** (то есть наши логи прогонов, решения, куски кода,
данные клиентов) уходит в `api.openai.com` на извлечение сущностей. Это не «телеметрия»,
это основной режим работы. Переключается на локальные модели, но требует осознанного
действия и обхода блокера 5.3.

**Вывод по приватности:** телеметрия — мелочь, отключается одной переменной и не содержит
контента. Настоящий риск — что дефолтный путь отправляет **всё** содержимое памяти в OpenAI.

## 11. План внедрения (того, что мы действительно берём)

Внедряем **не Graphiti, а его идею** — в нашу существующую схему. Один заход.

### Этап 1 — таблица `facts` в `bcc/db.py` (~60 строк)

Единственный владелец схемы — `bcc/db.py`, туда и добавляем:

```
facts:
  id, subject (str), predicate (str), object (str), statement (Text)
  valid_at (DateTime), invalid_at (DateTime|null)      # ось мира
  created_at (DateTime), expired_at (DateTime|null)    # ось знания
  superseded_by (FK → facts.id, null)                  # что заменило
  source_kind (str: run|intervention|human|note)
  source_run_id (FK → task_runs.id, null)
  source_note (str)                                    # путь в Obsidian
  confidence (Float), meta (JSON)
```

Индексы: `(subject, predicate)`, `(valid_at)`, `(invalid_at)`.

Ключевое правило: **UPDATE запрещён**. Замена факта = проставить старому
`invalid_at = valid_at нового`, `expired_at = now()`, `superseded_by = id нового`.

### Этап 2 — инструменты (~150 строк в `bcc/features/tools_memory.py`)

- `memory.fact_write(subject, predicate, object, statement, valid_at, supersedes?)` —
  записывает факт; при `supersedes` перекрывает старый по правилу выше. Права: `write`.
- `memory.fact_query(subject?, predicate?, as_of?, include_superseded=false)` —
  «что мы считаем правдой сейчас» / «что считали на дату». Права: `read`.
- Дополнить существующий `memory.search` полем `as_of` — чтобы поиск по заметкам мог
  быть отфильтрован по актуальности, если чанк связан с фактом.

Факты пишутся **людьми и агентом явно**, а не извлекаются LLM из всего подряд.
Ноль дополнительных вызовов модели. Это принципиальное отличие от Graphiti.

### Этап 3 — представление поверх существующих таблиц (~80 строк)

Задание спрашивает прямо: «может, нам нужен не граф, а представление?». Да.
`interventions` (action=switched, reason) и `checkpoints` уже содержат моменты смены
решений. Добавляем read-only функцию `decision_timeline(target_kind, target_id)`,
которая собирает из `interventions` + `facts` ленту «что решили и когда это перестало
действовать». Никакого нового хранилища.

### Этап 4 — отложено до реальной потребности

Dense-эмбеддинги для `facts.statement` — только после того, как в таблице накопится
хотя бы несколько сотен фактов и BM25 начнёт промахиваться. Не раньше.

**Оценка объёма:** ~300 строк нашего кода, одна миграция, ноль новых сервисов,
ноль новых зависимостей, ноль дополнительных вызовов LLM.
Для сравнения: путь B из раздела 5.2 — 600–900 строк наших + 36 688 чужих + графовая СУБД.

## 12. Критерии приёмки

Проверяемые утверждения для будущих тестов:

1. Запись факта Б, перекрывающего факт А, оставляет А в таблице с
   `A.invalid_at == B.valid_at`, `A.expired_at != null`, `A.superseded_by == B.id`.
   Строк в `facts` становится 2, не 1.
2. `memory.fact_query(subject='BOSSMAN', predicate='использует хранилище')` без `as_of`
   возвращает **только** Б.
3. Тот же запрос с `as_of='2026-03-01'` возвращает **только** А.
4. Тот же запрос с `include_superseded=true` возвращает оба, с датами.
5. Прямой `UPDATE` строки в `facts` не выполняется ни из одного места кода
   (проверяется grep-тестом по репозиторию, как у нас сделано для владельца схемы).
6. Запись факта не порождает ни одной записи в `tool_calls` с обращением к модели —
   то есть стоимость операции равна нулю токенов.
7. `decision_timeline()` для миссии с двумя `interventions` возвращает ленту из двух
   событий в хронологическом порядке.
8. Существующие тесты `memory.*` продолжают проходить без изменений.

Отдельно, если когда-нибудь вернёмся к Graphiti — критерий для пилота:
на 50 реальных эпизодах BOSSMAN с локальной моделью доля корректно распознанных
противоречий должна быть **> 80%**, иначе темпоральность создаёт ложную уверенность (риск 2).

## 13. Что не проверено

Честно, без прикрас:

1. **Реальная работа с настоящей LLM.** Все замеры сделаны с фейковым LLM-клиентом,
   который возвращал минимально валидные ответы. Реальное качество извлечения сущностей
   и — главное — распознавания противоречий на нашей локальной модели **не измерено**.
   Это самый большой пробел исследования.
2. **Потребление RAM у Neo4j** — цифра 1–2 ГБ взята из общих знаний о JVM-дефолтах,
   Docker не запускался. Проверить перед любым решением, если Neo4j вообще рассматривается.
3. **Рост RAM у FalkorDB на реальном объёме.** Замерены только ~24–31 МБ на пустом графе.
   Оценка 600 МБ на 100k фактов — арифметика по размеру вектора, не замер.
4. **MCP-сервер не запускался.** Совместимость с нашим `mcp_runtime.py` выведена из чтения
   кода (`run_stdio_async` есть, SDK тот же), но живого рукопожатия не было.
5. **`falkordblite` под нашим рантаймом.** У нас Python 3.11 в основном окружении;
   эксперимент шёл на отдельном venv с 3.12. Требование 3.12+ не сверено с нашим деплоем.
6. **Точность оценки токенов.** Символы делены на 3. Настоящий токенайзер не применялся;
   промпты английские, содержимое у нас будет русское — там соотношение хуже.
7. **Оценка «200 эпизодов в день»** (8.3) — моя прикидка, а не измерение нашей нагрузки.
   Порядок величины устойчив, точное число — нет.
8. **`add_episode_bulk`** — существует и может быть дешевле поштучного добавления,
   но не разобран.
9. **Communities и Sagas** — прочитаны поверхностно, стоимость их построения не измерена.
10. **Качество гибридного поиска Graphiti против нашего BM25** — не сравнивалось.

## 14. Вердикт

### **ВЗЯТЬ ИДЕЮ**

Библиотеку — **НЕ ВНЕДРЯТЬ** сейчас. Идею bi-temporal — **внедрить своими силами**
по плану раздела 11.

**Почему не библиотеку:**

- Цена измерена и она высокая: `2 + N_рёбер` вызовов LLM и минимум ~4k входных токенов
  на эпизод, при 10 предыдущих эпизодах в контексте — реалистично 15–40k. Наша текущая
  память стоит ноль вызовов.
- Главная заявленная ценность — «автоматическая инвалидация противоречий» — на деле
  **решение LLM**, а не свойство хранилища. На локальной модели это ненадёжно, а
  ненадёжная темпоральность хуже её отсутствия: она заявляет актуальность, которой нет.
- Требуется четвёртое хранилище в системе, у которой уже есть SQLite, Obsidian и
  собственный BM25-индекс.
- Дефолтный путь отправляет всё содержимое памяти в OpenAI.

**Почему идею — да:**

- Пробел реальный. Наши `tool_calls`, `interventions`, `checkpoints`, `kpi_history`
  фиксируют **события**, но ни одна таблица не хранит **утверждение с интервалом
  валидности**. Ответ на вопрос «что мы считали правильным способом деплоя в марте»
  сейчас требует чтения логов, а не запроса.
- Реализация идеи стоит ~300 строк, одну таблицу и ноль вызовов модели.

### Сценарии BOSSMAN, где «факт устарел и был заменён» действительно важно

Задание просило 3–5 конкретных. Вот те, где обычного поиска по заметкам не хватает:

1. **Соглашение по коду сменилось.** В марте: «в этом проекте состояние держим в SQLite».
   В июне: «переехали на Postgres». Обе заметки лежат в Obsidian, BM25 найдёт **обе** и
   выдаст модели без указания, какая живая. Агент напишет миграцию под SQLite. С парой
   `valid_at/invalid_at` мартовская заметка приходит помеченной «перекрыта 2026-06-01».
   *Это самый частый и самый дорогой класс ошибок.*

2. **Клиент передумал.** «Клиент X хочет отчёты по понедельникам» → «клиент X перешёл на
   ежедневные». Старое требование не ошибочно — оно было верно **до** даты. Удалять его
   нельзя (нужно понимать, почему в апреле отчёты были недельные), но и выдавать как
   текущее нельзя. Это ровно тот случай, для которого удаление не работает, а
   перекрытие работает.

3. **Решение по проекту отменено вмешательством.** У нас есть `interventions` с
   `action=switched` и `reason` — момент смены зафиксирован. Но само **содержание**
   решения («используем модель-роутер с шортлистом из 3») нигде не хранится как
   утверждение с интервалом. Восстановить «на чём мы работали в мае» можно только
   вычитыванием `checkpoints`. Таблица `facts` со ссылкой на `interventions.id` закрывает это.

4. **Статус задачи как утверждение, а не как поле.** `tasks.status` — единственное
   текущее значение, история переходов размазана по `task_runs.attempt` и `run_events`.
   Вопрос «сколько эта задача простояла в `waiting_approval` и почему её оттуда вывели»
   сейчас не имеет прямого ответа.

5. **Возможности моделей меняются.** `models.caps` и `models.bench` перезаписываются
   при проверке. Когда `model_router` в июле выбрал модель, а в августе она деградировала —
   мы не можем сказать, какие `caps` были верны на момент решения. Это ретроспективный
   разбор инцидентов, и без оси «когда мы это знали» он невозможен.

Сценарии 1 и 2 оправдывают этап 1–2 плана прямо сейчас. Сценарии 3–5 — приятный бонус
той же таблицы.

### Путь MCP против пути «библиотека» — что честнее для V3

**Дешевле — MCP:** ноль нашего кода, `mcp_runtime.py` уже умеет stdio, конфиг и всё.
**Честнее — ни один из них**, пока не решён вопрос учёта: `add_memory` — fire-and-forget,
и весь расход токенов на ведение графа станет невидимым для `task_runs.cost_usd` и
`missions.spent_usd`. Система, у которой в схеме есть `cloud_budget_usd`, не должна
заводить статью расхода, которую не измеряет.

Если однажды решим пилотировать — **только путь MCP** (изолированный процесс, легко
отключить, чужой код не в нашем адресном пространстве), **только на локальной модели**,
**только с `GRAPHITI_TELEMETRY_ENABLED=false`**, **только на встроенной FalkorDB Lite**,
и **только после** того, как критерий из раздела 12 (>80% распознанных противоречий на
50 реальных эпизодах) будет измерен.

### Преждевременно ли это для нашей стадии

Да. У нас пока нет ни dense-эмбеддингов, ни гибридного поиска, ни cross-encoder —
об этом прямо сказано в `docs/research/README.md`. Строить граф знаний с LLM-извлечением
поверх памяти, у которой ещё нет плотного вектора, — это надстройка четвёртого этажа
над вторым. Сначала таблица `facts` (300 строк, ноль сервисов). Через несколько месяцев
эксплуатации будет видно, упирается ли что-нибудь в отсутствие именно **графа**, а не
темпоральности. Пока — не упирается.
