# Владельческие сценарии: первые 20

Табло: **OWNER SCENARIOS**. Прогресс отчитывается строкой `OWNER SCENARIOS: X / 20`,
а не числом коммитов, веток, модульных тестов или документов.

> **Два табло, которые НИКОГДА не складываются.**
> **REGRESSION** — существующие инженерные наборы (Core, Command Center, Astra,
> Fable, PostgreSQL). Это не определение готовности.
> **OWNER SCENARIOS** — настоящие интегрированные рабочие цепочки владельца.
> Сложить их — значит объявить готовым то, что никто не проходил целиком.

## Где что лежит

| Путь | Что это |
| --- | --- |
| `tests/owner_scenarios/owner_scenarios.json` | ЕДИНЫЙ канонический реестр 20 сценариев |
| `tests/owner_scenarios/scn_*.py` | реализации, привязанные к id реестра |
| `tests/owner_scenarios/capabilities.py` | честные пробы способностей среды |
| `tests/owner_scenarios/spine_fixtures.py` | строители цепочек поверх модулей продукта |
| `tests/owner_scenarios/test_owner_scenarios.py` | прогон в корневом CI + контроль каркаса |
| `tools/scenario_runner.py` | каркас: прогон, уровни улик, JSON-отчёт |
| `tools/ci_ai_provider.py` | адаптер ИИ для CI вместо локальной модели владельца |

Название, цепочка, требуемые способности и шаг модели живут ТОЛЬКО в реестре.
Строка без кода и код без строки роняют загрузку: два источника правды
разъехались бы на первой же правке.

## Уровни улик

| Уровень | Что означает |
| --- | --- |
| `AI_BACKED_CI` | прошло в CI; где в цепочке есть шаг модели — он прошёл через CI-адаптер ИИ |
| `OWNER_HARDWARE_REQUIRED` | нужна физическая машина: браузер, GPU, камера, рабочий стол |
| `OWNER_REQUIRED` | нужен секрет или решение владельца |
| `FAIL` | цепочка исполнялась и не прошла |
| `INSUFFICIENT_EVIDENCE` | прогон не доказал ничего: способности нет, провайдер лёг |
| `NOT_RUN` | не запускалось |

`AI_BACKED_CI` — единственный зелёный уровень. Меток `OWNER_LOCAL_MODEL` и
`LOCAL_MODEL_CERTIFIED` в словаре нет и быть не может: прогон идёт через
CI-адаптер, локальной модели владельца в нём нет, и приписывать ей заслугу
нельзя.

## Глубина улики пишется ОТДЕЛЬНО у каждого сценария

«Импорт исходника → вызов функции → PASS» не равно «продукт владельца →
возможность → PASS». Поэтому кроме уровня каждый сценарий несёт глубину:

| Глубина | Что означает |
| --- | --- |
| `installed_product` | цепочка прошла через модули установленного продукта (`bossman.*`, `bcc.*`, `tools/media_roundtrip.py`) |
| `product_contracts` | цепочка прошла через контракты продукта этой ветки (`bossman_shared.*`), но не через CLI/сервис |
| `adapter_contract` | проверен только контракт CI-адаптера ИИ, продукт не задействован |

Ни один из 20 сценариев пока не доходит до глубины «поднятый сервис + HTTP + UI»:
эта цепочка живёт в `tools/installed_product_chain.py`, и связать её со сценариями
— следующий шаг, а не сделанный.

## Правила, встроенные в каркас

1. **Пара обязательна.** Без хотя бы одной положительной и одной отрицательной
   проверки уровень `INSUFFICIENT_EVIDENCE`, каким бы зелёным ни был код.
2. **Упавший сценарий — `FAIL`,** а не «не удалось проверить».
3. **Нет синтетического запасного пути.** Живой шаг модели зеленеет ТОЛЬКО от
   настоящего успешного вызова адаптера, посчитанного каркасом по журналу
   вызовов; сам сценарий приписать себе `AI_BACKED_CI` не может.
4. **Недостающая способность не заменяется заглушкой.** Сценарий не исполняется
   вовсе и получает честный вердикт с названным блокером.
5. **Чистота ветки измеряется.** Модуль, приехавший из другого рабочего
   каталога через editable-установку, считается ОТСУТСТВИЕМ способности: иначе
   табло зеленело бы на коде, которого на этой ветке нет.

## Адаптер ИИ для CI

`tools/ci_ai_provider.py` говорит тем же проводом, что и продукт:
`POST {base}/chat/completions` с телом `{"model", "messages", "tools", "max_tokens"}`
— ровно как `bossman.gateway.backends.OpenRouterBackend` и
`bcc.v2.openrouter_ext.OpenRouterClient.chat_raw`; `AIResult.as_core_message()`
отдаёт ту же форму, что возвращает `bossman.llm.chat`.

* Ключ — ТОЛЬКО из `os.environ` (`BOSSMAN_CI_AI_API_KEY`,
  `BOSSMAN_OPENROUTER_API_KEY`, `OPENROUTER_API_KEY`). Наружу выходит лишь
  булево `key_present` и ИМЯ переменной.
* **Четыре разных исхода, которые никогда не сливаются:** `NO_KEY`,
  `RATE_LIMITED`, `MODEL_UNAVAILABLE`, `INVALID_RESPONSE`.
* Потолок расходов объявлен константами: `MAX_CALLS_PER_RUN = 8`,
  `MAX_REQUEST_BYTES = 16384`. Превышение — отдельный исход `BUDGET_EXCEEDED`.
* Без ключа адаптер НЕ ходит в сеть и НЕ придумывает ответ.

## Два прогона, два числа

Числа различаются потому, что различаются среды, и оба честные.

| Среда | Команда | Итог |
| --- | --- | --- |
| Постная (как корневой CI: без sqlalchemy/pydantic/asyncpg) | `PYTHONPATH=<lean> python tools/scenario_runner.py` | `OWNER SCENARIOS: 5 / 20` |
| Полная (этот контейнер: продукт, ffmpeg; без ключа ИИ, браузера, PostgreSQL) | `python tools/scenario_runner.py` | `OWNER SCENARIOS: 12 / 20` |

В корневом CI набор `tests/` требует только `pytest pytest-timeout psutil httpx
pyyaml`; сценарии, которым нужен весь продукт, там честно не исполняются и
получают `INSUFFICIENT_EVIDENCE` с названным блокером.

## Что НЕ зелено и почему

### Нужны секреты владельца
* **1, 2, 10, 11** — живой шаг модели: нет ключа ИИ → `OWNER_REQUIRED`.
* **9** — нужен настоящий браузер (бинарь playwright не скачан) →
  `OWNER_HARDWARE_REQUIRED`.

### Пробелы ПРОДУКТА, найденные прогоном
* **15 (Telegram).** `bcc/telegram_companion/adapters.py` своим же контрактом
  объявляет: «No shell, desktop, arbitrary file-read, or **approval API**».
  Компаньоном круг одобрения не замкнуть. Круг, который умеет одобрения
  (`bossman.telegram` → `bossman.approvals` → `notifications.telegram_transport`),
  требует живого PostgreSQL и настроенного бота владельца.
* **16 (студия изображений).** Сохранение и измерение типа ПО БАЙТАМ доказаны на
  настоящем PNG через `tools/media_roundtrip.py`, но сама генерация в продукте —
  детерминированный мок (`provider_gap.generation_is_real = false`). Половина
  цепочки владельца закрыта, и выдавать её за зелёную нельзя.
* **18 (убийство посреди задачи).** Задача, убитая БЕЗ работы в полёте,
  возобновляется. Задача, убитая С работой в полёте, — НЕ возобновляется сама:
  `AdmissionKernel.admit` не записывает `effect_class` в полезную нагрузку
  брони, а `objective_recovery._effect_class` трактует отсутствующий класс как
  `IRREVERSIBLE`. Поэтому паркуется ЛЮБАЯ бронь — даже идемпотентная запись
  файла, — и следующий допуск отбивается `admission_state_changed`, пока
  владелец не разберёт парковку.

## Побочные находки прогона (вне зоны правки)

* `objective_reconcile.reconcile_after_mission` принимает `now`, но вниз, в
  `ObjectiveStore.set_condition`, его НЕ передаёт: свежесть улики там меряется
  `time.time()`. Вызывающий с модельными часами получает `stale` без причины.
* `tests/test_dependency_pinning.py::test_there_is_something_to_check` красный и
  без этих изменений: сканер не находит ни одного requirements-файла, хотя в
  ветке их несколько.

## Как запускать

```bash
# всё табло, JSON-отчёт рядом
python tools/scenario_runner.py --json owner_scenarios_report.json

# один сценарий
python tools/scenario_runner.py --only OS-18

# как это увидит корневой CI
python -m pytest tests/owner_scenarios -q -p no:asyncio -p no:randomly
```

Коды возврата: `0` — нет `FAIL` и нет «не доказано»; `1` — есть `FAIL`;
`2` — есть `INSUFFICIENT_EVIDENCE`/`NOT_RUN`. Флаг `--strict` делает ненулевым
всё, что не `AI_BACKED_CI`.
