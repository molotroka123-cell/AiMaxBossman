# Tailscale v1 — политика внешней поверхности

## Принцип

Наружу (через Tailscale) публикуется ТОЛЬКО клиентская поверхность:

```
/remote/*        — мобильный/удалённый API (Stage 6/12, свои скоупы)
/remote/app/*    — PWA-оболочка
```

Сырую поверхность ядра (`/tasks`, `/approvals`, `/sandbox/*`, `/api/lab/*`, …)
наружу НЕ публикуем. Это defense in depth: даже при ошибке в auth внешний
периметр меньше.

Это не замена аутентификации. Каждый маршрут ядра уже под Stage 6 scopes
(см. `docs/context/CORE_AUTH_MATRIX.md`); сетевое положение аутентификацией не
является (за `tailscale serve` запрос приходит с loopback). Слои складываются:
**приватная сеть + токен устройства + скоуп**.

## Команда (владельцу)

Публиковать префикс `/remote`, а не весь порт ядра:

```bash
# ТОЛЬКО клиентская поверхность:
sudo tailscale serve --bg --https=9443 --set-path=/remote http://127.0.0.1:8700/remote

# НЕ так (публикует всё ядро наружу):
# sudo tailscale serve --bg --https=9443 http://127.0.0.1:8700
```

`--set-path=/remote` монтирует внешний путь `https://<tailnet>:9443/remote` на
внутренний `/remote`; всё, что вне этого префикса, снаружи недоступно.

## Funnel (публичный интернет)

`tailscale funnel` (выход в публичный интернет) для ядра НЕ включать. Если
когда-нибудь понадобится — только для `/remote/app` статики и только после
отдельного аудита. По умолчанию — tailnet-only.

## Проверка

```bash
tailscale serve status          # должен показывать только путь /remote
curl -sk https://<tailnet>:9443/tasks      # ожидаем отсутствие маршрута снаружи
curl -sk https://<tailnet>:9443/remote/... # ожидаем 401 без токена устройства
```
