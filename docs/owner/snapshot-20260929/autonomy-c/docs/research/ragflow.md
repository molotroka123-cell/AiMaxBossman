## 2. Что делает на самом деле

**Развёртывание по умолчанию — ровно 5 контейнеров.** Проверено не на глаз, а
командой `docker compose -f docker-compose.yml config --services`:

```
es01  minio  mysql  ragflow-cpu  redis
```

`COMPOSE_PROFILES=${DOC_ENGINE},${DEVICE},metadata-${METADATA_DB_PROFILE}` =
`elasticsearch,cpu,metadata-mysql`; `minio` и `redis` профилей не имеют и
поднимаются всегда. Смена `DOC_ENGINE=infinity` меняет `es01` на `infinity` —
число сервисов остаётся 5.

Роли: **MySQL 8.0.40** — метаданные (пользователи, датасеты, документы, чаты),
**Elasticsearch 8.11.3** (или Infinity / OpenSearch / OceanBase / SereneDB /
SeekDB / GaussDB — 7 взаимозаменяемых движков) — чанки и векторы,
**MinIO** (форк `pgsty/silo`) — исходные файлы, **Valkey/Redis** — очередь
задач парсинга, **ragflow-cpu** — nginx + API-сервер + admin-сервер +
task_executor + Go-бинари в одном контейнере.

Ключевые модули:
* `deepdoc/vision/` — 4 ONNX-модели: layout (архитектура **YOLOv10**), OCR
  detection + recognition (наследие PaddleOCR), TSR (структура таблиц).
  3 256 строк чистого numpy/opencv/onnxruntime.
* `deepdoc/parser/pdf_parser.py` — 2 145 строк сборки примитивов в текст:
  порядок колонок через `KMeans` + `silhouette_score`, склейка соседних боксов
  через **xgboost-модель** `updown_concat_xgb`, слияние таблиц через страницы.
* `rag/app/naive.py` — чанкер и **диспетчер из 9 PDF-бэкендов**: `deepdoc`,
  `mineru`, `docling`, `opendataloader`, `paddleocr`, `somark`,
  `mistral ocr`, `tcadp parser`, `plaintext`.
* `rag/nlp/search.py` — гибридный поиск: `weighted_sum` с весом вектора **0.3**
  против полнотекста **0.7**, затем реранк с `tkweight=0.3 / vtweight=0.7`.
* `mcp/server/server.py` — их собственный MCP-сервер, ровно 3 инструмента:
  `ragflow_retrieval`, `ragflow_list_datasets`, `ragflow_list_chats`.
* `agent/`, `web/` (67 МБ фронтенда) — свой конструктор агентов и свой UI.

Состояние: MySQL (метаданные) + ES/Infinity (векторы и чанки) + MinIO (файлы) +
Redis (очередь). Четыре независимых хранилища, каждое надо бэкапить и обновлять.

## 3. Проверка утверждений консультации

| Утверждение | Вердикт | Факт |
|---|---|---|
| «Пока не внедрял бы» | **подтвердилось, но по другой причине** | Дело не в «пока» и не в незрелости — проект зрелый и очень активный. Дело в том, что RAGFlow **дублирует наш control plane целиком**, а его уникальная часть отделяется без него (§5) |
| Тяжёлое развёртывание | **подтвердилось** | 5 всегда работающих сервисов, 4 хранилища, ~9–11 ГБ образов, 183 зависимости, требование 16 ГБ RAM в README |
| Сильная сторона — разбор документов | **подтвердилось и это единственное, что нам нужно** | DeepDoc — цельный layout + OCR + TSR пайплайн, работающий **на CPU без torch** |
| Лицензия свободная | **подтвердилось** | чистый Apache-2.0 без исключений. Оговорка про веса моделей — §9 |

**Где я не согласен с формулировкой.** «Пока не внедрять» подразумевает «потом
может быть всю». Мой вывод сильнее и уже: платформу — **никогда**, а вернуться
стоит **только за DeepDoc-сервисом**, и это не «внедрение RAGFlow», а установка
одного отдельного контейнера, который команда RAGFlow сама уже упаковала
отдельно (`Dockerfile_deepdoc_oss`).

## 4. Сопоставление с нашим кодом

| Функция RAGFlow | Что у нас | Вывод |
|---|---|---|
| Хранилище знаний (MySQL + ES + MinIO) | `ObsidianVault` — markdown-файлы, `bcc/db.py` — SQLite | **дублируется**. Наш источник истины — vault пользователя, а не чужая БД |
| Индекс и BM25 | `LocalMemoryBackend` — свой Okapi BM25 на stdlib, инкрементальность по sha256, `expand` по секции | **дублируется**. Их BM25 живёт внутри ES — забрать нельзя, только вместе с ES |
| Чанкинг | `local_index.py::split_sections` + `_split_long` (по заголовкам, потом по абзацам) | **частично дублируется**; у них есть 2 приёма лучше наших (§5) |
| Реранк | `LexicalReranker` (эвристика), `LocalCrossEncoderReranker` (мёртв — нет `sentence-transformers`) | **дублируется**; полезна их схема весов (§5) |
| Бюджет контекста | `context_pack.py::build_context_pack` | у них аналога с явным бюджетом нет — **наше решение лучше** |
| Инструменты агента | `bcc/tools.py`, `REGISTRY`, права AUTO/ASK/DENY, approvals, anti-replay | **прямой конфликт**: у RAGFlow свой агент, свой tool-registry, свой UI-конструктор. Двух control plane быть не может |
| MCP | `bcc/v2/mcp_runtime.py`, официальный SDK, stdio | **не конфликтует** — их MCP-сервер можно подключить как обычный сервер, если он вообще появится |
| **Разбор PDF, таблиц, сканов, OCR** | **нет вообще ничего** | **единственная область, где RAGFlow добавляет то, чего у нас нет** |

Ключевой факт: наша память — это markdown из Obsidian. У markdown **нет
вёрстки**. Весь смысл существования RAGFlow — восстановить структуру там, где
её потеряли (PDF, скан, вёрстка в две колонки). На нашем корпусе 100 % этой
машинерии простаивает.

## 5. Что берём

### 5.1. Сейчас и дёшево (без RAGFlow, только приёмы из их кода)

| # | Приём | Куда | Объём |
|---|---|---|---|
| 1 | **Никогда не резать атом.** `rag/nlp/__init__.py::_merge_paragraph_groups`: абзац больше лимита становится своим чанком, а не режется пополам. У нас `_split_long` жёстко пилит по `MAX_CHUNK_CHARS*2` — это ломает code-fence и markdown-таблицу посередине | `bcc/v2/memory/local_index.py::_split_long` | ~30 строк |
| 2 | **Границы, которые нельзя пересекать.** `split_sections` уже отслеживает ```` ``` ````, а `_split_long` — нет. Добавить тот же учёт fence и markdown-таблиц в разрезание | `local_index.py::_split_long` | ~20 строк |
| 3 | **Явные веса вместо магических чисел.** У них `tkweight=0.3 / vtweight=0.7` — параметры, а не константы в формуле. Наш `LexicalReranker` зашивает `coverage*2.0 + head_hit*1.5 + score*0.05`. Вынести в поля dataclass — и когда появится dense-путь, смешивание уже будет готово | `bcc/v2/memory/reranker.py` | ~20 строк |
| 4 | **Пост-атрибуция цитат.** `rag/nlp/search.py::insert_citations`: ответ режется на предложения, каждое сопоставляется с чанками, порог адаптивно опускается 0.63 → 0.3, пока не найдётся хотя бы одна привязка. Нам это доступно **на одном BM25**, без эмбеддингов | новая функция в `bcc/v2/memory/context_pack.py` | ~60 строк |
| 5 | **Контекст вокруг таблицы.** `rag/nlp/__init__.py::attach_media_context`: чанк-таблица дополняется ближайшим предшествующим прозаическим предложением, иначе таблица из одних чисел не находится ничем. У нас markdown-таблица внутри секции ищется только по своим цифрам | `local_index.py::chunk_markdown` | ~40 строк |
| 6 | **Реестр парсеров вместо одного хардкода.** `rag/app/naive.py::PARSERS` + `_dispatch_pdf_parser` — словарь имён → callable. Когда мы добавим первый не-markdown источник, сразу делать реестр, а не `if suffix == ".pdf"` | будущий `bcc/v2/memory/parsers.py` | архитектурное решение |

Всё вместе — примерно 170 строк в наших файлах, без единой новой зависимости и
без Docker. Это и есть реальный полезный исход исследования.

### 5.2. Позже и по триггеру — только DeepDoc

Команда RAGFlow **сама** выделила DeepDoc в автономный сервис
(`Dockerfile_deepdoc_oss` + `deepdoc/server/`), и это меняет расклад:

* зависимостей — **7** (`litserve`, `onnxruntime`, `opencv-python-headless`,
  `numpy`, `pillow`, `pyclipper`, `shapely`, `six`). **torch не нужен**;
* моделей — 4 ONNX + `ocr.res`, из HF-репозитория `InfiniFlow/deepdoc`;
* «отвязка» от платформы уже написана ими: `deepdoc/server/docker_stubs.py`,
  174 строки, подменяет `common.settings`, `common.file_utils`,
  `rag.nlp.rag_tokenizer`, `rag.utils.lazy_image` заглушками;
* запускается одним `docker run`, порт 9390, три эндпойнта:
  `/predict/dla`, `/predict/ocr`, `/predict/tsr`, плюс `/health`;
* `docker compose --profile deepdoc` тянет только `minio, redis, deepdoc` —
  без ES и MySQL; а вне compose — вообще один контейнер.

**Честная оговорка:** этот сервис отдаёт только **примитивы** — рамки блоков,
рамки и текст строк, ячейки таблицы. Превращение примитивов в читаемый markdown
живёт в `deepdoc/parser/pdf_parser.py` (2 145 строк, тянет `pdfplumber`,
`pypdf`, `xgboost`, `scikit-learn`). Либо вендорить его (Apache-2.0 разрешает),
либо писать сборку самим. Это не «поставил и работает».

## 6. Что НЕ берём и почему

1. **Платформу целиком** — 5 сервисов, 4 хранилища, 183 зависимости, свой UI на
   67 МБ. Мы получили бы вторую систему рядом со своей.
2. **Их control plane** (`agent/`, `web/`, свой tool-registry, свой чат) —
   прямой конфликт с `bcc/tools.py`, `bcc/engine.py`, правами AUTO/ASK/DENY и
   approvals. У нас это уже DONE и проверено тестами.
3. **Elasticsearch / Infinity** — наш корпус это markdown-заметки одного
   человека. Для такого объёма поисковый кластер — не решение, а накладной
   расход. Наш BM25 на stdlib честно закрывает задачу.
4. **MySQL + MinIO** — `bcc/db.py` уже единственный владелец схемы; вводить
   второй метаданный движок и объектное хранилище ради заметок бессмысленно.
5. **Их MCP-сервер** — 3 инструмента, каждый требует RAGFlow позади. Ставить
   всю платформу ради `ragflow_retrieval` — тот же вопрос с другой стороны.
6. **Их гибридный поиск** — работает внутри ES-запроса (`FusionExpr`,
   `weighted_sum`). Без ES его не существует. Забираем схему весов, не код.
7. **Их резюме-парсер, финансовые и мессенджерные интеграции** — не наша задача.

## 7. Точки интеграции

Для §5.1 — только наши файлы, новых контрактов не нужно:

* `bcc/v2/memory/local_index.py`: `_split_long()`, `chunk_markdown()`,
  константы `MAX_CHUNK_CHARS`, `CHUNK_OVERLAP_CHARS`.
* `bcc/v2/memory/reranker.py`: `LexicalReranker.rerank()` — веса в поля
  dataclass.
* `bcc/v2/memory/context_pack.py`: новая `attribute_citations(answer, items)`,
  использует `local_index.tokenize` — общий стеммер уже есть.
* `INDEX_VERSION` в `local_index.py` поднять с `3` на `4`: чанкинг меняется,
  старый индекс должен пересобраться (механизм уже реализован — `load()`
  выбрасывает индекс при несовпадении версии).
* Новых таблиц в `bcc/db.py` **не требуется**.

Для §5.2 (по триггеру) — новый бэкенд под уже существующий протокол:

* `MemoryBackend` (`bcc/v2/memory/service.py`) остаётся без изменений: новый
  парсер отдаёт те же `MemoryHit`. Ничего в контракте ломать не надо.
* Новый `bcc/v2/memory/pdf_ingest.py` + `ToolSpec` `memory.ingest_pdf`
  (`source="memory"`, `category="write"`, `permission="filesystem.write"`,
  `default_effect="ask"` — как `memory.write`).
* Адрес DeepDoc-сервиса — в `settings_kv` под тем же шифрованием
  (`svc.vault.encrypt`), как `memory.vault` и `terminal.roots`. Никакого
  автопоиска.
* Результат парсинга — **внешние данные**: `external_output=True`
  обязателен, как у `memory.search`.

**Только DeepDoc-сервис:** 1 контейнер, ubuntu:24.04 + venv с 7 пакетами + 4

разбор PDF вызывает `snapshot_download` из HuggingFace — в
`deepdoc/vision/ocr.py`, `recognizer.py` и `pdf_parser.py` (репозитории
`InfiniFlow/deepdoc` и `InfiniFlow/text_concat_xgb_v1.0`). Модели надо
скачивать заранее.

Контекст: на целевой машине 128 ГБ, 6–8 ГБ — это ~5 %. **Аргумент против —
не RAM.** Аргумент против — 5 всегда работающих сервисов, 4 хранилища для
бэкапа и обновления, и вторая система управления рядом с нашей.

## 9. Риски

1. **Архитектурный конфликт — главный.** RAGFlow спроектирован быть *системой*:
   свои пользователи, свой чат, свои датасеты, свой конструктор агентов, свой
   реестр инструментов, свой MCP-сервер. У нас всё это есть и закрыто тестами.
   Двух control plane не бывает — либо наш становится клиентом чужого, либо мы
   держим их синхронными вручную. Оба варианта хуже, чем не внедрять.
2. **Лицензия весов.** Код — Apache-2.0, тут чисто. Но модель разметки —
   `LayoutRecognizer4YOLOv10` (`deepdoc/vision/layout_recognizer.py:189`),
   архитектура **YOLOv10**, чей upstream — AGPL-3.0. Лицензию HF-репозитория
   `InfiniFlow/deepdoc` проверить не удалось (домен закрыт). Для приватного
   сервера без распространения — практического значения нет. **Если BOSSMAN
   когда-нибудь начнёт что-то отдавать наружу — проверить заново.**
3. **Объём сопровождения.** 183 зависимости включают `browser-use`,
   `crawl4ai`, `selenium-wire`, 7 spacy-моделей, десяток SDK мессенджеров. Это
   поверхность CVE, которую придётся обновлять ради поиска по markdown.
4. **Темп изменений.** 200 коммитов за 30 дней и ночные теги — плюс для
   продукта, минус для того, кто вендорит их модули: `pdf_parser.py` при
   форке начнёт расходиться сразу.
5. **Только x86-64.** README прямо предупреждает, что ARM-образов нет.
   Для целевой машины (Ryzen) не проблема, но сужает варианты.
6. **`sandbox-executor-manager`** (профиль `sandbox`) требует
   `privileged: true` и монтирует `/var/run/docker.sock`. Профиль не
   включён по умолчанию, но существует. Ни при каких условиях не включать.

## 10. Приватность

По умолчанию **наружу ничего не уходит** — и это проверено, а не принято на
веру:

* `otel.enable: false` в `docker/service_conf.yaml.template`;
* грепом по `.py/.ts/.tsx/.yaml/.json` не найдено ни posthog, ни sentry, ни
  mixpanel, ни analytics-эндпойнтов на серверной стороне; ни одного
  «phone home»;
* все пароли в `.env` — дефолтные (`infini_rag_flow`), сервисы биндятся на
  хост-порты. Для приватного сервера это надо закрывать руками.

Что **уходит**, если пользоваться:
1. **HuggingFace** при первом разборе PDF — `snapshot_download` за ONNX и
   xgboost-моделью. Отключается предзагрузкой моделей в том.
2. **Провайдер LLM/embedding.** По умолчанию модели не настроены; пользователь
   обязан ввести ключ. Если это внешний API — **весь текст документов и все
   запросы уходят туда**. Локальный путь есть (TEI-профиль,
   `TEI_MODEL=Qwen/Qwen3-Embedding-0.6B`, Ollama в списке провайдеров), но он
   не по умолчанию и включается явно.
3. **Облачные парсеры** `mistral ocr` и `tcadp parser` (Tencent Cloud LKEAP)
   отправляют документ целиком стороннему сервису. Не выбраны по умолчанию —
   `layout_recognize` по умолчанию `DeepDOC`, то есть локальный.

Вывод: RAGFlow **можно** держать полностью офлайн, но это не дефолт, а
результат нескольких осознанных действий.

## 12. Критерии приёмки

**Этап 0:**
* абзац длиннее `MAX_CHUNK_CHARS` не разрезается посередине code-fence или
  строки markdown-таблицы — тест на файле с блоком кода в 3 000 символов;
* чанк, состоящий из markdown-таблицы, находится по запросу словами из
  предшествующего абзаца;
* `attribute_citations` для ответа из 3 предложений возвращает `source` хотя бы
  для одного, и не возвращает ни одного при заведомо чужом ответе;
* веса `LexicalReranker` меняются полем dataclass, поведение по умолчанию
  не изменилось (существующие 16 тестов памяти зелёные);
* `INDEX_VERSION=4` заставляет пересобрать индекс, старый JSON не читается.

**Этап 1 (если наступит):**
* DeepDoc-контейнер в простое < 2 ГБ RSS — **измерить `docker stats`, а не
  оценить**;
* на 10 наших реальных PDF таблицы извлекаются с полнотой ≥ 80 % ячеек при
  ручной сверке; иначе этап 1 останавливается на шаге 1;
* весь путь работает при выключенной сети (модели предзагружены) —
  проверяется отключением egress у контейнера;
* `memory.ingest_pdf` требует approval, помечен `external_output=True`,
  пишет только внутрь `BOSSMAN Memory/`.

### Ориентир по разбору PDF (короткое сравнение)

Из `PARSERS` видно, что RAGFlow сам считает конкурентами. Свойства ниже —
внешнее знание, в этой сессии **не проверено** (см. п. 5 выше):

| Вариант | Локально | Таблицы | Сканы/OCR | Цена входа |
|---|---|---|---|---|
| `pypdf` / `pdfplumber` | да | только текстовый слой | нет | ~0, 1–2 зависимости. **Начинать надо отсюда** |
| **DeepDoc (RAGFlow)** | да | да (TSR) | да (свой OCR) | 1 контейнер, 7 зависимостей, **без torch**; сборку в markdown пишем сами |
| Docling (IBM) | да | да | да | pip-библиотека, интегрируется проще всего, но тянет torch |
| MinerU | да | да | да | тяжёлый, желателен GPU; в RAGFlow подключён по HTTP как внешний сервис |
| PaddleOCR / PP-Structure | да | да | да | зависимость `paddlepaddle` — тяжёлая и капризная |
| Mistral OCR / Tencent TCADP / облачные | **нет** | да | да | дёшево по деньгам, но **документ уходит наружу** — против нашей приватности |

Место RAGFlow здесь: **единственный вариант, дающий layout + OCR + таблицы
одним CPU-сервисом без torch**. Это его настоящее преимущество для нас — не
качество как таковое, а вес.

### Условие возврата (единственное)

Вернуться к DeepDoc **только когда одновременно выполнены оба условия**:

1. Появился устойчивый поток PDF в память: **≥ 20 документов или ≥ 200 страниц
   в месяц** на протяжении **двух месяцев подряд** — не разовый импорт архива.
2. Дешёвый путь доказанно не справился: `pdfplumber`/`pypdf` по текстовому
   слою дают негодный результат **на ≥ 30 % этих документов** (сканы, две
   колонки, таблицы, слитые в кашу) — и это зафиксировано на конкретных файлах,
   а не предположено.

**Дополнительный самостоятельный триггер:** появилась задача, где ответ должен
цитировать **ячейку таблицы**, а не абзац. Наш markdown-BM25 этого не умеет
принципиально, и обойти это чанкингом нельзя.

Пока ни одно условие не выполнено, правильный ответ на «а не поставить ли
RAGFlow» — `pip install pdfplumber` и один вечер работы.

### Что мы потеряем, если не внедрим никогда

Честно и без смягчения:
* **Разбор PDF со сложной вёрсткой, сканов и таблиц.** Память останется
  markdown-only. Это реальная потеря, а не воображаемая.
* **OCR.** Изображение с текстом для нас навсегда останется непрозрачным.
* Готовую абстракцию из 9 парсеров — но её мы всё равно не могли бы
  использовать без платформы.
* Гибридный dense+BM25-поиск и cross-encoder-реранк из коробки — но это наш
  собственный PARTIAL из `V2_1_FINAL_SCORECARD.md` (п. 5), и закрывать его
  надо `memsearch`/`lancedb`, а не платформой на 5 сервисов.

Всё остальное, что даёт RAGFlow, у нас уже есть — и в нашей архитектуре,
с нашими approvals и нашими правами.
