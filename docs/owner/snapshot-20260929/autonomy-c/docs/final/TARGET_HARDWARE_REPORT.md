# Отчёт по целевому железу

## Вердикт

```
TARGET_HARDWARE_VERDICT=SOFTWARE_READY_FOR_TARGET_HARDWARE_RUN
```

Прогон на машине владельца НЕ выполнялся. Раздел 29 задания разрешает сказать
`TARGET_HARDWARE_READY` только тогда, когда тесты действительно шли на машине
целевого класса; сказать это по прогону в сборочном контейнере было бы враньём,
которое невозможно обнаружить по отчёту.

## Целевая машина и машина прогона

| | Цель владельца | Где выполнен этот прогон |
|---|---|---|
| CPU | AMD Ryzen AI Max+ 395 (Strix Halo) | Intel(R) Xeon(R) Processor @ 2.10GHz |
| GPU | Radeon 8060S (iGPU, общая память) | не опознан |
| Память | 128 ГБ единой | 15.7 ГиБ |
| ОС | Windows 11 | Linux-контейнер |

Замер сделан самим инструментом, не переписан руками:
`python scripts/target_hardware_acceptance.py`.

## Инструмент

`scripts/target_hardware_acceptance.py` опознаёт КЛАСС машины (несколько
торговых имён Strix Halo, `gfx115x` для iGPU, порог памяти с запасом вниз —
часть памяти удерживает прошивка) и выдаёт один из трёх вердиктов:

| Условие | Вердикт |
|---|---|
| железо целевое и все проверки прошли | `TARGET_HARDWARE_READY` |
| железо целевое, хоть одна проверка не прошла или отсутствует | `TARGET_HARDWARE_FAILED` |
| железо не целевое | `SOFTWARE_READY_FOR_TARGET_HARDWARE_RUN` |

Флага «считать железо целевым» нет намеренно — вердикт поднимает только само
железо. Отсутствующий скрипт проверки считается НЕПРОЙДЕННОЙ проверкой, иначе
удаление файла делало бы приёмку зелёной.

Заперто тестами `tests/test_target_hardware_acceptance.py` (8 тестов), включая
контроль над самим детектором: на сборочной машине он обязан отвечать «не
целевая».

## Что владельцу прогнать на своей машине

```
python scripts/target_hardware_acceptance.py --json artifacts/target-hardware.json
```

Скрипт сам последовательно выполнит:

| Проверка | Что доказывает |
|---|---|
| `scripts/verify_clean_install.py` | продукт ставится с нуля и владельческие сценарии отвечают по HTTP |
| `scripts/bossman_doctor.py` | подсистемы готовы на реальном железе |
| `scripts/evening_acceptance.py` | вечерний владельческий прогон проходит |

## Что именно может повести себя иначе на целевом железе

Перечислено не для отговорки, а чтобы прогон смотрел в правильные места:

* **единая память 128 ГБ.** Допуск ресурсов рассчитан на раздельные CPU/GPU
  пулы. На Strix Halo память общая: занятое моделью вычитается из того, что
  видит остальная система. Проверять надо не «влезла ли модель», а остаётся ли
  рабочим продукт при загруженной модели.
* **iGPU вместо дискретной карты.** Раздел 16 задания запрещает постоянное
  резервирование GPU. На общей памяти цена такого резервирования выше: оно
  съедает системную память, а не только видеопамять.
* **Windows вместо Linux.** Проверены пути, консольные обёртки и кодировка
  вывода (cp1252 ломала реле на сборке архива), но живого запуска на Windows в
  этом прогоне не было.
* **задержки хранилища.** Гейт человеческой скорости на общем раннере ловил
  чужие срывы fsync (см. BL-002). На машине владельца распределение будет
  другим — и именно оно является настоящим ответом на вопрос о скорости.

## Раздел 26: одна большая модель против команды маленьких

Задание прямо запрещает зашивать ответ: «Do not hard-code the philosophical
answer. Measure it on the actual machine.» Поэтому здесь нет рекомендации —
здесь инструмент, которым владелец получит ответ сам.

```
# по одному прогону на конфигурацию — измеряет настоящая обвязка
python tools/intelligence_preservation_run.py --model <БОЛЬШАЯ> ... \
    --out artifacts/one-large-model.json
python tools/intelligence_preservation_run.py --model <КОМАНДА> ... \
    --out artifacts/small-model-team.json

# сравнение
python tools/local_model_strategy_compare.py \
    A=artifacts/one-large-model.json \
    B=artifacts/small-model-team.json \
    --out artifacts/strategy-comparison.json
```

Инструмент сам ничего не измеряет — измеряет раннер. Он делает то, чего нельзя
доверить глазам: проверяет, что два прогона ВООБЩЕ сравнимы, и говорит, различимы
ли они.

**Отвергает, а не помечает звёздочкой:** разные наборы задач, разные коммиты,
разное число предметов, одну и ту же модель под двумя именами, и полосу FULL,
которая не исполняла инструменты (AF-04 держится и здесь).

**Не объявляет победителя, когда интервалы пересекаются.** Это главное
свойство. 0.85 против 0.75 на двадцати предметах — разница, которую видно
глазом, и шум, который нельзя защитить. Человек скажет «A лучше» и купит
архитектуру за счёт шума; инструмент говорит `INDISTINGUISHABLE` и называет,
чего не хватает — предметов, а не вывода. Когда стратегии ведут по РАЗНЫМ
метрикам, вердикт `SPLIT`, а не выбранная задним числом метрика.

**Скорость, память и энергия печатаются, только если прогон их принёс.** Пустая
клетка говорит «не измерено», а не ноль. Раздел 26 перечисляет их среди осей
сравнения, и соблазн подставить туда правдоподобное число здесь закрыт
конструкцией.

Проверено `tests/test_local_model_strategy_compare.py` (19 тестов), где каждая
проверка отказа имеет обратный контроль: без него ужесточения можно было бы
довести до состояния «не принимается ничего», и набор остался бы зелёным.

## Что этот прогон про целевое железо НЕ выяснил

Ни одного числа с машины владельца. Ни скорости декодирования, ни поведения
единой памяти под нагрузкой, ни циклов загрузки и выгрузки модели, ни
параллельных агентов. Всё это перечислено в задании (раздел 25) и всё это
остаётся владельческим — не потому, что было некогда, а потому, что такие
числа неоткуда взять в сборочном контейнере, и выдуманные были бы хуже
отсутствующих.
