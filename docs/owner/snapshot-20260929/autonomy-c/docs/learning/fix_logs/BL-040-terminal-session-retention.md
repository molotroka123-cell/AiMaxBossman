## Task
Длинная владельческая задача на установленном продукте: сотни подтверждённых команд подряд, жёсткое убийство процесса в середине, проверка по файлам на диске.

## Symptom
RSS сервера растёт линейно всё время прогона (≈ +10 КБ на каждую команду владельца) и после перезапуска начинает расти заново с той же скоростью. Ни один юнит-тест этого не видит: на десятке команд прирост неотличим от шума.

## Reproduction
scripts/windows_owner_tasks.py --minutes 2 против установленного продукта; 368 и 491 подтверждённая команда в двух прогонах. Замер памяти сервера снимается каждые 25 команд.

## Evidence
- прогон 1: 116576 КБ на 25-м шаге -> 118260 КБ на 175-м (+9.6 КБ/команду)
- после жёсткого убийства: 116372 КБ на 200-м -> 118164 КБ на 350-м (та же скорость)
- tracemalloc на TerminalManager: 5542 байта на команду не возвращаются; 400 объектов asyncio/streams.py:132 на 200 команд (по два потока на команду)
- словарь сессий: 10 -> 210 записей после 200 команд, ни одна не удалена
- после починки, tracemalloc запущен ДО прогрева: 13 байт на команду на установившемся режиме
- изолированно: удержанная куча 116 КБ при 200, 400 и 800 командах (не зависит от числа)
- по всему продукту: пока кэш наполняется +7.92 КБ/команду, после потолка +1.52 КБ/команду
- рост файла БД на той же дистанции: +1.02 КБ/команду — объявленная цена истории
- обратный контроль: 300 голых подпроцессов вне продукта дают +0.28 КБ/команду

## Hypotheses considered
- словарь TerminalManager.sessions не чистится и держит объекты процессов
- фрагментация аллокатора от постоянного порождения подпроцессов
- рост страничного кэша SQLite от долговечных строк истории команд
- очередь шины событий без потребителя

## Rejected hypotheses + why
- фрагментация аллокатора и порождение процессов — обратный контроль вне продукта дал +0.28 КБ/команду, это не объясняет +8
- поднять лимит памяти или перезапускать сервер по расписанию — прячет причину, а не убирает её, и владелец платит перезапуском за чужую ошибку
- вытеснять сессии по времени жизни — таймер не знает, жив ли процесс, и может выбросить запись работающей команды
- хранить меньше вывода в сессии — вывод уже ограничен 5000 строк, держит не он, а сам объект процесса с транспортом и каналами

## Root cause
TerminalManager.sessions[sid] = session не удалялся никогда: ни по завершении команды, ни по числу, ни по времени. Каждая запись удерживала объект процесса, его транспорт и буферы каналов давно закончившейся команды.

## Relevant code paths
- command-center/bcc/v2/terminal_control.py
- command-center/bcc/features/terminal.py

## Fix strategy
Ограниченное вытеснение ТОЛЬКО завершённых сессий (RETAIN_FINISHED = 200), самые старые первыми. Живая сессия не вытесняется никогда. Финальный статус выселенной сессии дописывается в БД в тот же момент.

## Alternatives considered
- слабые ссылки на объект процесса — не спасают: транспорт держится циклом asyncio
- чистить по завершении каждой команды — ломает чтение статуса сразу после запуска
- вытеснять по общему числу сессий, включая живые — потеря контроля над процессом

## Why this fix was chosen
Долговечная история команд лежит в БД и отдаётся /api/terminal/sessions, поэтому вытеснение теряет не историю, а только живой хвост вывода уже закончившейся команды. Запрос по забытому id уже отвечал честным 404 «сессия не найдена (возможно, после рестарта)» — контракт менять не пришлось.

## Adversarial variants
- живых сессий больше потолка — не вытесняется ни одна
- живые и завершённые вперемешку — живые не съедают бюджет завершённых
- прогон короче потолка — не вытесняется ничего
- обратный контроль: словарь действительно растёт один к одному (иначе тест был бы зелёным просто оттого, что сессии не появляются)
- мутация: убрать вызов вытеснения из /api/terminal/run — HTTP-тест краснеет
- сбой БД при записи финального статуса (open/write/commit) — кандидат остаётся в памяти до успешного commit, иначе теряется единственная копия статуса

## Regression
command-center, terminal + approvals: 193 passed, 5 skipped. Тесты вытеснения: 9 passed.

## Fresh external verification
Независимый автор на другой модели прочитал починку и нашёл в ней реальный пробел: сессия выселялась ДО успешного commit, и сбой БД терял единственную копию финального статуса. Коммит 14d29612 добавил retire_finished(remove=False) и три теста с инъекцией сбоев open/write/commit. Проверка нашла дефект, а не поставила печать — поэтому ей можно верить.

## Failed approaches / recovery lessons
- Первый замер ПОСЛЕ починки сказал «RSS растёт ровно как раньше» и едва не отправил верную починку в мусор. Ошибка была в способе смотреть: один усреднённый наклон смешал два режима — наполнение ограниченного кэша (законный разовый расход) и установившийся режим. В том прогоне потолок достигался на 200-й команде из 225, то есть почти вся серия была разгоном.
- tracemalloc, запущенный ПОСЛЕ прогрева, не видит уже существующих объектов и читает их штатную замену как рост. Запускать надо до прогрева, иначе инструмент показывает утечку там, где её нет.

## Generalizable lessons
- Кэш с потолком имеет два режима, и наклон, усреднённый по обоим, скрывает починку так же надёжно, как скрывал бы дефект. Мерить надо отдельно по режимам.
- Прежде чем объяснять рост внутренностями продукта, нужен обратный контроль на постороннюю причину: та же нагрузка ВНЕ продукта.
- Дефект, который виден только на дистанции в сотни операций, не будет найден ни одним юнит-тестом — для него нужна длинная задача, а не ещё один быстрый тест.

## Teach local model
- Распознать: словарь или список, куда кладут запись на каждую операцию, и ни одного места, где её оттуда убирают
- Предпочесть: вытеснять только ЗАВЕРШЁННЫЕ записи с потолком; живую не трогать никогда
- Проверять: удержанная память перестала зависеть от числа операций (замер при N, 2N, 4N даёт одно и то же), а не просто «стало меньше»
- Не путать: выход на полку — это наполненный кэш, а не остановленная утечка
- Перед выводом об утечке: тот же замер вне продукта, иначе это может быть аллокатор

## Limitations / follow-up
- Проверено на Linux; на Windows тот же прогон на момент записи ещё идёт в CI.
- Остаточный рост ≈1 КБ на команду — это файл БД (terminal_sessions/approvals). Не дефект и не устранён намеренно: это цена долговечной истории команд владельца.
- Потолок 200 выбран как рабочее множество, а не измерен по реальному профилю использования владельца; если он обычно смотрит вывод команды часовой давности, число надо будет поднять.
