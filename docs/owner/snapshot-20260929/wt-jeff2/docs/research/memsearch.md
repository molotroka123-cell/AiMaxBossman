## 2. Что делает на самом деле (по исходникам)

### Архитектура

```
CLI (click, cli.py, 1435 строк)
  └─ MemSearch (core.py) — оркестратор
       ├─ scanner.py   — обход путей, .md/.markdown, скрытое пропускается
       ├─ chunker.py   — markdown → чанки по заголовкам
       ├─ embeddings/  — 8 провайдеров за общим Protocol
       └─ store.py     — MilvusStore: dense + BM25 sparse в одной коллекции
  └─ maintenance.py / skills.py / compact.py — LLM-надстройки (нам не нужны)
  └─ plugins/{claude-code,codex,opencode,dsh} — хуки для чужих агентов
```

### Чанкование (`chunker.py`)

По заголовкам, как у нас. Секция = от заголовка до следующего заголовка любого
уровня. `max_chunk_size=1500` символов, длинные секции режутся по абзацам с
`overlap_lines=2`. Пустые секции (`## Session 03:16` без тела) выбрасываются —
у нас этого нет. Перед эмбеддингом вырезаются HTML-комментарии
(`clean_content_for_embedding`), чтобы UUID сессий не пачкали вектор, а в Milvus
кладётся оригинал.

`chunk_hash` = `sha256("markdown:{source}:{start}:{end}:{content_hash}:{model}")[:16]`.
**В хэш входит имя модели эмбеддингов** — смена модели инвалидирует все хэши.

### Индекс и состояние

Единственное хранилище — коллекция Milvus. Схема (`store.py::_ensure_collection`):

| поле | тип |
|---|---|
| `chunk_hash` | VARCHAR(64), primary key |
| `embedding` | FLOAT_VECTOR(dim), индекс FLAT, метрика COSINE |
| `content` | VARCHAR(65535), `enable_analyzer=True` |
| `sparse_vector` | SPARSE_FLOAT_VECTOR, индекс SPARSE_INVERTED_INDEX, метрика BM25 |
| `source`, `heading`, `heading_level`, `start_line`, `end_line` | скаляры |

`sparse_vector` **генерируется самим Milvus** через `Function(FunctionType.BM25)`
из поля `content` — memsearch не считает BM25 сам, это делает движок.

Где лежит состояние: `~/.memsearch/milvus.db/` (каталог, Milvus Lite 3.x),
конфиг `~/.memsearch/config.toml`, проектный `.memsearch.toml` (у него
жёсткий allowlist ключей: только `chunking`, `indexing`, `watch` — провайдер и
api-key из проектного файла подменить нельзя, это правильно сделано).
В индексируемый каталог memsearch **не пишет** (проверено: vault остался чистым);
`.index-state.json` пишется только если путь содержит `.memsearch`.

### Поиск (`core.py::search` + `store.py::search`)

Это **настоящий гибрид**, а не «dense вместо BM25»:

1. запрос эмбеддится провайдером;
2. `AnnSearchRequest` №1 — dense по `embedding` (COSINE, limit=top_k);
3. `AnnSearchRequest` №2 — BM25 по `sparse_vector` (тот же limit);
4. `client.hybrid_search(..., ranker=RRFRanker(k=60))` — слияние **RRF**;
5. score нормируется в [0,1] делением на `len(reqs)/(k+1)`;
6. **опционально** cross-encoder реранк (`reranker.py`), если задан
   `--reranker-model`; при этом с движка забирается `top_k*3` кандидатов.

Реранкер по умолчанию **выключен** (`RerankerConfig.model = ""`).
Когда включён — два бэкенда с автодетектом: ONNX Runtime (предпочтительно) или
sentence-transformers CrossEncoder; если нет ни одного — реранк молча пропускается.
Дефолтная модель `Alibaba-NLP/gte-reranker-modernbert-base`.

### Инкрементальность

По множеству `chunk_hash` на файл: считаются хэши новых чанков, из Milvus
берутся старые для того же `source`, лишние удаляются, эмбеддятся только новые
(`core.py::_index_file`). Файлы, удалённые с диска, вычищаются **только** внутри
директорий-корней текущего запуска — ровно та же аккуратность, что у нас
(`_cleanup_roots_for_paths`). Проверено: повторный `index` → `Indexed 0 chunks.`

### Эмбеддинги

8 провайдеров: `openai` (дефолт), `google`, `voyage`, `jina`, `mistral`,
`ollama`, `local` (sentence-transformers), `onnx` (onnxruntime, CPU).
Дефолтные модели: `text-embedding-3-small` (1536), `nomic-embed-text` (ollama),
`all-MiniLM-L6-v2` (local, 384), `gpahal/bge-m3-onnx-int8` (onnx).
ONNX-провайдер сначала пробует кэш HF **офлайн** (`local_files_only=True`)
и только потом лезет в сеть — сделано осознанно, для песочниц.

## 4. Сопоставление с нашим кодом

### 4.1. Главная находка: наш `MemSearchBridge` почти угадал CLI

`command-center/bcc/v2/memory/memsearch_bridge.py` писался вслепую по документации
и никогда не проверялся. Я прогнал каждую команду ровно так, как её формирует мост.

**Совпало (проверено запуском):**

* подкоманды `index`, `search`, `expand`, `stats` — все существуют с теми же именами;
* флаги `--provider`, `--model`, `--collection`, `--milvus-uri`, `--base-url`,
  `--api-key`, `--top-k`, `--json-output`, `--force` — все существуют, имена точные;
* `stats` действительно принимает **только** `--collection/--milvus-uri/--milvus-token`
  (мост это угадал и не шлёт туда `--provider` — иначе была бы ошибка click);
* `search -j` печатает **JSON-массив** объектов; мост обрабатывает и массив, и dict —
  фактический формат это массив;
* ключи результата: `chunk_hash`, `content`, `source`, `heading`, `heading_level`,
  `start_line`, `end_line`, `score` — мост читает `content/source/heading/score/chunk_hash`,
  всё на месте;
* `expand -j` печатает объект с `chunk_hash/source/heading/start_line/end_line/content`
  (+ `anchor`, если в тексте есть `<!-- session: ... -->`); `service.py` берёт `content` — совпадает;
* стандартный вывод при успехе — **чистый JSON**, stderr пуст (проверено: 0 байт),
  так что `stderr=STDOUT` в `_run` не ломает `json.loads`.

**Не совпало — это и есть список дефектов моста:**

1. **`stats` не умеет `--json-output`** (проверено: `Error: No such option '--json-output'`).
   Мост это, к счастью, не шлёт, но `stats()` возвращает строку
   `"Total indexed chunks: 40"`, которую `tool_stats` заворачивает в `{"raw": ...}`.
   Контракт `memory.stats` ломается: у `LocalMemoryBackend` это dict с
   `files/chunks/terms/backend`, у memsearch — строка. Для агента это разные ответы.
2. **`expand` несуществующего хэша даёт exit-code 1 и текст `Chunk not found: ...`.**
   Мост превращает это в `RuntimeError`, а `tools_memory.tool_expand` ловит только
   `KeyError` (контракт `LocalMemoryBackend`). Итог: `memory.expand` по устаревшему
   хэшу **уронит tool-handler**, а не вернёт данные-ошибку. Это нарушение нашего
   принципа «ошибка приходит модели как данные».
3. **`source` в ответе — абсолютный путь** (`/home/user/vault/notes/x.md`), у нас —
   путь относительно корня vault. `context_pack` подставляет `source` прямо в
   `[SOURCE: ...]`, то есть в контекст модели утекает абсолютный путь домашнего
   каталога человека. Расхождение цитирования между двумя backend'ами.
4. **`heading` — только ближайший заголовок** («Database choice»), у нас — полный
   путь («Note 1 > Database choice»). Наш вариант информативнее.
5. **Мост не передаёт `--exclude` / `--ignore-file`.** Скрытые каталоги
   (`.obsidian`, `.trash`, `.git`) memsearch пропускает сам (`ignore_hidden=True`) —
   проверено, `.trash/deleted.md` в индекс не попал. Но **`node_modules/` попадает**:
   проверено, файл `vault/node_modules/README.md` проиндексирован и вернулся первым
   результатом. `ObsidianVault.excluded_dirs` при переходе на memsearch **перестаёт
   действовать** — гарантия исчезает молча.
6. **Мост не умеет `--reranker-model`**, `--source-prefix`, `--milvus-token`,
   `--max-chunk-size`. То есть главная фича (cross-encoder) через наш мост
   **недоступна** — она выключена по умолчанию и включить её нечем.
7. **`--milvus-uri` по умолчанию пуст → БД уезжает в `$HOME/.memsearch/`**, а не
   в наш `data_dir`. Состояние памяти BOSSMAN оказывается вне каталога данных BOSSMAN.
8. `memsearch index` печатает `Indexed N chunks.` — человекочитаемо, JSON нет.
   `service.index()` вернёт строку; `tool_index` завернёт в `{"raw": ...}` вместо
   нашего `{files, chunks, added, updated, skipped, removed}`.

Итого: **мост синтаксически корректен и запустился бы**, но семантически
не эквивалентен `LocalMemoryBackend` по четырём пунктам (stats, ошибки expand,
формат source, исключения каталогов). Это не «всё выдумано», но и не «готово».

### 4.2. Что даёт memsearch, чего у нас нет

| Возможность | У нас (`local_index.py`) | У memsearch |
|---|---|---|
| Лексический поиск | BM25 Okapi на stdlib, RU/EN-стеммер, заголовок ×2 | BM25 внутри Milvus (Function), анализатор Milvus |
| Dense-эмбеддинги | **нет** (`load_dense_encoder` честно падает) | **есть**, 8 провайдеров |
| Гибрид + RRF | **нет** | **есть**, `RRFRanker(k=60)` |
| Cross-encoder реранк | `LexicalReranker` (покрытие термов) | ONNX/torch cross-encoder, по умолчанию **выключен** |
| Прогрессивное раскрытие | `expand` по `section_id` — точная секция | `expand` по строкам — **с багом**, см. ниже |
| Инкрементальность | sha256 файла | множество `chunk_hash` (точнее: правка одной секции не переэмбеддит весь файл) |
| Watch за файлами | нет | `watchdog`, `memsearch watch` |
| Компакция памяти LLM | нет | `compact`, `skills distill`, `project_review` |

**Баг в их `expand`** (`cli.py::_extract_section`, проверено на живом запуске):
поиск начала секции идёт с `range(start_line - 2, ...)`, то есть **пропускает
собственный заголовок чанка** и цепляется за предыдущий. На чанке
«## Database choice» (строка 9) вернулась секция, начинающаяся с
«## Architecture» (строка 5) — то есть **две секции вместо одной**.
Наш `expand` через `section_id` такого не допускает по конструкции.

### 4.3. Цифры на одном и том же корпусе (10 файлов, 40 чанков)

| Метрика | `LocalMemoryBackend` | `memsearch` CLI |
|---|---|---|
| Индексация | **0.005 с** | 5.4 с (с фейковым эмбеддером **на localhost**) |
| Повторная индексация | ~0.005 с, `skipped=10` | 2.4 с, `Indexed 0 chunks.` |
| Один поиск | **0.025 мс** (в процессе) | **~2.15 с** (запуск процесса + старт Milvus Lite) |
| RSS на запрос | в процессе сервера | ~250 МБ на дочерний процесс |
| Диск | JSON ~десятки КБ | 88 КБ на 40 чанков (без модели) |

2.1 секунды на каждый `memory.search` в tool-loop — это ощутимо, и это **нижняя
граница**: измерено с 128-мерным фейковым эмбеддером по локальному HTTP.
С `onnx`+bge-m3 добавится загрузка ONNX-сессии в каждый процесс.

## 5. Что берём

**Идеи и куски кода — да. Библиотеку целиком как backend — нет (пока).**

Конкретно берём:

1. **Гибридный поиск dense+BM25 с RRF** — как алгоритм, не как зависимость.
   RRF тривиален: `score(d) = Σ 1/(k + rank_i(d))`, `k=60`. Реализуется в
   `local_index.py` на ~30 строках поверх уже имеющегося BM25, как только
   появится любой источник dense-векторов. Формулу нормировки
   (`/ (len(reqs)/(k+1))`) тоже берём — она даёт сопоставимый score в [0,1].
2. **Отбрасывание пустых секций** (`_has_meaningful_content`) — у нас заголовок
   без тела становится чанком и шумит. 10 строк.
3. **Очистку текста перед эмбеддингом** (`clean_content_for_embedding`):
   вырезать HTML-комментарии, схлопывать пустые строки — эмбеддить очищенное,
   хранить оригинал.
4. **Инкрементальность по множеству чанков, а не по хэшу файла.** У нас правка
   одного абзаца перестраивает весь файл; у них — только затронутые чанки.
   Для BM25 это дёшево, но станет критично, когда появятся эмбеддинги.
5. **Включение имени модели в `chunk_hash`** — страховка от «сменили модель,
   а индекс остался». У нас `INDEX_VERSION`, что грубее.
6. **`memsearch` как опциональный внешний backend** — оставить код-путь, но
   починить мост (раздел 7) и **не делать его дефолтом**.

## 6. Что НЕ берём и почему

1. **Milvus / `milvus-lite` как обязательную зависимость.** Тянет `pymilvus`,
   `grpcio`, нативный движок `milvus-lite` и безусловно `openai`. Для нашего
   сценария несоразмерно: 250 МБ RSS и 2 секунды на запрос против 0.025 мс
   у BM25 в процессе. Плюс Windows не поддерживается вовсе.
2. **CLI-мост как основной транспорт.** Процесс на каждый вызов + старт
   встроенной БД — архитектурно неудачно для tool-loop. Если внедрять
   memsearch по-настоящему, правильный путь — **Python API
   (`from memsearch import MemSearch`) в процессе**, а не `subprocess`.
3. **`compact` / `skills distill` / `project_review`.** LLM-надстройки, которые
   сами ходят к OpenAI/Anthropic; `maintenance.py` даже исполняет shell-команды
   из ответа модели (allowlist есть, `MAX_TOOL_CALLS=3`, но всё равно).
   У нас для этого свой tool-loop с правами AUTO/ASK/DENY — вторую систему
   исполнения команд заводить нельзя.
4. **Плагины `claude-code`, `codex`, `opencode`, `dsh`** — хуки для чужих агентов.
5. **Их `expand`** — содержит off-by-one (раздел 4.2). Наш точнее.
6. **Дефолтный провайдер `openai`.** См. раздел 10.

| `bcc/v2/memory/memsearch_bridge.py` | `stats()` → парсить `Total indexed chunks: N` в dict `{"backend":"memsearch","chunks":N}`; `expand()` → при exit-code 1 и тексте `Chunk not found` бросать `KeyError`, а не `RuntimeError`; добавить параметры `exclude`, `ignore_files`, `reranker_model`, `milvus_token`, `source_prefix`; сделать `milvus_uri` обязательным и указывать на `data_dir`; приводить абсолютный `source` к пути относительно `vault_root` |
| `bcc/features/tools_memory.py::build_service` | передавать мосту `vault.excluded_dirs` как `--exclude` и `vault.root` для релативизации; `milvus_uri = data_dir/memory/milvus.db` |

**Контракты.** `MemoryBackend` (Protocol в `service.py`) менять **не нужно** — он уже
описывает ровно `available/index/search/expand/stats`, и memsearch в него ложится.
Единственное, что стоит зафиксировать в самом Protocol документацией:
`stats()` обязан возвращать `dict`, `expand()` при неизвестном хэше обязан бросать
`KeyError`, `MemoryHit.source` — путь относительно корня vault. Сейчас эти три
инварианта соблюдает только `LocalMemoryBackend`.

`ToolSpec`'ы в `tools_memory.SPECS` не меняются. `Feature` не меняется.

**Таблицы БД: не нужны ни одной.** Конфиг уже живёт в существующей
`settings_kv["memory.vault"]` (зашифрован `svc.vault`), индекс — файл в `data_dir`.
`bcc/db.py` не трогается.

## 9. Риски

1. **Зрелость.** Репозиторию 6.5 месяцев, версия 0.4.19, **240 открытых issue**
   при 236 форках. Найденный off-by-one в `expand` — иллюстрация: это центральная
   для «progressive disclosure» функция, и она возвращает не ту секцию.
2. **Привязка к вендору.** Весь слой хранения — Milvus. Заменить его =
   переписать `store.py` целиком; вся гибридность (`Function(BM25)`,
   `hybrid_search`, `RRFRanker`) — это API Milvus, а не код memsearch.
3. **Объём на сопровождение.** Библиотека — 6.6 тыс. строк чужого кода плюс
   `pymilvus`/`milvus-lite` в дереве зависимостей. Идеи — ~80 строк своих.
4. **Транзитивная зависимость `openai`** ставится всегда, даже при локальном
   провайдере. Сам пакет ничего не отправляет, но он в процессе.
5. **Лицензия — MIT, рисков нет.** Копирование алгоритмов допустимо при
   сохранении копирайта в комментарии.
6. **Телеметрии нет.** Проверено grep'ом по `src/` и `plugins/`: ни `telemetry`,
   ни `analytics`, ни posthog/sentry/segment/mixpanel — ноль совпадений.
   Единственные внешние хосты в коде — `api.jina.ai` (провайдер jina) и
   `memsearch.dev/configuration` (текст ошибки).
7. **Смена модели эмбеддингов = полный переэмбеддинг** (модель в `chunk_hash`)
   и жёсткая ошибка при несовпадении размерности коллекции.

## 10. Приватность

**Да, по умолчанию данные уходят в облако.** Это главный пункт.

`config.py::EmbeddingConfig.provider = "openai"` и
`core.py::MemSearch(embedding_provider="openai")`. При настройках «из коробки»
**текст каждого чанка каждой заметки** уходит в `api.openai.com` на
`text-embedding-3-small`. Milvus Lite при этом локальный, но контент утекает
на этапе эмбеддинга. Аналогично `compact.llm_provider = "openai"` — компакция
отправляет содержимое заметок в LLM.

Как выключить (порядок приоритета
`defaults → ~/.memsearch/config.toml → .memsearch.toml → CLI-флаги`):

* **явно передавать `--provider onnx`** (или `local`, или `ollama`) в каждом вызове —
  CLI-флаг бьёт любой конфиг. Наш `MemSearchBridge` уже так и делает:
  `provider: str = "onnx"` по умолчанию и всегда шлёт `--provider`. **Это единственное
  место, где мост угадал лучше, чем дефолт апстрима.**
* `memsearch config set embedding.provider onnx` — в глобальный `~/.memsearch/config.toml`;
* следить, чтобы `OPENAI_API_KEY` / `OPENAI_BASE_URL` не попадали в окружение
  процесса — SDK читает их сам, если явно не переданы;
* первая загрузка модели с `huggingface.co` — сетевая, дальше офлайн.
  «Полностью офлайн» достижимо, но не «из коробки».

Отдельно: проектный `.memsearch.toml` **не может** подменить провайдер или api-key —
там allowlist только на `chunking`/`indexing`/`watch`. Это хорошо: чужой репозиторий
не перенаправит эмбеддинги на свой endpoint.

Что memsearch **не** делает: не пишет в индексируемый каталог (проверено),
не собирает телеметрию, не ходит никуда, кроме выбранного провайдера.

## Оценка

# ВЗЯТЬ ИДЕЮ

**Обоснование.**

memsearch — аккуратно сделанный проект, и он **не заменяет** наш
`local_index.py`: он решает ту же задачу другой ценой. Сравнение на одном
корпусе: наш поиск — 0.025 мс в процессе, их — 2.15 с через процесс с поднятием
встроенной БД, при 250 МБ RSS ещё **без** модели эмбеддингов. За эти два порядка
латентности мы получили бы dense-эмбеддинги и RRF, качество которых я
**не смог измерить** (HF закрыт), плюс cross-encoder, который через наш
мост всё равно не включается.

Дополняет ли? Да — но ровно тем, что переносится в наш код за ~80 строк:
RRF-слияние, фильтр пустых секций, очистка текста перед эмбеддингом,
инкрементальность по чанкам, модель в хэше чанка. Никакой из этих идей
не нужны ни Milvus, ни pymilvus, ни 477 МБ venv.

Против внедрения библиотеки целиком: версия 0.4.19, 240 открытых issue,
жёсткая привязка всего слоя хранения к Milvus (гибрид — это API Milvus,
а не код memsearch), нерабочий Windows, и найденный на живом запуске
off-by-one в `expand` — именно в той функции, ради которой мы бы это брали
(progressive disclosure L2). Наш `expand` через `section_id` точнее.

Отдельно и важно: **дефолт memsearch отправляет содержимое всех заметок в
OpenAI**. Отключается одним флагом, и наш мост этот флаг уже шлёт, но по
нашим требованиям приватности продукт, у которого «облако по умолчанию»,
не может быть дефолтным backend'ом памяти BOSSMAN.

`MemSearchBridge` при этом **не выбрасываем**: он оказался почти верным
(все подкоманды, флаги и формат JSON совпали), его надо доработать по
четырём пунктам раздела 7 и оставить как честный опциональный путь для тех,
у кого memsearch уже установлен. Приоритет — низкий.

К пересмотру возвращаемся, если: (а) vault перевалит за ~10 тыс. заметок,
где JSON-индекс целиком в памяти перестанет годиться; или (б) замер recall
на реальных запросах покажет, что чистого BM25 не хватает. Тогда правильный
путь — не CLI-мост, а `from memsearch import MemSearch` в процессе.
