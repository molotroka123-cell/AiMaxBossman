## [CRITICAL] (security) Core HTTP/WS API has zero authentication and binds 0.0.0.0 — any network peer can approve pending actions and flip cloud_policy, defeating the entire approval + cloud boundary
- **Где:** `/home/user/AiMaxBossman/bossman-core/bossman/api.py`
- **Сценарий:** config.py:40 sets host default to 0.0.0.0 (not 127.0.0.1, despite the module docstring claiming loopback-only). api.py registers no auth dependency on any route. The runner parks every confirm=True tool call (e.g. browser.confirmed_click that will place an order, or a cloud_policy=ask send) in waiting_approval and blocks on approvals.wait (runner.py:89-105, 177-191). An attacker who can reach the box on port 8700 approves it with no credential: POST /telegram/webhook with body {"callback_query":{"data":"approve:<id>","from":{"username":"x"}}} (api.py:130-139 verifies no X-Telegram-Bot-Api-Secret-Token and no signature) or POST /approvals/<id> {"approve":true} (api.py:122-127). The blocked runner immediately executes the sensitive action. The same attacker calls PATCH /agents/<name> {"cloud_policy":"allowed"} (api.py:167-176 -> agents.set_cloud_policy) to permanently disable the cloud_policy=never guard for any agent, then POST /tasks to make that agent exfiltrate data to cloud. GET /approvals leaks every pending preview and the /events WebSocket (api.py:96-107) streams task text/results/approval previews to any unauthenticated listener.
- **Свидетельство:** config.py:40 host default '0.0.0.0'; api.py has no Depends/auth on any endpoint; api.py:122-127 POST /approvals/{id} open; api.py:130-139 /telegram/webhook has no secret-token/signature check; api.py:167-176 PATCH /agents/{name} cloud_policy open; api.py:96-107 unauthenticated WS /events broadcast; runner.py:94-105 (action approval) and runner.py:181-189 (cloud approval) both resolve via this open endpoint.
- **Как чинить:** Bind to 127.0.0.1 by default and require auth on the whole app: a bearer/session middleware for /tasks, /approvals, /agents PATCH, /projects, /models and /events. Verify Telegram webhooks with the X-Telegram-Bot-Api-Secret-Token set at setWebhook time and reject mismatches. Do not rely on network placement ('Tailscale serve') as the only control while the default bind is 0.0.0.0.

## [CRITICAL] (context) apply_compaction() unconditionally wipes the entire working history; an empty/short summary destroys all context with no fallback
- **Где:** `bossman-core/bossman/context.py + runner.py (live compaction)`
- **Сценарий:** During a long run, runner.py triggers compaction (fill>0.70 or every 25 tool calls). It calls the model to summarize, then does builder.apply_compaction(summary_msg.get('content') or ''). apply_compaction sets self.history=[] UNCONDITIONALLY and self.summary=summary[:1500]. (1) If the compaction call returns content=None or empty/whitespace/a refusal, apply_compaction('') sets summary='' AND history=[]: the agent's entire working memory (every tool result, decision, error, path) is erased and replaced by NOTHING. The loop then keeps running blind on build() with no history and no summary. (2) Even on a good summary, the SUMMARY_FORM orders sections Goal/Done/Decisions/Открыто(blockers)/Дальше(next-step) and the result is hard-truncated at SUMMARY_MAX_TOKENS*3=1500 chars mid-string, so a summary slightly over budget silently loses exactly the trailing anchors: blockers and next-step.
- **Свидетельство:** context.py:150-153 (apply_compaction: `self.summary = summary[: SUMMARY_MAX_TOKENS * 3]` then `self.history = []` with no non-empty/format guard); context.py:29 SUMMARY_MAX_TOKENS=500; context.py:31-36 SUMMARY_FORM places Открыто/Дальше last; runner.py:166-168 (`summary_msg = await chat(...)`; `builder.apply_compaction(summary_msg.get('content') or '')` — `or ''` turns a None/empty completion into a total wipe); comment context.py:151 claims full log stays in journal.md, but the loop never re-reads journal.md so the running agent proceeds with amnesia.
- **Как чинить:** In apply_compaction, refuse to clear history unless the new summary is non-empty and passes a minimal shape check (contains the required section headers); otherwise keep the previous history/summary and retry or skip compaction. Never truncate the summary blindly at 1500 chars — trim from a low-priority section, and preserve the Открыто (blockers) and Дальше (next-step) anchors explicitly.

- **Сценарий:** The runner only forces its approval path for tools whose confirm resolves True (runner.py:87-105), which for the browser is exactly browser.confirmed_click and browser.confirmed_press (agents.py:22-31, browser.py:647,650). ## [HIGH] (reliability) No circuit breaker / cooldown: a dead backend is retried on every request at full timeout, and the request-path 'mark unhealthy' is a routing no-op
- **Где:** `bossman-core/bossman/gateway/router.py:62, app.py:69-99`
- **Сценарий:** A backend goes hard-down (TCP connect/read hangs). An alias has one target pointing at it. Every incoming /v1/chat/completions request runs the fallback loop in run_json (app.py:76-99): it acquires the per-backend semaphore (default max_concurrency=2, config.py:18) and calls route.backend.json_request(...), which hangs up to timeout_seconds (default 120s, config.py:17) before raising BackendError, returning HTTP 502. There is no cooldown, so request N+1 pays the full 120s again. Once >2 requests are concurrent, the extras block on the semaphore for up to queue_timeout_seconds (default 300s, config.py:70) and THEN pay 120s each -> ~420s worst case per request. resolve() (router.py:46-62) never removes an unhealthy target from candidates; it only sorts it last, so with a single (or all-down) target it is still tried every time. Worse, run_json/run_stream mark failure via 'route.backend.health.healthy = False' (app.py:95, app.py:134) but never set health.checked_at, and never call refresh_health on the request path. The resolve() sort key is `(health.checked_at > 0 and not health.healthy, priority)` (router.py:62): if the backend was never probed (checked_at==0), the conjunction is False, so the unhealthy flag has ZERO effect on ordering. Net: no fast-fail, no provider cooldown, sustained retry load and 120-420s stalls against a backend the gateway already knows is failing.
- **Свидетельство:** router.py:59-62 keeps unhealthy targets in candidates and gates deprioritization on checked_at>0; app.py:95 and app.py:134 set healthy=False without touching checked_at; app.py run_json/run_stream never invoke owned_router.refresh_health; config.py:17 timeout_seconds=120.0, config.py:70 queue_timeout_seconds=300.0, config.py:18 max_concurrency=2; grep across gateway/ for cooldown|circuit|breaker|backoff|retry returns NONE.
- **Как чинить:** Add a real circuit breaker per backend: on repeated failures set an 'open until' monotonic timestamp and have resolve() SKIP (not merely deprioritize) open backends for the cooldown window, falling through to a 503 fast-fail when all are open. Distinguish this from checked_at (set an explicit cooldown field the router honors regardless of probe state), and add an overall per-request deadline across the fallback chain so one request can never occupy a worker for 120-420s.

## [HIGH] (reliability) Health probe treats any status < 500 as healthy, so auth failures (401/403) and rate-limits (429) report healthy while every real request fails
- **Где:** `bossman-core/bossman/gateway/backends.py:46-56`
- **Сценарий:** A backend is configured with a missing/invalid API key. probe() does GET on health_path (default /v1/models, config.py:21) and evaluates `ok = r.status_code < 500` (backends.py:50). The provider returns 401, so ok=True and health.healthy=True. The /health endpoint (app.py:44-48) reports status 'ok'. The router keeps this backend at top priority (router.py:62). Every real chat/completions request then hits json_request, which raises BackendError for any status>=400 (backends.py:60-61), so the client gets a 502 on 100% of requests while monitoring shows green. The same bug means a 429 (provider overloaded / rate-limited) is scored 'healthy', so the gateway keeps routing to a throttled provider instead of preferring a fallback target that is actually serving.
- **Свидетельство:** backends.py:50 `ok = r.status_code < 500`; backends.py:60-61 json_request raises BackendError for status>=400; config.py:21 health_path default '/v1/models'; app.py:47 usable = any(v['healthy'] ...) drives the /health verdict.
- **Как чинить:** Treat only 2xx (optionally 2xx/3xx) as healthy on the probe, and explicitly classify 401/403 as hard-down (bad credentials) and 429/503 as unavailable-with-backoff so the router can shed load to fallback targets. Do not fold auth and throttling failures into 'healthy'.

## [HIGH] (routing) Any non-2xx from a backend — including 4xx client errors — triggers failover to the next route (the cloud fallback), so a request the local model merely rejects silently escalates to cloud
- **Где:** `gateway/backends.py (json_request) + gateway/app.py (run_json fallback loop)`
- **Сценарий:** json_request raises BackendError for ANY status >= 400 (backends.py:60-61), not just 5xx/transport failures. run_json treats every exception identically: mark backend unhealthy and `continue` to the next route (app.py:94-97). So if the local ollama model returns 400/422 for a bossman-smart request — e.g. the local model doesn't support the `tools` field, or the prompt exceeds its context and the server 400s — the gateway does NOT surface that client error; it fails over to the openrouter cloud target and sends the same payload to the cloud. A deterministic bad request thus becomes cloud egress (compounding the cloud_policy bypass), and the client gets a cloud answer for what should have been a 400. Health is also flipped to unhealthy on a pure client error.
- **Свидетельство:** backends.py:60-61 `if r.status_code >= 400: raise BackendError`; app.py:94-96 `except Exception: route.backend.health.healthy = False; errors.append(...)` then `continue`; app.py:98-99 only raises 502 after ALL routes exhausted. Same pattern in run_stream app.py:133-135.
- **Как чинить:** Distinguish retriable/failover errors (connect/timeout/5xx) from non-failover client errors (4xx). On a 4xx from the first route, return that error to the caller instead of failing over, and do not mark the backend unhealthy. Only fail over to the next (possibly cloud) route on genuine backend/transport/5xx failures.

## [LOW] (routing) Streaming responses leak the real backend/cloud model id — the json path rewrites body['model']=alias but the streaming path forwards upstream bytes untouched

## [LOW] (routing) Cloud classification is a hardcoded Python prefix list that both false-negatives every gateway alias and false-positives local open-weight models (e.g. gpt-oss)
