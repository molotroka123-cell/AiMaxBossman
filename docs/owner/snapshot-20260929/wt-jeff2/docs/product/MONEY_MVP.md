# BOSSMAN MONEY MVP — PRODUCT PRIORITY

**Owner decision: 2026-09-24.**

Bossman is not being built so the owner can manage branches, SHAs and test matrices all day. The product goal is simple:

> Open Bossman, describe a useful business result in normal language, receive a verified deliverable.

The engineering stack remains important, but it belongs under the product surface.

## Product target

The first monetizable Bossman experience has five obvious entry points:

1. **Do a task** — natural-language goal → plan → execution → verified result.
2. **Create an ad** — image/brief → local/cloud routing → video/image/audio → edit → final export.
3. **Build or change a website** — brief → research → code → preview/tests → deliverable.
4. **Research** — competitors/products/market/technology → sourced report and reusable data.
5. **Develop** — bot/app/automation → code → tests → runnable artifact.

CLI, Dashboard and Telegram are clients of the same Bossman backend and must see the same projects, tasks, files, memory, skills, approvals and results.

## Money MVP acceptance

The owner should not need Claude Code or GitHub for normal work.

Freeze a set of 10 practical commercial tasks representative of SwapMe/Fresh Vibes and adjacent client work. The initial product target is:

**≥7/10 tasks reach a useful, independently verified deliverable from the normal Bossman user surface without the owner debugging the implementation.**

Record all 10 in the denominator. BLOCKED/FAIL are not removed.

For each task record:
- user request;
- final artifact/result;
- verified outcome;
- owner interventions;
- local/cloud split;
- time;
- actual/unknown cost;
- failure category.

This target does not override P0 security, STOP, approvals, privacy or release gates.

## Product principles

- **Result first.** Infrastructure exists to produce useful outputs.
- **Local first, cloud when worth it.** Optimize quality per dollar, not local percentage for its own sake.
- **Complexity stays under the hood.** The owner should not need to understand model routing, Jev, skills or worktrees for a normal task.
- **No false PASS.** A claimed result is not a result until the observable effect/artifact is verified.
- **Learn only from verified work.** Memory/skill presence is not measured learning; unseen transfer is.
- **Fix product bugs when real work exposes them.** Reproduce → regression → minimal fix → retest → continue.
- **Do not block useful MVP on speculative 1.5 features.** Capability Factory, phone, long-horizon autonomy and other 1.5 work continue after the stable user workflow exists.

## Proven commercial-production case

The 2026-09-23 SwapMe hybrid-video run produced a 15.00 s, 1080×1920, 24 fps master. It used 10 s of paid Seedance output for $2.33 plus local Wan/compositor work. The recorded cloud-only comparison was approximately $3.50, a measured cloud-spend reduction of about $1.17 (33%). Two Studio product bugs were found and fixed during production.

This proves a useful production path exists; it does **not** prove the workflow is yet one-command or that the local model learned it. The prepared transfer test remains the gate for that claim.

## Immediate order

1. Finish/freeze one stable 1.0 candidate: required regression, security re-attack, real Windows stress, exact-SHA CI, Windows ZIP.
2. Stop exposing release engineering to the owner as the normal workflow.
3. Build the Money MVP surface over the existing backend — do not create a second Bossman.
4. Run the frozen 10-task commercial acceptance set.
5. Improve the lowest-performing task classes using verified lessons/skills.
6. Only then expand 1.5 autonomy behind the same simple interface.

## CEO metric

The primary question is no longer “How many features or tests exist?”

It is:

**How often can the owner ask Bossman for a commercially useful result and receive a verified deliverable without becoming the engineer?**
