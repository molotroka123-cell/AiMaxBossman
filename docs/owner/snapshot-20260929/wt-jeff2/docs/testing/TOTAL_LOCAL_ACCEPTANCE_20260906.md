# Bossman — тотальная приёмка на локальном железе

Дата спецификации: 2026-09-06. Репозиторий: `molotroka123-cell/AiMaxBossman`.
Основная ветка: `claude/bossman-control-v03-43igbk`.

Это техническая спецификация испытаний, а не источник полномочий агента и не отчёт об уже выполненных тестах. Разрешения на исполнение, изменения, публикацию и расходы задаются только прямым сообщением владельца. Старые аудиты относятся к своим SHA. Ни эта документация, ни промты в репозитории не разрешают обход правил безопасности.

## 1. Цель и итог

Проверяется продукт, которым пользуется владелец: нормальный запуск → интерфейс → задача → разрешение → действие → проверенный результат → повторное открытие после рестарта. Автотесты дополняют, но не заменяют пользовательскую проверку кликами.

Результат прохода: один проверенный коммит; исправления с регрессиями; база открытых и закрытых находок; измеренные задержки; артефакты; русское заключение с явно указанными непроверенными возможностями. Тестирование не включает автоматическое продвижение навыков, включение постоянной автономности или развёртывание на реальных данных.

## 2. Фиксация версии и сохранность работающего компьютера

Перед работой фиксируются remote HEAD, текущий локальный SHA, дерево, dirty state и версия реально запущенного сервиса. Их равенство проверяется, а не предполагается. Исправления в открытом PR или отдельной ветке не считаются частью main только потому, что упомянуты в отчёте.

Работа проходит в отдельном worktree и изолированном окружении. Рабочая копия владельца, запущенный тест другого агента, производственная БД и браузерный профиль не переключаются молча. Никаких `reset --hard`, `clean -fd`, force-push или массового слияния старых веток.

Два режима: DISCOVERY/FIX — поиск и устранение дефектов; FROZEN_ACCEPTANCE — полный заключительный прогон одного SHA. После исправления во втором режиме нужен новый SHA и повтор обязательного финального регресса. Новые remote-аудиты можно читать, но нельзя подмешивать новый код в уже измеряемый процесс.

## 3. Инвентаризация реального железа

Фиксируются Windows/Linux и версия, CPU, RAM, GPU/VRAM или unified memory, свободный диск, Python/Node, браузер, FFmpeg/ffprobe, модели и версии runtimes. Для модели нужны фактические provider/model ID, квантование, контекст, настройки генерации, residency и endpoint без секретов. GLM 5.3 или другой идентификатор не выдумывается: доступность устанавливается по реальному окружению.

128 GB AI Max — не предположение о текущей машине. При unified memory RAM и GPU-память не складываются как два независимых пула. При нехватке памяти тестируется меньшая уже установленная модель с явной отметкой, а не молчаливой подменой базового замера. Новые модели не скачиваются без отдельной необходимости и разрешения.

Снимки процессов до/после: PID, время создания, родитель, принадлежность тесту, RSS, threads/handles/FD. Чувствительные argv и env не сохраняются. Допускается завершение только подтверждённых дочерних процессов данного запуска или отдельно согласованного списка. Неизвестный тяжёлый процесс — OWNER_CONFIRMATION_REQUIRED. Системные службы, защита, VPN/SSH, редакторы, личные браузеры, текущий терминал и нужные model/DB-сервисы сохраняются. Встроенные failsafe управления компьютером не отключаются.

## 4. Реальная параллельность без взаимных помех

До пяти фактически доступных агентов: Core/миссии; Video/Higgsfield; Web/UX; V4/V5/хранилища; независимый verifier/CI/метрики. Отсутствующие субагенты не имитируются. Один интегратор владеет общим реестром и Git.

Один физический рабочий стол — один управляющий агент. Остальные тестируют изолированные страницы, каталоги, процессы и БД. Общие файлы изменяет один назначенный исполнитель; остальные возвращают тесты или патчи. Пять логических ролей не требуют загрузки пяти больших моделей. Начало с одного worker, увеличение только при наличии ресурсов. Для итоговых latency-замеров конкурирующая нагрузка фиксируется; idle и loaded результаты разделены.

## 5. Журналы и единая база аудита

Каталог вне tracked дерева: `../bossman-acceptance/<UTC>-<SHA>/`.
Минимум: `manifest.json`, `acceptance-matrix.json`, `findings.jsonl`, `commands.jsonl`, `phase-samples.jsonl`, `resources.jsonl`, `process-before.json`, `process-after.json`, `junit/`, `artifacts/`, `OWNER_REPORT_RU.md`.

Каждая попытка содержит run/scenario ID, code SHA/tree, конфигурацию, начало/конец, монотонную длительность, команду или последовательность кликов, exit code, pass/fail/skip/xfail и ссылки на доказательства. Непроверенное поле — null/NOT_MEASURED, не ноль.

Доказательства: USER_UI_LIVE, USER_UI_LOCAL_FIXTURE, REAL_COMPONENT, MOCK, STATIC_ONLY, NOT_RUN. Включённый headed-браузер без реального результата ещё не PASS. История находки сохраняет discovered_sha, reproduced_sha, fixed_sha, verified_sha; дубли связываются по причине, не удаляются. При наличии используется существующий Audit intake, а не ещё одна конкурирующая БД. Пустой список ошибок не означает полноту аудита.

Не публикуются пароли, ключи, cookies, скрытые рассуждения, полные промты, пациентские данные и приватные фотографии. Скриншоты только тестового профиля, после проверки приватности. Логи ограничены по размеру и ротируются. Перед commit/upload отдельная проверка секретов/PII. Прерывания и неудачи не выбрасываются из статистики.

## 6. Запуск и основной пользовательский путь

Сначала изучаются действующие launcher, doctor, pyproject и workflows; затем используются их актуальные команды. Установка зависимостей только в выделенное окружение. Скрипты и hooks проверяются до запуска. Отсутствующий компонент не заменяется заглушкой для получения PASS.

Проверки через видимый интерфейс:

1. Запуск штатным ярлыком/launcher, вход, Home. Нет пустой страницы, бесконечной загрузки и необработанной ошибки.
2. Отправка сообщения локальной модели, streaming, отмена ответа, повтор после ошибки, продолжение чата после перезапуска.
3. Создание миссии словами, выбор executor/model, видимый прогресс, ASK approval, настоящий локальный эффект и открытие результата.
4. Создание/изменение тестового файла, браузерная задача, coding-задача с проверяемым патчем, разрешённая terminal/MCP-операция. Для доступных интеграций — тестовые endpoints, не настоящие рассылки/ордера.
5. Перезапуск и повторное открытие миссии, артефакта и истории. Данные и подтверждённые эффекты не теряются.
6. Pause, Stop, Take control, Resume из UI во время наблюдения, ожидания модели, approval и после dispatch. Сохраняется решение владельца и исход уже отправленного действия.
7. Отказ, недоступный executor/model, timeout, исчерпание бюджета, PRIVATE без локальной модели: понятный blocker, без молчаливого cloud fallback.

API/SQL/CLI допускаются для fixtures и диагностики, но не вместо пользовательского пути. Отсутствие GUI/computer-control возможности означает USER_UI=BLOCKED_BY_ENVIRONMENT, а не попытку выдать backend-тест за UI. Для уже выполненного эффекта cancellation не должна скрывать неопределённый исход: требуется reconciliation, а не повтор.

## 7. Регрессии из прошлых аудитов

Эти сценарии перепроверяются на текущем коде, независимо от старого статуса:

- AT-01: эффектная цель требует файл, планировщик сразу сообщает COMPLETE, файла нет. Итог не COMPLETED. Положительный контроль — действительный проверенный результат; отдельный контроль для целей без внешнего эффекта.
- AT-02: PAUSED, USER_CONTROL, WAITING_APPROVAL сохраняются после завершения тестового процесса и нового запуска. Только допустимый явный Resume разрешает продолжение.
- AT-03: popup, смена вкладки/фокуса, layout, значение поля или внешняя модификация после verified observation и во время планирования/approval. TTL и task generation не заменяют актуальность цели на границе эффекта.
- AT-04: evidence не становится повторно доступным после заполнения журнала, повреждения JSON, рестарта и конкурентного потребления независимыми процессами. Повтор того же consumer идемпотентен; новый consumer отклоняется. Ошибка записи не даёт разрешения.
- AT-05: root-тесты собираются с объявленными root-зависимостями; нельзя случайно требовать полный HTTP/Core стек.
- Валидный старый journal, подмена снимка того же номера, отсутствующий anchor, crash между snapshot/anchor: поведение fail-closed или документированное безопасное восстановление. Ограничения защиты от совместного отката файлов указаны явно.
- Отмена await с `asyncio.to_thread` не оставляет незавершённые UIA/model операции, которые позже вмешиваются в новый запуск; отмена wrapper не считается остановкой потока.
- Sandbox-путь вне allowed roots отклоняется до бесполезного запроса approval. Экспериментальный Fleet явно помечен, ошибка загрузки решений не отображается как «ничего не требуется».

## 8. Video Studio, Web Designer, Higgsfield

### Video Studio

Видимый путь: открыть единственный канонический редактор → создать проект → импортировать собственный fixture → добавить на timeline → trim/split/move/delete → undo/redo → seek первый/средний/последний кадр → доступный эффект → сохранить → Export → увидеть progress → открыть/скачать готовый файл → повторно открыть после рестарта.

Результат проверяется настоящими FFmpeg/ffprobe: decode, codec, длительность, последний CFR-кадр, аудио и ожидаемое изменение. Дополнительно corrupt media, нулевая/NaN-длительность, stale revision, cancel и ограниченные concurrent exports. Derivative без необходимого manifest не считается доверенным; безопасная регенерация проверяется отдельно. Отсутствие FFmpeg — blocker, не принятие сценария.

### Web Designer

Открытие через Apps → выбор элемента → изменение текста/свойства → preview → save → reload/reopen. Сохраняются вложенные дети, DOCTYPE, comments, JSON-LD, scripts, SVG/viewBox, templates, Unicode/entities и несвязанный source. Проверяются stale selection, конфликт сохранений, manual/AI edit race, preview sandbox/origin и сообщения ошибок. Path/symlink-атаки используют только временные каталоги.

Общий UX: кнопка запуска при нескольких агентах, back/forward, клавиатура/focus, длинные русские подписи, масштаб 100/125/150/200%, доступность длинного результата. До/после screenshot сопровождается реальным изменением состояния, не только отсутствием ошибки клика.

### Higgsfield

По умолчанию режим без новой генерации. Используется только отдельно разрешённый аккаунт/профиль; никаких автоматических логинов, копирования личных cookies, обхода CAPTCHA и предположения «Unlimited значит бесплатный».

Проверки на локальных fixtures: полный текст Lexical и упорядоченные mention chips, ожидаемое source video по идентичности, отсутствие лишних chips, job binding, duplicate response, auth loss, atomic state, BOM, download retry, corrupt media. DOM edit не подменяется записью напрямую в БД редактора.

Для разрешённого live-запуска: перед Generate подтверждены текущие параметры, права и лимит расходов; click не равен queued job, queued job не равен completed video. Сохраняются job ID, связь с prompt/source и результат. Timeout после Generate — UNKNOWN, не основание нажать ещё раз. Timestamp/watermark и наличие старых видео в истории не доказывают принадлежность результата текущей задаче. Следующий Extend начинается только от проверенного нужного сегмента. Ошибка download повторяет download того же результата, а не генерацию.

Измеряются отдельно site wait, ready→agent reaction, agent overhead, download/probe, весь цикл. Подготовка следующего текста может идти во время ожидания, но не разрешает преждевременный эффект. Двух сегментов недостаточно для заявления о правильной цепочке из шести сцен.

## 9. V4/V5, Fleet, память и бюджеты

Для всех существующих M0–M11 и N0–N8 составляется requirement → canonical implementation → test → evidence → gap. Названия и зависимости берутся из актуального ТЗ; наличие файла не означает завершение узла.

V4: единый Mission IR, DAG, сохранение obligations при replan, current authorization, re-observe, restore из последнего verified checkpoint, migration старых миссий, bounded retries, skill applicability/invalidation, scoped context, бюджеты/residency. Исчезновение обязательного результата при перепланировании запрещено. История verified success не заменяет новую проверку текущего эффекта.

V5: durable spec/revision/CAS; scoped observers; freshness/UNKNOWN; proposal dedup; owner/scope/action/budget binding; current grants; conflicts/cooldown/fairness; canonical mission adapter; revoke/expire перед эффектом; reconciliation и повторное наблюдение. H01–H10 выполняются с явным разделением настоящих production ports и fake ports.

UI целей: DRAFT, Pause, Revoke, Expire; lifecycle отдельно от condition; UNKNOWN не зелёный. Healthy unchanged objective не вызывает лишних model calls. Цель не становится SATISFIED только по факту завершения миссии. Никакой активации постоянных целей владельца: тестовый профиль/фикстура не является выпуском N0.

Fleet: действительная identity, revoke/replay, leases/fences, ownership completion, reconnect/restart, admission unified memory, PRIVATE placement. Loopback TLS — компонентная проверка, не production multi-node acceptance. Переполнение бюджета проверяется совместными запросами и ошибками reserve/settle; UNKNOWN reserve не освобождает права для повторного расхода.

Memory: scopes, чужой tenant, устаревшие навыки, инструкции внутри документов, сжатие контекста, tool overload. Память остаётся данными и не расширяет права. На известных задачах контекст подбирается релевантно, без полной истории и всех инструментов сразу.

## 10. Измерение скорости — без смешения метрик

Один профиль модели, задач, разрешений и железа фиксируется до сравнения. Разные виды событий измеряются раздельно, иначе ранний UI ack скрывает медленное выполнение.

| Метрика | Начальная инженерная цель | Что измеряется |
|---|---|---|
| UI feedback | p95 ≤100 ms | От пользовательского input до видимого подтверждения UI |
| Stop ack | p95 ≤200 ms | От input Stop до принятого запрета нового dispatch |
| Ready-action overhead | p95 ≤150 ms | От готового разрешённого действия до передачи исполнителю, без нового model turn |
| Verified cycle | p50 ≤1 s, p95 ≤2 s | Наблюдение → локальное решение → разрешение → действие → независимая проверка |
| CAS | p95 <10 ms | Отдельные create/transition/update операции, не скрытый средний по разным операциям |
| Recovery | <2 s для заявленного fixture | До безопасного известного состояния, включая PARKED, а не до обязательного возобновления |

Это проектные цели, а не универсальное определение человеческой реакции. Полное время с обязательным ожиданием владельца и сервиса тоже сохраняется, отдельно от машинного hot path.

Минимум 100 повторов на выбранный механический сценарий, сырые samples и число ошибок. p50/p95/p99 по явному алгоритму; при малом n хвостовые оценки отмечены как слабые. Cold/warm, idle/loaded отдельно. При сбоях успехи и таймауты показываются раздельно, неудачи включаются в общий rate и длительность попыток. Synthetic costs и mocks исключены из заявлений о реальной модели/экране. Отсутствие `sleep` не метрика.

Для human comparison — одинаковые сценарии на той же машине, одинаковый результат/разрешения, минимум 20 пар как предварительный замер, с временами и ошибками. Нет записи действий человека — HUMAN_COMPARISON=NOT_RUN. Малый набор не доказывает превосходство во всех приложениях.

## 11. Сохранение качества локальной модели

Сравнение RAW / SYSTEM / CONTEXT / FULL выполняется на одном фактическом model/config/dataset. Reasoning — без неравного преимущества tools; tool tasks — с одинаковыми affordances и бюджетом. Router сначала фиксирован, сравнение моделей через router — отдельный эксперимент.

Категории: reasoning, coding с исполнением тестов, structured output, выбор инструмента/аргументы, память, адаптация к неизвестному, computer-use planning. Заранее фиксируются rubric и held-out набор, не пересекающийся с обучением навыков. 20 задач — smoke; статистическая достаточность для 2% noninferiority рассчитывается, а не предполагается даже при 200 задачах.

Относительное retention 0.98 не равно падению на два процентных пункта. При ненулевом RAW — отношение оценок и парные доверительные интервалы; при нулевом RAW ratio N/A. Нельзя прятать регрессию категории средним. Tokens, latency, cost и все failed attempts сохраняются. Веса модели не меняются во время acceptance.

Результаты привязаны к измеренному SHA, task/config digest и происхождению, хранятся как артефакты. Коммит с собственным ещё неизвестным SHA внутри benchmark JSON не требуется. Stale/missing evidence означает INSUFFICIENT_EVIDENCE, не PASS и не доказательство деградации.

## 12. Контролируемый стресс и восстановление

Сначала функциональная корректность. Затем 1 → 2 → 4 worker при наличии памяти, 50 → 100 → 200 инструментальных действий и до 1000 bounded duplicate событий на локальной фикстуре. Физическим desktop всё ещё управляет один executor. Нет бесконтрольного параллельного кликанья.

Fault injection: DB lock, недоступная модель, краткий обрыв тестового соединения, завершение только тестового worker/browser/FFmpeg, crash до dispatch/после dispatch/после effect/до journal/при verification. Для необратимых действий используются локальные счётчики/fixtures. Проверяется отсутствие повторов и корректный PARKED.

Память, CPU, GPU при доступности, FD/handles/threads, очередь, размер БД и дочерние процессы измеряются каждые 2 секунды с bounded логом. Эскалация прекращается при RAM>85%, свободной RAM<max(1GiB,15%), диске<max(5GiB,10%), thermal throttling или потере интерактивности; нагрузка снижается/запуск корректно останавливается. Превышение лимита не лечится убийством пользовательских программ. OOM и disk-full инъектируются в ограниченные fixtures, системный диск не заполняется.

Soak: сначала 15 минут, затем до 60 при бюджете и ресурсах. Статус 24h допустим только после реальных 24 часов. Обход прав, утечка, дубликат эффекта или потерянный Stop — остановка опасного сценария, сохранение доказательств, исправление. Остальные независимые безопасные проверки могут продолжаться.

## 13. Исправления и обязательные полные наборы

Цикл дефекта: UI/тестовая репродукция → причина → минимальный фикс → узкая регрессия → hostile проверка → повтор того же UI-пути → независимый результат. Нельзя менять ожидаемый результат только ради зелёного теста, снижать coverage, прятать ошибки skip/xfail или расширять права.

Полный root, Core и Command Center выполняются раздельно из правильных package directories с текущими declared dependencies. Обязательны действующие repo workflows и их coverage/security gates. Дополнительно — все изменённые границы V4/V5 и browser/media tests. Shell glob и Linux-команды не копируются вслепую в PowerShell; отсутствие собранных тестов не PASS.

У каждого запуска JUnit, exit code и bounded deadline; watchdog применяется из правильного каталога. «249 passed» перед зависанием процесса не считается успешным завершением. Ошибки startup/import/dependency отделяются от тестовых failures. Таймаут — отдельный результат, не повод удалить тест.

## 14. Git, текущий SHA и передача результатов

Исправления готовятся в своей ветке от фактического main. По прямому разрешению владельца в main попадают только законченные проверенные изменения, с учётом branch protection и других исполнителей. Каждому checkpoint предшествует fetch и semantic reconciliation; force запрещён. Новая версия исходников не заменяет код уже работающего тестового процесса.

Финальный freeze фиксирует source SHA/tree и одинаковые версии поднятых сервисов. GitHub PR head_sha не гарантирует, что job проверял именно head: записываются actual checkout SHA, event, run ID и attempt. Merge SHA проверяется отдельно. Старый зелёный CI, skipped/cancelled и PR-снимок не сертифицируют новый main. Недоступные GitHub checks — BLOCKED_GITHUB, локальная приёмка продолжается без выдуманного push.

Итоговые измерения публикуются артефактом/комментарием после freeze, чтобы docs-only commit не выдавался за тот же протестированный SHA. Допустим отдельный docs-коммит с явной ссылкой на предыдущий TESTED_SHA. Новые улучшения после freeze идут следующим циклом.

Вердикты: LOCAL_ACCEPTANCE_PASS; PARTIAL_ACCEPTANCE_WITH_BLOCKERS; FAIL. Обязательный непроверенный сценарий исключает полный PASS. Неподтверждённый owner UI, human comparison или N0 не объявляется завершённым из-за удачного component benchmark.

Опциональный scorecard /10000: десять прежних осей по 0–1000, только с восстановленной общей рубрикой и evidence по оси. Неизвестная оценка — N/A, не ноль. Без сопоставимой рубрики итог обозначается PRELIMINARY_NOT_COMPARABLE, без выдуманного ускорения и процента готовности. Эпохи закрываются выполненными требованиями, а не нужной суммой баллов.
