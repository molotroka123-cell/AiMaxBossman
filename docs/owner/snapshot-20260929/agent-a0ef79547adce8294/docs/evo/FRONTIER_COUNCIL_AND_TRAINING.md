# Frontier Council и обучение Bossman

Дата решения: 2026-09-21.
Статус: **SPECIFICATION / PLANNED — не реализация и не сертификат**.
Область: развитие EVO после приёмки стабильной 1.0.
Каноническая линия: `release/bossman-owner`; stable определяется неизменяемыми SHA, тегом и архивом, а не текущей вершиной ветки.

## 1. Что хочет владелец

Bossman должен не только выполнять поручения локальными моделями, но и улучшаться с помощью сильных внешних моделей. Разрешённые frontier-модели выступают независимыми аудиторами, учителями и авторами изолированных исправлений. Локальный Bossman остаётся исполнителем; полезность обучения доказывается новой самостоятельно выполненной задачей, а не красивым отчётом учителя.

Целевой цикл:

```text
Реальная задача и проверенный результат
  -> локальный журнал опыта
  -> безопасный пакет для аудита
  -> независимые frontier-аудиторы
  -> воспроизведение находки / отклонение ложной тревоги
  -> коррекция учителя
  -> повторная попытка локального Bossman
  -> проверенный урок / кандидат skill или patch
  -> неизвестные ранее задачи + сравнение со stable
  -> предложение владельцу
  -> разрешённое продвижение / наблюдение / откат
```

Не обещаем фиксированный процент локальной работы, рост интеллекта или успешности. Всё это измеряется. Наличие документа не означает настроенный облачный доступ, активный scheduler, проведённый тренинг или изменённые веса.

## 2. Связь с существующим продуктом и очередность

Этот документ дополняет [EVO proposal](EVO_1_0_PROPOSAL.md), [owner behavior](OWNER_MODEL_BEHAVIOR.md) и [Product Council](PRODUCT_COUNCIL_PRE_EVO.md). Не создаётся второй Gateway, отдельная память, новый approval engine или альтернативная финальная ветка.

Сначала завершить repair и приёмку 1.0 по [действующему протоколу](../../OWNER_ACCEPTANCE.md). Уже разрешённые coding-coaching и подготовка проверяемых эпизодов могут идти в текущем проходе. Автоматизацию council, новые training jobs и автоматический отбор обновлений включать отдельным этапом после приёмки. Документация не меняет [release gates](../../tools/exact_sha_certify.py) и не подменяет [известные ограничения](../../KNOWN_LIMITATIONS.md).

Этапы внедрения, каждый с отдельным evidence:

| Этап | Исполняемый результат | Не разрешает |
|---|---|---|
| FC-M1 | Пакет аудита, независимые findings, локальное воспроизведение | Автоприменение совета |
| FC-M2 | Teacher feedback, student retry, durable lessons, holdout | Объявление изменённых весов |
| FC-M3 | Isolated code/skill/model-routing candidate и arena | Самоодобрение stable upgrade |
| FC-M4 | Опциональный LoRA/QLoRA-кандидат по отдельному решению | Прямую замену основной модели |

Все строки — требования к будущей реализации, не список уже завершённых функций.

## 3. Состав совета и независимость

Роли: code/reliability reviewer, security reviewer, UX/vision reviewer, curriculum teacher, red-team и evidence adjudicator. Используются доступные владельцу разрешённые модели; конкретные версии Claude/GPT/Gemini или других семейств не фиксируются навсегда и не считаются лучшими по названию.

Перед назначением роли проверяются официальный model ID, фактические capabilities, доступность, условия использования, цена и политика данных. Эти сведения должны иметь дату проверки. Секреты живут в существующем Secret Store, не в spec или audit pack.

Для независимого council нужно не менее двух реально раздельных reviewer contexts. Для рискованных изменений предпочтительны разные семейства/провайдеры, но сам факт разных названий не доказывает независимость. Если доступен только один — `SINGLE_REVIEWER`, не имитация совета.

Первый раунд слепой: аудиторы получают один и тот же разрешённый пакет или явно записанные role-specific subsets, но не ответы друг друга. Первый red-team видит требования и границы, не решение автора patch. После фиксации собственных выводов разрешается перекрёстная проверка.

Автор исправления не может быть его единственным verifier или approval authority. Adjudicator составляет карту доказательств; голосование и самооценка уверенности не заменяют воспроизведение, регрессии и обязательные safety gates.

Каждому actor отдельный session_id/worktree; один интегратор публикует код в canonical. Изолированные кандидаты не являются параллельными финальными продуктами. UI и GPU имеют одного владельца на время теста; никакого общего Git index и переключения чужой ветки.

## 4. Audit pack и защита данных до внешнего вызова

Пакет собирается локально. Содержит минимально необходимое: спецификацию задачи, relevant diff, краткую цепочку tool actions, post-state, ошибки, воспроизводящий fixture, измерения и ссылки на обезличенные артефакты. Весь репозиторий и весь журнал не пересылаются на каждый запрос.

Привязка пакета: `audit_id`, `schema_version`, `source_sha`, `artifact_sha256`, `config_fingerprint`, `student_model_id/revision`, `runtime_version`, `task_ids`, `time_range`, `evidence_manifest`, `privacy_class`, `redaction_report`, `export_authorization_id`, `permitted_uses`. Хэш экспортируемого пакета вычисляется ПОСЛЕ очистки. Не экспортировать секреты, даже в виде удобных для перебора хэшей.

Политика:

- `LOCAL_ONLY` никогда не экспортируется. Если воспроизводимый синтетический пример разрешён отдельно, наружу идёт только он, без исходного личного содержимого.
- Private/неразмеченные данные по умолчанию остаются локально. Требуется точное разрешение на допустимый обезличенный subset и конкретный provider; очистка не является автоматическим согласием на передачу.
- PUBLIC и SYNTHETIC также проходят secret scan, проверку артефактов и применимость разрешения. Скриншоты проверяются отдельно: одних regex по тексту недостаточно.
- Cookies, authorization headers, токены, пароли, raw browser profile, личные документы и сторонние персональные данные исключаются. Неразрешимая неоднозначность -> `EXPORT_BLOCKED`.
- Контент страниц, файлов и teacher response — untrusted data. Он не может расширить scope, бюджет, доступ к секретам или изменить политику вывода.

Доступ к коду не означает доступ к машине, её localhost или реальному desktop. Cloud-аудитор без этих инструментов публикует code/harness findings, а не owner-hardware PASS. Нужный runtime test передаётся разрешённому локальному исполнителю с явной границей ответственности.

## 5. Запуск аудитов, стоимость и отказоустойчивость

Планируемые триггеры: повторяющиеся подтверждённые ошибки; release candidate; значимая смена модели/runtime; деградация метрик; инициатива владельца; заданное владельцем расписание. Никакого расписания этим commit не создаётся.

Использовать существующие queue, Gateway, budget governor и circuit breaker. Один audit key связывает source/config/evidence digest, роль и версию evaluator. Повтор события после crash не порождает повторный совет или лишние API-вызовы без reconciliation.

До внешнего вызова обязательны конкретные лимиты: общая стоимость, стоимость запуска, токены, время, число reviewers/retries, квота файлов/изображений, параллелизм и cooldown. Незаданный денежный лимит блокирует платный запуск. Неизвестная цена не считается нулём. Резервирование бюджета должно учитывать параллельные calls.

Rate limit, 401/403, недоступность teacher, разрыв stream и частичный ответ имеют явные состояния. Ограниченные retries; не обходить ограничения и не менять провайдера молча. Не тратить повторно бюджет на uncertain outcome без проверки provider/request ledger. При отсутствии внешнего teacher локальная работа продолжается, audit получает `BLOCKED`/`INSUFFICIENT_EVIDENCE`, не fake PASS.

Стоимость записывать по фактическому usage, отдельно от оценок. Повторно использовать разрешённый неизменённый контекст; не обещать экономию без замера. Audit/обучение не вытесняют активное поручение владельца из RAM/GPU. На целевом 128 GB компьютере concurrency и residency проверяются измерением.

## 6. Контракт находки и исправления

Предлагаемый logical FindingRecord, который нужно сопоставить с существующими схемами, а не заводить дублирующий registry:

`finding_id, audit_id, reviewer_id, category, severity, claim, source_refs, reproduction, expected, observed, evidence_refs, suggested_fix, regression_required, status, adjudication_reason`.

Жизнь находки:

`PROPOSED -> TRIAGED -> REPRODUCED / NOT_REPRODUCED / EXPECTED_BEHAVIOR / INSUFFICIENT_EVIDENCE -> PATCH_CANDIDATE -> VERIFIED_FIXED`.

Старые выводы не стирать; correction содержит ссылку на прежний вывод. Разные API-контракты, data directories или SHA не сводить в один «противоречивый» результат. Например, пустой список из неверного фильтра не доказывает удаление данных; сначала проверяются семантика и storage.

Confirmed defect получает минимальную regression перед fix; уже воспроизведённую находку не нужно заново искать общим аудитом. Patch от учителя проходит тот же review, что код от локальной модели. Нельзя просто изменить критерий success или тест ради зелёного цвета.

## 7. Учитель -> локальный ученик -> проверенный навык

Разделять пять исходов: `STUDENT_UNASSISTED_PASS`, `STUDENT_COACHED_PASS`, `TEACHER_PATCH`, `FAIL`, `NOT_RUN`. Успех teacher не приписывается student.

Цикл одного эпизода:

1. Локальный Bossman получает задачу без подсказки, выполняет её через штатные tools; фиксируются попытка и реальный результат.
2. Учитель получает разрешённый ProblemBundle и объясняет конкретную ошибку кратко, с проверяемой коррекцией. Не требуется и не сохраняется скрытый chain-of-thought.
3. Student повторяет самостоятельно. Число попыток ограничено. Когда учитель вынужден дать готовый patch, это явно отмечается.
4. Исполняемый verifier проверяет diff, тесты и post-state. Уверенный текст не доказательство.
5. В существующую память записывается обобщённый lesson candidate: когда применять, шаги, ограничения, отрицательный пример, доказательства, источник, версии, срок актуальности и степень помощи.
6. После restart новая похожая задача должна извлечь и использовать навык штатным путём. Нельзя подкладывать готовое решение в prompt и называть это retrieval.
7. Только успешная проверка переноса и требуемое approval позволяют promotion.

Предлагаемые поля EpisodeRecord: `episode_id`, `project_scope`, `task_class`, `student_model/revision`, `teacher_model/revision`, `source_sha`, `config_hash`, `attempts`, `observable_error`, `correction`, `assistance_level`, `tool_events`, `verifier_evidence`, `lesson_id`, `privacy_class`, `allowed_training_uses`, `outcome`.

Learning Ledger хранит переходы, а не только последний статус:

`FAILED -> VERIFIED_FAILURE -> TEACHER_CORRECTION -> STUDENT_RETRY -> VERIFIED_SUCCESS -> LESSON_CANDIDATE -> HOLDOUT_SUCCESS -> AWAITING_OWNER_APPROVAL -> PROMOTED_SKILL`.

Ветви отказа: `REJECTED`, `QUARANTINED`, `STALE`, `NO_MEASURED_GAIN`. Дубликаты, противоречащие уроки и советы «отключить проверку» не продвигаются автоматически. Skill не обладает полномочиями: действующая policy всегда выше памяти. После смены API/Windows/model релевантные навыки пересдают regression/holdout, деградировавшие карантинируются и имеют откат.

## 8. Три разных уровня обучения

**Память и skills.** Быстрое переиспользование проверенных стратегий с bounded retrieval. Метка `WEIGHTS_UNCHANGED`. Файл Markdown в Git не доказывает память: нужен save -> restart -> retrieval -> новая задача.

**Curriculum и датасет.** Учитель группирует реальные слабости и генерирует разнообразные задачи, не копии с заменёнными именами. Автоматический oracle проверяет задачи там, где это возможно; teacher-generated «правильный ответ» тоже может быть ошибочным. Provenance, дедупликация, разрешённое использование и train/validation/holdout split обязательны. Частая ошибка получает больше практики, но не вытесняет другие способности.

**Изменение весов.** Поздний отдельный эксперимент LoRA/QLoRA, не часть текущего документационного push. Нужны явное разрешение владельца, пригодность runtime/памяти, проверенные права на датасет и teacher outputs, воспроизводимый training run, base-model hash и adapter hash. Нельзя предполагать, что успешный inference на 8060S гарантирует возможность обучения выбранной модели. Если teacher/provider terms не позволяют желаемое использование — training block, не обход доступа/массовая выгрузка. Только разрешённые внешние ответы и наблюдаемые результаты, не извлечение скрытых reasoning traces.

Adapter-кандидат проверяется против исходной модели и текущих skills. Обязательны forgetting/general-capability tests, safety/tools/JSON/vision, latency и ресурсы. Улучшение на тренировочной задаче не даёт права заменить MAIN. Нет прироста — отклонить, не объявлять обучение успешным.

## 9. Evolution Arena и честное сравнение

Для оценки skills держать неизменными модель/runtime, source SHA, инструменты, permissions, task fixtures и бюджеты; отличаться должен только проверяемый компонент. Для code/model-кандидатов записывать неизбежные различия. Teacher suggestions не видят private holdout и его answers. Задачи, использованные для настройки, не остаются holdout; нужен обновляемый закрытый набор и финальная одноразовая проверка после выбора кандидата.

Первые критерии и допустимые регрессии фиксируются ДО запуска. Не подбирать пороги после получения результата. Случайные seed, повторения, task-class coverage и размер выборки публикуются. Небольшая выборка даёт предварительный результат; отсутствие наблюдавшегося P0 не доказывает отсутствие неизвестных уязвимостей.

Метрики: verified pass@1; coached/unassisted отдельно; вмешательства владельца и учителя; ошибки выбора tools/аргументов; время до проверенного результата; TTFT и decode отдельно; cost/usage; RAM/GPU; сохранность после restart; false success; безопасность; перенос на новые задачи. У каждого процента есть числитель/знаменатель и scope. При достаточных данных публикуются интервалы неопределённости; неизвестное не отображается нулём или придуманным ростом.

Число учебных эпизодов, consensus моделей, длинный ответ и успешный API preview не заменяют end-to-end outcome. Для media раздельны generation provenance, целостность файла и визуальное качество. Проверка 4K-контекста не сертифицирует 32K; direct-model benchmark не сертифицирует Bossman tool loop.

Promotion требует обязательных safety/release gates, независимого review и улучшения выбранной цели без недопустимой регрессии по другим осям. Голосование не может перекрыть подтверждённый P0/P1. При смешанном результате — явный trade-off владельцу, не автоматическое обновление.

## 10. Code improvement и обновление моделей

Если урока недостаточно, Bossman создаёт инженерную миссию и изолированный patch candidate. Author, reviewer и red-team разделены. Тесты, permission/budget policy и ground truth не меняются кандидатом ради собственной победы.

Новые локальные модели проходят discovery по первичным источникам, проверку лицензии/runtime, download budget, role-specific arena и сравнение с действующим MAIN/FAST. Новизна не является причиной replacement. Совместимость inference, image/video и training проверяется отдельно; рекомендуемый cloud teacher не становится автоматически локальным default.

Тот же протокол promotion для code, skill, routing и adapter:

`candidate hashes -> evidence -> independent review -> owner-visible proposal -> explicit owner approval bound to these hashes -> controlled deployment -> monitoring -> rollback`.

Для code release нужны exact-SHA CI, соответствующий Windows artifact и нужная owner-приёмка. Для skill/config/model дополнительно фиксируется snapshot обучающего состояния: один source SHA не описывает изменившуюся память. Поздние docs-only commits не наследуют старой сертификации и не требуют перемещения уже выпущенного stable tag.

Откат включает зависимые skill versions, config, adapter, миграции и caches, а не только git checkout. При отзыве опасного урока новые и активные задачи должны повторно проверить право его использования. Append-only audit не уничтожается; чувствительные payload живут отдельно с политикой удаления и обезличенными tombstones.

## 11. EVO Lab: что увидит владелец

Планируемый раздел существующего Command Center, не отдельное приложение:

- какая stable/candidate версия и какая модель сейчас реально работают;
- кто и когда проводил аудит, что проверено, где нет инструментов или evidence;
- список подтверждённых, отклонённых и спорных findings;
- чему student научился, уровень помощи, доказательство применения после restart;
- сравнение до/после на новых задачах, объём выборки и стоимость;
- ожидающие решения об обновлении, карантин и возможность отката.

Действия: «Посмотреть урок», «Запустить разрешённый экзамен», «Сравнить», «Отклонить», «Предложить обновление», «Подтвердить конкретный кандидат», «Откатить». Одобрение проверяется сервером; агент не может сам нажать себе approval через Computer Use.

В пустой установке показывать «Нет измерений / Не настроено». Любые демонстрационные значения явно synthetic; никаких придуманных 89% или тысяч якобы выполненных задач.

## 12. Качество самих frontier-аудиторов

Per role/model revision хранить число проверенных находок, confirmed/false-positive/unresolved, уникальный вклад, regression-test quality, стоимость и время. Сравнивать на общих пакетах с сопоставимым scope: raw count не рейтинг интеллекта. Unresolved не считать ложной находкой; один root cause не размножать для улучшения рейтинга.

Только после накопления данных советовать назначение reviewer на роль. Разные models могут ошибаться одинаково; большинства голосов недостаточно. Sampling и спорные случаи проверяются независимым арбитром/тестами. Обновление teacher model сбрасывает неподтверждённые предположения о его качестве; модель не получает постоянный статус «лучший учитель».

| FC-07 | Poisoned/cross-project/stale lesson не меняет полномочия и не продвигается. |
| FC-08 | Budget race, timeout, частичный ответ и crash не вызывают неограниченные calls или ложный completion. |
| FC-09 | Учитель недоступен: локальная работа безопасно продолжается, аудит честно blocked. |
| FC-10 | Изолированный code/skill/model candidate не меняет stable и не самоодобряет deployment. |
| FC-11 | Approval привязан к exact hashes; изменение candidate инвалидирует старое approval; rollback возвращает согласованное состояние. |
| FC-12 | Показатели EVO Lab соответствуют evidence; отсутствие данных не превращается в нулевые ошибки или рост. |
| FC-13 | При опциональном weight training проверены права, compatibility, dataset/adapter provenance, forgetting и отдельный holdout. |
| FC-14 | Полный живой цикл на Windows владельца отдельно от CI/mocks; code release имеет свой exact-SHA artifact. |

Для каждого теста хранить setup, expected/actual, evidence refs и verdict. Общие статусы: `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN`, `OWNER_REQUIRED`, `INSUFFICIENT_EVIDENCE`. При code/skill regression — карантин и новый кандидат; не переименовывать FAIL в ограничение владельца.

## 14. Передача следующему инженеру

Не начинать реализацию совета, пока текущая 1.0 не прошла требуемую приёмку. После этого сопоставить логические контракты с уже существующими Gateway/queue/learning/approval/evaluation modules, реализовать FC-M1, затем FC-M2, и опубликовать действительные результаты FC-01…FC-14 по достигнутому scope. Не расширять release branch альтернативным ядром.

Итог каждого цикла для владельца: что найдено; что исправлено; что Bossman сделал сам; чему научился; где потребовался teacher; что доказано на новых задачах; стоимость; риски; точные candidate/stable references; требуется ли решение. Если измеримого выигрыша нет — написать `NO_MEASURED_GAIN` и сохранить baseline.
