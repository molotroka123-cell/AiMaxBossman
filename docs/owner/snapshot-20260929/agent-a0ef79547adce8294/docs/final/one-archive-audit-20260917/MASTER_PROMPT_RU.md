## 2. Сначала исправь OA-01: ложный PASS вечерней диагностики

Файл: `tools/bundle_evening_test.py`.

На проверенном исходнике воспроизведено локально, с синтетическими subprocess-результатами:

- обязательный `bossman_doctor.py` отсутствует → `doctor=NOT_SHIPPED`, итог PASS;
- doctor возвращает не-JSON → `doctor=UNREADABLE`, итог PASS;
- doctor завершился с кодом 9 и JSON `{}` → `doctor=OK`, итог PASS;
- doctor пропущен через `--skip-doctor` → итог всё равно PASS.

Проблема: решение учитывает список `blocking`, но не валидность и полноту самой проверки. Это P1 доверия к диагностике, не утверждение о поломке всех пользовательских функций.

Нужно:

1. Проверять exit code, тип/схему результата, обязательные проверки, допустимые статусы. Пустой объект не равен успешно выполненной диагностике.
2. Отсутствующий обязательный файл, повреждённый ответ, таймаут или авария проверки → FAIL, структурированная причина, ненулевой exit code. Исключения не должны оставлять старый успешный результат.
3. Настоящая отсутствующая модель/credential → OWNER_REQUIRED с конкретной причиной. Не переводить повреждённую поставку в OWNER_REQUIRED.
4. Диагностический `--skip-doctor` разрешён, но общий результат PARTIAL/NOT_RUN, а не полный PASS; агрегатор его не принимает как полную приёмку.
5. Отдельный run_id и свежий каталог результатов на каждый запуск; привязка к source SHA и payload identity. Старый JSON предыдущего запуска не может удовлетворить текущий запуск.
6. Согласовать коды возврата и текстовые статусы: ошибка комплектации не должна возвращать код, означающий «нужен владелец».
7. Добавить положительные и отрицательные контроли: валидная диагностика проходит; отсутствие/битый JSON/ненулевой код/неверная схема/пропуск/устаревшая улика отвергаются. Проверить это также на разложенном архиве, не только в source tree.

Не исправляй это ещё одним косметическим предупреждением при сохранении PASS.

## 3. Исправь OA-02: финальный freeze-валидатор слабее реальной приёмки

Файл: `tools/astra6_freeze.py`.

На точном исходнике воспроизведено:

- итоговый агрегатор принимает 13 успешных JUnit cases, хотя текущий installed workflow требует 40;
- шесть одинаковых строк одной задачи одной модели удовлетворяют проверке «две модели × три задачи»;
- JUnit с явным чужим `source_sha` принимается: SHA этого отчёта не проверяется.

Это независимые негативные проверки самого агрегатора. Они НЕ означают, что реальные 40 Windows-тестов сфальсифицированы: тот прогон действительно выполнил 40 сценариев, и его предшествующий шаг проверяет количество. Нужно убрать расхождение контрактов, а не объявить все старые улики неверными.

Требования:

- Один версионированный реестр обязательных acceptance cases для workflow, JUnit-проверки и агрегатора. Для текущего профиля минимум 40; проверять не только число, но и присутствие нужных сценариев. Нельзя добрать количество повторениями.
- Обязательные тесты не могут быть skipped/cancelled/не выполнены. Отказ матрицы не компенсируется успехом другой платформы.
- Модельные результаты должны покрывать точное множество `(model, case)`: две выбранные различные модели и три разных предусмотренных случая у каждой. Дубликаты, пропущенный случай, чужая модель, неизвестный случай — отказ. Учитывай, что task_id в двух изолированных БД может совпадать: связывай его с model/run/session, а не требуй глобальной уникальности чисел.
- Связать JUnit, UI, live-result и bundle-result с source SHA, хешем payload/архива и идентичностью проверяющего harness/run. Не просто вписать ожидаемый SHA в любую старую улику.
- Проверить согласованность `status` с содержимым отчёта; не принимать «PASS» при обязательных отказах/неполном наборе.
- Чётко разделить запись отчёта и разрешение публикации. Текущий main агрегатора намеренно возвращает 0 даже для BLOCKED: это допустимо для REPORT_WRITTEN, но НЕ для RELEASE_READY. Сделай отдельный строгий publish gate или явный строгий режим. Нельзя выпускать по одному зелёному значку job.
- Успешная smoke-проверка не означает проверку локального интеллекта и целевого GPU. Сохрани независимые поля статуса.
- Полный негативный набор: 13 вместо 40; 40 повторений; чужой SHA; подмена hash; шесть дублей одного model/case; один отсутствующий обязательный тест; stale/malformed/duplicate evidence; реальный корректный набор. Первый обязан краснеть, последний обязан проходить.

## 4. Сделай сборку фиксированной: один SHA не должен тянуть случайные зависимости

Сейчас `.github/workflows/windows-bundle.yml` использует `FFmpeg-Builds/releases/download/latest/...`, а `install_packages()` делает обычный `pip install --upgrade --target ...` без release-lock с хешами. Версия embedded Python берётся из текущего build-интерпретатора. Записать хеш после скачивания полезно, но это не закрепление входных данных ДО сборки.

Доработай существующий builder, не пиши новый:

- Закрепи точный CPython patch, совместимые wheels, Playwright и Chromium revision, media build, существенные build tools и источники по версии/хешу.
- Для внешних бинарников сначала проверь ожидаемый digest из доверенного lock, потом распаковывай/запускай. Сохраняй исходный URL и лицензионные материалы. Не заменяй работающий FFmpeg без реального x264/AAC encode/decode-теста.
- Подготовь wheelhouse: все транзитивные runtime-зависимости закреплены. Установка в bundle из локального wheelhouse с `--no-index`, проверкой hash и без неконтролируемого dependency resolution. Локальные Bossman wheels собирай отдельно из чистого точного source snapshot и устанавливай по проверенным хешам с `--no-deps`, когда зависимости уже разрешены.
- Не включай лишние dev/test-пакеты в постоянный runtime, но не удаляй нужные owner diagnostics.
- После формирования runtime проверяй импорты/зависимости именно embedded Python, а не Python машины сборки.
- Два clean build на одинаковых locks должны иметь одинаковый состав и версии файлов. Не заявляй бит-в-бит воспроизводимость, если остаются временные метки/pyc/metadata; перечисли такие различия и нормализуй их там, где безопасно.
- Для выпуска продвигай ОДИН проверенный ZIP байт-в-байт. Повторная сборка из того же source SHA не получает автоматически улики старого ZIP.

## 5. Замкни поставку: владелец не должен клонировать репозиторий ради приёмки

`INSTALL.md` сейчас прямо требует clone для полной target-hardware и intelligence-приёмки. `SUPPORT_SCRIPTS` не содержит `live_openrouter_owner.py`, а CI запускает его из checkout с embedded Python. Это действительно проверяет установленное приложение, но сам сценарий не поставляется владельцу этим способом.

Приведи обещание «один архив» к факту:

- `Start-Bossman.cmd`, `Evening-Test.cmd`, `Machine-Report.cmd` остаются существующими точками входа. Не создавай конкурирующие launcher-версии.
- Обязательное приложение, runtime, Chromium, FFmpeg/ffprobe, shipped apps, статические UI/assets, иконки, нужные библиотеки и standalone diagnostics — внутри ZIP.
- Стандартный запуск приложения и локальных редакторов после распаковки не должен вызывать pip/npm/git/winget или скачивать обязательные компоненты. Для закрытого профиля `required_downloads` пуст.
- Нужные owner runners и ресурсы перенеси в установленный package или `app-support`, используя имеющиеся реализации. В режиме downloaded archive получай identity из проверенного manifest/runtime, а не из вымышленного Git HEAD. Проверки не должны зависеть от cwd и `scripts/` в чужом клоне.
- Не вкладывай весь dev-repository или тысячи тестов только ради нескольких проверок. Поставь минимальный самостоятельный runner плюс малые публичные fixtures.
- Ключи, аккаунты, приватные файлы и большие веса НЕ кладутся в ZIP. Модели выбирает владелец; отсутствие весов не маскируется как работающая локальная LLM.
- Для каждого из восьми уже принятых OSS-направлений покажи отдельно BUNDLED / CONFIGURED / MODEL_REQUIRED / EXTERNAL_SERVICE_REQUIRED / VERIFIED. «Настроено» не значит «задача выполнена».
- Если локальный inference engine объявлен частью обязательного профиля, его redistributable бинарник и нужные DLL тоже должны поставляться. Если это отдельная опциональная служба, назови границу в UI и манифесте. Не называй комплект полностью автономным локальным ИИ без весов и сервера.
- Не устанавливай автоматически все ComfyUI/SearXNG/модельные сервисы; они не должны мешать запуску основного приложения или постоянно занимать RAM.
- Доктор предлагает понятное действие в UI; владелец не должен разбираться в консольных командах для базового запуска.

## 7. Настоящие модели: smoke, agent task и retention — разные вещи

Проведи имеющийся OpenRouter smoke через установленный архив при наличии предоставленного безопасно ключа. Только явно бесплатные маршруты, ограничения попыток/токенов, без платного fallback. Не выводи ключ в logs/evidence. Нет credentials → OWNER_REQUIRED, но остальные задачи этого master-run продолжай.

Проверь submit helper: таймаут ожидания response не доказывает отсутствие POST. Не повторяй отправку неоднозначной задачи без request identity/reconciliation; не создавай незаметные дубликаты. Это требование проверки, а не заявленный доказанный runtime-баг.

Дополнительно в уже существующем owner_acceptance проверь одну настоящую агентную задачу: выбранная модель → разрешённый инструмент в отдельной тестовой папке → наблюдаемый результат → независимое чтение/проверка → рестарт → сохранение. Текстовая арифметика не заменяет этот путь. Реальные файловые изменения делай только в sandbox fixtures, не в документах владельца. Никаких реальных сделок/публикаций/писем в приёмке.

Отдельно Intelligence Preservation:

- Сначала пройди preflight текущего `tools/intelligence_preservation_run.py` и проверь реальные требования gate.

## 10. Доставка: одна ссылка на один ZIP приложения

Сейчас GitHub Actions выдаёт внешний ZIP-артефакт, внутри которого находится ZIP приложения. `INSTALL.md` просит распаковать дважды; опубликованного GitHub Release при аудите не было.

После разрешённых проверок:

1. Зафиксируй один source SHA и проверенный payload. Разделяй runtime SHA, harness SHA, report SHA и artifact digest.
2. Загрузи в release именно внутренний проверенный `BOSSMAN-Windows-x64-<SHA>.zip`, а не Actions wrapper и не GitHub Source code.zip. Пользователю нужен один application ZIP с одной папкой, без выбора wheels.
3. Посчитай SHA-256 ФИНАЛЬНОГО application ZIP. Digest Actions wrapper — другое значение; не путать их.
4. Перед публикацией повторно скачай будущий release asset и проверь именно его hash/size/состав. Не пересобирай и не перезапаковывай после acceptance.
5. Внутри ZIP: build identity, inventory, лицензии и краткий START_HERE_RU с существующими launcher-командами. Финальные свидетельства приёмки и hash всего ZIP держи снаружи, привязанными к нему. Не пытайся записать внутрь ZIP его собственный hash или финальный отчёт после теста: это изменит проверяемые байты.
6. Обнови PR/INSTALL/CURRENT_STATE; исторические V6_FREEZE_REPORT и старые кандидаты пометь историей. Не переписывай историю их доказательств.
7. Не объявляй метку «Астра 6» Authenticode-подписью. Подпись отдельна; не выключать SmartScreen/Defender ради запуска.
8. При наличии разрешения публикации оформи неизменяемый versioned release/RC. Если запись запрещена, сохрани проверенные bytes и точное описание одной необходимой операции владельца. Не обходи ограничения permissions и не обещай уже опубликованный release.

До успешного live gate допускается выдать RC с OWNER_REQUIRED, но не FROZEN. Наличие внешних блокеров не повод удерживать от владельца уже пригодный для теста архив. Не создавай альтернативный упрощённый продукт ради более удобного статуса.

## 11. Итог, после которого работа закончена

Отчёт короткий, фактический:

```

APP_ZIP_NAME / APP_ZIP_SHA256 / SIZE / DIRECT_URL
CORE_ARCHIVE: PASS | FAIL
INSTALLED_WINDOWS: PASS | FAIL + cases/count + CI run
LIVE_MODEL_SMOKE: PASS | FAIL | OWNER_REQUIRED
REAL_AGENT_TASK: PASS | FAIL | OWNER_REQUIRED
TARGET_HARDWARE: PASS | FAIL | OWNER_REQUIRED
LOCAL_INTELLIGENCE: PASS | FAIL | INSUFFICIENT_EVIDENCE
OA-01 / OA-02 / OA-03 / OA-04: FIXED | BLOCKED + proof
BL-057: preserve closure; BL-063: actual disposition
REMAINING_P0 / REMAINING_P1 / ACCEPTED_LIMITATIONS
ROLLBACK: exact package + compatible data-backup procedure
RELEASE_STATE: RC_OWNER_REQUIRED | FROZEN_WITH_EXPLICIT_SCOPE | BLOCKED
```

Цель — закрыть подтверждённые репозиторные дефекты и выдать один package. Не закрывай запись одним отчётом без изменения кода и регрессии. Не увеличивай количество проектов, агентов, экранов или зависимостей. Не дублируй существующие registry/gateway/policy/memory/sidecar.

Порядок: OA-01/OA-02 → locks/standalone packaging → BL-063 validation → clean Windows ZIP → live model при наличии доступа → release. Корпус retention можно готовить отдельно без задержки репозиторных исправлений; он не становится PASS от подготовки.
