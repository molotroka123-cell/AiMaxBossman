# Telegram Companion V8 — реализация, запуск и границы приёмки

Статус этой поставки: код и offline-контракты проверены в Linux/Python 3.13.5. **Живой Telegram, локальная модель, облачный Claude, Windows GUI и новый application ZIP не приняты этим отчётом.** Бот выключен до явного запуска. Ни токены, ни сообщения реальным людям в этом проходе не использовались.

## Что сделано

`bcc.telegram_companion` — отдельный процесс, а не фоновая задача окна Bossman. Можно продолжать беседу и проверку связи, когда приложение Bossman закрыто. Основная модель — уже установленный локальный OpenAI-compatible сервер. Модель выдаёт только текст: она не получает shell, desktop, произвольные файловые инструменты, токен Command Center или метод утверждения approvals.

Обычный текст → разговор с короткой отдельной памятью пользователя. `/search` → явный запрос существующему локальному SearXNG. `/task` → показ полного поручения → `/confirm` с одноразовым кодом → задача заданному исполнителю в существующем TaskEngine. `/result ID` выдаёт только свою задачу. Состояния queued, blocked и waiting approval не называются завершением. Уведомления о завершении также ограничены собственными задачами чата.

`/status` работает независимо от занятой/сломанной LLM и проверяет доступность процесса, не все функции компьютера. `/watch on` включает сообщения владельцу о двух подряд неуспешных проверках и восстановлении связи. `/lock` запрещает НОВЫЕ поручения; он не выдаётся за остановку уже выполняющейся задачи. Разблокировка только локально. `/forget` удаляет локальную разговорную память и отключает облачное согласие, но не удаляет Telegram-историю и выполненные задачи Bossman.

Владелец и гость привязываются к точным числовым user_id+chat_id в личных чатах. Группы, каналы, forwarded-команды, посторонние пользователи и сообщения ботов не авторизуются. Гость не видит мониторинг владельца. Исполнители двух людей не могут иметь одинаковый ID; локальный владелец обязан заранее ограничить их права и данные в Bossman. Мост не исправляет слишком широкие права уже выбранного агента и не обходит проверки эффектов ядра.

## Облачный резерв

Используется точная модель `anthropic/claude-*` через OpenRouter, а не приложение/подписка Claude. Для резерва локально задаются ключ и пределы USD/запрос и USD/день. По умолчанию бюджет 0 и резерв выключен. Каждый пользователь отдельно выполняет `/cloud on`; при сбое локальной модели новые сообщения этого чата переходят в облако. Ответ помечен как облачный. `/cloud off` действует и на ожидающие запросы, а изменение локальной облачной политики отзывает старое разрешение до перезапуска.

В облако передаётся только текущее человеческое сообщение после проверки секретов. История локального диалога, файлы, результаты задач и внутренний статус НЕ подмешиваются. Это ограничение конфиденциальности, а не незаметная потеря памяти. Telegram сам по себе является внешним каналом: не отправляйте туда чувствительные документы и пароли.

Тариф точной модели запрашивается из каталога OpenRouter ДО POST генерации; неизвестные/неподдерживаемые тарифы отвергаются. Используется существующий Cost Governor с отдельным долговечным ledger: консервативная оценка списывается до отправки и не возвращается после неоднозначного сетевого отказа. Повтор генерации автоматически не выполняется. Если провайдер заявляет цену выше оценки, резерв блокируется до локального разбора. Это локальный предохранитель, не гарантия расчётов стороннего биллинга: дополнительно ограничьте кредит API-ключа у провайдера.

## Надёжность и ограничения

Входящие события сохраняются до подтверждения offset; дубликаты не создают повторные задачи. Одновременный poller на одном каталоге блокируется ОС. Обнаруженный webhook не удаляется: используйте отдельного Companion-бота, чтобы не перехватывать существующий мост approvals. В процессе восстановления неоднозначная отправка/делегирование не повторяется; запись остаётся `interrupted_unknown`/`dispatch_unknown`/`delivery_unknown`.

Очереди и история ограничены: до 8 участников, две полосы на человека (чат и управление), до четырёх ожидающих сообщений на полосу; последние четыре пары разговора, максимум 8000 символов контекста; не более одного локального инференса одновременно. При переполнении новое сообщение не выполняется; нужна повторная отправка после освобождения очереди. Сбор и сеть не запускают бесконечные активные опросы. Long polling 25 секунд, мониторинг по умолчанию 60 секунд. Диск состояния отдельный от БД Bossman; содержимое бесед и настроек зашифровано Vault. Шифрование с ключом на том же ПК не защищает от компрометации учётной записи ОС.

Задачи связаны не только по ID, но и по агенту, prompt и created_at. Повторное использование числового ID после смены базы не раскрывает чужой результат. Проверка разрешений повторяется перед передачей поручения и перед отправкой Telegram, включая повтор после явного 429.

**Если выключен весь ПК, уснул Windows, пропал интернет или умер сам процесс моста, этот локальный процесс не сможет ответить.** Облачная модель не заменяет работающий Telegram-транспорт. Для связи при полном отключении ПК нужен отдельно разрешённый always-on relay/VPS и heartbeat. В этой поставке VPS, удалённые порты, службы автозапуска, VPN, драйверы и firewall не устанавливаются и не меняются.

Голосовые сообщения, фото/файловые вложения, автоматические напоминания, автоматическое выполнение действий из свободного текста, универсальный read-all-доступ к внутренним данным и cloud-relay пока не реализованы. Не выдавать их за готовую возможность.

## Подключение на компьютере

Новый модуль входит в wheel Command Center благодаря существующему `bcc*` package discovery. Добавлена команда `bossman-telegram`. Для relocatable Windows-архива надёжный путь запуска — его ВСТРОЕННЫЙ Python, не системный Python и не чужой старый `.exe` entrypoint:

```powershell
# Выполнять из папки нового распакованного приложения, не из старого кандидата:
.\runtime\python.exe -I -m bcc.telegram_companion --setup
.\runtime\python.exe -I -m bcc.telegram_companion --diagnose
.\runtime\python.exe -I -m bcc.telegram_companion
```

`--setup` открывает локальную браузерную форму: токены вводятся в password-поля, пользовательские ID, модель, исполнитель, гость и optional облако — обычные поля. Мастер не пересылает их в сеть и не устанавливает модели. Он слушает только 127.0.0.1, работает до 10 минут, проверяет Host+Origin+одноразовый секрет запроса, запрещает встраивание и внешние скрипты; секрет не находится в query или логах. Закройте окно после сохранения. `--setup-console` — запасной интерактивный путь со скрытым вводом токенов, не основной GUI.

Требования: отдельный BotFather-бот; известный собственный числовой user ID; точный ID загруженной локальной модели; исходящий HTTPS Telegram. Гость сам открывает бота и нажимает Start после локального внесения своего ID. Бот не может просто начать личную переписку с произвольным человеком.

Настройки: `%LOCALAPPDATA%\Bossman\telegram-companion\config.json`; секреты — `credentials.enc`, отдельный Vault. Существующий `.env` старого уведомительного бота не сканируется и не переиспользуется молча. Секретные переменные `TG_COMPANION_BOT_TOKEN`, `TG_COMPANION_CORE_TOKEN`, `TG_COMPANION_LOCAL_TOKEN`, `TG_COMPANION_CLOUD_TOKEN`, `TG_COMPANION_PROXY` — только необязательный путь для администратора. Не указывать значения в командной строке и не коммитить.

Для делегирования нужен отдельный агент, созданный через UI Bossman с заданными инструментами и разрешённой папкой. Core API здесь использует существующий `X-BCC-Token`; когда legacy-token режим сознательно отключён, делегирование честно откажет. Не включайте его автоматически ради теста: отдельный scoped credential/session endpoint — незакрытая работа для такой конфигурации. Беседа и проверка публичной доступности не требуют токена Core.

Настройка адресов/участников/бюджетов сохраняется локально. Изменённые endpoints/токены и добавленные пользователи требуют остановки/перезапуска моста; удаление пользователя и отзыв облачного разрешения проверяются на текущих данных. Форма первой установки не перезаписывает существующий профиль. При восстановлении не удалять единственную копию Vault и зашифрованной истории.

В итоговую root-панель запуска Windows ещё надо добавить проверенную кнопку/ярлык Telegram. Наличие пакета в wheel и CLI не является проверкой этого удобства. Включать модуль автоматически при каждом старте Bossman нельзя.

## Живая приёмка от лица владельца

1. Открыть форму, ввести тестового бота/свой ID, проверить диагностику. `getMe` подтверждает только авторизацию Bot API, не «100% готовность».
2. Из личного чата отправить `/start`, затем обычный вопрос. Увидеть реальный ответ именно локальной модели.
3. `/task` с безопасной тестовой папкой → увидеть полный preview → `/confirm` → новый task ID → `/result` и независимое открытие файла на ПК. Не выполнять работу за Bossman вручную.
4. От гостя попробовать `/status` и ID чужой задачи: отказ без раскрытия. Затем проверить собственную задачу гостя у отдельного ограниченного исполнителя.
5. Остановить только локальный model-server: `/status` отвечает; без разрешения облака нет POST; с отдельно разрешёнными ключом/бюджетом/`/cloud on` — помеченный настоящий Claude-ответ. Вернуть локальную модель, проверить возврат после 45-секундного cooldown.
6. Остановить только приложение Bossman: мост остаётся в сети и не утверждает, что недоступная задача выполнена. Проверить `/watch on`, восстановить Bossman. Затем повторить после рестарта самого моста и проверить отсутствие двойного поручения.
7. Связать результат с точным source SHA и application ZIP hash; только после этого отмечать live Telegram и целевую Windows-приёмку PASS.

## Аудит старого транспорта

В `bossman-core/bossman/notifications/telegram_transport.py` HTTP 200 с повреждённым JSON возвращал выдуманный `{"ok":true}`; `ok:false` также не отклонялся. Исправлено: требуется настоящий объект `ok is True` с `result`. Цепочка сетевого исключения с URL, содержащим токен, наружу не передаётся. Старый маршрут уведомлений и callback approvals не заменён новым ботом.

## Воспроизведение offline-проверок

Command Center CI намеренно не устанавливает bossman-core в родительский процесс pytest. Новые тесты находятся в `command-center/tests/telegram_contracts/`; их локальный fixture временно добавляет реальные исходники core только на время одного теста и удаляет новые `bossman.*` импорты после него. Пропуски вместо отсутствующего core не используются. В готовом Windows-продукте нужны оба уже поставляемых wheel.

```sh
python -m pytest command-center/tests/telegram_contracts/test_companion.py
# В окружении core отдельно:
python -m pytest bossman-core/tests/test_telegram_transport_response_truth.py
```

Исходники для локального isolated-прогона взяты из package artifact `cc794b0662ec2e83eea10434942c058e2d2d0ab3`, а изменяемые исходные файлы сверены с актуальной рабочей веткой перед публикацией. Это не clean-install новых Windows-байтов.

Дополнительный прогон source-CI без установленного core в глобальном PYTHONPATH: 73 те же Companion-контракта + отдельный контроль отсутствия загрязнения sys.modules после fixture — **74/74 passed**. Это повторная проверка окружения, не 74 новых возможностей. Inline JavaScript формы прошёл `node --check`; все изменяемые Python-файлы разбираются AST.
