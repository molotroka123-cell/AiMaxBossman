# Локальный OpenCode — подготовка к роли владельца

Это подготовка ТЕСТИРУЮЩЕГО OpenCode, а не подмена Bossman. Основной прогон описан в `OPENCODE_OWNER_RUN_RU.md`. Дата проверки документации: 18.09.2026. Конкретная версия OpenCode, id локальной модели и GUI-driver владельца пока не установлены этим документом.

## 1. Разделить три компонента

OpenCode управляет приёмкой. Его локальная модель решает, куда нажать. Отдельный GUI-инструмент передаёт реальный экран/доступные элементы и выполняет мышь/клавиатуру. Наличие OpenCode и текстовой LLM само по себе не даёт доступа к экрану.

Bossman — тестируемый продукт со своей моделью, задачами, памятью и политиками. Когда сценарий просит Bossman создать файл, внешний OpenCode НЕ создаёт файл вместо него. Иначе получится проверка OpenCode, не Bossman.

Для тестов рабочего стола драйвер OpenCode должен продолжать работать после закрытия Bossman. Не делать его единственным клиентом внутреннего сервиса, который требуется перезапускать. Для браузерных сценариев допустим существующий разрешённый MCP с headed-браузером; он не заменяет native-проверки Проводника/Блокнота.

## 2. Снять инвентаризацию до конфигурации

Подготовитель фиксирует версию OpenCode, Windows build, путь точного application ZIP и его SHA-256, модель/id, backend/version, endpoint, quantization, context limit, поддержку tool calling и способ восприятия UI. Это setup-данные, не PASS продукта.

OpenCode имеет различные поколения конфигурации. В официальной документации v1 используются `provider`, `mcp.<name>`, `permission`; у v2 описаны `providers`, `mcp.servers` и массив `permissions`. Проверить именно установленную версию и её schema/help. Не вставлять пример v1 в v2, не перезаписывать существующий opencode.json и не включать tool permissions наугад. Сначала резервная копия локальной конфигурации.

## 3. Подключить существующую локальную модель

Использовать уже установленный и согласованный backend. Не выбирать модель только по названию и не объявлять текстовую модель зрячей. Для OpenAI-compatible endpoint фактический model id должен совпадать с тем, что отдаёт сервер; пустой каталог, маршрут cloud или имя без загруженных весов не считаются локальным запуском.

Пример структуры v1, ТОЛЬКО после проверки версии (не готовая конфигурация машины):

```json
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "bossman-owner-local": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Owner test driver — local",
      "options": {"baseURL": "http://127.0.0.1:8080/v1"},
      "models": {"REPLACE_WITH_ACTUAL_LOADED_MODEL_ID": {"name": "Actual local model"}}
    }
  }
}
```

Порт 8080 — пример, не автоматическая замена существующей настройки. Модель не выбирать, пока placeholder не заменён. Размеры контекста/вывода должны соответствовать реальной конфигурации backend, не рекламному максимуму. V2: использовать настройку провайдера через его текущую схему/интерфейс, не переименовывать ключи механически.

Все runtime-пакеты OpenCode и driver должны быть подготовлены заранее из зафиксированных источников; не запускать плавающий npx/uvx latest в день приёмки. Не отключать безопасность ради установки. Проверить, что локальный режим не вызывает скрытую облачную модель для основного ответа, компактизации или дополнительного анализа. Большую загрузку весов выполнять только после подтверждения объёма и свободного диска.

## 4. Подключить GUI-driver и ограничить инструменты

Переиспользовать уже проверенный Windows-MCP/desktop-adapter, если он реально доступен. Для тестового браузера — существующий разрешённый headed-путь. Записать источник, точную версию, способ запуска, перечень инструментов и ограниченную область действия. Не устанавливать случайный сервер с похожим названием.

Нужны возможности: screenshot/наблюдение, активное окно, click/double-click, type, hotkey, scroll, drag, диалог выбора файла. Accessibility/DOM допускается для поиска видимого элемента. Произвольные eval/script/PowerShell-команды внутри универсального инструмента должны иметь отдельное ограничение; разрешение на click не даёт разрешение на выполнение произвольного кода.

Если MCP упаковывает все возможности в один инструмент и нельзя отделить exec от мыши, не выдавать blanket allow. Оставить ask либо использовать заранее ограниченную обёртку. Имена инструментов берутся из фактической tools/list; не угадываются. Включать только необходимый набор, а не десятки коннекторов в контекст.

Политика роли owner: разрешены наблюдение и действия в тестовом Bossman, Проводнике тестовой папки и Блокноте; подтверждение требуется для секретов/платежей/внешнего эгресса/системных изменений. Изменение исходников и shell по умолчанию не являются средствами прохождения GUI-сценария. Чтение диагностики и repair — отдельная явно отмеченная фаза.

## 5. Обязательная калибровка драйвера, до теста продукта

Через видимый Пуск открыть Блокнот. Напечатать `Боссман: GUI-драйвер проверен`. Сохранить через настоящий диалог в тестовой папке, закрыть, снова открыть и прочитать текст. Снять до/после. Через доступные элементы найти точный контрол; через screenshot сверить положение окна, масштаб и фокус. Выполнить один безопасный drag/scroll в тестовой области.

При vision-модели проверить, что изображение действительно передаётся и правильно распознаётся. При text-only+accessibility отдельно отметить, что визуальный дизайн/видеокадры моделью не проверены: на такие проверки нужен локальный визуальный путь или явная человеческая проверка. Текст дерева интерфейса не доказывает внешний вид.

Провал калибровки = BLOCKED_DRIVER, не баг Bossman. Нельзя продолжить «GUI-тест» через API только потому, что нет мыши или зрения. Проверка JSON/tool-call также обязательна: инструмент реально вызван, а не описан текстом.

## 6. Ресурсы, изоляция и данные

Записать отдельно ресурсы тестового OpenCode/модели, Bossman/backend/браузера и модели Bossman. 128 GB — общий пул; не складывать физическую RAM и shared VRAM как независимые объёмы. Стартовать с минимально необходимого количества моделей; никакого параллельного большого видео и большой LLM до измерений.

Если оба клиента используют один model-server, пометить это и не выключать его при unload-тесте без резервного канала управления. До performance-замера выключить фоновые тесты/инференс OpenCode либо отдельно учесть его нагрузку. Нельзя приписывать Bossman задержку собственной тестирующей модели и нельзя вычитать её без измерений.

Подготовить только тестовые копии. Предлагаемые пути: `%LOCALAPPDATA%\Bossman\owner-runs\<run_id>` для доказательств и отдельная папка `Bossman Owner Test` в доступном владельцу каталоге для входов/выходов. Не сканировать весь диск, рабочую почту, кошельки, пациентские базы и личные фото.

Fixtures: два текстовых документа с заранее известными фактами, CSV с числами 1200 и 1800, PNG/JPG, короткий 8–12-секундный MP4 с движением и звуком, короткая запись речи с известной фразой, файл с кириллицей и пробелами в имени. Подготовитель создаёт их заранее; происхождение помечено test_fixture, не model_generated. Нет нужного fixture — соответствующий сценарий BLOCKED_ENV, не выдуманный PASS.

## 7. Запуск

В UI OpenCode выбрать подготовленную локальную модель/роль. Передать файл `OPENCODE_OWNER_RUN_RU.md` и короткий текст из `START_PROMPT_RU.md`. Не публиковать сессию и не включать cloud fallback. После старта оператор сам ведёт checkpoint и последовательно проходит сценарии. Диагностика и тесты кода могут помогать расследованию, но не заменяют пользовательские действия.
