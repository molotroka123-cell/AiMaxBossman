# Как снять доказательство удержания интеллекта

Проверка `Intelligence Preservation` в CI падала на текущем main не из-за модели
и не из-за кода: файла `docs/benchmark/intelligence-preservation-current.json`
не существовало, потому что его никто не производил. Гейт
(`tools/intelligence_preservation_gate.py`) был, измерителя не было.

Теперь измеритель есть: `tools/intelligence_preservation_run.py`.

## Что измеряется

Одна и та же модель на одном и том же отложенном наборе в четырёх режимах:

| Полоса | Что добавлено |
|---|---|
| `raw` | только задача |
| `system` | + системный промпт оператора |
| `context` | + срез контекста (память, факты о проекте) |
| `full` | + инструменты и полная обвязка |

Смысл: обвязка не должна ОТНИМАТЬ у модели способности. Каждая задача идёт во
всех четырёх полосах, поэтому по каждой метрике считается парное расхождение с
базовой полосой (`lost` / `gained`) — что именно полоса потеряла и что
приобрела на тех же самых задачах.

## Запуск на машине владельца

```
python tools/intelligence_preservation_run.py \
    --model qwen2.5-coder:14b \
    --endpoint http://127.0.0.1:11435 \
    --quantization Q4_K_M \
    --hardware "i9-14900HX / RTX 4060 8GB / 16GB RAM" \
    --out docs/benchmark/intelligence-preservation-current.json

python tools/intelligence_preservation_gate.py \
    docs/benchmark/intelligence-preservation-current.json \
    --expect-sha $(git rev-parse HEAD)
```

Прогон делает `задач × 4` вызовов модели: на текущем наборе это 880 вызовов.

## Сколько задач нужно на самом деле

**`--min-samples 20` в CI — это нижняя граница допустимости, а не достаточность.**

Утверждение «удержано не меньше 98%» — доверительная нижняя граница, и она
зависит от размера выборки. Измерено прямым прогоном гейта:

| Задач на метрику | Вердикт при БЕЗУПРЕЧНОМ прогоне |
|---|---|
| 20 | `INSUFFICIENT_EVIDENCE` |
| 100 | `INSUFFICIENT_EVIDENCE` |
| 150 | `INSUFFICIENT_EVIDENCE` |
| **189** | **`PASS`** |

И отдельно: при ОДНОЙ потерянной задаче на метрику `PASS` не достигается ни при
каком размере выборки до 4000. То есть гейт требует и объёма, и отсутствия
регрессии одновременно.

Текущий набор `docs/benchmark/intelligence_tasks.json` содержит 20 задач на
каждую из 11 метрик (220 задач). Этого достаточно, чтобы прогон был осмысленным
smoke-измерением всех четырёх полос, и НЕдостаточно для вердикта `PASS`.
Измеритель говорит об этом до начала прогона, а не после.

Чтобы получить `PASS`, набор нужно довести примерно до 189 задач на метрику
(~2100 задач). Дополнять задачами того же класса и НЕ размножать существующие:
одинаковые по сути пункты раздувают выборку, но доказательства не добавляют.

## Что делает результат доказательством

* `evaluated_sha` берётся из git и обязан совпасть с проверяемым коммитом —
  вердикт по старому SHA не является вердиктом по новому;
* полосы отличаются только обвязкой, задача в них одна и та же, поэтому гейт
  может считать их парными;
* модель, которая не ответила, проваливает задачу, а не выбывает из набора:
  выброшенная задача ломает парность;
* каждая проверка детерминированная (точное совпадение, разбор JSON, имя
  инструмента). Мнение второй модели измерением не является — оно само зависит
  от обвязки, которую мы и проверяем;
* температура 0 и фиксированный seed: измерение обязано повторяться.

Метрика без задач — не ноль, а отказ: измеритель не выпустит файл, в котором
требуемая гейтом метрика ничем не измерена.
