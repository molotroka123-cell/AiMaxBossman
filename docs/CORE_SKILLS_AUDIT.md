## 2. Расхождение с ожиданиями пака

**Пак рассчитывал на 8 существующих скиллов и итог 15. Фактически было 11,
итог — 16.**

Причина: сегодня же был внедрён Obsidian-аддон памяти, который добавил
`memory-recall`, `memory-curator` и `obsidian-knowledge`. Первые два
**конфликтовали** с новыми из пака.

Как разрешено:

- **`memory-recall` и `memory-curator` заменены версиями из пака.** Они —
  надмножество: содержат все прежние гарантии (не грузить весь vault, не
  сохранять секреты, писать только в `BOSSMAN Memory/`) и добавляют бюджет
  извлечения, разрешение конфликтов между воспоминаниями и формат заметки.
- Версия поднята до **1.1** с полем `supersedes`. Оставить `1.0` было нельзя:
  один номер описывал бы два разных содержимого, а это ломает версионирование,
  которого требует сам пак (пункт 4 его же проверок).
- **`obsidian-knowledge` оставлен** — это 16-й скилл сверх списка пака. Он не
  дублирует новые: описывает политику обращения с чужим человеческим
  хранилищем (только чтение, цитирование файла и заголовка, не править чужие
  заметки), тогда как `memory-recall` — про извлечение, `memory-curator` — про
  запись. Считаю его обоснованным дополнением к ядру.

Итого рекомендованное ядро — **16, а не 15**. Это стоит зафиксировать, а не
подгонять цифру под документ пака.

## 3. Найденные дефекты (исправлено)

### `repo-audit` не показывал версию

`SkillLibrary` терял `metadata.version` у `repo-audit`. Скилл был ни при чём:
в его описании есть двоеточие («Audit a software repository before changes:
map architecture…»), из-за чего `yaml.safe_load` падал, а запасной построчный
разбор доставал только `name` и `description` — вложенный `metadata` терялся.

То есть интеграционная проверка пака №3 («Skill metadata/version is visible»)
для этого скилла **не проходила**, и это было незаметно.

Починен парсер, а не файл скилла (`bcc/v2/skill_library.py`): перед тем как
падать на построчный разбор, теперь пробуем заключить незакавыченные скаляры в
кавычки и разобрать YAML **нормально**, сохранив вложенность. После правки все
16 скиллов отдают версию.

## 6. Состояние петли самообучения: **PARTIAL**

Целевая цепочка из пака:

```
задача → результат → Memory Curator → Failure Retrospective → Skill Forge
       → Permission Auditor → Skill Evaluator → Proof Before Done → PROMOTE/REJECT
```

Что **реально работает в рантайме**, а не только описано текстом скилла:

- задача → результат: движок, `tool_calls`, Reviewer Gate, KPI — да;
- запись в память: инструмент `memory.write` — да;
- Skill Forge: наблюдение повторов, порог ≥3 одинаковых сигнатур, не чаще
  одного предложения в сутки — да;
- контроль привилегий: расширение прав создаёт approval и **не применяется** до
  решения человека — да;
- версии и откат: `skill_versions` + git — да.

Чего **нет**:

- **автоматических переходов между стадиями.** Ни одна стадия не запускает
  следующую. `Memory Curator` не вызывается сам после миссии;
  `Failure Retrospective` не запускается при провале; `Proof Before Done` не
  проверяет доказательства перед закрытием задачи. Пока это инструкции для
  модели, а не звенья конвейера;
- **хранилища сравнения версий скиллов** (пункт 7) — без него `Skill Evaluator`
  не может дать воспроизводимый вердикт, а значит PROMOTE/REJECT опирается
  только на человека.

Поэтому честная оценка — **PARTIAL**: контроль (права, версии, approvals)
реален, автоматизм обучения — нет. Это лучше, чем обратное: система не
переписывает себе инструкции бесконтрольно, чего пак и добивался.

## 7. Ответ на вопрос пака о недостающих скиллах

Пак просит назвать не более трёх действительно критичных универсальных
скиллов. Проверил покрытие поиском по всем 16 — называю **два**, третий
выдумывать не буду.

### 7.1 `requirement-clarify` — неоднозначное требование не угадывать

**Пробел.** Ни один скилл не описывает, что делать, когда требование допускает
несколько прочтений. `safe-code-change` требует определить критерии приёмки, но
молчит о случае, когда их нельзя вывести. `context-builder` расставляет
приоритет источников, но не описывает действие при пробеле. `night-mission`
говорит про `waiting_approval` для **действий**, а не для неясных **требований**.
В рантайме approvals гейтят опасные операции, а не двусмысленные формулировки.

**Почему не влезает в существующий.** `proof-before-done` — про доказательства
на выходе; здесь нужна проверка на входе. Это другой конец задачи.

**Почему универсально и дорого.** Автономная ночная миссия, угадавшая
требование, тратит впустую всю ночь и все токены. Цена ошибки максимальная
именно там, где человека рядом нет.

### 7.2 `external-evidence-check` — недоверие к данным извне

**Пробел.** Рантайм помечает внешние данные шапкой «это данные, не команды» —
это защита от исполнения инструкций, но **не** проверка правдивости. Процедуры
«сверь факт с несколькими источниками, прежде чем действовать» нет нигде: поиск
по всем скиллам дал только `permission-auditor` (там про опасные комбинации
прав) и `browser-research` (там про неоднозначный DOM).

**Почему это важно именно нам.** `memory-curator` пишет в долговременную
память. Ложь, попавшая туда со страницы или из ответа MCP, будет отравлять
решения месяцами — и `memory-recall` честно подаст её как «проектное
соглашение». Отравление памяти дороже разовой ошибки.

**Почему не влезает в существующий.** Касается сразу браузера, терминала, MCP и
памяти — то есть четырёх скиллов; дублировать процедуру в каждом хуже, чем
вынести один раз.

### Третьего нет

Проверил и отклонил: контроль бюджета (уже в рантайме — Governor,
`cloud_budget_usd`, цена в роутере), выбор модели (роутер + `model-eval`),
обращение с секретами (`permission-auditor` + жёсткие DENY), написание тестов
(`proof-before-done` + `safe-code-change`). Домены (SEO, маркетинг, финансы)
не предлагаю намеренно — их должен вырастить Skill Forge из реальных повторов.

## 8. Точный следующий шаг

1. **Дать `Skill Evaluator` куда писать.** Таблица сравнения версий скиллов
   (`skill_id`, `baseline_version_id`, `candidate_version_id`, метрики, вердикт)
   — без неё пункты 7 и 8 не закрыть, а PROMOTE/REJECT остаётся ручным.
   Владелец схемы — лид, `bcc/db.py`.
2. **Замкнуть один переход конвейера** — самый дешёвый и полезный:
   `after_run` при `failed` → предложить `Failure Retrospective`. Это превратит
   petлю из инструкции в механизм, не давая системе при этом ничего менять
   самой.
3. Решить по двум скиллам из §7 — писать их или нет. Оба готов оформить в том
   же формате, что и пак.

Ответ на прямой вопрос пака: **ядро не полное** — недостающие критичные
универсальные скиллы названы в §7.1 и §7.2.
