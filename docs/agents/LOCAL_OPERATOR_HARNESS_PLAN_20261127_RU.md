# План: Bossman Harness + чат с локальными моделями Ollama + управление компьютером (27.11.2026)

Ветка `claude/local-operator-harness-20261127` (в `main` — только по «да» владельца).
Квитанция: [`docs/audits/2026-11-27-local-operator-harness/README.md`](../audits/2026-11-27-local-operator-harness/README.md).

## Что уже было и чего не хватало

Было: движок задач с инструментами и одобрениями, полный computer use под Windows (`computer.observe` / `computer.act`
/ `computer.processes`, UIA, белый список приложений, одобрение каждого действия, STOP), чат `/chat.html` с выбором
агента, агент 80 «Bossman Harness» — но только как строка в базе на ПК владельца, руками.

Не хватало трёх вещей, без которых «чат с моими локальными моделями и управлением ПК» не работал из коробки:

1. Модели, установленные в Ollama, не попадали в чат сами: каждую надо было регистрировать и создавать под неё агента.
2. Не было готового агента «локальная модель + управление ПК» с правильной политикой.
3. Harness нельзя было воспроизвести из кода, и не было способа прогнать задачу с **независимой** проверкой и квитанцией.

## Архитектура (одна линия, без второго агентного цикла)

```
Ollama (/api/tags, /api/show)
   │  bcc/local_operator/inventory.py — только чтение: модели и их возможности по словам самой Ollama
   ▼
bcc/local_operator/provision.py — чистый план
   │  • модель → строка registry (только локальные чат-модели; :cloud и embedding — пропуск с причиной)
   │  • «Локально · <модель>»       — чат без инструментов
   │  • «Локально · <модель> · ПК»  — computer.observe/act/processes (только если Ollama сообщает tools)
   │  • «Bossman Harness»           — если такого агента ещё нет: самая крупная локальная модель с tools
   ▼
POST /api/local-operator/sync (bcc/features/local_operator.py) — применяет план, ничего существующего не меняет
   ▼
обычный чат /chat.html и обычный движок: те же одобрения, STOP, бюджеты, история, квитанции
   ▲
tools/harness_agent.py run "<цель>" --verify "<команда>" — через тот же API чата; вердикт решает команда владельца
```

Почему так: правила безопасности (одобрение каждого действия на экране, запрет паролей/платежей/отправки, STOP)
уже живут в `tools_computer` и движке. Второй цикл агента рядом с ними означал бы второй набор правил. Здесь его нет:
всё, что создаёт эта ветка, — обычные агенты, и каждый их вызов проходит через `decide_effect` и `execute_tool`.

## Политика агентов

| Агент | Инструменты | Без вопроса | С одобрением владельца | Облако |
|---|---|---|---|---|
| Локально · модель | нет | — | — | нет (нет fallback) |
| Локально · модель · ПК | computer.observe / act / processes | смотреть на экран (`computer.observe`) | каждое действие (клик, ввод, запуск) — пол политики `computer.act`, право его не снимает | нет |
| Bossman Harness | code.\*, guard.\*, computer.\*, terminal.\* | чтение файлов, наблюдение экрана | запись, команды, действия на экране | нет |

Пароли, платежи, отправка, публикация, удаление без явной просьбы — `computer.act` отказывает всегда (DENY-пол).

## Вердикты Harness (`tools/harness_agent.py run`)

`PASS` — задача завершена **и** команда проверки владельца вернула 0. `UNVERIFIED` — задача завершена, проверки не было.
`FAIL` — задача упала или проверка не прошла (слова агента «готово» проверку не перевешивают). `STOPPED`, `TIMEOUT`
(задача не отменяется драйвером), `NOT_RUN`. Драйвер ничего не одобряет: он печатает, какое одобрение ждёт в пульте.

## Что проверено где

| Пункт | Здесь (облако, без ПК) | На ПК владельца |
|---|---|---|
| Инвентарь Ollama, возможности, :cloud, embedding, порт 11435 | юнит-тесты на фейковой Ollama | **NOT_RUN** — `python tools/harness_agent.py models` |
| Регистрация моделей и агентов, повторный sync ничего не создаёт | тесты через настоящий API | **NOT_RUN** — кнопка «Взять модели из Ollama» на странице «Локальные модели» |
| Политика: наблюдение без вопроса, действие = одобрение, чат без инструментов | тесты с настоящим движком и настоящими `computer.*` | **NOT_RUN** — живой прогон «· ПК» агента в чате |
| Harness: цель → чат → движок → проверка → квитанция | e2e-тест через настоящее приложение | **NOT_RUN** — `harness_agent.py run … --verify …` |
| Страница пульта | node-рендер настоящего модуля | **NOT_RUN** — открыть «Локальные модели» |

## Шаги на ПК владельца (по порядку, ~10 минут)

1. `git fetch && git checkout claude/local-operator-harness-20261127`, перезапуск Bossman.
2. `python tools/harness_agent.py models` — список моделей Ollama с возможностями. Сверить с `ollama list`.
3. Пульт → «Локальные модели» → «Взять модели из Ollama». Ожидание: модели подключены, созданы агенты; «Bossman Harness»
   уже есть (агент 80) — отчёт `exists`, его настройки не тронуты.
4. Открыть «Чат + ПК» у модели с инструментами, задача: «Открой Блокнот и напиши: проверка Bossman». Ожидание:
   наблюдение без вопроса, запуск Блокнота и ввод — каждый своим одобрением; в конце наблюдение подтверждает текст.
5. Harness с проверкой: `python tools/harness_agent.py run "Создай файл C:\Users\asd\Bossman\tmp\harness_ok.txt с текстом OK" --verify "python -c \"import pathlib,sys; sys.exit(0 if pathlib.Path(r'C:\Users\asd\Bossman\tmp\harness_ok.txt').read_text().strip()=='OK' else 1)\"" --receipt docs\audits\2026-11-27-local-operator-harness\pc_receipt.json`
6. Квитанции шагов 2–5 положить в папку аудита; по ним — решение о слиянии.
