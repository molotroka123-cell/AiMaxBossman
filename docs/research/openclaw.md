## 2. Граница продукта — проверяется ли она технически

Гипотеза владельца: BOSSMAN — control plane (миссии, Governor, права, Resource
Brain, реестр моделей, долговременная память, скиллы, аудит), OpenClaw —
execution engine для каналов связи и личного ассистента.

**Ответ: граница проходит по живому шву, но она НЕ бесплатна.**

Что подтверждает её осуществимость (всё измерено, §3):

- у Gateway **один вход** — WebSocket-протокол, версия 4. HTTP отдаёт только
  `/health`; попытка `GET /api/sessions` вернула `404`. Значит контролировать
  надо одну поверхность, а не россыпь эндпоинтов;
- у него **есть роли и scope'ы на входе** (`operator` / `node`,
  `operator.read/write/admin/pairing/approvals/questions/talk`). Мост можно
  выдать с минимальным набором, а не «под админом»;
- есть **режимы разрешений сессии** (`read-only`/`guarded`/`workspace`/`full`),
  и `full` требует `operator.admin` — то есть у них самих есть понятие
  «эта сессия не имеет права трогать ФС».

Что мешает считать границу самоподдерживающейся:

- **OpenClaw — не тонкий транспорт.** Это полноценный агентный рантайм со своей
  моделью по умолчанию (`openai/gpt-5.6-sol` — увидено в логе старта на пустом
  конфиге), своими сессиями, своим exec-approval, своими скиллами и своей
  памятью. Он не «канал», он второй мозг. Если не связать эти подсистемы
  явно, получатся две системы принятия решений с общими руками;
- **`node.invoke` — дыра в границе по умолчанию.** Метод существует и позволяет
  operator'у вызывать команды на подключённых устройствах
  (`canvas.*`, `camera.*`, `screen.record`, `location.get`, `sms.send` —
  список из их же документации протокола). Это не «канал связи», это доступ к
  устройству. Если мост даст кому-то `operator.write`, он даст и это;
- **`exec.approval.*` — их очередь подтверждений, не наша.** Семь методов
  (`request/resolve/waitDecision/get/list` + node-варианты). Пока BOSSMAN не
  подписан на неё, человек будет подтверждать опасные действия дважды в двух
  разных местах, а это ровно тот сценарий, в котором подтверждают не глядя.

**Вывод по §2: граница технически осуществима, но она не свойство OpenClaw, а
работа, которую мы должны сделать.** Формулировка «OpenClaw — просто канал»
неверна и её нельзя закладывать в план.

## 3. Поверхность Gateway/API — измерено

Всё в этом разделе получено живым вызовом, а не чтением схем.

### 3.1 Что слушает

```
LISTEN 127.0.0.1 18789        # Gateway, только loopback
```

Порт по умолчанию — **loopback**, наружу ничего не торчит. `--bind` умеет
`loopback|lan|tailnet|auto|custom`, дефолт безопасный. Для сценария владельца
(телефон через Tailscale) это ровно тот режим, который нужно включать осознанно.

`GET /health` без авторизации: `{"ok":true,"status":"live"}`. Больше HTTP не
отдаёт ничего: `GET /api/sessions` → `404`.

### 3.2 Авторизация — проверена на отказ, а не на успех

| Что послано | Ответ Gateway |
|---|---|
| WS upgrade без всего | `101 Switching Protocols` — апгрейд принимается |
| первый кадр от сервера | `connect.challenge` с `nonce` и `ts` |
| `connect` без токена | `NOT_PAIRED`, `details.code: DEVICE_IDENTITY_REQUIRED` |
| `connect` с неверным токеном | `INVALID_REQUEST`, `AUTH_TOKEN_MISMATCH`, `canRetryWithDeviceToken:false` |
| `connect` с `client.id:"probe"` | отклонён: `client/id must be equal to one of the allowed values` |

**Апгрейд WS ничего не авторизует — авторизует кадр `connect`.** Для нас это
означает: наличие открытого сокета не является признаком доверенного клиента, и
любой мониторинг «сокет жив» безопасностью не является.

**`client.id` — закрытый перечень** (`GATEWAY_CLIENT_IDS` в
`packages/gateway-protocol/src/client-info.ts`): `cli`, `gateway-client`,
`webchat`, `openclaw-control-ui`, `node-host`, `openclaw-worker`,
`openclaw-probe`, приложения платформ, `test`, `fingerprint`.
**Отдельного id для стороннего control plane нет.** Мост обязан представляться
`gateway-client` (`mode: "backend"`) — так и было сделано в прогоне. Просить
апстрим о собственном id стоит, но закладываться на это в план — нет.

### 3.3 Реальная поверхность методов

Авторизованный `connect` (Gateway поднят с `--auth none` специально для замера)
вернул `hello-ok` с:

```
protocol: 4      server: 2026.6.34
auth:    {"role":"operator","scopes":["operator.read","operator.write"]}
methods: 193     events: 27
policy:  maxPayload 25 МБ, maxBufferedBytes 50 МБ, tickIntervalMs 30000
```

**193 метода.** Распределение по префиксам (топ):

| Префикс | Методов | Префикс | Методов |
|---|---|---|---|
| `sessions.*` | 22 | `agents.*` | 7 |
| `skills.*` | 20 | `device.*` | 6 |
| `talk.*` | 17 | `config.*` | 6 |
| `node.*` | 17 | `chat.*` | 6 |
| `exec.*` | 9 | `channels.*` | 4 |
| `tts.*`, `doctor.*`, `cron.*` | по 8 | `tools.*`, `models.*` | по 3 |

Восьмиметодный контракт моста из шаблона существует у них целиком и без обходных
путей:

| Нужно мосту | Метод OpenClaw | Проверено вызовом |
|---|---|---|
| health | `health` | ✅ вернул `eventLoop`, `plugins.loaded`, `modelPricing` |
| agents | `agents.list` | ✅ `{"defaultId":"main","agents":[{"id":"main","workspace":"/root/.openclaw/workspace",…}]}` |
| sessions | `sessions.list` / `sessions.create` / `sessions.describe` | ✅ `count:0, limitApplied:100, hasMore:false` |
| send | `sessions.send` (и `chat.send`) | ✅ метод есть; схема строгая — `text` отвергнут, требуется `message` |
| abort | `sessions.abort` (и `chat.abort`) | есть в списке |
| channels | `channels.status` / `start` / `stop` / `logout` | ✅ на пустом конфиге `{"channels":{},"channelMeta":[]}` |
| nodes | `node.list` (+ `describe/invoke/pair.*/pending.*`) | ✅ `{"nodes":[]}` |
| events | `sessions.subscribe`, `sessions.messages.subscribe` | есть в списке |

**Строгая схема параметров — это плюс, а не помеха.** `sessions.send` с полем
`text` отклонён с точным указанием (`must have required property 'message'; at
root: unexpected property 'text'`). Мост будет падать на несовпадении контракта
сразу и громко, а не «отправлять в пустоту».

**Идемпотентность у них есть.** `idempotencyKey` — обязательное поле в схемах
агентных запросов (`packages/gateway-protocol/src/schema/agent.ts:126`), а
документация протокола прямо говорит: «Side-effecting methods require
idempotency keys». Для отправки сообщений живым людям это главное, что нас
интересовало: **дублирование предотвращается на их стороне, если мост
передаёт ключ**. Ключ обязан выводиться из `mission_id + run_id + call_id`
BOSSMAN — тогда наш повтор после сбоя не станет вторым сообщением человеку.

`traceparent` (W3C) принимается на каждом запросе — сквозная трассировка
BOSSMAN → OpenClaw делается без изобретений.

## 4. Локальные модели

Проверить прогоном локальной модели здесь нечем (нет весов и GPU) — **НЕ
ИЗМЕРЕНО**, и я это не маскирую. Что установлено чтением кода и документации:

- `models.providers.<id>.localService` поднимает локальный сервер **по
  требованию**: проба `healthUrl` → запуск `command` при неудаче → ожидание
  готовности → запрос → остановка после `idleStopMs` простоя;
- **если сервер уже здоров по тому же `healthUrl`, OpenClaw использует его и не
  усыновляет** («each process only manages the child it personally started»).
  Это ровно тот механизм, который нужен для схемы §5: один inference server на
  три системы без дублирующей загрузки весов;
- запуск сериализован по провайдеру и набору аргументов — две одновременные
  сессии не поднимут два сервера;
- поддержаны LM Studio, Ollama, llama.cpp (managed), vLLM, MLX и произвольный
  OpenAI-совместимый эндпоинт;
- для локального `baseUrl` (loopback/LAN/`.local`) принимается нессекретный
  маркер вроде `apiKey: "ollama-local"` — ключ не требуется.

**Предупреждение владельца про Ollama через `/v1` их документация косвенно
подтверждает** в другой формулировке: «small or aggressively quantized models
truncate context and skip provider-side safety filters». Проверять tool calling
конкретной локальной модели всё равно придётся у нас — у нас для этого уже есть
`capability_probe` и verified-gate в роутере. **Это не работа моста, это работа
Resource Brain.**

## 5. Топология одной модели на три системы

```text
BOSSMAN Resource Brain
      ↓ (владеет решением: какая модель, сколько VRAM, когда выгрузить)
общий локальный inference server
 ↙        ↓        ↘
BOSSMAN OpenClaw OpenCode
```

Схема реализуема **без нового кода в OpenClaw**: достаточно указать ему
провайдера с `baseUrl` нашего сервера и **не задавать `localService`**, чтобы он
никогда не поднимал свой процесс. Тогда единственный, кто управляет жизнью
модели, — Resource Brain, как и задумано.

Риск, который надо записать сейчас: если `localService` всё-таки настроят,
OpenClaw поднимет **свой** сервер при недоступности пробы — и мы получим вторую
загрузку весов в самый неудачный момент. **Правило для конфига моста:
`localService` у общих провайдеров запрещён.**

## 6. Скиллы — формат совпал

Их формат: `SKILL.md` с YAML-фронтматтером `name` + `description`
(проверено на `skills/healthcheck/SKILL.md`). **Это тот же формат, что у нас.**

Корни поиска (`src/skills/loading/session.ts:345-350`, `skill-paths.ts:54-55`):

| Корень | Класс |
|---|---|
| `<agentDir>/skills` | `user` |
| `<cwd>/.openclaw/skills` | `project` |
| `CONFIG_DIR/skills` | managed |
| `CONFIG_DIR/plugin-skills` | от плагинов |
| bundled рядом с бинарём | встроенные |

Наш `default_skill_roots` уже смотрит в `.agents/skills`, `.opencode/skills`,
`.claude/skills`. **Добавить `.openclaw/skills` — действительно одна строка**,
как и предполагалось в `docs/NIGHT_HANDOFF.md` §7.

Но есть то, чего в том предположении не было: у них **20 методов `skills.*`**,
включая целый конвейер предложений — `skills.proposals.create/inspect/apply/
reject/revise/requestRevision/quarantine/update/list`. То есть **OpenClaw умеет
сам предлагать и применять скиллы**. Это прямая конкуренция нашему Skill Forge и
`skill_evaluations` (V2.2 §7).

**Решение, которое надо зафиксировать до моста:** источник истины скиллов —
BOSSMAN; конвейер `skills.proposals.*` у OpenClaw при интеграции **выключается
или его `apply` заворачивается в наш approval**. Две системы, независимо
меняющие один и тот же `SKILL.md`, — это не «синхронизация», это гонка.

Про «не класть все скиллы в каждый промпт»: у них есть
`skills.search`/`skills.detail`/`skills.bins`, то есть выборочная подача. Схема
строгая — пустой `query` отклонён (`must not have fewer than 1 characters`).

## 7. Память — здесь конфликт, а не стык

Это самый неприятный результат исследования, и он меняет план.

У OpenClaw **своя долговременная память, и не одна**:

- плагин `memory-core` **загружен по умолчанию** (виден в `health.plugins.loaded`
  на пустом конфиге, вместе с `browser`, `canvas`, `device-pair`,
  `file-transfer`, `phone-control`, `talk-voice`);
- официальный плагин `@openclaw/memory-lancedb` — LanceDB, векторный поиск,
  **auto-recall и auto-capture**, инструменты `memory_store`/`memory_recall`/
  `memory_forget`;
- расширение `memory-wiki` — вики-хранилище, **с режимом рендера `obsidian`**,
  вики-ссылками, фронтматтером и собственным скиллом
  `obsidian-vault-maintainer`, который правит vault;
- `Active Memory` — отдельная линия глубокого припоминания с блокирующим
  под-агентом.

**У нас источник истины памяти — Obsidian-хранилище, и у них тоже может быть
Obsidian-хранилище.** Это ровно тот «несовместимый второй слой правды», о
котором предупреждает шаблон, — и он не гипотетический, он с готовым скиллом,
который пишет в vault.

Что из этого следует, по убыванию жёсткости:

1. **`memory-wiki` в режиме `obsidian` не должен указывать на наш vault.**
   Никогда. Два писателя в одни заметки без общего слоя блокировок — потеря
   данных, а не «расхождение».
2. **`auto-capture` LanceDB-плагина должен быть выключен** при интеграции.
   Иначе разговоры из Telegram будут молча оседать во второй памяти, минуя наш
   `external-evidence-check` (V2.2 §8) и нашу bi-temporal модель.
3. Правильная цель — **узкий адаптер**: OpenClaw спрашивает память у BOSSMAN
   (через MCP-инструмент или наш HTTP), а не ведёт свою. Их `tools.*` (3 метода)
   и поддержка MCP делают это выполнимым, но это отдельная работа, а не
   «настройка».

**Пока это не решено, мост давать OpenClaw доступ к нашему vault не должен
вообще.**

## 8. Права и безопасность — может ли BOSSMAN остаться последней инстанцией

### 8.1 Что у них уже хорошо

- бинд по умолчанию — **loopback**;
- `connect` без валидного токена/устройства отклоняется (§3.2, проверено);
- scope'ы разделены, `operator.admin` нужен для конфигурации, обновлений и
  «high-risk approvals»;
- режимы разрешений сессии ограничивают ФС по `sessionRoot`, есть явный запрет
  выхода по символическим ссылкам и `..`;
- **телеметрия функций выключена по умолчанию**; единственный автоматический
  исходящий запрос — суточная проверка обновлений (и она **наблюдалась** в
  логе старта: «update available … v2026.7.1-2»). Отключается конфигом.

### 8.2 Где граница ломается без нашей работы

| Поверхность | Почему это проблема для нас |
|---|---|
| `node.invoke` | доступ к камере, экрану, геолокации, **SMS** на парном устройстве. Это не «канал», это устройство |
| `exec.*` (9 методов) | своя очередь подтверждений: без подписки BOSSMAN человек подтверждает опасное **дважды**, в двух местах |
| `sessions.send` / `chat.send` | **отправка живым людям** — то самое, чего у BOSSMAN раньше не было |
| `skills.proposals.apply` | самостоятельное изменение скиллов (см. §6) |
| `config.*` (6 методов) | правка конфигурации Gateway из-под operator-роли |
| память по умолчанию | `memory-core` включён без спроса (см. §7) |

### 8.3 Три механизма, которые делают границу настоящей

Это и есть содержание будущей работы — не «мост как транспорт», а мост как
граница:

1. **Мост подключается с минимальным scope.** `operator.read` +
   `operator.write` и НИКОГДА `operator.admin`. Проверено, что scope виден в
   `hello-ok.auth.scopes` — то есть мост может **сам убедиться**, что ему не
   выдали лишнего, и отказаться работать, если выдали.
2. **Отправка в канал — ASK по умолчанию, всегда.** Не «ASK для незнакомых
   контактов», а ASK на любую отправку, пока владелец явно не разрешит
   конкретный канал и конкретный контакт. `docs/NIGHT_HANDOFF.md` §7 уже
   называет это главным риском; исследование ничего не нашло, что позволяло бы
   его смягчить, — наоборот, `node.invoke` с `sms.send` его усиливает.
3. **Идемпотентность обязательна с первой строки.** `idempotencyKey` выводится
   из `mission_id + run_id + call_id`. Иначе наш собственный ретрай станет
   вторым сообщением человеку — и это не чинится откатом.

### 8.4 Ответ на прямой вопрос шаблона

> Может ли BOSSMAN остаться последней инстанцией по send/login/upload/terminal/
> filesystem/MCP/account/payment?

**Да — но только для тех действий, которые проходят через мост.**
Действия, инициированные внутри OpenClaw (человек написал в Telegram, их агент
решил выполнить exec), идут по **их** конвейеру подтверждений и наш
`decide_effect` не видят. Считать иначе — самообман.

Значит, вариант «A. execution engine под BOSSMAN» в полном смысле недостижим без
подписки на их `exec.approval.*` и переадресации их подтверждений в наш
approvals. Это и есть причина, по которой ниже выбран вариант **B**, а не A.

## 9. Узлы и устройства

`node.*` — 17 методов: `list`, `describe`, `invoke`, `invoke.result`, `event`,
`rename`, `pluginSurface.refresh`, парная группа `pair.*`
(`request/approve/reject/verify/remove/list`) и очередь `pending.*`
(`enqueue/pull/ack/drain`).

Устройство **не становится вторым control plane**: у него роль `node`, а не
`operator`, и оно исполняет команды, а не раздаёт их. Очередь `pending.*` даёт
поведение при офлайне — команды копятся и разбираются.

Старый TCP-мост (`bridge.*`, порт 18790, JSONL) **удалён** — их же документация
помечена как историческая. Это важно: любые сторонние инструкции про порт 18790
устарели, единственный вход — WS-протокол.

Для сценария «второй ноутбук как ограниченный работник» это подходит. Но
парность даёт устройству и `canvas/camera/screen/location/sms` — то есть
подключать чужую машину узлом можно только с осознанием §8.2.

## 10. Ресурсы — измерено на пустом конфиге

| Метрика | Значение | Как получено |
|---|---|---|
| Процессов | **1** | `ps` |
| RSS сразу после `ready` | **273 МБ** | `ps -o rss` через 35 с |
| RSS через 2 мин 15 с простоя | **280 МБ** | `ps -o rss` |
| CPU в простое | **≈0.33 %** одного ядра | `/proc/<pid>/stat`: 15 тиков за 45 с |
| `eventLoop.utilization` в простое | **0.012** | ответ метода `health` |
| Время до «http server listening» | **0.6 с** | лог |
| Время до `ready` | **~0.7 с** | лог |
| Плагинов загружено | **7** | `health.plugins.loaded` |
| Диск: установка | **351 МБ** | `du -sh` |
| Диск: состояние после старта | **~2.2 МБ** | `du -sh` |

**Без весов моделей.** 280 МБ RSS в простое — это не «лёгкий транспорт», но и не
катастрофа: сопоставимо с одним нашим воркером. Замер «5 сессий» не делался —
для этого нужна работающая модель (**НЕ ИЗМЕРЕНО**).

Отдельно: RSS вырос на 7 МБ за две минуты полного простоя. Одного замера мало,
чтобы называть это утечкой, но при длительной эксплуатации за этим надо следить —
и это дешёвая метрика для нашего Resource Brain.

## 11. Отказы

Проверено вживую:

- **старт без конфигурации** — честный отказ:
  `Missing config. Run 'openclaw setup' or set gateway.mode=local (or pass --allow-unconfigured)`.
  Не «поднялся наполовину»;
- **отсутствующий токен** — `NOT_PAIRED`, соединение не даёт ничего;
- **неверный токен** — `AUTH_TOKEN_MISMATCH` с полем `recommendedNextStep`;
- **неправильные параметры метода** — отказ с точным путём в схеме
  (`at /query: must not have fewer than 1 characters`).

Не проверено (**НЕ ИЗМЕРЕНО**): рестарт Gateway под нагрузкой, обрыв канала,
недоступность локальной модели, офлайн узла, таймаут отправки, фактическое
поведение `idempotencyKey` при повторе. Последнее — **первое, что должен
измерить следующий этап**, потому что на нём держится весь §8.3.

Ошибки протокола структурированы (`{code, message, details, retryable,
retryAfterMs}`) — мост сможет различать «повторить» и «сдаться» по коду, а не по
тексту. Отдельно замечено: `connect` может вернуть retryable `UNAVAILABLE` с
`details.reason: "startup-sidecars"` — мост обязан это уметь, иначе он будет
считать нормальный холодный старт отказом.

## 12. Выбор интеграции

**B. channel gateway only.**

Почему не A (execution engine под BOSSMAN): §8.4. Полное подчинение требует
перехвата их конвейера подтверждений и отключения их памяти и их конвейера
скиллов. Это возможно, но это не первая фаза — это результат нескольких.

Почему не C (только узлы): выбрасывает главную ценность — каналы связи.

Почему не D: каналы у них работают, лицензия MIT, протокол стабилен и
версионирован, авторизация настоящая. Отказываться не от чего.

### Контракт V1 моста (только следующая фаза)

| Наш вызов | Метод OpenClaw | Обязательное |
|---|---|---|
| `health` | `health` | таймаут 5 с; `UNAVAILABLE`+`startup-sidecars` = повторить |
| `agents` | `agents.list` | только чтение |
| `sessions` | `sessions.list`, `sessions.create`, `sessions.describe` | — |
| `send` | `sessions.send` | **`idempotencyKey` = `sha256(mission_id:run_id:call_id)`**, эффект **ASK** |
| `abort` | `sessions.abort` | идемпотентно по natural |
| `channels` | `channels.status` | только чтение; `start/stop/logout` — ASK |
| `nodes` | `node.list`, `node.describe` | **`node.invoke` в V1 не проксируется вообще** |
| `events` | `sessions.subscribe`, `sessions.messages.subscribe` | переподключение с backoff |

Параметры контракта:

- **auth:** отдельный токен Gateway только для моста, роль `operator`, scope
  ровно `["operator.read","operator.write"]`. Мост проверяет `hello-ok.auth.scopes`
  и **отказывается стартовать**, если ему выдали больше;
- **client.id:** `gateway-client`, `mode: "backend"` (своего id нет, §3.2);
- **таймауты:** 5 с на `health`, 30 с на `sessions.send`, переподключение с
  экспоненциальной задержкой;
- **идемпотентность:** ключ из наших идентификаторов, всегда;
- **корреляция:** `traceparent` на каждый запрос, `mission_id`/`run_id` в нём;
- **бинд:** `loopback`; выход в тайнет — только явным решением владельца.

### Что в V1 НЕ входит

`node.invoke`, `exec.*`, `config.*`, `skills.proposals.*`, любой доступ к vault,
`memory-wiki` в режиме `obsidian`, `localService` у общих провайдеров.

## 13. Итог

**ВЕРДИКТ: ВНЕДРЯТЬ ПОЗЖЕ** (вариант B, контракт §12).

**OPENCLAW NEXT PHASE ALLOWED: YES**, при трёх условиях, каждое проверяемо:

1. **ASK на любую отправку в канал** — до первой строки моста, а не после. Без
   этого запрет из мастер-промпта («не отправлять сообщения без подтверждения»)
   держится на честном слове.
2. **`idempotencyKey` в `sessions.send` с первого коммита** и тест, который
   доказывает, что повтор не создаёт второго сообщения. Пока не измерено (§11) —
   это первое измерение следующей фазы.
3. **Решение по памяти принято до моста** (§7): `memory-wiki` не смотрит в наш
   vault, `auto-capture` выключен, цель — узкий адаптер к памяти BOSSMAN.
   Иначе появится второй слой правды, и это не откатывается.

### Что измерено и что нет

**Измерено:** лицензия и коммит; разрыв npm↔main; установка 351 МБ / 296 пакетов
/ 17 с; один процесс; RSS 273→280 МБ; CPU простоя 0.33 %; старт 0.6–0.7 с;
loopback-бинд; отказ авторизации в трёх вариантах; закрытый перечень `client.id`;
193 метода и 27 событий; живые ответы `health`, `agents.list`, `channels.status`,
`node.list`, `sessions.list`; строгость схем на `sessions.send` и `skills.search`;
7 плагинов по умолчанию, включая `memory-core`; исходящая проверка обновлений.

**НЕ измерено (и не выдаётся за измеренное):** любые прогоны с реальной моделью;
RSS на 5 сессиях; поведение каналов (нет учётных данных Telegram/WhatsApp);
фактическая работа `idempotencyKey` при повторе; отказы под нагрузкой; узлы
(ни одного устройства не подключалось); tool calling локальных моделей через
их провайдеров.
