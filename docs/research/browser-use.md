## 2. Что делает на самом деле (по исходникам)

### 2.1 Архитектура

Четыре независимых слоя, и это важно — они **разделимы**:

1. `browser/` (19 117 строк) — `BrowserSession` + 15 «сторожей» (watchdogs) на
   шине событий `bubus`: `DefaultActionWatchdog` (3 746 строк — клики, ввод,
   прокрутка, дропдауны), `DOMWatchdog`, `PopupsWatchdog`, `SecurityWatchdog`,
   `DownloadsWatchdog`, `CrashWatchdog`, `CaptchaWatchdog`, `StorageStateWatchdog`.
2. `dom/` (6 118 строк) — построение и сериализация дерева. Ядро:
   `dom/serializer/serializer.py` (1 393) + `dom/views.py` (1 043).
3. `tools/` (3 591 строка) — реестр действий, ровно то же место, что наш
   `bcc/tools.py` + `bcc/features/tools_browser.py`.
4. `agent/` (7 767 строк) — **их собственный агентный цикл**, свой
   `message_manager`, свой системный промпт на 24 КБ, свой «судья».

**Проверено экспериментально** (`/tmp/bu/exp/standalone.py`): слои 1–3 работают
без слоя 4. `BrowserSession` + `Tools.registry.execute_action(...)` выполняют
`navigate`/`input`/`click`/`scroll` без единого вызова LLM. То есть теоретически
можно взять «движок», не беря агента.

### 2.2 Пространство действий, которое видит модель

Реально зарегистрированные действия (снято с живого объекта `Tools`):

```
click, close, done, dropdown_options, extract, find_elements, find_text,
go_back, input, navigate, save_as_pdf, screenshot, scroll, search,
search_page, select_dropdown, send_keys, switch, wait
+ evaluate (произвольный JS), upload_file, write_file, read_file, replace_file
```

Категории, которых у нас нет вообще: `scroll`, `wait`, `find_text`,
`search_page` (grep по тексту страницы, 0 токенов), `find_elements` (CSS-запрос,
0 токенов), `dropdown_options`, `switch`/`close` (вкладки), `send_keys`,
`extract` (отдельный вызов LLM по markdown страницы), файловая система агента.

### 2.3 Как описываются элементы страницы — **главное отличие**

Не индексы по порядку, не CSS-селекторы, не разметка на скриншоте.
Индекс элемента — это **CDP `backendNodeId`**
(`dom/serializer/serializer.py:_allocate_selector_index` — возвращает сам
`backend_node_id`, синтетический счётчик только при коллизии).

Живой вывод `llm_representation()` на нашей тестовой странице
(`/tmp/bu/exp/dom_dump.py`):

```
Форма заявки
Мы используем cookie.
[5]<button id=accept />
	Принять
[3]<input id=name name=name placeholder=Имя />
*[4]<select id=city name=city expanded=false compound_components=(name=Dropdown Toggle,role=button),(name=Options,role=listbox,count=2,options=Москва|Питер) />
[6]<button id=go />
	Отправить
пока пусто
[35]<a />
	Другая страница
```

После клика по «Отправить» (JS добавляет кнопку):

```
[6]<button id=go />
	Отправить
Принято:
*[68]<button id=extra />
	Подтвердить
```

Что тут спрятано, по пунктам:

* **Одно дерево, а не «текст + список»**. Текстовые узлы — дети своего
  интерактивного родителя, отступ табами. Модель видит, что «Принять» внутри
  cookie-баннера, а не рядом с ним.
* **`*` перед индексом — элемент новый с прошлого шага.** Это встроенный
  сигнал «твоё прошлое действие вызвало вот это»: автодополнение, модалка,
  подтверждение. `serializer.py:_assign_interactive_indices_and_mark_new_nodes`.
* **`compound_components`** — содержимое `<select>` и ARIA-комбобоксов
  инлайнится прямо в описание: `count=2, options=Москва|Питер`. Модель не гадает,
  какое значение подставить в `select_dropdown`.
* **Индексы стабильны между снимками** (5, 3, 4, 6, 35 — те же в шаге 1 и 2),
  потому что это идентификаторы узлов в рендерере, а не позиции в списке.
* **Значения `input[type=password]` вырезаны намеренно** —
  `serializer.py:1281`: «Never include values from password fields — they contain
  secrets that must not leak into DOM snapshots sent to the LLM, where prompt
  injection could exfiltrate them».
* Фильтрация: видимость по layout-снимку, paint order, вложенность
  bounding box'ов (`_apply_bounding_box_filtering`), схлопывание SVG.

Плюс отдельный блок `page_info`, который переводится в текст
«0.0 pages above, 0.6 pages below — scroll down to reveal more content»
(замерено: `pixels_below=668` на нашей странице).

Плюс `<page_stats>`: «Page appears empty — consider waiting», «N network
request(s) in flight and little text rendered — page may still be loading»
(`agent/prompts.py:_get_browser_state_description`).

### 2.4 Что происходит при устаревшем индексе

Проверено экспериментально. Узел удалён → `get_element_by_index(5)` возвращает
`None` → инструмент отдаёт **не ошибку, а подсказку**:

```python
# tools/service.py:716
msg = f'Element index {params.index} not available - page may have changed. Try refreshing browser state.'
return ActionResult(extracted_content=msg)   # НЕ error=... — счётчик провалов не растёт
```

Разница с нами принципиальная: у них попытка кликнуть по исчезнувшему узлу
**никогда не попадёт по другому элементу**. У нас — попадёт (см. §4.2).

### 2.5 Восстановление после сбоя (recovery loops)

Это то, чего у нас практически нет. По слоям:

**Клик** (`default_action_watchdog.py:_click_element_node_impl`) — каскад:
отказ до попытки, если это `<select>` или `input[type=file]` (с подсказкой,
каким действием это делается правильно) → `DOM.scrollIntoViewIfNeeded` →
геометрия; нет геометрии — **fallback на JS `this.click()`** →
`_check_element_occlusion` (в точке клика сверху чужой элемент → **снова
JS-клик**) → выбор самого большого видимого quad'а → для checkbox/radio снимок
`checked` до и проверка после → таймауты на `mouse down/up` с комментарием
«likely due to dialog, continuing» (модалка не вешает шаг) → принудительный
возврат фокуса на исходную вкладку (клик мог открыть новую).

**Последовательность действий** (`agent/service.py:multi_act`) — два барьера
против «кликаем по устаревшему снимку»: статический — флаг
`terminates_sequence=True` у `navigate`/`search`/`go_back`/`switch`/`evaluate`
отменяет остаток очереди; динамический — до и после каждого действия снимаются
`url` и `agent_focus_target_id`, изменились → «Page changed after "X" —
skipping N remaining action(s)».

**Страница.** `PopupsWatchdog`: `alert`/`confirm`/`beforeunload` принимаются
автоматически, `prompt` отклоняется, текст диалога складывается в
`_closed_popup_messages` и **показывается модели** следующим шагом
(«Auto-closed JavaScript dialogs: …»); три подхода к закрытию по 0.5 с.
`SecurityWatchdog`: домен проверяется до навигации, после навигации (редирект →
уход на `about:blank`, сессия жива, агент видит ошибку) и при открытии новой
вкладки (вкладка закрывается). Реконнект CDP-вебсокета («reconnection attempt
1/3» — видел в живом логе). `CrashWatchdog`; `CaptchaWatchdog` (ждёт их прокси —
вне их облака бесполезен).

**Агент.** `max_failures=5` подряд со сбросом при успехе;
`planning_replan_on_stall` впрыскивает «замысел не работает, перепланируй»;
при исчерпании — принудительный `done`, чтобы отдать частичный результат.

**Промпт** (`agent/system_prompts/system_prompt.md`, 270 строк) — эвристики
словами, и они хорошие: закрывать popup/модалки/куки **до** всего остального;
при 403/бот-детекте не долбить один URL; «if you are on the same URL for 3+
steps without meaningful progress, or the same action fails 2-3 times, try a
different approach»; после прерванной последовательности доделать несделанное;
для комбобоксов — ввести, дождаться подсказок и кликнуть по новому `*`-элементу,
а не жать Enter.

### 2.6 Состояние между шагами

Контекст модели — **ровно два сообщения**: system + одно перестраиваемое
`state` (`message_manager/service.py:_set_message_with_type`). Замерено на живом
запуске: system 24 087 символов (постоянный), user 663 → 714. История прошлых
шагов лежит внутри `state` короткими `HistoryItem`
(`evaluation_previous_goal`/`memory`/`next_goal`/`action_results`). Полный DOM в
истории **не накапливается** — он всегда только текущий.

Результат действия двухслойный (`agent/views.py:ActionResult`):
`long_term_memory` — короткая строка, живёт в истории вечно;
`extracted_content` + `include_extracted_content_only_once=True` — большой блок,
показывается **один раз** следующим шагом как `<read_state>` и выбрасывается
(лимит 60 000 символов). Ещё состояние: файловая система агента (`todo.md`,
`results.md`), `available_file_paths`, вкладки, `storage_state`.

### 2.7 Безопасность у них

`allowed_domains` (по умолчанию `None` = **разрешено всё**), проверка в трёх
точках `SecurityWatchdog`. **`sensitive_data` с привязкой к домену**
(`tools/registry/service.py:_replace_sensitive_data`) — это сильно: модель видит
`<secret>x_password</secret>` и никогда значение; подстановка в момент
исполнения и **только если текущий URL подходит под доменный шаблон этого
секрета**; есть TOTP-суффикс `bu_2fa_code`; обратно `_filter_sensitive_data`
вычищает настоящие значения из сообщений, уходящих модели. Значения
password-полей не попадают в снимок (§2.3). `domains=[...]` на самом действии —
действие **исчезает из пространства действий** на неподходящем домене
(`registry/views.py:RegisteredAction.domains`). `exclude_actions=[...]` убирает
действие из реестра. `Agent.pause()/resume()` — пауза цикла агента.

Чего у них **нет вообще**: подтверждения человеком конкретного действия;
понятия «запрещено навсегда»; разделения актёров human/agent на уровне браузера;
пометки внешних данных как «это не команды» (грепом по всему репозиторию по
`prompt injection|untrusted|not commands` — **одно** попадание, и то комментарий
про password-поля). Зато есть действие `evaluate` — произвольный JS в контексте
страницы, доступное модели автоматически.

### 4.2 Где мы объективно слабее — с доказательствами

Всё ниже воспроизведено на живом Chromium через **наш** `BrowserManager`
(`/tmp/bu/exp/ours.py`).

**(а) Модели нечем адресовать элемент.** Полный текст, который наш `_render()`
отдаёт модели на той же странице:

```
Интерактивные элементы:
[0] <button> Принять
[1] <input name=name> Имя
[2] <select name=city> Москва Питер
[3] <button> Отправить
[4] <a> Другая страница
```

В снимке **нет ни `id`, ни `class`, ни селектора** — JS в
`browser_control.py:snapshot()` собирает только
`tag/role/text/aria/name/type/placeholder/href/disabled`. При этом
`browser.click` требует аргумент `selector` (CSS) с описанием «CSS-селектор из
DOM-снимка» — **такого селектора в снимке не существует**. Индекс `[0]`
декоративен: ни один инструмент его не принимает. `id=accept` на странице есть,
но модель его не видит. В тесте `test_model_drives_browser_end_to_end` модель
«знает» `#name` и `#go` только потому, что сценарий захардкожен в `ToolAdapter`.

**(б) Неоднозначный селектор молча кликает не туда.** Замер: `click("button")`
вернул успех и `url` без изменений, а cookie-баннер исчез — `locator(...).first`
(`browser_control.py:314`) выбрал первую из двух кнопок. Ни ошибки, ни
предупреждения; модель считает, что нажала «Отправить».

**(в) Промах по селектору стоит 30 секунд.** Замер: `click("#nope")` →
`Locator.click: Timeout 30000ms exceeded`. При `timeout_seconds=60.0` два таких
промаха съедают весь бюджет инструмента. У них тот же случай возвращается
мгновенно строкой-подсказкой.

**(г) Значение password-поля утекает в снимок.** В `snapshot()`:
`text: clean(el.innerText || el.value || '')`. У `<input type=password>`
`innerText` пуст → берётся `el.value` → **введённый пароль попадает в текст,
уходящий модели**. У них это явно закрыто (§2.3). Дефект безопасности в нашем
коде, а не «отставание по фичам».

**(д) Пароль проходит через контекст модели.** `browser.login` принимает
аргумент `password` (`tools_browser.py:288`): модель должна его сгенерировать,
значит он у неё в контексте и в `tool_calls.args` в БД. У них модель видит
только `<secret>label</secret>`.

**(е) Контекст растёт линейно снимками.** `bcc/engine.py:615` —
`messages.append(_tool_message(call, result.render()))`, полный текст каждый раз.
Поле `ToolResult.one_line` объявлено в `bcc/tools.py:43` и **движком нигде не
используется** (проверено грепом — только присваивания в `tools_*.py`). После
десяти шагов браузера в контексте десять полных DOM.

**(ж) Нет прокрутки** — ни `scroll`, ни `scroll_to_text`, ни «сколько ещё ниже».
Всё, что не влезло в `TEXT_LIMIT=6000`, недостижимо; при этом `more` предлагает
«`browser.read_dom` с уточняющим запросом», чего этот инструмент не поддерживает
(`input_schema={}`).

**(з) Снимок не фильтрует невидимое.** `document.querySelectorAll` берёт и
скрытые элементы, и элементы под модалкой. Нет ни `*`-пометки новых, ни
информации о перекрытии.

**(и) После Resume снимок не инвалидируется технически.** Докстринг
`tools_browser.py` требует «модель обязана перечитать DOM», но кода, который это
обеспечит, нет: селектор из позапрошлого снимка примут молча.

**(к) Никакой обработки диалогов.** `alert`/`confirm` заблокируют Playwright до
таймаута; модель об этом не узнает.

## 6. Что НЕ берём и почему

1. **Библиотеку как зависимость.** Жёсткий, неразрешимый конфликт версий: они
   пинят **точные** версии (`mcp==1.28.1`, `openai==2.26.0`, `anthropic==0.76.0`,
   `pydantic==2.12.5`, `httpx==0.28.1`), мы требуем `mcp>=2.1,<3` и `httpx>=0.27`.
   В одном окружении `pip` это не соберёт. Пришлось бы держать отдельный venv и
   IPC — то есть отдельный процесс, отдельный жизненный цикл, отдельные ошибки.
2. **Их агентный цикл (`agent/`, 7 767 строк).** У нас **уже есть** канонический
   tool-loop с правами, approvals, anti-replay, checkpoint'ами и восстановлением
   после рестарта. Второй цикл — это второе место, где принимаются решения о
   правах, и рано или поздно они разойдутся. Проговариваю явно: **второй
   агентный цикл нам не нужен ни в каком виде.**
3. **Действие `evaluate` (произвольный JS).** Обнуляет весь наш `HARD_DENY`:
   платёж — это просто клик, а клик — это JS. Не портировать никогда.
4. **Их файловые действия** (`write_file`/`read_file`/`replace_file`) — у нас
   есть `terminal.*` с корнями и правами; их версия без границ ФС.
5. **Переход с Playwright на сырой CDP.** Наш `browser_control.py` компактен
   (388 строк) именно потому, что Playwright берёт на себя ожидания,
   auto-waiting, iframes. Их 3 746 строк одного `default_action_watchdog.py` —
   это цена отказа от него. Приёмы (occlusion check, scroll-into-view, fallback
   на JS-клик) переносятся на Playwright без смены транспорта.
6. **Скриншот с bounding-box разметкой и vision-режим.** Мы DOM-first
   осознанно; DOM дешевле и детерминированнее. Скриншот у нас уже есть как
   отдельный инструмент.
7. **`CaptchaWatchdog`** — работает только с их облачным прокси, который сам
   решает капчи. Вне их облака это пустышка. И капча — это ровно тот случай,
   когда правильный ответ у нас — Human Take Over, а не обход.
8. **Телеметрия, cloud sync, `browser-use-sdk`, `browser-harness`, `skills/`,
   `integrations/gmail`, `sync/auth.py`** — чужая продуктовая обвязка.
9. **Их `done`-действие и «судья»** (`use_judge=True` по умолчанию — лишний
   вызов LLM на весь трейс в конце). У нас завершение run'а решает движок.

## 7. Точки интеграции

Всё, что предлагается, — правки в двух наших файлах плюс один в движке.
Новых внешних контрактов не появляется.

**`command-center/bcc/v2/browser_control.py`**
* `BrowserRuntimeSession` — новые поля: `refs: dict[int, Any]`,
  `snapshot_gen: int`, `prev_fingerprints: set[str]`, `dialogs: list[str]`.
* `snapshot()` — переписать JS: `id`/`value`/`checked`/`expanded`, опции
  `<select>`, фильтр видимости и перекрытия, вырезание password-значений;
  вернуть `refs`, `page_info`, пометку новых элементов; поднять `snapshot_gen`.
* `click/type_text/select` — принимать `ref: int` (селектор оставить как
  запасной путь), проверять поколение, `.first` убрать, таймауты 5 000 мс.
* Новые методы: `scroll(session_id, down, pages)`, `scroll_to_text(text)`,
  `find_text(pattern)`, `query(css, attributes)`.
* `resume()` / `takeover()` — инкремент `snapshot_gen` (инвалидация ссылок).
* `navigate()` — повторная проверка `domain_allowed(page.url)` после перехода.
* `start()` — подписка на `page.on("dialog")`.

**`command-center/bcc/features/tools_browser.py`**
* `_render()` — дерево вместо «текст + плоский список», `*` для новых,
  `page_info`, блок «автоматически закрытые диалоги».
* `SPECS` — заменить `selector` на `ref` в `click/type/select/submit`;
  добавить `browser.scroll`, `browser.scroll_to_text`, `browser.find_text`,
  `browser.query` (все `category="read"`, `permission="browser.read"`,
  `default_effect="auto"`).
* `_login` — `login_ref`/`password_ref` + подстановка из `svc.vault` с проверкой
  привязки секрета к домену. `effect_hook` остаётся `("ask", "вход в аккаунт")`.
* `NEVER` и `ASK_ACTIONS` не трогать.

**`command-center/bcc/engine.py`**
* `_run()` — при добавлении нового сообщения инструмента схлопывать текст
  предыдущих вызовов того же `source="browser"` до их `one_line`. Использовать
  уже существующее поле `ToolResult.one_line`.

**Контракты.** `ToolSpec` менять не нужно. Опционально — необязательное поле
`domains: list[str] | None` для сужения пространства действий по текущему URL
(их `RegisteredAction.domains`), но это отдельная, более поздняя история.

**Таблицы.** Новых не требуется. `bcc/v2/tables.py:browser_sessions` уже хранит
`current_url`, `last_action`, `takeover`, `paused`. Ссылки на элементы живут
только в памяти процесса — как и сами Chromium-контексты; при рестарте сессия и
так помечается прерванной (это уже описано в докстринге `BrowserManager`).

  версиями почти гарантированы, значит пин + регулярное сопровождение.

**Если брать приёмы (рекомендуется):**
* новых зависимостей **ноль** — всё делается на текущем Playwright;
* объём правок: ~250–350 строк в `browser_control.py`, ~120 в
  `tools_browser.py`, ~20 в `engine.py`;
* RAM: JS-снимок станет тяжелее (фильтр видимости, `elementFromPoint`) —
  единицы миллисекунд на страницу, память не растёт;
* хранение `ElementHandle` на снимок: ~200 handles × сессия, десятки килобайт;
  освобождаются при следующем снимке;
* **экономия контекста** от п.12 больше, чем перерасход от более богатого
  снимка: сейчас каждый шаг браузера навсегда оставляет в контексте до 6 000
  символов;
* внешние сервисы: не нужны. Docker, WSL2, облако — ничего.
  Офлайн-работа сохраняется полностью.

Против бюджета машины (128 ГБ unified memory, память общая с моделями) вариант
«взять приёмы» стоит ~0, вариант «взять библиотеку» — сотни мегабайт и чужой
набор SDK в нашем процессе.

## 12. Критерии приёмки

Проверяемые утверждения после этапов 1–2.

1. `browser.read_dom` на фикстуре возвращает для каждого интерактивного
   элемента `ref`, и `browser.click(ref=...)` по нему срабатывает — модели
   больше не нужно изобретать CSS-селектор.
2. Клик по `ref`, элемент под которым удалён из DOM, возвращает **не** ошибку
   и **не** таймаут: результат приходит быстрее 2 с и содержит инструкцию
   перечитать DOM. Соседний элемент при этом **не нажат** (проверяется по тексту
   страницы).
3. На странице с двумя кнопками одинакового вида действие по неоднозначному
   селектору отклоняется с перечислением кандидатов, а не выполняет `.first`.
4. `browser.click` по несуществующему `ref` укладывается в 5 с (сейчас — 30 с).
5. После `takeover()` → `resume()` `ref` из снимка до Take Over отклоняется как
   устаревший.
6. В снимке страницы с `<input type="password" value="секрет">` строки `секрет`
   нет ни в одном поле результата.
7. `browser.login` вызывается с `password_ref`, а не с паролем: в
   `tool_calls.args` в БД настоящего пароля нет; при несовпадении домена
   подстановка не происходит и действие отклоняется.
8. После клика, добавляющего кнопку, следующий снимок помечает её `*`.
9. Скрытый элемент (`display:none`) в снимке отсутствует.
10. `browser.scroll(down=True, pages=2)` меняет `pixels_above` в `page_info`.
11. `alert()` на странице не вешает шаг; текст алерта появляется в следующем
    снимке отдельным блоком.
12. Редирект с разрешённого домена на запрещённый останавливается, сессия
    остаётся живой, модель получает внятную ошибку.
13. После 10 шагов браузера длина контекста растёт не более чем на одну полную
    выдачу DOM (остальные схлопнуты до `one_line`).
14. **Регрессия гарантий (обязательно, без правок самих тестов):**
    `test_browser_payment_is_never_allowed`,
    `test_sensitive_browser_actions_ask_even_with_permission`,
    `test_human_takeover_blocks_agent_then_resume_works` проходят;
    `EXTERNAL_DATA_HEADER` присутствует в выдаче `browser.read_dom`.

## 13. Что не проверено

Честно, по пунктам.

1. **Реальные тяжёлые сайты.** Всё гонялось на локальной странице-фикстуре и на
   `about:blank`. Google, маркетплейсы, банковские SPA, Cloudflare — не
   проверялись: сеть в этой среде идёт через прокси, часть внешних запросов
   отбивается 403. Значит, утверждение «их движок надёжнее на реальных сайтах»
   я **не подтвердил измерением** — оно опирается на чтение кода и на объём
   их обработанных краевых случаев.
2. **Их полный агентный прогон с настоящей LLM.** Использовался фиктивный
   endpoint. Качество их промпта и action space в бою не измерялось; их action
   JSON в моём фейке был отвергнут валидацией (`index: 0` — недопустим), то
   есть полный цикл «модель → действие → страница» проверен только на
   `navigate`/`done`.
3. **`ElementHandle` как замена `backendNodeId`.** Утверждение, что
   Playwright-хендл ведёт себя эквивалентно (не «переезжает», а становится
   detached), взято из семантики Playwright и **не проверено экспериментом в
   нашем рантайме**. Это первое, что нужно проверить на этапе 1: тест на
   перерисовку списка между снимком и кликом.
4. **Стоимость фильтра видимости.** `elementFromPoint` на 200 элементов может
   стоить заметно на тяжёлых страницах — не замерялось.
5. **Их поведение внутри iframe и shadow DOM.** В моём дампе появлялись
   префиксы `|SHADOW(open)|` на обычных `<input>`/`<select>`, где никакого
   shadow DOM нет, — похоже на дефект их сериализатора. Глубоко не разбирал;
   для нас важно, что iframe/shadow у нас не поддержаны вообще.
6. **`search_page` у них зависал** в моём standalone-эксперименте (шаг не
   завершился за 150 с). Причина не выяснена — возможно, моя схема вызова, а не
   их баг. Приём (grep по странице без токенов) от этого не хуже, но их
   реализацию копировать вслепую не стоит.
7. **Долгие сессии, устойчивость профилей, `storage_state`, скачивания,
   несколько вкладок** — не проверялись.
8. **Потребление RAM браузером** под нагрузкой (много вкладок) — не мерил ни у
   них, ни у нас.
9. **Их `demo_mode`, `har_recording`, `recording`, `judge`** — прочитаны
   поверхностно, в оценку не входили.
10. **Совместимость их strict structured output с нашими локальными моделями**
    через `bcc/v2/model_router.py` — не проверялась. Для варианта «взять идеи»
    это неважно, для варианта «второй бэкенд» это был бы отдельный риск.

### 14.1 Почему бенчмарка A/B из десяти задач нет

Он требует двух вещей, которых в этой среде нет одновременно:

1. **Настоящей модели с tool calling.** Прогон шёл на фиктивном OpenAI-endpoint'е.
   Сравнивать «доля успеха A против B» на фиктивной модели бессмысленно: измерялся
   бы мой сценарий, а не движки.
2. **Настоящих тяжёлых сайтов.** Внешняя сеть идёт через прокси, часть запросов
   отбивается 403. Google, маркетплейсы, банковские SPA недоступны — а именно на
   них и держится единственное преимущество browser-use, которое стоило бы денег.

Гонять A/B на локальной странице-фикстуре я не стал сознательно: на простой
странице оба движка проходят все задачи, и цифра «10/10 против 10/10» создала бы
ложное впечатление проверенного паритета. Пустая клетка честнее подделанной.

**Это не блокирует вердикт.** Вердикт «ВЗЯТЬ ИДЕЮ» опирается не на сравнение
успеха, а на десять воспроизведённых дефектов НАШЕГО рантайма (§4.2) — они
существуют независимо от того, насколько хорош browser-use.

### 14.2 Условие возврата — измеримое

Возвращаемся к вопросу «взять browser-use как изолированный тяжёлый режим»
только при выполнении **любого** из трёх условий, и каждое проверяется цифрой:

1. **После этапов 1–2 из §11 набор приёмки §12 даёт < 12 из 14 пунктов.**
   То есть приёмы, взятые словами, не дали надёжности, и нужен их движок целиком.
2. **Три подряд задачи на реальных сайтах, воспроизведённые в тестах, падают у
   нас и проходят у них.** «Воспроизведённые» — обязательное слово: разовый
   провал не считается, нужна фикстура, которую можно прогнать дважды.
3. **Наша доля успеха на браузерных задачах миссии за месяц < 70 %** при том, что
   тот же набор задач у их движка ≥ 85 %. Метрику даёт `skill_evaluations` по
   браузерному скиллу — с V2.2 §7 она наконец есть.

Пока ни одно условие не выполнено и проверить их нечем, browser-use остаётся
источником приёмов, а не зависимостью.
