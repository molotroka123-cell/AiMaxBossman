## 1. Что такое Genjutsu

**Genjutsu** — инструмент Higgsfield «видео → видео» (страница `https://higgsfield.ai/genjutsu`,
блог `https://higgsfield.ai/blog/higgsfield-genjutsu`). Он умеет два действия.

| Функция | Что сохраняется из исходника | Что меняется |
|---|---|---|
| **Motion Transfer** | движение, камера, тайминг | персонаж и/или сцена пересобираются по референсам |
| **Object Swap** | весь кадр, кроме выбранного объекта | один выбранный объект: персонаж, одежда, продукт, локация, предмет |

Цитаты из блога [ПРОВЕРЕНО 2026-10-05]:
- Motion Transfer: «uses the motion from an existing video as a reference, then applies that movement to a new character or rebuilt scene».
- Object Swap: «replaces the object or element you specify while preserving the rest of the original footage».

Ограничения и параметры [ПРОВЕРЕНО по блогу]:
- длина входного видео от 4 до 30 с;
- до 30 референс-изображений на одну генерацию;
- промпт необязателен, вместо него можно выбрать пресет («a preset alone can drive the entire change»);
- выход до 1080p;
- работает и на снятом, и на сгенерированном видео;
- цена за 15 с: 480p стоит 40 кредитов ($2.00), 720p стоит 104 кредита ($5.20), 1080p стоит 144 кредита ($7.20);
- **базовая модель не раскрыта.**

Маршрут в Higgsfield MCP [ПРОВЕРЕНО по инструкциям сервера]: оба действия идут через
`generate_video`. Motion Transfer использует модель `hf_mult_motion_control`, Object Swap использует
`hf_mult_replace_object`. Legacy-`motion_control` и `ad-multiplier` для одной правки Genjutsu не
используются. На аккаунте Higgsfield сейчас 0 кредитов (из памяти чекпоинта 30.09), поэтому облачный
эталон для сравнения пока недоступен без решения владельца.

## 2. Как это, скорее всего, устроено технически

Higgsfield архитектуру не раскрывает, поэтому этот раздел **[НЕ ПРОВЕРЕНО]**. Это реконструкция по
открытым аналогам, которые дают такой же набор функций.

```
исходное видео ──► извлечение управляющих сигналов ──┐
                    • поза (скелет тела/рук/лица)    │
                    • глубина / контуры (камера, сцена)│
                    • маска объекта по кадрам (Swap) │
референсы (1..30) ──► энкодер внешности / VAE-латенты ─┤
промпт / пресет ──► текстовый энкодер ────────────────┤
                                                      ▼
                     видео-диффузионный трансформер (DiT) с
                     условием «контекст + маска + референс»
                     (класс моделей VACE / Wan-Animate)
                                                      ▼
                     VAE-декодер ─► апскейл до 1080p ─► композит
                     с исходником вне маски (Swap) ─► звук из исходника
```

Почему это вероятная схема:
1. **VACE** (ali-vilab, Apache-2.0) обучен ровно на этих задачах: R2V (видео по референсу), V2V
   (видео по позе, глубине, потоку, серому, скетчу, раскладке) и MV2V (правка видео по маске).
   Авторы прямо называют комбинации «Swap-Anything», «Animate-Anything» и «Move-Anything»
   [ПРОВЕРЕНО: github.com/ali-vilab/VACE].
2. **Wan2.2-Animate-14B** (Apache-2.0) имеет режимы *animation* (персонаж с картинки повторяет движение
   из видео; это Motion Transfer) и *replacement* (персонаж в видео заменяется персонажем с картинки;
   это Object Swap для людей). Предобработка у него такая: поза, лицо, маска через SAM2, ретаргетинг
   [ПРОВЕРЕНО: huggingface.co/Wan-AI/Wan2.2-Animate-14B].
3. Видимые ограничения Genjutsu (30 с, 1080p) сходятся с типовой реализацией: генерация сегментами
   по ~5 с, сшивка и апскейл. Ограничение в 30 референсов указывает на отдельный энкодер внешности
   (несколько ракурсов одного объекта), а не на одну картинку в латенте.

Вывод для локальной версии: нужны три блока. (a) Извлечение управляющих сигналов (поза, глубина,
маска). (b) Видео-DiT, который принимает «контрольное видео + референс». (c) Постобработка:
композит, звук, сшивка сегментов.

### 3.2. Пайплайн A: Motion Transfer

```
src.mp4 ─ffmpeg→ кадры 16 fps, 4k+1 штук ─DWPose ONNX→ скелеты на чёрном (PNG)
                                         └Depth-Anything-V2-S ONNX→ глубина (PNG, по желанию)
ref.png (персонаж на чистом фоне, тот же аспект) ──┐
pose/ (или pose+depth/) ───────────────────────────┤
промпт (внешность + сцена) ────────────────────────┴► sd-cli VACE ─► out.webm
out.webm + звук из src ─ffmpeg→ out.mp4 ─► приёмка (раздел 4.3)
```

**Шаг A1. Нормализация исходника.** Wan работает на 16 fps. Число кадров на сегмент должно иметь
вид 4k+1 (17/33/49/65/81).

```powershell
$W=832; $H=480; $N=33          # горизонтальное видео; для вертикального W=480 H=832
$job="C:\Users\asd\Bossman\media-work\genjutsu\job-001"
New-Item -ItemType Directory -Force "$job\src","$job\pose","$job\depth","$job\ctrl" | Out-Null
ffmpeg -y -i src.mp4 -vf "fps=16,scale=${W}:${H}:force_original_aspect_ratio=increase,crop=${W}:${H}" `
       -frames:v $N "$job\src\%04d.png"
ffmpeg -y -i src.mp4 -vn -c:a aac "$job\audio.m4a"   # если звука нет, команда упадёт; это нормально
```

**Шаг A2. Поза.** Скрипт `tools/genjutsu_prep.py pose` (его нужно написать, около 200 строк; numpy,
Pillow и onnxruntime уже стоят в рантайме):
1. YOLOX-L (`yolox_l.onnx`, вход 640x640) находит рамки людей (class 0, score > 0.5, NMS).
2. DWPose (`dw-ll_ucoco_384.onnx`, вход 288x384, выход SimCC) даёт 133 точки на рамку.
3. Рисует скелет в стиле OpenPose (18 точек тела + руки + лицо, цветные конечности на **чёрном фоне**)
   через `PIL.ImageDraw`. **OpenCV не нужен**, лишний неподписанный `cv2.pyd` не тянем.
4. Пишет `pose\0001.png …`. Имена с нулями обязательны: sd-cli сортирует файлы лексикографически.

Когда добавлять глубину: если важно сохранить **камеру и геометрию сцены** («rebuilt scene» в терминах
Genjutsu), берётся `pose+depth`. Так сделано в примере sd.cpp `post+depth`: скелет накладывается поверх
глубины. Если персонаж-замена сильно отличается телосложением, берётся только поза, иначе глубина
«вытягивает» силуэт исходного актёра.

**Шаг A3. Референс.** Один PNG. Персонаж в полный рост на нейтральном фоне, аспект как у выхода,
лучше в позе, близкой к первому кадру. Из нескольких фото выбирается одно (у sd.cpp VACE один
референс, см. 3.0). Коллаж из нескольких ракурсов в одном PNG ничем не подтверждён: **[НЕ ПРОВЕРЕНО]**,
это отдельный эксперимент.

**Шаг A4. Генерация (шаблон, 1.3B).**

```powershell
$SD ="C:\Users\asd\Bossman\media-runtime\sdcpp\vulkan\sd-cli.exe"
$M  ="C:\Users\asd\Bossman\models\media"
& $SD -M vid_gen `
  --diffusion-model "$M\wan21-vace-1.3b\wan2.1-vace-1.3b-q8_0.gguf" `
  --vae            "$M\wan21-vace-1.3b\wan_2.1_vae.safetensors" `
  --t5xxl          "$M\wan22-ti2v-5b\umt5-xxl-encoder-Q8_0.gguf" `
  -p "<кто в кадре, одежда, сцена, свет; описывать результат, а не исходник>" `
  -n "<стандартный негатив Wan из docs/wan.md>" `
  -i "$job\ref.png" --control-video "$job\pose" --vace-strength 1.0 `
  -W $W -H $H --video-frames $N --fps 16 `
  --steps 20 --cfg-scale 6.0 --sampling-method euler -s 42 `
  --offload-to-cpu --temporal-tiling `
  -o "$job\out.webm" -v
```

- `--diffusion-fa` **сначала A/B**. В живом прогоне 2026-09-21 TI2V-5B с `--diffusion-fa`/`--vae-tiling`
  при 480x288 дал цветной шум, причина не изолирована (`SDCPP_ENGINE_RU.md`). При этом **без FA
  память внимания растёт квадратично**, см. 3.4. Порядок проверки: 17 кадров с FA и без FA, сравнить
  кадры. Если FA даёт чистый результат, оставить его для всех длин > 33.
- `--vace-strength`: начинать с 1.0. Если поза «продавливает» внешность исходника, пробовать 0.7–0.9.
- Ракурс: 832x480 / 480x832 для 1.3B (родное разрешение около 81x480x832). Для 14B до 1280x720.

**Шаг A5. Сборка.**
```powershell
ffmpeg -y -i "$job\out.webm" -i "$job\audio.m4a" -map 0:v -map 1:a? -c:v libx264 -pix_fmt yuv420p -crf 18 -shortest "$job\out.mp4"
```

**Длинные видео (4–30 с, как у Genjutsu).** 30 с при 16 fps дают 481 кадр. Получается 6 сегментов
по 81 кадру со стыковкой по одному кадру, так же, как у существующего `segments_for()` в провайдере.
Честное ограничение: из-за того, что маска в sd.cpp равна единице везде, нельзя сказать модели «первые
кадры сегмента уже готовы, продолжи». Стыки удерживаются только общим референсом, сидом и промптом,
поэтому на стыках вероятен скачок цвета или деталей. Смягчение: перекрытие 8 кадров и кроссфейд в ffmpeg
(`xfade`). Основной режим v1: **один сегмент до 81 кадра (около 5 с)**.

### 3.3. Пайплайн B: Object Swap

```
src кадры ─► рамка объекта на 1-м кадре (клик владельца | Qwen3-VL bbox | Grounding DINO)
          ─► SAM2.1-tiny ONNX по кадрам (рамка протягивается от маски t к t+1)
          ─► маски: расширение 8–16 px, сглаживание по времени (медиана по 3 кадрам)
          ─► контрольные кадры: исходник, где область маски залита серым 127
             (+ по желанию поза или глубина объекта ВНУТРИ маски, для формы)
ref.png (новый объект или персонаж на белом фоне) ─┐
промпт (новый объект в этой сцене) ────────────────┴► sd-cli VACE ─► gen.webm
gen + src + маски ─► КОМПОЗИТ: out = src·(1−m̃) + gen·m̃  (m̃ = маска с растушёвкой)
                 ─► подгонка цвета в кольце вокруг маски ─► out.mp4 ─► приёмка
```

**Почему именно так.** Нативный VACE-инпейнтинг требует маски, а в sd.cpp она зашита в единицы
(3.0, п. 3). Поэтому:

- **Вариант B1 (stock-бинарь, путь v1).** Модель получает «исходник с серой дырой» как контекст при
  маске = 1 и перерисовывает весь кадр. Затем **гарантия сохранения фона даётся композитом**: вне маски
  пиксели берутся из исходника байт в байт. Как VACE поведёт себя на сыром RGB-контексте при маске = 1
  (будет ли фон близок к исходнику, займёт ли новый объект именно дыру), **[НЕ ПРОВЕРЕНО]**. Это
  первый эксперимент пайплайна B. Если объект «вытекает» за дыру, его обрежет композит. Если объект
  в дыре не появляется, нужно добавить в контрольные кадры силуэт или позу внутри маски и снизить
  `--vace-strength`.
- **Вариант B2 (правильный, требует изменения движка).** Добавить в sd.cpp флаг `--control-mask <dir>`:
  кадры маски подставляются вместо `sd::full(..., 1.0f)` и в `mask_context`, это около 30–50 строк
  в `src/pipeline/video.cpp` и CLI. **Локальная сборка не годится**: свежий неподписанный exe без
  репутации — именно то, что режет SAC. Путь по правилу «сначала open source»: PR в
  `leejet/stable-diffusion.cpp` → официальная release-сборка → пин sha256 в `MANIFEST.json`. Сколько
  ждать, неизвестно.

**Шаг B1. Маски** (`tools/genjutsu_prep.py mask --box x0,y0,x1,y1`):
1. SAM2 vision encoder на кадре (1024x1024, нормализация ImageNet) → эмбеддинги.
2. Prompt encoder + mask decoder с рамкой → маска 256x256 → апсемпл до W x H → порог 0.
3. Рамка следующего кадра равна bbox текущей маски плюс 12 %. Если площадь маски скачет больше чем на 40 %,
   кадр помечается как «потеря трека», и задача останавливается с понятной ошибкой, а не
   генерирует мусор.
4. Расширение маски (`PIL.ImageFilter.MaxFilter(17)`), медиана по времени, сохранение `mask\0001.png`.

**Шаг B2. Контрольные кадры:** `ctrl\NNNN.png = where(mask, 127, src)`.

**Шаг B3. Генерация.** Шаблон A4 с `--control-video "$job\ctrl"` и `-i "$job\obj_ref.png"`. Промпт
описывает **итоговый кадр** с новым объектом.

**Шаг B4. Композит** (`tools/genjutsu_prep.py composite`, numpy + Pillow):
`m̃ = GaussianBlur(mask, r=6)/255`, `out = src*(1−m̃) + gen*m̃`. Перед смешиванием сопоставляются
среднее и дисперсия цвета `gen` с `src` в кольце 16 px вокруг маски, по каналам в Lab или просто в RGB.
Композит — **отдельный этап с собственным хешем в трассе**, по аналогии с транскодом, чтобы склейка
не выдавалась за генерацию (граница честности провайдера).

Ограничения B: объект другой формы (бутылка → кроссовок) упирается в форму маски. Маску надо расширять
до нужного силуэта вручную или рамкой. Тени и отражения старого объекта вне маски останутся.

### 3.4. Бюджеты: разрешение, кадры, время, RAM

**Исходные замеры:** TI2V-5B, 17 кадров, 640x1152, 24 шага ≈ 510 с, то есть около 21 с/шаг, около
3.6 тыс. токенов (VAE 16x + патч 2). Задача на 81 кадр 704x704 исчерпала 120 ГБ. Причина **не
изолирована**. Гипотеза: декод Wan2.2-VAE на 81 кадре без тайлинга [НЕ ПРОВЕРЕНО].

**Токены у VACE (Wan2.1 VAE 8x, патч 2x2):** 832x480 даёт 52x30 = 1560 токенов на латентный кадр.
Латентных кадров (N−1)/4+1 плюс 1 на референс.

| Кадры (16 fps) | Латентных (+ref) | Токены | Матрица внимания без FA, 1.3B (12 голов, fp32) | То же, 14B (40 голов) |
|---|---|---|---|---|
| 17 (1.06 с) | 6 | 9.4k | ≈ 4 ГБ / слой | ≈ 14 ГБ / слой |
| 33 (2.06 с) | 10 | 15.6k | ≈ 12 ГБ | ≈ 39 ГБ |
| 49 (3.06 с) | 14 | 21.8k | ≈ 23 ГБ | ≈ 76 ГБ ⚠ |
| 81 (5.06 с) | 22 | 34.3k | ≈ 56 ГБ ⚠ | ≈ 188 ГБ ✗ |

[ОЦЕНКА: предполагается, что ggml держит `QK^T` целиком в fp32 на один слой. С `--diffusion-fa`
память линейна и эти цифры не применяются.]

**Расчётное время** (масштабирование от 510 с по FLOP, эффективная производительность около 4 TFLOPS,
CFG = 2 прохода, 20 шагов) [ОЦЕНКА, заменить замером]:

| Модель | 832x480x17 | 832x480x33 | 832x480x81 |
|---|---|---|---|
| VACE 1.3B Q8 | ≈ 10 мин | ≈ 20 мин | ≈ 75 мин |
| VACE 14B Q4_K_M | ≈ 1.2 ч | ≈ 2 ч | ≈ 9 ч ✗ |
| VACE-Fun A14B (2 эксперта, активен 1) | как 14B | как 14B | ✗ |

Плюс загрузка весов, umt5 и декод VAE: ещё 1–3 мин на задачу.

**Консервативная лестница (не перескакивать ступени):**

| Ступень | Модель | Размер | Кадры | Шаги | Флаги | Условие перехода |
|---|---|---|---|---|---|---|
| L0 | 1.3B Q8 | 832x480 | 17 | 20 | без FA, `--temporal-tiling`, `--offload-to-cpu` | ролик проходит приёмку, пик RAM < 60 ГБ |
| L0-FA | 1.3B Q8 | 832x480 | 17 | 20 | + `--diffusion-fa` | кадры не шумные (визуально и по метрикам A/B) |
| L1 | 1.3B Q8 | 832x480 | 33 | 20 | FA, если L0-FA чистый | пик < 70 ГБ |
| L2 | 1.3B Q8 | 832x480 | 49 | 20 | FA обязателен | пик < 80 ГБ |
| L3 | 1.3B Q8 | 832x480 | 81 | 20 | FA обязателен | пик < 85 ГБ |
| Q1 | 14B Q4_K_M | 832x480 | 17 | 20 | FA обязателен | только после L3 |

**Сторож RAM — обязательное условие для любого прогона.** Отдельный процесс опрашивает раз в 2 с
`\Memory\Committed Bytes` и `\Memory\Available MBytes`. Если доступно меньше 16 ГБ, он **убивает
`sd-cli`** и пишет `OOM_GUARD` в трассу. Сегодняшний OOM показал, что без сторожа под удар попадают
LLM-модели (MAIN/FAST) и десктоп. Во время медиа-задачи держать резидентным не больше одной LLM.

### 3.5. Как остаться в рамках Smart App Control

1. **Никаких новых нативных бинарей**, кроме уже работающих: `sd-cli.exe` + его DLL (`74988b2`), `ffmpeg`.
   Не ставить torch, ROCm, ComfyUI или opencv. Не собирать sd.cpp локально.
2. Предобработка выполняется **только** в Python рантайме Bossman, где `numpy`, `Pillow` и
   `onnxruntime` уже проходят SAC [ПРОВЕРЕНО]. ONNX Runtime DLL подписаны Microsoft [ПРОВЕРЕНО].
   CPU-провайдера хватает: DWPose, DA2-small и SAM2-tiny на 81 кадр — это минуты, а не часы [ОЦЕНКА].
3. `onnxruntime-directml` по желанию и **в отдельном venv**: он конфликтует с `onnxruntime` в одном
   окружении. Его DLL тоже подписаны Microsoft, но работа на gfx1151 **[НЕ ПРОВЕРЕНО]**. Если SAC
   заблокирует что-то в нём, возвращаемся на CPU.
4. Новый движок появляется только как **официальная release-сборка** с GitHub. При первом запуске
   нужно смотреть журнал `Microsoft-Windows-CodeIntegrity/Operational`: события 3077/3033 означают
   блокировку. Если SAC заблокировал, отказываемся от сборки, а не выключаем SAC.
5. Веса моделей (`.gguf`, `.onnx`, `.safetensors`) — данные, а не код. SAC на них не реагирует.

### 4.1. MANIFEST.json (новые записи)

    "vae":          {"path": "wan21-vace-1.3b/wan_2.1_vae.safetensors",      "bytes": <из HF>, "sha256": "<посчитать>"},
    "text_encoder": {"path": "wan22-ti2v-5b/umt5-xxl-encoder-Q8_0.gguf",      "bytes": 6043068256,

Общий файл (`umt5`) указывается тем же путём. Схема это уже допускает: `flux1-schnell` использует

### 4.2. Изменения в провайдере (минимальные)

1. `ENGINES` / `REQUIRED_ROLES`: `"sdcpp:wan2.1-vace-1.3b"` и `"sdcpp:wan2.1-vace-14b"` с ролями
   `("diffusion","vae","text_encoder")`.
2. Новая входная роль `control`: **каталог PNG**, созданный `tools/genjutsu_prep.py` внутри рабочего
   каталога задачи. Провайдер проверяет: число файлов не больше `frames`, все файлы PNG одного размера
   `W x H`, имена только `^\d{4}\.png$`, каталог внутри job-dir (без выхода через `..`). Роль
   `reference` (уже есть в `ALLOWED_INPUT_ROLES`) передаётся как `-i`.
3. Ветка `_argv` для VACE: `-M vid_gen --diffusion-model --vae --t5xxl -i <ref> --control-video <dir>
   --vace-strength <s> --video-frames --fps 16 --sampling-method euler --cfg-scale --offload-to-cpu
   --temporal-tiling [--diffusion-fa по итогам A/B]`.
4. Для Swap пост-этап `composite` с отдельным хешем в трассе (generation → composite → transcode → import).
5. Сторож RAM (3.4) встраивается в существующий контроль процесса (`CANCEL_WAIT_S`/`KILL_WAIT_S`).

### 4.3. Пресеты каталога (`tools/studio_models.json`)

|---|---|---|---|
| `sdcpp:wan2.1-vace-1.3b` + пресет `genjutsu-motion` | video | `width/height` ∈ {832x480, 480x832}; `frames` ∈ {17,33,49,65,81}; `fps` = 16; `steps` 16–30 (20); `cfg_scale` ∈ {5.0, 6.0}; `vace_strength` 0.5–1.0 | `reference: 1`, `control: 1` (pose / pose+depth) |

`deadline_seconds` считается по замерам лестницы L0–L3, а не по формуле `_REFERENCE_WORK` для TI2V.

### 4.4. Приёмочные тесты

Тесты на `MOCK_ENGINE` проверяют только проводку. **Доказательством генерации они не являются.**
Живая приёмка:

1. **ffprobe**: кодек h264, `W x H` как в запросе, `nb_frames` и длительность в допуске
   существующего `duration_mismatch()` (2 кадра или 5 %).
2. **Полный декод**: `ffmpeg -v error -i out.mp4 -f null -` без единой строки в stderr. Это существующий `runtime.verify_file`.
3. **Не копия исходника**: средняя абсолютная разница с `src` выше порога (для Motion Transfer по
   всему кадру, для Swap внутри маски).
4. **Движение сохранено** (Motion Transfer): DWPose на выходе против контрольных скелетов, PCK@0.1
   ≥ 0.7 по видимым точкам тела [порог ОЦЕНКА, калибровать на L0].
5. **Фон сохранён** (Swap): PSNR вне расширенной маски ≥ 40 дБ после композита (практически
   тождественно). До композита PSNR пишется в трассу как диагностика варианта B1.
6. **Идентичность** с референсом: косинус эмбеддингов DINOv2-small (ONNX) между `ref.png` и
   кропами по маске или позе на 5 равномерных кадрах ≥ порога, откалиброванного на парах
   «тот же / другой». Второе мнение даёт локальный Qwen3-VL-8B («тот же ли это персонаж/объект? да/нет
   + причина»). Ответ VLM — сигнал, а не вердикт.
7. **Мерцание**: медиана межкадровой разницы выхода не больше чем в 2 раза медианы исходника.
8. **Трасса**: хеши на каждом этапе. `backend` берётся из лога (`observe_backend`), иначе UNVERIFIED.
   `completed` ставится только при прохождении 1–3.

### 4.5. Риски интеграции

- Без FA память внимания растёт квадратично, а с FA есть непонятый «цветной шум». Тупик возможен на
  длинах > 33 кадров (лечится только A/B на L0).
- Локальный `74988b2` может отличаться от master по VACE-Fun (проверяется прогоном).
- Каталог `control` — новая поверхность для path traversal и бомб из файлов. Нужны проверки из 4.2.2
  и red-team-тест в духе `test_studio_sdcpp_hostile.py`.
- Задача на 1–9 часов блокирует iGPU. Нужна очередь «не больше 1 медиа-задачи» и уведомление в пульт.
