# Bossman Tree: подготовка навыков и OSS-кандидатов

Дата: 2026-10-07  
Состояние: подготовлено к завтрашней оценке; навыки и проекты пока не установлены и не подключены к runtime Bossman.

## Зачем и откуда список

Это 15 подготовленных карточек навыков: 10 для работы с компьютером и браузером и 5 для оркестрации, кода и технического письма. Они описывают повторяемые приёмы, которые используются при управлении браузером и экраном: сначала наблюдать состояние, выбирать цель по видимым данным, выполнять ограниченное действие, затем проверять результат. Это не утверждение, что инструменты Codex уже доступны Bossman.

Ссылка владельца ведёт к ветке Open source в Bossman Tree: https://molotroka123-cell.github.io/subtle-baklava-676893/#/n/oss-119. Узел `oss-119` — `modelcontextprotocol/servers`: справочные реализации MCP. Авторы проекта прямо предупреждают, что это учебные примеры, а не готовые production-серверы. В каталоге Bossman уже есть связанные ссылки на Agents SDK (`oss-113`), LangGraph (`oss-114`), MCP Python SDK (`oss-117`), FastMCP (`oss-118`), CrewAI (`oss-116`), Temporal (`oss-121`), Superpowers (`oss-71`) и Anthropic Skills (`oss-72`).

## План внедрения и доказательство пользы

1. Завтра открыть кандидатов в Bossman Tree и сверить их с существующими `computer`/`skills` листьями. Не создавать второй браузерный или агентный runtime: подключать при необходимости только адаптеры к текущему Bossman.
2. Для каждого выбранного OSS-проекта проверить текущую лицензию, зависимости, активность, security notices, локальность данных и модельные расходы. Лицензии библиотек и весов проверять отдельно.
3. Начать с узкого сравнения Playwright как детерминированной основы; Browser Use, Stagehand и OmniParser оценивать как альтернативные/дополняющие кандидаты, не подключать все сразу.
4. До внедрения зафиксировать одинаковые задачи и условия baseline/candidate: одна машина, браузер, модель и набор страниц. Измерить успех, время, число шагов, ошибочные клики/вводы, обращения к владельцу и стоимость. Добавить новые удержанные сценарии и отрицательные контроли.
5. Проверить, что запрет на внешнюю отправку без одобрения, локальные секреты, STOP, лимиты и изоляция сохраняются. Полезный кандидат должен пройти функциональные/regression проверки и независимый просмотр diff.
6. Принять навык в рабочий runtime только после измеримого выигрыша и одобрения владельца. До этого tree status остаётся `prepared` для навыков и `recorded` для OSS-ссылок.

## Связь с доказательством пользы

Код, ссылка на репозиторий, зелёный unit-test или красивый demo сами по себе не доказывают полезность. Сохранять для пилота коммит, конфигурацию, задачи, сырые результаты baseline/candidate, отрицательные контроли, ошибки, ресурсы и явное решение владельца. Утверждать только то, что реально измерено.
