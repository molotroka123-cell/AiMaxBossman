# 11. Восстановление и откат (сверено 11.10.2026)

## 1. Откат приложения

Пошаговая процедура: `docs/owner/ROLLBACK_RU.md`. Суть: каждый архив `BOSSMAN-Windows-x64-<SHA>` самодостаточен,
данные лежат отдельно в `%LOCALAPPDATA%\Bossman\CommandCenter` (или `BCC_DATA_DIR`), поэтому откат = запуск `Start-Bossman.cmd`
прежнего архива. Перед первым запуском нового архива: не удалять прежний, скопировать папку данных
(`Copy-Item $d "$d.bak-<время>" -Recurse`), записать SHA-256 нового ZIP. Если новая версия мигрировала БД и старая её не
открывает: переименовать текущую `CommandCenter` в `CommandCenter.failed-<время>` и вернуть `.bak`.
Откат НЕ возвращает файлы, изменённые агентом в папках владельца, и не отменяет внешние действия.

Ловушка: если `BCC_DATA_DIR` не задан, исходная установка использует `<repo>/command-center/data`, установленная —
`%LOCALAPPDATA%`; это РАЗНЫЕ базы (`bcc/config.py::_data_dir`). Перед восстановлением убедитесь, какую из них открыл процесс.

## 3. Восстановление состояния автономии

* Журнал: `bossman autonomy journal verify` проверяет хэш-цепочку и `journal.head` (обрезание, правка, перестановка).
* Аренда писателя: устаревшая (нет heartbeat/нет процесса) перехватывается, осиротевшие процессы убиваются.
* Цикл: конечный автомат возобновляем; шаг USER_APPROVAL ждёт владельца; релиз только по ff-командам и откату, выданным панелью.
* Модельные сбои: отказ провайдера превращается в читаемый ответ владельцу, а не в тишину (`test_rc19_model_recovery.py`).

## 4. Git: как восстановиться

* Ветки не переписываются, force-push не используется; ветка с портами строится merge-коммитами (`merge(port): ...` в истории).
* Каноническая ветка и ночная ветка связаны слиянием; точное соотношение SHA записано в `docs/owner/WHERE_WE_STOPPED_20261011.md`.
* Вернуть один порт: `git revert -m 1 <merge-sha>`.
* Сырые данные (экспорты, видео, веса) под git не лежат; их резервную копию делает владелец (см. раздел 1).
