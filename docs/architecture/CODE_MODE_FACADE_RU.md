# Фасад «Code Mode» — архитектурная записка

## 1. Назначение и статус

Фасад «Code Mode» — опциональный режим, при котором модель вместо полного набора схем инструментов видит ровно две функции: `bossman_search(query, k)` и `bossman_run(code)`. Поиск возвращает Python-сигнатуры доступных инструментов, сниппет исполняет их через обычный конвейер движка.

Мотивация: при большом реестре схемы всех выданных инструментов уходят в `tools=[...]` каждого вызова модели. Подход Cloudflare «Code Mode» (blog.cloudflare.com/code-mode-mcp, github.com/cloudflare/mcp) показывает, что 2500 эндпоинтов, стоивших 1.17M токенов, сводятся к ~1000 через две функции.

Статус:

| параметр | значение |
|---|---|
| ветка | `feat/code-mode-facade-20261010` (от `feat/bossman-genjutsu-jeff-unified-20261010`) |
| по умолчанию | ВЫКЛЮЧЕН |
| backend / tool loop / permission / approval | без изменений, тот же код |
| новый «core» | не создан (AGENTS.md) |

## 2. Как было (baseline)

- `bcc.tools.ToolRegistry.resolve(allowed)` — `schema()` каждого выданного инструмента уходит в `tools=[...]` каждого вызова модели (`engine._run`).
- В bossman-core существует отдельный механизм `context_engine.prune_tool_schemas` (лексическая обрезка, `keep_min=10`, `_ALWAYS_TOOLS`). Он **не тронут** и работает иначе: режет набор инструментов, тогда как фасад набор не режет, а убирает схемы из контекста. Риск потери нужного инструмента при обрезке задокументирован (`test_fable_context_tool_overload`).

## 3. Дизайн

### 3.1 Инструменты фасада

- `bossman_search(query, k)` — BM25 (pure Python, без новых зависимостей) по имени, описанию, именам и описаниям аргументов; 4-символьные «стемы» для словоформ; бонус за слово в имени инструмента; стоп-слова ru/en. Возвращает Python-сигнатуры (типизированный SDK) 1..10 лучших (по умолчанию 5), с пометкой `[needs owner approval]` для ASK.
- `bossman_run(code)` — исполнение сниппета в дочернем процессе.

Оба инструмента **не в глобальном реестре**: нельзя выдать по имени, отсутствуют в capability manifest. Создаются в `bcc/code_mode/facade.py`.

### 3.2 Флаг включения

```
task.meta.code_mode (true/false)
  -> agent.permissions.code_mode (только литерал true; список прав флагом не является)
    -> env BOSSMAN_CODE_MODE
```

Модель флаг изменить не может. Режим включается только если у агента есть хотя бы один выданный инструмент. При включении модель видит ровно 2 схемы; выданные инструменты остаются исполняемыми (`tool_specs` движка = выданные + фасад).

### 3.3 Видимость в поиске

Видимость = выданные агенту инструменты (`allowed_tools_for`, живьём) минус:
- то, что политика запрещает при любых аргументах (`decide_effect({}) == deny`);
- почта владельца (`owner_only_denial`);
- всё вне периметра `TelegramToolPolicy` для агента, привязанного к гостю Telegram.

Нечитаемая конфигурация гостей -> fail-closed (считается гостем).

### 3.4 Песочница

`bossman_run` исполняет код в дочернем процессе: `python -I -S _child.py`, очищенное окружение без ключей/токенов, временный cwd, NUL stderr.

Диалект — статический allowlist AST:
- запрещены: `import`, `class`, `with`, `global`, `await`, `yield`, `**`, ловля `BaseException`, голый `except`;
- имена и атрибуты на `_` запрещены;
- атрибуты только из allowlist методов `str`/`list`/`dict`/`set`;
- `tools.<имя>` только для имён из каталога; `tools` нельзя присвоить, передать или затенить;
- урезанные builtins: `len`, `range`, `sorted`, `min`/`max`/`sum`, `isinstance`, `json_loads`/`json_dumps`, `re_findall`, `print` и т.п.; нет `type`/`getattr`/`open`/`eval`/`exec`/`__import__`.

Результат: `print()` + значение последнего выражения.

### 3.5 Схема потока

```
модель
  |
  | bossman_search(query, k)          bossman_run(code)
  v                                        |
facade.py (каталог, BM25)                  v
  |                              дочерний процесс (python -I -S)
  | сигнатуры 1..10              сниппет: tools.x(**kw) ...
  |                                        |
  |                                        v
  |                          engine._execute_tool_calls
  |                          (id "<внешний>~<n>", decide_effect,
  |                           правила владельца, context_deny,
  |                           bind_args, leases, fence, WAL,
  |                           STOP-проверка)
  |                                        |
  |                                        v
  |                          ToolResult.content -> песочница
  |                                        |
  v                                        v
вывод/значение последнего выражения -> модель
```

Каждый `tools.x(**kw)` — отдельный настоящий вызов инструмента движка (`TaskEngine._execute_tool_calls`): проверка «выдан ли», malformed args, `decide_effect` + правила владельца (floor/DENY), `context_deny`, `bind_args`, аренды (leases), строка `tool_calls`, fence, write-ahead неидемпотентных, STOP. Политика не переписана — вызывается тот же код.

### 3.6 ASK внутри сниппета

Песочницу нельзя припарковать (одобрение может ждать часами, возможен рестарт). Конвейер останавливается **до** создания одобрения (`facade_probe`), дочерний процесс убивается, внешний вызов `bossman_run` получает результат «needs_approval: tool args; остальная часть кода НЕ исполнялась», а тот же вызов подаётся в конвейер как обычный отдельный tool call (дописывается в тот же assistant-message, чтобы у каждого tool_call id был tool-ответ).

Владельцу задаётся вопрос про конкретный вызов: инструмент, канонические аргументы, `approval_digest` (инструмент + отпечаток реализации + аргументы + capability + контекст). Одобрение привязано к вызову, не к блоку кода. После решения исполняется ровно один раз с `ctx.approval_id`, выданным движком; отказ — ничего не исполняется; другой вызов того же инструмента спрашивает заново.

### 3.7 STOP и лимиты

- STOP: перед каждым внутренним вызовом проверяется статус задачи; Hard Cancel убивает дочерний процесс (finally).
- Лимиты: 60 с собственного вычисления кода (время внутри инструментов не считается, у них свои таймауты), 25 вызовов, 8000 символов вывода, 100k символов аргументов, 200k результата одного инструмента, код ≤ 20000 символов, ≤ 6000 узлов AST.
- Память: Windows Job Object (512 MB на процесс, `ActiveProcessLimit=1`, kill-on-close), POSIX `RLIMIT_AS`/`NPROC`.
- Промежуточные результаты инструментов остаются в песочнице — модель видит только вывод/значение.

## 4. Аргумент безопасности

| свойство | чем обеспечено | каким тестом доказано |
|---|---|---|
| модель не может изменить флаг | флаг только из meta/permissions/env, модель не участвует | test_code_mode_engine (default OFF, приоритет флага) |
| модель видит только разрешённые инструменты | видимость = `allowed_tools_for` минус `decide_effect({})==deny`, `owner_only_denial`, периметр `TelegramToolPolicy`; fail-closed при нечитаемой конфигурации гостей | test_code_mode_engine (запрещённый не виден в search; гость не видит почту владельца и terminal; нечитаемая конфигурация гостей скрывает всё вне периметра) |
| невыданный инструмент не исполняется | проверка «выдан ли» в `_execute_tool_calls` | test_code_mode_engine (невыданный инструмент недоступен) |
| DENY-правило действует внутри сниппета | тот же `decide_effect` + правила владельца | test_code_mode_engine (DENY-правило внутри сниппета = тот же отказ) |
| побег через gadget'ы (`__class__.__mro__`, `__globals__`, `gi_frame`, `str.format`, `__builtins__`, подмена `tools`) | статический allowlist AST; отклонение статически либо неисполнимость | test_code_mode_gadgets (39; в т.ч. «скомпрометированный» дочерний процесс: незаявленный инструмент, неверный id, не-JSON, неизвестный тип сообщения, превышение лимита вызовов — родитель завершает прогон как violation и не вызывает конвейер) |
| отсутствие секретов в дочернем процессе | очищенное окружение | test_code_mode_gadgets (окружение дочернего процесса без секретов) |
| дочерний процесс не остаётся после прогона | kill в finally; kill-on-close Job Object | test_code_mode_gadgets (дочерний процесс убит после прогона) |
| ограничение памяти/процессов | Windows Job Object (512 MB, ActiveProcessLimit=1), POSIX RLIMIT_AS/NPROC | test_code_mode_units (memory bomb) |
| ограничение времени/вывода/вызовов | 60 с, 8000 символов вывода, 25 вызовов | test_code_mode_units (timeout, abort, кап вывода, max_calls) |
| STOP/Hard Cancel | проверка статуса перед каждым внутренним вызовом; kill дочернего процесса | test_code_mode_engine (STOP прерывает между вызовами) |
| ASK: одобрение привязано к вызову, исполняется ровно один раз | `facade_probe` останавливает до создания одобрения; `ctx.approval_id` движка | test_code_mode_engine (ASK внутри run; одобрение исполняет ровно один раз; отказ ничего не исполняет; одобрение одного вызова не покрывает другой) |
| валидная история tool_call/tool-ответ | внутренний вызов дописывается в тот же assistant-message | test_code_mode_engine (история валидна) |
| фасад-инструменты не выдаются по имени | отсутствуют в глобальном реестре и capability manifest | test_code_mode_engine (не в реестре; `bossman.run` вне движка отказывает) |

## 5. Измерения

Реальный реестр этого checkout, 104 инструмента; скрипт `command-center/scripts/code_mode_token_report.py`. Прокси chars/4; cl100k_base через tiktoken (установлен вне репозитория).

| набор | инструментов | схемы за вызов, baseline (chars/4 / cl100k) | фасад за вызов (chars/4 / cl100k) | «типичный ход»: 4 вызова модели + 1 листинг поиска + 1 сниппет, baseline | фасад | доля |
|---|---|---|---|---|---|---|
| все зарегистрированные | 104 | 10153 / 12102 | 246 / 256 | 40613 | 1297 | 3.2% |
| типичный агент (terminal, memory, browser, computer, apps, code) | 36 | 3828 / 4955 | 246 / 256 | 15311 | 1314 | 8.6% |
| синтетический реестр (копии схем) | 500 | 48616 / 58819 | 246 / 256 | 194466 | 1319 | 0.7% |
| синтетический реестр | 2500 | 246100 / 295537 | 246 / 256 | 984401 | 1318 | 0.13% |

Оговорки:
- «Типичный ход» не включает результаты инструментов (фасад держит их в песочнице — выигрыш только больше) и не включает стоимость качества: сколько шагов потратит модель на поиск/ошибки в коде — **не измерено**.
- Листинг поиска (5 сигнатур) < 3500 символов.

Качество поиска на реальном реестре (top-3):

| запрос | результат |
|---|---|
| «run a shell command» | terminal.run |
| «open a web page» | browser.open |
| «send a telegram message» | plugin:telegram.send |
| «read my gmail inbox» | plugin:gmail.read |
| «click a button in the browser» | browser.click |
| «search memory» | memory.search |

Промахи (лексический поиск, нет синонимов): «fetch a url» не поднимает `plugin:http.get` в top-3; «query the database» не поднимает `plugin:sql.read`; описание `terminal.run` на русском, поэтому английский запрос находит его по имени, а не по описанию.

- Полный набор `command-center/tests` (667 файлов) не прогонялся.

## 7. Как включить

- На задачу: `meta: {"code_mode": true}` при создании задачи (API/CLI).
- На агента: `PATCH /api/agents/{id}` с `{"permissions": {"code_mode": true, ...}}` (сохраните остальные ключи `permissions`, включая `tool_rules`).
- Глобально: переменная окружения `BOSSMAN_CODE_MODE=1` перед запуском backend.
- Выключить: убрать флаг; `meta.code_mode=false` перекрывает агента и env.
- Замер: `python command-center/scripts/code_mode_token_report.py [--json]`.

## 8. Что НЕ сделано

1. **Нет OS-изоляции сети и файловой системы для дочернего процесса** (только Job Object: память, число процессов; POSIX rlimit). Защита = диалект без import/open/socket + пустое окружение. Побег из интерпретатора дал бы права пользователя ОС; это остаточный риск, не доказанный отсутствием. Нужен AppContainer/низкоинтегритетный токен или контейнер — не сделано.
2. **Первый ASK прерывает сниппет**: нет возобновления «с середины»; остаток модель пишет заново после решения. Если ASK-вызовов несколько — по одному на ход.
3. **Синтезированный tool_call** (имя внутреннего инструмента, которого нет в `tools` запроса) в истории не проверен на живых провайдерах (OpenAI-compat/Anthropic) — тесты офлайн. Если провайдер отвергает такое имя, нужен другой способ (вернуть результат в сообщении внешнего вызова).
4. **Не проверено на живых моделях**: напишет ли конкретная бесплатная модель корректный сниппет и сколько шагов потратит. Экономия — это токены схем, а не доля решённых задач. До включения по умолчанию нужен A/B на одинаковых задачах (Qwen/GLM/GPT-OSS) с учётом числа шагов и успеха.
5. **Поиск лексический** (BM25 + стемы), синонимы и кросс-язычные запросы не покрыты; эмбеддинги не добавлены (потребовали бы модель). `k` по умолчанию 5.
6. **Не включён для Jeff/PIT-участников** (PIT не использует engine tools; его периметр `TelegramToolPolicy` не менялся). bossman-core runner (`prune_tool_schemas`) не затронут.
7. **Gmail send / Computer Use отдельных тестов внутри фасада нет**: они идут через тот же конвейер (одобрение выдаётся движком в `ctx.approval_id`), что доказано общим тестом approval; специфичных e2e для gmail/CU под фасадом нет.
8. **Из ToolResult в песочницу попадает только `content`** (+ok, status); `data` не передаётся.
9. **Узкий диалект Python** в песочнице (нет классов, import, `**`, with, генераторов-yield, str.format); модели придётся писать простой код.
10. **Аренды (leases)** покрывают вызов внутри сниппета тем же кодом, но отдельного теста lease-под-фасадом нет.
11. **UI/дашборд не показывает фасад-специфичных данных** (в журнале видны внешний `bossman.run` и внутренние вызовы `id~n`).
12. **Hard Cancel (CancelledError) -> kill дочернего процесса в `finally`** проверен чтением кода; отдельного теста на этот путь нет (STOP через статус задачи — тестом доказан).
13. **Отметка North Star**: это функция экономии контекста, не ступень лестницы (SELF_IMPROVEMENT_INFRASTRUCTURE_PRESENT и выше без изменений); Terminal Run — тот же Bossman: CLI/дашборд/Telegram используют тот же backend и инструменты.
