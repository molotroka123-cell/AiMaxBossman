# Bossman speed pass 2 - 2026-09-30 (measured, not estimated)

Builds: before = snapshot of HEAD 05d58fa7 (`swarm-20260930/perf/before-src`), after = the same snapshot plus only the files listed
below (`perf/after-src`). Both run from a copy WITHOUT a `.git`, so the git calls of `bcc.build_identity` are not in either number
(measured separately). Machine: the owner's PC (Ryzen AI MAX+ 395, 32 threads), a low-priority test run and the live Jeff were
running during the measurements, so every value is the median of the stated number of runs and the before/after runs were
interleaved (control rows below). Raw values: `swarm-20260930/perf/raw/*.json|txt`, scripts: `swarm-20260930/perf/*.py`.
Builds on `docs/audits/PERF_20260929.md` (probe cache); nothing from it is repeated.

## Stand
Port 8848, `BCC_DATA_DIR` = a clean dir ("clean": wiped before every start) or a SYNTHETIC seeded copy ("seeded": 1200 tasks,
1755 runs, 60k run_events, 60k events, 6k tool_calls, 2k facts, 14 healthy models; only terminal statuses, no secrets). Real
owner data was not touched. Start = `python -X utf8 -m bcc.app` spawned from the harness; "listen" = first LISTEN socket (polled via
psutil: on this Windows box a connect to a closed loopback port takes 2.05 s, which would otherwise quantise every number in
0.5 s steps), "live" = first 200 on `/health/live`, "ready200" = first 200 on `/health`.

## What changed (tests: `command-center/tests/test_perf_20260930.py`, 11 tests; 9 are red on the old code, 2 are negative controls that are green on both: legacy DB still gets a missing column, a substitute HTTP transport is still asked)
1. `bcc/db.py` - indexes `ix_task_runs_task_id`, `ix_task_runs_status`, `ix_tool_calls_task_id`, `ix_approvals_task_id` (new DBs via `index=True`;
   existing DBs via `V2_NEW_INDEXES` + `CREATE INDEX IF NOT EXISTS` in `_migrate`, same pattern as `V2_NEW_COLUMNS`). `_migrate` also reads
   `PRAGMA table_info` once and stops issuing ~26 failing `ALTER TABLE ... ADD COLUMN` per start (each cost a connection and an exception).
2. `bcc/api.py` - `GET /api/tasks` reads the last run of every task with one query (`max(id) GROUP BY task_id`) instead of one per task; response shape unchanged.
3. `bcc/features/v15_autonomy.py` - `bossman_v3` (which pulls `bossman.resource_brain -> remote_client -> runner -> redis, asyncpg, playwright`, about 250 ms of
   importtime) is imported and the kernel built on first use of `/api/v15/autonomy/*` instead of at start. Behaviour change, stated: the
   `data/v1.5/society` directory now appears on first use, not at boot.
4. `bcc/features/v15_owner_run.py` - `subprocess.run` of a Python interpreter (and up to 30 s timeout) ran inside `async def` handlers; now `asyncio.to_thread`.
5. `bcc/features/skills.py` - catalog scan + sha256 of every SKILL.md (also run at each task start through `skills_for_task`) now in a thread. The hashing itself
   is kept on every call on purpose (it is the quarantine check); a stat-based cache was NOT added.
6. New `bcc/portcheck.py` + `bcc/features/apps.py` - on Windows a closed loopback port answers only after 2.05 s. The apps probe asks the socket table (psutil, ~2 ms)
   first and answers STOPPED at once; only for the real network client (`_probe_client`), substitute transports (tests) are still asked. Any doubt (no psutil, not
   loopback) falls back to the old network probe. This removed the 1.2 s first tick of `reality` that delayed `/health` ready by 1.2 s.
7. `bcc/build_identity.py` - the boot identity is reused as the first cache value: one git resolution (2 spawns, 37 ms measured in this checkout) fewer per start.
   Measured only as a micro-benchmark and by test (the snapshot has no `.git`), not in the table above.

## Not done / not confirmed (honest)
* Browser/UI load (request count, bytes, gzip, Cache-Control): NOT_RUN. Static files are served by `StaticFiles` with ETag and Last-Modified but no
  `Cache-Control` and no compression; on loopback this is expected to be NO_CHANGE, it matters over Tailscale/phone. No change made.
* Idle CPU of the background loops: NOT_RUN (the script exists, `idle_cpu.py`; the first attempt was killed by the lead's wrap-up).
* `PRAGMA synchronous=NORMAL` (WAL): not measured and not applied; it changes the durability promise on power loss and needs an owner decision.
* `task_history` (`/api/tasks/{id}/events`, `/api/events/stream?after=`) scans `events` with `json_extract` per row (32 ms p50 on 60k rows); an expression index was not attempted.
* `/api/agentmap`, `/api/studio/models`, `/api/video-studio/capabilities` still issue 17-25 statements (cheap now, N+1 shape remains).
* Other closed-port probes (`/api/coding-tasks/readiness` first call 4.1 s, `/api/opencode/health` 6.6 s, `/api/music/health` 2.2 s, `/api/offline` 1.8 s,
  `/api/watchdog` 1.5 s, `/api/jeff-settings/status` 1.0 s) have the same cause (2.05 s per closed loopback port). The probe cache only hides repeats; `portcheck` could
  be applied there, not done (other owners / time).
* `/health/live` still runs `git` (2 spawns, ~37 ms) on the event loop every 5 s in a dirty checkout; an installed build reads a file. Not changed.
* Lazy mounting of the 99 feature routers (route registration is still ~0.3 s of start) was not attempted.
* Numbers are from a synthetic DB and a shared, loaded machine; the ranking is reliable, the absolute milliseconds are not a promise for other data.
