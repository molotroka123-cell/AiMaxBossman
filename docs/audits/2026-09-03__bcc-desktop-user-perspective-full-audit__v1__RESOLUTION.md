## CR-1 — запуск без консоли больше не может умереть молча

Аудит просил две вещи, и обе сделаны, но в разных коммитах.

**Первая половина — `auth.py` — уже была починена владельцем в `60e74f4`**
(`bcc/auth.py:48,55`): `announce()` переводит поток в UTF-8 с
`errors="replace"`, а при отказе печатает ASCII-эскейпы. Проверено чтением
кода на текущем HEAD, а не по словам коммита.

**Вторая половина — перенаправление потоков процесса — сделана здесь.**
Под `pythonw` (ярлык без консоли) `sys.stdout` и `sys.stderr` равны `None`.
Защита в `auth.py` спасает только `auth.py`: любой другой `print` — uvicorn'а,
чужой библиотеки, трейсбека — по-прежнему падает
`AttributeError: 'NoneType' object has no attribute 'write'`, и двойной клик
умирает без единой строчки объяснения.

`desktop.bind_missing_std_streams()` подставляет вместо `None` файловый журнал
`<data_dir>/desktop-console.log` **до** того, как что-либо начнёт писать.
Дальше падать некуда: писать всегда есть куда, и написанное владелец может
переслать. Путь к журналу пишется в `desktop-run.log`, чтобы файл искали не
наугад. Если сам `data_dir` недоступен — подставляется `os.devnull`: поток
остаётся валидным в любом случае.

**Граница секрета, которую аудит не рассматривал.** После подстановки
`sys.stdout` перестаёт быть `None`, а значит `TokenAuth.announce()` снова
захотел бы напечатать токен — теперь уже в файл, который владелец пересылает
при разборе сбоя. Поэтому запуск без консоли одновременно:

- добавляет `--no-show-token` (баннер с токеном читать некому);
- ставит `BCC_TOKEN_STDOUT=0`, и `announce()` молчит.

Токен остаётся только в своём файле с правами 600. Явный `--show-token` при
этом уважается: если владелец попросил токен сам, он его получит — молча
отменять его выбор нельзя. С живой консолью не изменилось ничего: владелец
видит баннер и вводит токен в окне. Подмена только `stderr` (консоль жива)
токен не прячет.

Доказательства (`tests/test_ux2_desktop.py`):
`test_missing_std_streams_are_bound_to_a_file_log`,
`test_console_binding_is_a_no_op_when_a_console_exists`,
`test_std_streams_are_never_left_none_even_if_data_dir_is_unusable`,
`test_gui_console_log_keeps_previous_runs`,
`test_gui_launch_keeps_the_token_out_of_the_file_log`,
`test_console_launch_still_shows_the_token`,
`test_token_announce_is_silenced_when_output_goes_to_a_file`.

## CR-2 — закрыт, но не тем способом, который рекомендовал аудит

Диагноз аудита верен: `lifetime=0.0s` у 4 из 16 запусков — это Chrome
single-instance на общем профиле, а daemon-поток uvicorn умирает вместе с
процессом, и порт закрывается.

Рекомендация была: «проверять жив lock и **убивать зомби-процессы на целевом
порту**; после запуска ждать готовности сервера».

Сделана первая часть и отклонена вторая.

- **Живость lock — сделано** (`8f8990d`). `desktop.lock` теперь проверяется по
  живости pid, а не по факту существования файла: мёртвый lock снимается и
  пишет `stale-lock-cleared` в журнал. На Windows проверка идёт через
  `OpenProcess(SYNCHRONIZE)` + `WaitForSingleObject`, а не через
  `os.kill(pid, 0)` — последний на Windows вызывает `TerminateProcess` и убил
  бы проверяемый процесс. Тесты: `test_stale_lock_does_not_block_the_window`,
  `test_live_lock_still_refuses_a_second_window`, `test_pid_alive_is_honest`.
- **Ожидание готовности — уже было.** `_BackgroundServer.start(url)` опрашивает
  живой URL и возвращает `False` по таймауту; окно открывается только после
  этого, а при неудаче процесс выходит с кодом 3 и пишет причину.
- **Убийство процессов на порту — отклонено сознательно.** Порт 8800 может
  принадлежать чужому приложению владельца. Утилита запуска окна не имеет права
  убивать процессы, которых не создавала: цена ошибки — потерянная чужая
  работа, а выигрыш — экономия одного осмысленного сообщения. Вместо этого при
  занятом чужим порту возвращается код 4 с текстом, что именно занято и как
  задать другой `--port`.

## CR-3 — войти можно и без установленных entry points

Подтверждено на текущем HEAD: файла `bcc/__main__.py` не было, а
`bcc.app.main()` не смотрел на аргументы вообще — `--help` уходил в никуда, и
вместо справки поднимался сервер.

Сделано:

- добавлен `command-center/bcc/__main__.py` — `python -m bcc` работает без
  `pip install -e`;
- `bcc.app.main(argv=None)` разбирает аргументы: `--host`, `--port`,
  `--version`, `--help`. `--version` и `--help` возвращаются **до** запуска
  сервера.

Проверено запуском отдельного процесса, а не только внутри тестового:
`python -m bcc --version` → `bcc 0.1.0`, `python -m bcc --help` → код 0 и
справка. Тесты: `tests/test_cli_entrypoint.py` (6 тестов), среди них
`test_version_path_never_touches_uvicorn` — `uvicorn.run` подменён взрывающейся
заглушкой.

Рекомендация «установить entry-points (`pip install -e command-center`)» —
действие на машине владельца, коммитом её не выполнить. Именно поэтому
`python -m bcc` и добавлен: он снимает зависимость от установки.

## Что осталось недоказанным

- **Клик по ярлыку на настоящей Windows.** Здесь нет дисплея и нет Windows.
  Всё, что относится к `pythonw`, `.lnk` и cp1252, покрыто тестами как поведение
  кода (подстановка потоков, argv ярлыка, кодировка), но живого двойного клика
  на машине владельца в этих доказательствах нет.
- **Повторный прогон тех же 10 проверок аудита** на машине владельца — шаг,
  который сам аудит называет следующим. Он выполняется там, где воспроизводился
  сбой, а не здесь.

## Найдено попутно (вне CR-1..CR-4, не чинилось этим коммитом)

Прогон корневого набора (`python -m pytest tests -q`, 79 passed) **изменяет
отслеживаемые файлы в `data/learning/`**: из `fix_cases.jsonl` исчезают две
записи, `history.jsonl` очищается на 19 строк. Это не поломка стора —
`LearningStore` по построению считает `journal.jsonl` единственным
авторитетным источником и на каждом чтении пересобирает снимки под него
(`learning/trace.py:_ensure_consistent` → `_materialize`).

Причина в том, **как** эти записи попали в корпус: два fix-case'а
(`eb6f7fcd8af5fa49`, `96a79132f8bb3a73`) были дописаны прямо в
`fix_cases.jsonl`, минуя `store.add()`, поэтому в журнале их нет и первое же
чтение их удаляет. Строки `history.jsonl` не выводятся из текущего журнала по
той же причине.

Здесь файлы восстановлены (`git checkout -- data/learning/`) и в коммит не
попадают. Правильное закрытие — провести обе записи через `store.add()`, чтобы
они попали в журнал; это отдельное изменение с собственной проверкой, потому
что тот же вызов перепишет и `history.jsonl`. Пока этого нет, любой прогон
корневого набора оставляет рабочее дерево грязным, и это надо помнить перед
`git add -A`.
