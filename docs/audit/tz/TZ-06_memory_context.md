## 2. Требования

### 2.1 Решётка скоупов с наследованием (MEM-02) — MUST
Скоуп — путь в дереве `organization / department:d / project:p / mission:m / team:t / task:k`. Частичный порядок `⊑` — «предок». Правила чтения (INV-4):

```
read(s) = own(s) ∪ ⋃_{a ⊏ s} exported(a → s) ; read(s) ∩ own(sibling(s)) = ∅
```
- `exported(a → s)` — факты предка `a`, чей `kind ∈ allowed_exports(department(a))` **или** помеченные `visibility=descendants` при публикации. Экспорт вниз по дереву — автоматический (правила отдела видят все его миссии); вверх и вбок — только явный `export()` с сохранением происхождения (уже есть).
- Уверенность при наследовании не растёт: `confidence(read) = min(confidence(fact), trust(a→s))`, где `trust` по умолчанию 1.0 для прямого предка и `0.9^{distance}` для дальних.
- Реализация: `store.facts(scope)` → `store.facts_in(ancestors(scope) ∪ {scope})` + фильтр видимости. Строки скоупов — валидировать регэкспом; неизвестный сегмент → `ValueError` (INV-6).

### 2.2 Изоляция как граница исполнения, а не соглашение — MUST
1. `ScopedKnowledge.read` MUST принимать `ScopeToken` (подписан ключом TZ-01 §2.1): `{scope, allowed_ancestors, exp}`; выдаётся `OrganizationRuntime` команде на время контракта. Чтение чужого скоупа без токена → `PermissionError`, событие `memory.denied`.
2. Канареечные факты: при создании проекта автоматически публикуется `kind=canary` с уникальным маркером; тест на живом стеке (`test_v3_organization_command_center.py`) читает из соседнего проекта и утверждает отсутствие канарейки; CI падает при утечке.

### 2.3 Настоящие эмбеддинги и гибридный поиск (MEM-01) — MUST
1. `Embedder` реализации: (а) локальная многоязычная модель через существующий провайдер (Ollama `nomic-embed-text`/`bge-m3` или `sentence-transformers` если установлен); (б) `HashEmbedder` остаётся только как fallback с явным `degraded=True` в ответе поиска (честность: пользователь видит «поиск лексический»).
2. Гибридный ранкер: BM25 (SQLite FTS5) + косинус по векторам, объединение Reciprocal Rank Fusion: `score(d) = Σ_r 1/(k + rank_r(d))`, `k=60`. RRF выбран потому, что не требует калибровки шкал двух ранкеров.
3. Дедуп по смыслу при записи: если `cos(new, existing) ≥ 0.97` и одинаковый `kind` в том же скоупе → обновить `last_seen`, не создавать дубликат (битемпоральное правило сохраняется: старая версия закрывается, не переписывается).

### 2.4 Забывание и консолидация (MEM-03) — SHOULD
- Приоритет факта при сборке контекста: `w = confidence · e^{−age/τ} · (1 + log(1 + hits))`, `τ` по `kind` (правила отдела — ∞, наблюдения — 30 дней). Ниже порога `w < 0.05` → факт архивируется (не удаляется; битемпоральность).
- Консолидация раз в сутки: кластеры по косинусу ≥ 0.9 → один сводный факт с провенансом-списком; исходники архивируются.

### 2.5 Сборка контекста — MUST
1. `estimate_tokens = len//4` заменить на таблицу по скрипту (та же, что TZ-09 §2: латиница 4.0, кириллица 2.3, CJK 1.0 симв/токен; итог — минимум по присутствующим скриптам). Иначе русский контекст занижается на ~40 % и режется provider-ом.
2. Бюджет контекста — фиксированные доли: система 10 %, факты скоупа 25 %, журнал шагов 25 %, свежие наблюдения 30 %, резерв 10 %; переполнение секции — усечение внутри неё, не соседей (стабильный префикс сохраняет prompt-cache, см. `AnthropicAdapter` breakpoints).

## 3. Математика
- Решётка: `(Scopes, ⊑)` — дерево ⇒ у каждого узла единственный путь предков; `read` монотонна: `s ⊑ s' ⇒ exported(·→s) ⊆ exported(·→s')` не требуется, но `own(s) ∩ own(s') = ∅` для несравнимых — это и есть «нет утечки между проектами».
- RRF с `k=60`: документ, первый у одного ранкера и отсутствующий у второго, получает `1/61 ≈ 0.0164`; документ 5-й у обоих — `2/65 ≈ 0.0308` > 0.0164 ⇒ согласие двух ранкеров важнее одиночного лидерства — желаемое свойство для смешанных RU/EN запросов.
- Дедуп-порог 0.97 для многоязычных моделей класса bge-m3 соответствует парафразам; 0.9 — консолидации тем.
