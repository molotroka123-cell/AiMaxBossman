# BOSSMAN — ЭТАП 1.2: TERMINAL RUN

Owner decision / clarification: 2026-09-23. Status of this document: IMPLEMENTATION DIRECTIVE, NOT A WORKING-CLI CERTIFICATE.

## 0. Обязательное уточнение владельца

**Терминал — только дополнительный способ управления ТЕМ ЖЕ Bossman. Не отдельное приложение с отдельным мозгом или данными.**

CLI / существующий дашборд / Telegram используют один выбранный экземпляр backend, те же проекты, файлы, модели, агентные профили, skills, память, очередь, разрешения и журнал. Изменение файла через терминал видно в проекте и дашборде без экспорта, копирования и синхронизации папок. Нельзя создавать `terminal-memory`, `terminal-projects`, второй набор весов или второй task engine.

Самоисправление по-прежнему проходит через существующий изолированный кандидат и review. Это временная рабочая копия для проверки patch, а не отдельная версия продукта. Принятый patch обновляет тот же канонический проект обычным контролируемым способом; новая оболочка не разрешает ученику переписывать установленную стабильную программу.

**Цель этапа: удобно разговаривать и работать с Bossman в обычном CMD; Claude Code сможет обучать и аудировать его через машинно-читаемые команды, не тратя итерации на клики по дашборду.** Это гипотеза снижения накладных расходов, а не обещанное ускорение модели или отказ от качества пользовательских функций.

North Star не меняется: локальный Bossman улучшает Bossman, сохраняет проверенные рецепты, применяет их к новым задачам и постепенно требует меньше помощи учителя. Последнее уточнение владельца: **целевой горизонт 4–6 дней после принятого первого запуска — начать получать коммерчески полезные результаты и стремиться к первому заработку идеями, процессами и своим железом**. Это заменяет прежний ориентир 4–7 дней только в части горизонта. Доход и рост интеллекта не гарантируются, фактическая выручка учитывается отдельно от оценочной ценности.

Этап 1.2 — название режима приёмки, не команда механически поменять все версии пакетов на 1.2 или объявить готовой v1.1. Обычный выпуск, evidence и release gates сохраняются.

## 3. Архитектура: один продукт, три пульта

```text
человек -> интерактивный Bossman CLI -----------+
Claude Code -> Bossman CLI exec / JSON events -+--> один API / сервисный слой Bossman
дашборд ---------------------------------------+       |
Telegram --------------------------------------+       v
                                              policy / projects / tasks / gateway
                                                        |
                                 coding / browser / desktop / files / media / evolution
                                                        |
                                     общая память + evidence + проверенные артефакты
```

Терминал отвечает за ввод, вывод, autocomplete, отображение событий и transport. Он не владеет вторым planner, scheduler, verifier, model router или mutable memory store. Нет нового LLM-чата напрямую к модели в обход Bossman ради быстрого демо.

Подключение обнаруживает тот же configured instance и data root. Показывай instance ID, backend build SHA, client version, project ID и реальный путь. Несовместимый backend, другой профиль или недоступный data root дают явный отказ/выбор, а не молчаливое создание пустой базы.

Если backend не запущен, разрешён запуск существующим штатным механизмом после проверки настроек и единственного экземпляра. Не запускать новый backend от текущей папки только потому, что пользователь вызвал `bossman` из другого cwd. Первое сопряжение локально; повторный обычный запуск без лишних вопросов. Токены не передавать в argv, историю shell и логи; использовать существующее хранилище секретов и ограниченный локальный канал.

Все изменения проходят тот же API, ревизии и разрешения. CLI не пишет напрямую в SQLite/Postgres/JSON stores. Caches допустимы только как перестраиваемые представления, не как новая истина. Локальная история ввода не заменяет transcript и память backend.

## 4. Вид: настоящий Windows CMD, не браузер под видом терминала

Обязательны обычный `cmd.exe` с Windows Console Host и CMD-профиль Windows Terminal. PowerShell — дополнительный проверяемый запуск, не обязательная оболочка. WSL, Electron, браузер, Node и Rust toolchain не требуются только ради запуска клиента.

Основной вид — прокручиваемая беседа в одну колонку: компактный заголовок, workspace/model/status, пользовательское сообщение, ответ, свёрнутые tool events, diff, результат и prompt. Не тратить половину экрана на постоянные панели. Упор на русский язык, читаемость и малое число действий.

Enter отправляет ввод, Tab дополняет доступные команды/пути, история не теряется от потокового вывода. Многострочная вставка никогда не выполняет её строки автоматически; нужна явная отправка. Поддержать Unicode, кириллицу, resize, Ctrl+C, EOF, узкую консоль, copy/paste и режим без цвета. Опциональная панель не блокирует scrollback и не является обязательной для приёмки.

Ранее созданные картинки — только концепты. Их выдуманные модели, даты, счётчики PASS, CPU/GPU и проценты памяти не являются требованиями или реальными evidence. Не копировать из них «gpt-4o local» и иные неподтверждённые параметры.

Вместо выдуманного Thinking Process показывай наблюдаемые этапы, использованный контекст, краткое объяснение подхода, вызовы tools, тесты и ожидание ответа модели. Не извлекать скрытые рассуждения чужих сервисов; не придумывать их при отсутствии. Спиннер не доказывает, что модель выполнила действие. Показывать таймер/heartbeat и «ожидаю модель», а не фальшивый процент.

## 5. Человек и Claude используют один контракт

Ниже целевая поверхность для реализации, НЕ заявление о готовых командах. Сверь коллизии с существующим CLI; фактический синтаксис отрази в --help и тестах.

| Действие | Предлагаемая поверхность |
|---|---|
| Разговор | `bossman` и `bossman chat` |
| Задание без интерактивного экрана | `bossman exec --input-file <utf8-file> --json` |
| Ожидать результат или отсоединиться | явные wait/detach режимы с возвращённым task_id |
| Продолжить беседу | `bossman resume <session-id>` |
| Статус/события/результат | `bossman status`, `bossman events <task-id>`, `bossman result <task-id>` |
| Навыки/инструменты/модели | общие registries: skills, tools, models |
| Подтверждение | task-bound approve/deny через backend |
| Пауза/отмена/СТОП | отдельные операции над задачей, кампанией или всеми действиями |
| Самоулучшение | существующий evolution/learning controller через CLI |
| Машинный аудит | versioned JSON/JSONL, вывод артефактов и независимого verdict |

Внутри chat: `/help`, `/status`, `/tasks`, `/models`, `/skills`, `/tools`, `/memory`, `/diff`, `/approve`, `/deny`, `/pause`, `/stop`, `/resume`, `/evolve`, `/exit`. Выбор модели/профиля — без сброса задачи и без обхода Gateway. Файл по `@path` читать только через разрешённый проектный scope; длинные/личные файлы не отправлять автоматически в облако.

`exec` не требует TTY и не зависает на скрытом вопросе. stdin/file JSON должен иметь определённую версию и схему; stdout содержит только JSON/JSONL, диагностика идёт в stderr. Никаких баннеров, ANSI, спиннеров и секретов в машинном stdout. Лимиты input/output и завершение по EOF обязательны. Нет eval, shell-интерпретации произвольной строки модели или скрытого внешнего fallback.

Код возврата и payload отражают успех самой операции и отдельно состояние задачи. Успешный submit не означает выполненную задачу. Режим ожидания результата отличает PASS, FAIL, PARTIAL, BLOCKED, WAIT_APPROVAL, TIMEOUT и DISCONNECTED. Отказ подключения не открывает новую пустую сессию с ложным PASS.

## 6. Полная функциональная поверхность без ложных обещаний

Составь registry-backed parity matrix: capability -> существующий handler -> CLI operation -> permissions -> readiness -> tests. Покрой chat/context, agents/tasks, coding/diff/review, files/search, memory/skills, models/Gateway, browser/download, Computer Use, Image/Video/Music Studio, Web Designer, Telegram, diagnostics, budgets, Fleet и evolution.

Терминал должен предоставлять доступ ко всем существующим разрешённым операциям, а не повторять их реализацию. Неподключённые возможности явно показываются как unavailable с причиной. Нельзя скрыть обязательный путь релиза, назвав его optional, или считать registry list доказательством работы.

Фото/видео/PDF возвращают путь и подтверждённые метаданные общего артефакта; отдельная явная команда открывает его просмотрщиком. Не рендерить длинное видео в CMD ради оформления. Наука о моделях и загрузка — через существующий model-fetch; большие веса не скачивать при каждом запуске chat.

Настоящие desktop/browser задачи всё равно используют реальные наблюдения и действия. Мы убираем клики учителя по панели управления, а не пропускаем необходимую проверку конечного результата.

## 7. Непрерывная работа принадлежит backend, не окну CMD

Разрыв event-stream не повторяет мутацию. Использовать durable task/run IDs, idempotency keys, event cursor/sequence, reconnect/replay и ограниченные retries с backoff. Если backend не имеет durable event history — добавить минимальную общую поддержку, а не отдельный log-server терминала. Неизвестный внешний исход требует reconciliation, не слепого повтора.

Закрытие терминала отсоединяет клиента от backend-owned задачи; не убивает чужие модели, Telegram и всё приложение. Поведение ясно показывается перед выходом. Ctrl+C отменяет текущий ввод или запрашивает отмену текущей foreground-задачи согласно показанному режиму; глобальный STOP — отдельная явная команда. Отмена подтверждается backend, не мгновенно рисуется как выполненная. Повторное прерывание может отсоединить клиент, но не должно скрывать unknown effect.

STOP/PAUSE/RESUME общие для CLI/UI/Telegram. После restart STOP остаётся, stale approval не оживает, Resume требует свежего наблюдения перед эффектом. GUI-сессию/модельные серверы используют через существующие leases. 40 минут — лимит одной учебной попытки; общий бюджет кампании сохраняется после restart и не расширяется автоматически.

## 8. Безопасность нового входа

Никаких bypass-флагов ради похожести на Codex. Подготовленная машина не превращает вывод модели в разрешение владельца. Рутинные лабораторные действия допустимы в заранее заданном scope без лишних диалогов; платежи, внешние отправки, публикация и применение кандидата сохраняют свои gates.

Разрешение привязано к owner/project/task/action digest/revision/TTL/nonce и проверяется сервером перед эффектом. Одновременный approve из Telegram и CLI не исполняет действие дважды. Неинтерактивный Claude может использовать только реально делегированный scope, а не автоматически подтверждать всё за владельца.

Отображение недоверенного вывода: нейтрализовать ANSI/OSC/CSI-инъекции, OSC52 clipboard, управляющие последовательности, возвраты каретки, поддельные ссылки/заголовки и опасную Rich-разметку. Сам renderer генерирует цвета; содержимое файлов/модели не управляет терминалом. Отдельные тесты на traversal, Windows junction/reparse points, логи с секретами и историю ввода.

Python audit hook и Git worktree не считать OS sandbox. Не ослаблять изоляцию обучения ради CLI. Ученик не имеет доступа к holdout, verifier, installed stable, секретам и личному MVČR-проекту.

## 9. Быстрый путь реализации

1. Reuse entry point/argparse и локальный клиент существующего API; transport/auth/identity/parity до визуальных деталей.
2. Сделать exec/status/events/result с JSON, затем добавить удобную chat-оболочку.
3. Prompt Toolkit для ввода, Rich для вывода; один согласованный владелец перерисовки, без конфликтующих Live-циклов. См. OPEN_SOURCE_REUSE.md.
4. Подключить общие tools/coding/evolution/skills и проверить реальное редактирование через backend.
5. Подготовить teacher runbook и same-task GUI/CLI comparison.
6. Windows installed artifact, регрессии, один согласованный SHA и передача.

Не ждать нового самого большого LLM ради готовности интерфейса. Не покупать runtime/плагины, не скачивать мегакаталоги, не переносить Bossman на другой язык. Не переделывать интерфейс дашборда, кроме исправления подтверждённой общей ошибки.

## 10. Поставка и итог Claude

В существующий Windows ZIP включить CLI и его зависимости. Использовать установленный `bossman` entry point и/или тонкий `Bossman-CLI.cmd` рядом со штатным launcher, без второй установки. Из любой директории корректно находить bundle/runtime/config, включая пути с пробелами и кириллицей. Никаких pip/source-copy hotfix после распаковки.

Сохраняются обязательные checks текущего certifier и отдельные доказательства исходников/поставки/железа. До OWNER_RUN из облака допустим статус READY_FOR_TERMINAL_OWNER_RUN, если Windows package path реально проверен; не TERMINAL_OWNER_PASS, SELF_REPAIR_PASS или REVENUE_CAPABLE без живых evidence.

В финале передать: source SHA, ветку/PR, CI по этому SHA, ZIP и SHA-256, реальные команды запуска, parity matrix, остаточные P0/P1, выбранные лицензии/версии, результат двух-way state tests и teacher-сценарий. Указать, что реализовано, что протестировано с fixture, что проверено с настоящей моделью и что осталось NOT_RUN.

Главная формулировка для каждого handoff:

> TERMINAL RUN 1.2 = другой пульт того же Bossman, общие файлы/память/задачи; Claude обучает через CLI без кликов по дашборду; цель — измеряемое самоулучшение и первые коммерчески полезные результаты в целевом окне 4–6 дней, не гарантированный заработок.
