# Bossman Executive OS 0.1.0

Отдельная надстройка управления явно переданными локальными миссиями. Использует штатные порты Bossman: BCC Feature/авторизацию, V3 UniversalComputerAgent, Core ContextEngine и подписанные evidence. Исходники Core, Command Center, shared и замороженные проверки не меняются.

## Двенадцать механизмов

| № | Механизм | Исполняемый контракт |
|---|---|---|
| 1 | Единое состояние миссии | SQLite WAL, CAS по версии, неизменяемый hash контракта, журнал переходов. |
| 2 | Идентичность эффекта | claim → исполнение → независимое чтение → подписанная квитанция → confirm; привязка mission/step/actor/fence. Unknown не повторяется. |
| 3 | Пересечение полномочий | owner ∩ project ∩ role ∩ tool ∩ допустимое действие; проверка перед эффектом и при восстановлении. |
| 4 | Общий резерв ресурсов | Для всех управляемых миссий сумма резервов ≤ лимита; резерв захватывается транзакционно до действия/инференса. Это учёт допуска, не физическое ограничение RAM/VRAM. |
| 5 | DAG-планировщик | Шаг готов только при подтверждённых зависимостях; перед продолжением их файлы проверяются снова. Циклы и неизвестные зависимости отклоняются. |
| 6 | Проверенная память | Существующий ContextEngine; разделение проектов, неизменяемая идентичность факта, provenance. В память попадают подтверждённые hashes, не инструкции из модельного текста. |
| 7 | Полный контекст | Корни включаются вместе со всеми зависимостями. Срок, источник, privacy и бюджет проверяются до отправки модели; при переполнении отказ вместо обрезки. |
| 8 | Консервативный роутинг | Wilson lower bound и ожидаемые затраты; реальный локальный OpenAI-compatible adapter. Cold start имеет нулевую доказанную вероятность, доставка ответа не считается качеством решения. |
| 9 | Ограниченные роли | Host управляет контрактом, отдельный file-reader проверяет результат, модель выдаёт только предложение. Артефакты разделены по миссиям; ключи/БД вне artifact mount. Это не контейнерная изоляция ОС. |
| 10 | Восстановление | Каждый переход долговечен; после сбоя только наблюдение существующего эффекта, без повторной записи. Unknown сохраняет резерв. |
| 11 | Контролируемая оценка релиза | Неизменяемые baseline/candidate, одинаковые contracts/cases, отсутствие регрессий и hard failures, обязательное улучшение. Автопубликации кода/skills нет; откат надстройки — остановка отдельного процесса. |
| 12 | Оценка фактических результатов | PASS только по свежей проверке файла и подписи. `10000 × passed/total` и Wilson 95% относятся только к заданному набору миссий, не ко всей ОС. |

Роутинг использует `utility = WilsonLower(successes,total) × (1-risk) / ((1+cost×(1+retries))×latency)`; это формальная эвристика, не обещание оптимальности. Оценка размера контекста — `ceil(len(canonical_json(facts))/3)`, а не точный tokenizer модели. Интервал checkpoint `sqrt(2C/λ)` — справочная оценка при пуассоновских отказах; обязательные транзакционные checkpoints выполняются независимо от неё.

## Установка и запуск

Из корня репозитория в выделенном окружении Python 3.11 или 3.12:

```powershell
python -m pip install . ./bossman-core ./command-center ./addons/executive_os
python -m bossman_os.bcc_app --host 127.0.0.1 --port 8812 --data-dir C:\BossmanData\executive-os
```

Wrapper подключает новый Feature только к этому экземпляру BCC через штатное обнаружение расширений. Собственная БД задаётся явно, унаследованный `DATABASE_URL` не выбирает рабочую БД. Существующие фоновые workers не запускаются. Данные надстройки и артефакты находятся в разных подкаталогах выбранного data-dir.

API под `/api/executive-os`: `GET /status`, `POST /missions`, `GET /missions/{id}`, `POST /missions/{id}/run`, `POST /recover`, `POST /propose`, `POST /evaluate`. Каждый запрос требует существующий BCC token/session. Ключ владельца создаётся в `data-dir/token`; хранить его вне Git и не вставлять в URL/логи.

Консоль: `http://127.0.0.1:8812/executive-os`. Ввод токена остаётся только в памяти вкладки. Кнопки проверяют статус, создают миссию с двумя зависимыми шагами и запрашивают предложение модели. Статическая страница общедоступна на loopback; операции требуют авторизации.

Пример тела `POST /missions`:

```json
{"id":"demo","project":"default","steps":[{"id":"write","depends_on":[],"action":"artifact.write","path":"report.txt","content":"Verified local result"},{"id":"check","depends_on":["write"],"action":"artifact.verify","path":"report.txt","content":"Verified local result"}]}
```

`POST /propose` принимает `objective`, `project`, `context_roots`; разрешён только локальный endpoint `http://127.0.0.1:11435/v1` и установленные модели из host allowlist. Применяется существующий протокол «задача → ограничения → план → проверка». Это управление поведением при инференсе, не обучение весов и не перенос внутреннего мышления другой модели. Предложение не выполняется автоматически.

Для оценки зафиксировать baseline до выполнения набора миссий, выполнить миссии, затем записать candidate с теми же случаями: `{"suite_id":"local-suite","phase":"baseline","cases":{"case1":"demo"}}`. Улучшение завершённости такого набора не доказывает улучшение версии модели или обобщение на новые задачи. Gate не разворачивает ПО.

## Границы и откат

Управляются только явно отправленные сюда миссии. Существующие Core/Fleet/BCC задачи сохраняют свои полномочия и бюджеты. Облачные вызовы, платёжный учёт, произвольный shell, удалённые исполнители и автоматическое расширение прав отключены. Unknown после таймаута инференса требует разбора владельцем: надстройка не может доказать остановку внешнего локального сервера.

Откат: остановить только процесс, запущенный через `bossman_os.bcc_app`; при необходимости удалить пакет из выделенного окружения. Данные оставить для аудита/восстановления. Основной экземпляр Bossman и его файлы не затрагиваются.

V4: подключить этот контракт допуска к реальным Fleet-исполнителям через существующие порты, добавить проверяемые лимиты процессов и реальные профили ресурсов, накопить независимые holdout-оценки моделей. V5: распределённый authority с fencing, общая платёжная транзакция, изолированные workers и управляемое продвижение версий по неизменяемой внешней оценке. До этого статистика локальных миссий не должна называться оценкой всей ОС.
