# Stage 6 — Private Remote Client backend

Gated бэкенд для приватного телефон-клиента Bossman Core. Заменяет прототип
(`_staging/s17/.../remote_client`) продовым путём: устройства и сессии в
Postgres, скоупы проверяются на КАЖДОМ запросе, секреты хранятся только хэшами.

## Граница безопасности (предположение развёртывания)
Этот backend **не** является публичным. Он рассчитан на приватный туннель/TLS
(Tailscale serve, WireGuard и т.п.). **Сырые модельные бэкенды наружу не
публикуются никогда** — наружу выставляется только gated `/remote/*` API. Всё,
что ниже, защищает уже внутри этого периметра.

## Инварианты (не нарушать)
- **Секрет — только один раз.** Сырой токен возвращается вызывающему ровно при
  enrollment / открытии сессии и больше нигде не хранится и не логируется. В БД
  лежит только `sha256`. Сверка — в постоянном времени (`hmac.compare_digest`).
- **Скоупы проверяются на каждом запросе.** Гейт живёт в
  `security.require_scope(scope)` (FastAPI-зависимость). Без нужного скоупа
  запрос падает `ScopeDenied` (403) до тела обработчика. chat-устройство
  физически не достаёт до admin/approve/lock-маршрутов.
- **Устройство не может повысить свои права.** Нет маршрута правки скоупов
  существующего устройства; enrollment требует `admin` И запрещает выдавать
  скоупы шире собственных (анти-эскалация через прокси-устройство).
- **cloud_policy неприкосновенна.** Пакет осознанно не экспонирует ни одного
  маршрута мутации cloud_policy или иных границ безопасности агента. Удалённое
  устройство не может ослабить политику. Любой будущий agent-control маршрут
  обязан быть и scope-gated, и по-прежнему проходить через тот же cloud_policy
  gate ядра.
- **Fail-closed.** Экстренная блокировка (`/remote/lock`) гасит устройство или
  все сразу; пока активна — каждый запрос падает `DeviceRevoked`, enrollment не
  удаляется.

## Модель токенов и сессий
- Enrollment выдаёт **device-токен** (`rcd_…`) — долговременный креденшл.
- `POST /remote/auth` меняет device-токен на **session-токен** (`rcs_…`),
  отзываемый независимо от устройства.
- В заголовке `Authorization: Bearer <device-или-session токен>`. Префикс
  маршрутизирует поиск; финальное совпадение подтверждается `compare_digest`.

## Порт хранилища (одна логика, два бэкенда)
`store.DeviceStore` — протокол. `DeviceService` (service.py) не знает про БД и
работает поверх:
- `InMemoryDeviceStore` — асинхронный фейк (юнит-тесты + dev без Postgres);
- `PostgresDeviceStore` — боевой путь через `bossman.db` (asyncpg).

### Таблицы (создаются в `subsystem.validate()`, не в db/schema.sql)
| Таблица | Колонки | Зачем |
|---|---|---|
| `remote_devices` | id, name, created_at, revoked, locked | паспорт устройства; revoked=отзыв, locked=экстренная блокировка |
| `remote_device_scopes` | device_id, scope | права устройства (строка на скоуп) |
| `remote_device_credentials` | device_id, token_sha256, created_at | **только** sha256 enrollment-секрета; сырого нет |
| `remote_device_sessions` | id, device_id, token_sha256, created_at, last_seen, revoked | выданные сессии, отзываемые независимо |
| `remote_client_flags` | key, value | флаг глобальной блокировки (lock-all) |

## Скоупы
`chat` — диалог/задачи · `events` — push-поток · `approve` — решения
подтверждений · `admin` — провижининг устройств и экстренная блокировка.

## Фильтр событий (мост, а не второй брокер)
`/remote/events` (SSE) бриджит ядровую шину `bossman.events`. Устройство
получает событие, только если у него есть скоуп его категории:
`approval.*→approve`, `agent.*|model.*→admin`, `task.*|project.*|run.*|tool.*→chat`,
всё прочее → `admin` (fail-closed, не утекать неизвестное).

## Подтверждения
`POST /remote/approvals/{id}` (скоуп `approve`) идёт через `approvals.decide(...)`
— структурно как telegram-webhook. chat-only устройство сюда не проходит.

## Деградация
`build_subsystem()` → `critical=False`. `validate()` создаёт схему при живом
Postgres; при недоступной БД ловит ошибку, логирует, поднимает in-memory фейк и
помечает подсистему degraded — ядро всё равно стартует.
