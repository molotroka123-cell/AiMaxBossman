## Что реализовано
* **COACH**: `coach.py` — варианты действий, объяснение, неопределённость, дисклеймер (карты и диапазоны соперников неизвестны; эквити против случайных рук; не оптимально и не гарантия). Размер ставки выбирает политика, не кликер.
* **EXECUTOR** (`control/`): роли Vision → Policy → Locator → Executor → Verifier (`docs/COACH_EXECUTOR.md`). Перед каждым кликом: свежий кадр, идентичность окна (handle + pid + время старта процесса), перекрытие, размер, смещение с момента кадра, раздача/улица/ход/доступность действия, сумма CALL, **повторный поиск кнопки**, стабильность цели на двух кадрах (сдвиг раскладки), отображение кадр→экран (положение окна, масштаб, DPI), проверка «что сверху в точке клика» (дважды), клик, подтверждение новым кадром. Неподтверждённый клик не повторяется; STOP проверяется перед каждым шагом.
* **Сумма**: RAISE = открыть панель → прочитать пресеты и «Raise to» → выбрать пресет **в диапазоне политики** → read-back обязан совпасть → CONFIRM. Если пресета в диапазоне нет — остановка; кликер сумму не меняет.
* **Модель-кликер не может менять решение**: `ModelLocator` принимает ответ только при совпадении метки, рамки внутри кадра и пересечении с кнопкой, которую видит зрение.
* **Bossman Computer Use**: `ComputerUseBackend` — тонкий клиент существующего `computer.act`; периметр CU (allow-list Блокнот/Калькулятор, одобрение на каждое действие, STOP-эпоха) не менялся, поэтому реальный Poker Train через CU **не исполнялся (NOT_RUN)**. Какое изменение allow-list потребовалось бы — решение владельца, не принято.
* **Панель источника в Bossman** (вместо фиксированного холста): «Выбрать источник» → окно выбора с превью (как демонстрация экрана) → живой MJPEG-поток захвата → overlay Vision (карты, числа, кнопки, confidence) → режимы «Наблюдение/Подсказки/Управление», пауза, смена источника, STOP, идентичность источника, журнал решений с кадрами до/после и SHA. Это отображение захвата, а не перенос чужого приложения.
* Тестовый рабочий стол (`sandbox.py`) — двойник ОС для перемещения, размера, перекрытия, сворачивания, закрытия и повторного открытия окна (не поведение Windows).
* Калибровка нового окна: реализована для hero-карт, борда, банка, to-call, стека героя (`/api/v1/calibrate` + проверка на отложенных кадрах); **новое**: `/api/v1/verify` повторно проверяет сохранённый профиль на кадрах после смены масштаба/темы/положения; провал снимает доверие. Калибровка мест, кнопок и поля суммы для **внешних** окон — предложена в `docs/`, **не реализована**.
* Исправлен дефект прошлого этапа: тесты калибровки записывали синтетический профиль `ton_poker.json` с `verified: true` в репозиторий (попал в коммит). Файл удалён, тесты пишут в временную папку.

## Cygnet, Winnow-12B, Jev
По первичным источникам (часть — только сниппеты; помечено UNVERIFIED в `docs/UI_CONTROL_CANDIDATES.md`) это модели «типизированных решений» (состояние + варианты → буква варианта + вероятности). Они не принимают задачу «скриншот → координаты клика», а JevBench — текстовый бенчмарк роутинга/классификации, **не** UI-grounding и **не** покер; цифры со скриншота качество в покере не доказывают. Веса недоступны из контейнера, GPU нет, Windows/AMD для Winnow/Jev не подтверждены. **NOT_RUN**; в путь клика не добавлены. Если владелец запустит такую модель локально, она подключается через `ModelLocator` с той же защитой.

## Захват окна
Сравнение `python-mss` (текущий backend) и `windows-capture` (WGC) по документации — в `docs/UI_CONTROL_CANDIDATES.md`; на Windows не запускалось (**NOT_RUN**). Источник привязан к идентичности окна (handle + pid + время старта процесса), а не к заголовку; `WindowsProbe` (Win32/ctypes) написан, но **не запускался**. Захват через mss показывает и перекрывающие окна, поэтому исполнитель останавливается при перекрытии.
